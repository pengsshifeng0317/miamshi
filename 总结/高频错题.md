## Java：`==` 和 `equals` / `hashCode`

- **错在哪**：2026-08-31 天融信一面答成"equals 比较**哈希值**"，把 equals 和 hashCode 混为一谈。
- **正确答法**：
  - `==`：比较**引用地址**（基本类型比较值）。
  - `equals`：Object 默认实现就是 `==` 比地址；String / Integer 等**重写后比较内容**（不是哈希）。
  - 约定：**重写 equals 必须重写 hashCode**——相等对象哈希必须相等，否则 HashMap / HashSet 会错。

## Java：线程池参数（IO 密集型）

- **错在哪**：2026-08-31 天融信一面现场编"核心=CPU 数、最大=2 倍 CPU"，IO 密集这个配置偏保守，且没落到项目真实参数。
- **正确答法**：
  - 7 个参数：核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。
  - IO 密集合理线程数 ≈ `N×(1 + 等待时间/计算时间)`，通常取 2N 或 2N+1，不是"N 核心 / 2N 最大"这种保守配置。
  - 落到项目真实线程池（`ragRetrievalExecutor` / `mcpBatchExecutor` / `memorySummaryExecutor`），拒绝策略 `CallerRunsPolicy` 让主线程执行形成背压。
- **关联逐字稿**：简历面试逐字稿/项目深挖/多路检索怎么做.md（待补点）
- **核码补充（2026-09-09 小鹏一面 Q6）**：项目三个池参数不同，别用「CPU / CPU×2」一套话带过（CPU 数来自 `Runtime.availableProcessors()`，动态非写死 16）——意图识别 `intentClassifyExecutor` core=CPU / max=2×CPU / SynchronousQueue；检索 `ragRetrievalExecutor` core=max=4×CPU / SynchronousQueue；内部召回 `innerRetrievalExecutor` core=2×CPU / max=4×CPU / LinkedBlockingQueue(100)；三者均 CallerRunsPolicy（`ThreadPoolExecutorConfig`）。面试至少讲意图池 + 检索池两个。
- **全量核码补充（2026-09-16 店小秘一面 Q8 · 本条此前不完整，现扩到全域）**：⚠️ 上面那条**只记了 3 个池，实际是 10 个池 / 6 档配置**（`rag/config/ThreadPoolExecutorConfig.java`，README:221「10 个专用线程池隔离负载」；全部 60s keepAlive、全部 `TtlExecutors` 包装透传 TTL）：

  | Bean | 前缀 | core | max | 队列 | 拒绝策略 |
  |---|---|---|---|---|---|
  | `mcpBatchExecutor` | `mcp_batch_executor_` | CPU | **CPU×2** | SynchronousQueue | CallerRuns |
  | `ragContextExecutor` | `rag_context_executor_` | **CPU×4** | **CPU×4** | SynchronousQueue | CallerRuns |
  | `ragRetrievalExecutor` | `rag_retrieval_executor_` | **CPU×4** | **CPU×4** | SynchronousQueue | CallerRuns |
  | `innerRetrievalExecutor` | `rag_inner_retrieval_executor_` | CPU×2 | CPU×4 | **LinkedBlockingQueue(100)** | CallerRuns |
  | `intentClassifyExecutor` | `intent_classify_executor_` | CPU | **CPU×2** | SynchronousQueue | CallerRuns |
  | `memorySummaryExecutor` | `memory_summary_executor_` | **1** | max(2, CPU/2) | LinkedBlockingQueue(200) | CallerRuns |
  | `modelStreamExecutor` | `model_stream_executor_` | max(2, CPU/2) | max(4, CPU) | LinkedBlockingQueue(200) | **AbortPolicy** |
  | `chatEntryExecutor` | `chat_entry_executor_` | **10** | **10** | SynchronousQueue | **AbortPolicy** |
  | `knowledgeChunkExecutor` | `kb_chunk_executor_` | max(2, CPU/2) | max(4, CPU) | LinkedBlockingQueue(200) | **AbortPolicy** |
  | `memoryLoadExecutor` | `memory_load_executor_` | max(2, CPU/2) | max(4, CPU) | LinkedBlockingQueue(200) | CallerRuns |

  - **三处必须改的口径**：① **全仓没有任何一个池是 `core = CPU×2`**——CPU×2 只出现在 `mcpBatchExecutor` / `intentClassifyExecutor` 的 **max**；本场说「core=CPU×2」又说「core=CPU」，**前后矛盾且都不对**。② **拒绝策略不能一概而论**：7 个池 CallerRuns，**3 个是 AbortPolicy 会抛 `RejectedExecutionException`**（`modelStreamExecutor` / `chatEntryExecutor` / `knowledgeChunkExecutor`）——**主动划出这 3 个例外，比笼统说"全 CallerRuns"专业得多**。③ **SynchronousQueue 不能照教科书讲**：容量 0 → core 满后**入队几乎必然立刻失败 → 直接提前扩容到 max** → 到 max 再提交就拒绝；**队列长度恒为 0，`maxPoolSize` 才是真正的并发上限，`corePoolSize` 只管线程回收**（`chatEntryExecutor` 另开 `allowCoreThreadTimeOut(true)`，否则 core==max 时 10 个线程常驻）。**系统真正的排队在 Redisson 信号量层**（`ChatQueueLimiter` → `FairDistributedRateLimiter`），**线程池只是拿到许可后的执行入口**——本场把"排队/背压"都挂到线程池上，是错的。
  - **背分档骨架（开口先说这个）**：检索类固定 CPU×4 且 core==max / 轻量 IO 并行类 CPU→CPU×2（意图、MCP 批处理）/ 摘要·流式·加载类 max(2,CPU/2)→max(4,CPU) 配 200 有界队列 / `memorySummaryExecutor` core 锁死 1 / `chatEntryExecutor` core==max==10。

## 缓存：穿透 / 击穿 / 雪崩的解法归属记串

- **错在哪**：2026-09-03 小熊博望一面把「过期时间加随机漂移打散」这个**雪崩**的解法安到**击穿**头上；击穿漏了互斥锁 / 逻辑过期；雪崩整段解法没给。定义会、解法乱 = 没背熟。
- **正确答法**：先分清本质——穿透=数据本身不存在（缓存和库都没有）；击穿=单个热点 key 过期瞬间超高并发；雪崩=大批 key 同时失效或 Redis 整体不可用。
  - **穿透**：缓存空值（带短 TTL）+ 布隆过滤器前置 + 入口校验。
  - **击穿**：互斥锁（只放一个请求重建缓存，其余等待/返旧值）；逻辑过期（物理永不过期，异步重建读旧值）；热点永不过期。
  - **雪崩**：过期时间加**随机值打散**；多级缓存（本地+Redis）；熔断/限流/降级；Redis 高可用 + 持久化。
- **关联逐字稿**：面试题目/八股基础/数据库与Redis.md（待生成）

## MQ：消息丢失 / 重复（自己项目就有 RocketMQ 却卡壳）

- **错在哪**：2026-09-03 小熊博望一面 Q5，只说了「抖动没到 broker 做重试」就卡壳，主动喊停重来且没接上。自己项目就用了 RocketMQ，这题本不该卡。
- **正确答法**：先说「我们项目就用 RocketMQ，按三段讲」给骨架。
  - **丢失三环节**：生产端用**事务消息**（本地事务+回查）保证「本地操作+发消息」原子；Broker 靠主从/持久化；消费端**处理成功再提交 offset**，别 auto-ack。
  - **重复**：消费端幂等——框架层 `@IdempotentConsume`（Redis SET NX + CONSUMING→CONSUMED 状态机）+ 状态机 guard 兜底；实际去重靠 MessageWrapper.uuid 作 MQ keys + 事务回查。
  - ⚠️ 诚实边界：幂等组件目前未真正打在监听器上，简历/面试别说「所有消费者都走幂等注解」。
- **关联逐字稿**：简历面试逐字稿/项目深挖/MQ怎么做.md（待生成）
- **复发补充（2026-09-11 长鑫一面 Q19 · 第二次暴露，仍挂）**：半消息**两阶段框架答对了**，但**把"事务回查"讲反**——说成"**本地事务失败 Rollback 之后**再去做一次回查"。正确：回查 = **Broker 迟迟收不到二次确认**（生产者宕机/网络断/确认消息丢了）时，**主动回调生产者** `checkLocalTransaction`，让生产者**去查本地库现状**（"这单到底扣没扣成功"）再回答 `COMMIT`/`ROLLBACK`/`UNKNOWN`；答 `UNKNOWN` 就继续回查，**超过最大回查次数默认回滚丢弃**。回查解决的是"**生产者与 Broker 状态不一致**"，跟本地事务成功失败无关。补三个细节：半消息存在 **`RMQ_SYS_TRANS_HALF_TOPIC`**（消费者天然看不到）；commit 是**把消息从 half topic 恢复到真实 topic**（不是"再发一次"）；`checkLocalTransaction` 必须**幂等且只查不改**。必抛一句："事务消息只保证**本地事务与发消息**的原子，**不保证消费不重复**，消费端还要幂等。" ⚠️ `MQ怎么做.md` **仍未生成，已连挂两场**。

## 限流：把内存级 CAS 讲成 Redis 级 + 现场编"只做加操作"

## B+ 树与分库分表：因果讲反 + 漏叶子链表

- **错在哪**：2026-09-16 店小秘一面 Q11，① **分库分表因果讲反（硬伤）**——说成「表数据量过大 → 树高上涨 → 所以分表降低树高、提高索引效率」。**B+ 树高度增长极慢**（3~4 层就够亿级），**分库分表主因根本不是树高**，是**单机磁盘容量 / 连接数 / 写入吞吐**的瓶颈；② **漏了 B+ 树首要选型理由——叶子双向链表**（范围查询 / 顺序扫描顺链表走，不用回根），只讲了"树矮 / 省空间"。
- **正确答法**：
  - **B+ 树**：非叶子只存键+指针、数据全在叶子，且**叶子之间双向链表**串联 → **范围查询与顺序扫描**顺着链表走（**首要理由**）；配合 **InnoDB 按页读写（默认 16KB）**，一页塞几百个键 → **树高每降一层省一次随机 IO**；三层通常支撑千万~亿级。
  - **分库分表**：「是**单库单表的容量与写入瓶颈**驱动的——数据量、QPS、连接数逼近单机上限，所以**水平拆分**把数据分散到多库多表。降树高只是顺带的次要收益。**代价一起说**：跨库 JOIN 没了、要分布式事务 / 全局唯一 ID / 跨分片分页。」

## SQL：聚合过滤没点出 HAVING + 漏「参与所有科目」的完整性校验

- **错在哪**：2026-09-16 店小秘一面 Q12（"所有科目分数都大于 80 的学生"）：① **AVG 与 MIN 口径混了**——说成"先 AVG 再取 MIN"，而 `AVG(score)>80` 是**错的**（平均 >80 ≠ 每科 >80），`MIN(score)>80` 才对；② **全程没说 `HAVING`**——`GROUP BY` 后的聚合过滤必须走 `HAVING` 不能走 `WHERE`，这是本题必考点；③ **漏了"参与所有科目"这个真正考点**——只写 `MIN(score)>80` 会把"只考了一科且 >80"的缺考生也选出来，**语义就错了**。
- **正确答法**：

```sql
SELECT student_id
FROM score
GROUP BY student_id
HAVING MIN(score) > 80
   AND COUNT(DISTINCT subject) = (SELECT COUNT(DISTINCT subject) FROM score);
```
  有 `student` 表就 JOIN 取 `name`。**答题顺序**：先复述题意（"每科都 >80，且参加了全部科目"）→ 说 `GROUP BY` + `HAVING` → 写 `MIN(score)>80` → 主动补完整性校验那一行。

## Java 并发与算法：快慢指针答非所问 + FutureTask 与 CompletableFuture 混为一谈

- **错在哪**：2026-09-16 店小秘一面 Q6/Q7。① **Q6 答非所问**——滑动窗口**不是环**，却拿"快慢指针判环"去答，且**漏了"环入口"**这个判环题的真正考点（只答了"有没有环"）；② **Q7 概念混用**——把 **`CompletableFuture.allOf` 的"等最慢的那个、合并"语义安到了 `FutureTask` 头上**（`FutureTask` 只封装**单个**任务，没有合并能力）；状态机只说了三个，**漏掉取消链路**；`get()` 说成"阻塞或挂起"，准确说法是 `LockSupport.park()`。
- **正确答法**：
  - **Floyd 判圈**：先切分场景（「滑动窗口用首尾两个**索引**定位 id 区间，不是快慢指针」）→ 同起点、快 2 慢 1、**有环必相遇**（进环后相对速度恒为 1，环内距离每步减 1，必然追上）→ **相遇后把一个指针移回头结点，两指针同速各走一步，再次相遇点即环入口** → 时间 O(n) / 空间 O(1)（优于哈希表判环）。
  - **FutureTask**：`implements RunnableFuture<V>` ✅；状态 `private volatile int state`，**7 态** `NEW(0)/COMPLETING(1)/NORMAL(2)/EXCEPTIONAL(3)/CANCELLED(4)/INTERRUPTING(5)/INTERRUPTED(6)`；`state` 与 `runner` 都用 `UNSAFE.compareAndSwapInt` 改（**无锁**，`runner` 的 CAS 保证 callable 只跑一次）；结果存 `outcome`；`get()` 在 `state <= COMPLETING` 时走 `awaitDone()` = 自旋 + **`LockSupport.park()`**，完成 / 取消时 `unpark` 唤醒。
  - **职责切分（必说）**：**`FutureTask` = 单任务封装，是 `ThreadPoolExecutor.submit()` 的返回类型；`CompletableFuture.allOf` = 多任务编排**——项目里会话记忆 `load()` 的并行拉取用的就是后者（`DefaultConversationMemoryService.java:49`）。
