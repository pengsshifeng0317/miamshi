### Q2 ｜ 题型：项目深挖 ｜ 平台端到端怎么工作

- **我当时怎么答**：用户输入→问题改写/拆分→多子问题各自意图识别（返回 3 意图按置信度排序）→看意图表执行单元（KB/MCP/系统应答）→知识检索走多路检索→后置处理链→大模型整合召回回答。
- **标准答案（主线与代码一致，讲顺即可）**：输入 → 问题重写与子问题拆分（多子问题）→ 每子问题独立意图识别（全量叶子一次打分 → 过滤 `<0.35` → 取前 3，超限每子问题保底 1）→ 按叶子执行单元分派：KB（按 `rag.search.scope.confidence-threshold` 走定向/全局检索）/ MCP（工具）/ SYSTEM（直接应答）→ 检索多路召回 → 后置链（去重 → RRF 融合 → Rerank → EvidenceGate → MetadataEnrich）→ LLM 按召回生成。
  锚点：`DefaultIntentClassifier`（打分/过滤/取 top3）；`IntentResolver`（KB/MCP/SYSTEM 分派）；`RetrievalScopeResolver`（0.6 切定向/全局）。
- **自评**：🟢 顺。主线全对，术语自洽。可优化点：一句带出「置信度过滤 0.35 + 每问题最多 3」显得更专业。

### Q4 ｜ 题型：项目深挖 ｜ 意图识别怎么打分 / 澄清

- **我当时怎么答**：只有叶子打分；把路径/ID/属性给 LLM 抽取归属；返回 3 意图按置信度排序；重疾险意图可三向（KB/MCP/系统）；「意图落空或置信度太低 → 轻量 LLM 二次确认 → 用户选意图」。
- **标准答案 / 该答成什么样**：
  - 打分部分**准确**：叶子过滤后全量叶子一次给 LLM，输入含 id/path(fullPath)/description/type(+MCP toolId)/examples；输出 `[{id,score,reason}]`，path 只在输入不在输出；`INTENT_MIN_SCORE=0.35` 过滤，`MAX_INTENT_COUNT=3`，超限每子问题保底 1 个最高分。（`DefaultIntentClassifier:88-91,198-213,253-285`；`RAGConstant:47,53`）
  - **⚠️ 概念要拆清：识别/退化兜底/澄清是三个不同机制，别混成一句话**：
    ① 打分排序只在叶子层、cap 3；
    ② **score 不够走"退化兜底"**：KB top score `<0.6`（`rag.search.scope.confidence-threshold`）→ 不再走定向，改**全局/全库检索**；连 KB 意图都没有或绑定库全失效也退全局——不是"问用户"；
    ③ **澄清（AmbiguityLLMChecker）只在"路径重名分叉歧义"时触发**，且条件全满足才做：guidance 开 + **子问题数==1** + KB 候选去重后 ≥2 个 + 存在同名叶子/分叉中间节点同名且该名字出现在问题里 + Tier.FAST 二次确认 ambiguous，失败一律放行。触发后给用户选意图。
    所以「意图落空/太低→让用户选」在代码里其实是 **② 退全局兜底**，让用户选是 **③ 歧义澄清**，两者场景不同、不能并成一条。
  - 锚点：`RetrievalScopeResolver:54-87`；`IntentGuidanceService:68-103,130-186`；`AmbiguityLLMChecker:58-100`。
- **自评**：🟡 打分链路对；澄清与退化兜底边界说混了（这正是小熊场"0.7 澄清规则"编造同源的模糊区，务必按上面三层背清）。

### Q5 ｜ 题型：项目深挖 ｜ 定向 vs 全局检索（0.6 + 75/25）

- **我当时怎么答**：置信度 >0.6 做多路（定向）检索、<0.6 做全局检索；实践发现定向召回不全，故 75% 走定向意图库、25% 去剩余知识库全局兜底，交给后置粗排/精排排上来。
- **标准答案（与代码吻合，可放心讲）**：KB 意图 top score 用 `confidenceThreshold` 切——`topScore < 0.6` → 全库全局检索，否则定向 targetCollections（绑定 collectionNames）。主/兜底配比 `supplementRatio=0.25`：主定向路占 75%、supplement 路约 25%（无字面 0.75，是 `1-0.25`；`ScopeQuota.split` 按 `budget*0.25` clamp）。**⚠️ 但兜底 25% 的语义**：代码里 supplement 是"给未命中主路的补充召回预算"，不是字面的"抽 25% 去全库扫一遍"——讲成「主定向 75% + 补充召回 25%」更稳，别咬死「全库兜底 25%」。
  锚点：`SearchChannelProperties:158,167`；`ScopeQuota:45-53`；`RetrievalScopeResolver`。
- **自评**：🟢 数值全对，仅兜底语义表述可更准。

### Q6 ｜ 题型：项目深挖 × 八股 ｜ 并发 / 线程池调度

- **我当时怎么答**：三个子问题并发提交意图识别线程池；意图内四路召回提交检索线程池并发执行；把首字延迟压到 6s 内；核心线程=CPU 16、最大=CPU×2=32，有拒绝策略与队列；追问"不同意图同池会冲突吗"答不会。
- **标准答案 / 该答成什么样**：
  - **参数别一套话概括所有池**，真实是三个池不同配置（`ThreadPoolExecutorConfig`，CPU 数来自 `Runtime.availableProcessors()` 动态非写死 16）：
    - 意图识别 `intentClassifyExecutor`：core=**CPU**、max=**CPU×2**、SynchronousQueue、CallerRunsPolicy → 你答的 16/32 只对这一池；
    - 检索并行 `ragRetrievalExecutor`：core=max=**CPU×4**、SynchronousQueue、CallerRunsPolicy；
    - 内部召回 `innerRetrievalExecutor`：core=CPU×2、max=CPU×4、LinkedBlockingQueue(100)、CallerRunsPolicy。
  - 「不同意图同池冲突」：不会——任务级并发、同构任务、无共享可变状态，只有池的排队/背压语义（CallerRuns 让提交线程兜底执行）。
  - 锚点：`ThreadPoolExecutorConfig.java:41,85-98,104-117,123-136`。
- **自评**：🟡 6s / CPU×2 对，但把意图池参数讲得像全项目统一；追问时只说"不会"没给理由。**背熟三池参数表，面试至少讲意图池 + 检索池两个**。

### Q10 ｜ 题型：场景设计 ｜ 日均调用翻 30 倍到 50 万，哪环出问题

- **我当时怎么答**：先扩容（资源不够）→有限资源下做限流 → 入口一层 + 大模型资源一层（=项目里做过的分布式限流，信号量=120 全局）→ 队列 → 底层单表→分表→分库→TiDB / Milvus。追问"为什么两层"答 IO 密集（等结果不占 CPU，堆到模型排队反而延迟高），统一全局控量分两层。
- **标准答案 / 该答成什么样**：
  - 分层思考的骨架**对**（入口限流 → 模型资源限流 → 存储升级），"两层限流 + IO 密集"的论证是加分点。但：
  - **⚠️ 别把设计值当项目现值**：项目现状是**全局分布式信号量并发 = 10**（`rag.rate-limit.global.max-concurrent`，`application.yaml` 覆盖，运行时 10），**不是"每台 30×4=120"**——且它是**跨实例共享的全局信号量**，不是每台本地并发叠加。场景里你说"设 120"可以，但要讲清前提：**120 是压测支撑出的设计目标值**（每秒并发配额 = 你打算支撑的吞吐），前提是已扩容到能并发处理的算力；若沿用现有 4 台 × 单机 ≈10 量级，把 semaphore 调到 120 只会让请求全排队/超时，不是优化。
  - 干净的场景答题骨架：**1) 先算 QPS 量级**（50 万/日 ÷ 高峰时段的秒 = 数十 ~ 百级并发）→ **2) 先扩容**（实例 + 模型通道）→ **3) 再加全局限流保护模型**（信号量值 = 压测出的模型可并发上限）→ **4) 队列 + 僵尸清理 + 拒绝** → **5) 存储横向演进**（单表→分表→分库 / 分布式库；向量量级上 Milvus）。把"瓶颈在模型通道"点出来：RAG 长任务 IO 密集，模型并发/首 token 是咽喉。
  - 锚点：`RAGRateLimitProperties:40-59`；`application.yaml:108-114`；`FairDistributedRateLimiter`。
- **自评**：🔴 两层限流论证好，但限流数值口径混乱（10 vs 30×4=120）、混淆全局/每台，暴露对自身系统上限没数——这正是上一场小熊也翻车的点，务必按上面口径背一版干净的。

### Q11 ｜ 题型：场景设计（追问） ｜ 每台并发量怎么定 / Nginx

- **我当时怎么答**：按压测看首字延迟 + 日志链路耗时估算；初步判每台 30 并发、设 30×4；Nginx 平均分发；模型层限流按容量判断，入口限流超过即丢弃返错。录音里先后出现"每台 10 并发、四台 120"与"每台 30、30×4=120"两个说法（数字矛盾）。
- **标准答案 / 该答成什么样**：
  - 定并发量的**方法对**：压测（看 TTFT/吞吐拐点）+ 日志链路耗时（每段耗时占比）估算每实例可支撑并发 → 总数 = 单实例容量 × 实例数，入口按它限流。Nginx/负载均衡分发对。
  - **纠正表述**：① 自相矛盾的数字现场必须收口——先给**当前项目值（全局 10）**，再给**场景设计值（压测得出，例如每台 30 仅作假设）**，中间用"假设/如果要支撑到那量级"连接，别让面试官抓到两套数；② 模型层"按容量判断"要说具体：按模型通道并发上限 + 尾延迟拐点定 semaphore；③ 丢弃时机（拒绝策略）：队列满→入口直接拒绝并返回可读错误（对应你讲的"返回报错给前端"）。
  - 锚点：`RAGRateLimitProperties`；`FairDistributedRateLimiter`；拒绝/SSE 结束语义见分布式限流逐字稿。
- **自评**：🔴 方法对，两套数字打架 = 临场没口径。这是本场最需要重写记忆的题。

### Q12 ｜ 题型：项目深挖 ｜ Lua 脚本做什么（僵尸清理）

- **我当时怎么答**：Redis + 与(跨实例组件)相关；用户排队中可能关闭网页/请求已无用（死掉）；脚本做排队计算 → 能拿信号量就出队 → 出队时顺带清理僵尸请求 → 再调模型。类比医院叫号：急事先走，医生叫不到就拨下一个，顺便清号。
- **标准答案（概念与代码一致，讲得很好）**：公平排队基于 ZSet(score=seq)，Lua `queue_claim_atomic.lua` 原子做「队头窗口内出队 claim（ZREM+DEL entry）+ 清理 entry 标记缺失/过期的僵尸队列项」——你答的"排队计算+出队+清僵尸"与真实职责对得上。可再补两句：① 释放靠 Redisson Pub/Sub `permit_changed` → 本地 poller 批量重新扫描（`FairDistributedRateLimiter.publishQueueNotify/start`）；② 过期/僵尸 = 排队超 wait 上限或会话已断的项。
  锚点：`rag/src/main/resources/lua/queue_claim_atomic.lua`；`FairDistributedRateLimiter:117-120,301-354,427-429`。
- **自评**：🟢 顺，类比生动，职责准确。这是全场最能体现"真做过"的一段，保持。
