### Q4 ｜ 题型：项目深挖 ｜ **意图识别准确率 90+，这个是怎么做的？**

> ⚠️ **本题面以更新后的实录为准**：面试官问的不是"你们评测有哪些指标"，而是**"90+ 这个数是怎么做出来的"**——这是一道**指标可信度**题，考的是口径。

- **我当时怎么答**：先讲了 RAGAS 那一类**有/无类指标**（忠实度、答案相关性、上下文准确度、上下文召回率），并说"**这些跟意图不太相关**"；然后转到"自建旁路调用、把中间结果封装出来给评测集跑"，最后讲"看**三个层级**的意图准确率，最小那层叶子节点是我们关注的"。
  ⚠️ **完全没回答"90+ 是怎么来的"**——题目问的是**数字口径**，你答的是**指标清单**，且清单本身还缺项（见 Q5 下方）。
- **标准答案 / 该答成什么样**（**逐字稿 `意图识别树怎么做.md` Q9/Q10 有全套，一个字没抛**）：
  1. **先给口径，一句话定性**（必说）：
     > "这个 90%+ 是**意图 Top-1 的节点命中率**——正确叶子排第一的比例，**不是回答正确率**。回答质量另用 RAGAS 和检索指标看。"
     主动把口径讲清楚，立的是"诚实 + 有工程素养"的人设。
  2. **怎么测（离线为主）**：评测集里有一批**意图标注样本**（问题 → 期望命中的叶子节点），跑 `intent-resolve` 看 **Top-1 是否命中**，聚合出准确率；判分式就是 `intent_pred == intent_l2`，**只认第一名**。
  3. **分母口径（最亮的一句，务必抛）**：
     > "`intent_l2` 为空、也就是**触发澄清 / 没有唯一期望意图**的样本**不进分母**——所以这个 90%+ 是**『系统敢直接判定的那部分』的准确率**，不是把没把握的样本也算进去的平均分。口径**写死在评测脚本里**（空标注直接返回 `None` 不计），不是事后挑的数字。"
  4. **评估集可信度**（面试官必追"是不是你自己编的好样本"）：① **覆盖全部二级意图**，不只挑好分的；② **`trap_type` 专放易混淆 / 边界样本**（"产品收益"vs"条款解读"这种说法接近、意图不同的）；③ **按意图分层看命中率**，不是一个平均分糊过去。
  5. **和澄清联动**（把两个模块串起来讲）："敢直接给 Top-1 的都是高置信样本，**没把握的都去澄清了**——所以准确率高是设计结果，不是运气。"
  6. **量级与目标**：全量集 **150 条**、小集 **20 条**、冒烟 **5 条**；ragenteval 目标表 **意图 Top-1 ≥ 92%**。
  - 锚点：`ragenteval/eval/rag/metrics/intent.py:compute`（`intent_top1`、空 `intent_l2` 返回 None 不计）；`eval/rag/pipeline/runner.py:246`（`intent_pred` 取 `intent_leaf_ids[0]`）；`rag/eval/EvalController.extractTopLeafIds`；`eval/common/cli.py:188`（`--limit` 默认 20）。
- ⚠️ **两处口径要回源**：① 逐字稿写"覆盖全部 **22** 个二级意图"，而 README 待补点已记 enterprise 模板节点数回源 **29**（旧 22/23 均过期）——**面试前回源，别报 22**；② 下面 Q5 的"三层准确率"同样要改口径。
- **自评**：🔴 **答非所问**（问数字口径，答指标清单）+ **最亮的"澄清样本不进分母"没抛** + 指标清单还缺项。这是**本场最可惜的一题**：逐字稿连"90% 的分母排除多少？别藏，直接说"这种追问都预演过。

### Q5 ｜ 题型：项目深挖 ｜ 意图评测具体怎么跑、怎么算成功

- **我当时怎么答**：评测先跑 **20 条**；意图识别返回**三个意图**带置信度；取**置信度最高的第一个意图**与评测集标注比对，第一个准就算识别成功；看**三个层级**（大类/中类/小类）的准确率，最关心叶子节点那层。
- **标准答案 / 该答成什么样**：
  - **对的部分（与代码一致，放心讲）**：指标就是 **Top-1**（`intent_top1`），判分式 `intent_pred == intent_l2` 只认第一名；预测值取**每个子问题的第 1 个叶子**（上游已按分降序）；默认 **`--limit 20`**、全量集 **150 条**、冒烟 5 条。
  - **要改的一处**：**没有"三层分别算准确率"**——评估集只有 `intent_l1` / `intent_l2` **两级标签**，没有第三层；所谓分层只是按 `intent_l1`/`intent_l2` 标签对**同一个 Top-1 指标**做分组切片均值（`slice_mean`），不是每层各有一套准确率。该说成：「**只评叶子那一层的 Top-1 准确率**，再按一级/二级标签做分组切片看短板」。
  - **该补的一句**：**触发澄清的样本不进分母**（同 Q4 第 3 点）——这一句能立刻显出你懂评测边界。
- **自评**：🟡 Top-1 / 20 条对；"三层准确率"与代码不符，漏了"澄清样本不进分母"。

### Q7 ｜ 题型：项目深挖 ｜ 相近意图怎么处理（澄清机制）

- **我当时怎么答**：返回三个意图后，把**前两个意图的置信度**做判断是否相近，**公式是"第二个意图置信度 ÷ 第一个意图置信度"**看百分比；相近就把这两个意图**重新走一遍快速通道的大模型、再识别一次意图**，然后返回给用户让他澄清；这是我们**自研**的框架。
- **标准答案 / 该答成什么样**：
  - **真实机制（代码为准）**：澄清在 `IntentGuidanceService.detectAmbiguity`，触发条件是**四条全中**：
    1. `guidance.enabled = true`；
    2. **子问题数恰好 == 1**（多子问题直接 return 不做歧义检测——多子问题本来就 cap 到"每问题保底 1 个"，候选不足两个，判了白判，且会变成 N 次来回的灾难）；
    3. 过滤 `<0.35` 后**仍有 ≥2 个 KB 候选**；
    4. **路径重名分叉**：以最高分候选为主路径，与其它候选路径比较，**分叉之后存在重名节点**（如"产品咨询 > 重疾险"与"条款解读 > 重疾险"），**且该名字真的出现在用户问题里**。
  - 命中重名后才调一次 **FAST 档 LLM**（`AmbiguityLLMChecker`）做**布尔确认**：返回 `{ambiguous: true/false}`——**这是"是不是歧义"的确认，不是"重新识别一次意图"**。true 才发澄清卡（最多 6 个选项、展示带层级 fullPath、可多选、"都/全部"）；false 或 **LLM 失败/超时一律放行**（纯 RAG 只读流程，不能因模型抖动阻断用户）。
  - **你的说法错在哪（三处）**：
    1. **"前两意图置信度比值"这个判定，代码里没有**。你可能是照着 `GuidanceProperties.ambiguityScoreRatio = 0.8D` 讲的——但那个字段的 javadoc 明写「歧义判定按候选意图**路径重名**触发，**该值当前不参与判定**，保留以兼容既有 yaml」，全库无调用点。**你讲的是已废弃的残留配置**。
    2. **"重新识别一次意图"是错的**：FAST 档调用只返回布尔歧义判断，用户拿到的是**选项列表**让它选，不是模型重算后的新意图排序。
    3. 少了真正的触发条件（**路径重名 + 名字出现在问题里**），而这恰恰是**你上一题刚举过的重疾险例子**。
  - 锚点：`IntentGuidanceService.java:83`（size==1）、`:88`（≥2 候选）、`:109`（0.35 过滤）、`:92-95`/`:130-156`（`collectPathConflicts`/`detectConflictName` 路径重名）、`:97`（LLM 二次确认）；`AmbiguityLLMChecker.java:58-101`（`Tier.FAST`、输出布尔）；`GuidanceProperties.java:35-44`（`ambiguityScoreRatio`/`ambiguityMargin` **已废弃、不参与判定**）。
- **自评**：🔴 **本场最需要重写的题**。**第三次**在同一个点翻车：小熊"0.7 规则"（编的）→ 小鹏"低分当澄清"（混淆兜底与澄清）→ 长鑫"置信度比值"（**把废弃配置当现行机制**）。三次错法不同、病根同一个：**没有按"触发 → 判定 → 动作 → 兜底"四段把澄清背成一条不可换词的链**。

### Q9 ｜ 题型：项目深挖 ｜ MCP 写操作的权限 / 确认怎么控制

- **我当时怎么答**：内部有 MCP 服务分三层架构；意图识别挂执行单元（知识库/库检索/MCP 工具）；MCP 的**写场景**会做**拦截**、**检查权限**（是否有写权限、是否写操作）；是写操作就**让用户自己确认**，用**状态标志位把调用逻辑挂起**，**先落库**；之后**从库里拿到参数信息**，**再进行一次大模型推理**。
- **标准答案 / 该答成什么样**：
  - **骨架对**（拦截 → 权限 → 确认 → 挂起 → 落库 → 续跑），但有一条**最亮的设计讲反了**：
    - **参数不是"从库里拿的"，是从 `t_agent_state`（Agent 状态）里取当初模型提出的那个原件**。用户点确认时**只传 `approved=true/false`**，工具与入参一律从 `agent.getAgentState(userId, conversationId).getContext()` 里那条卡在 `ASKING` 的 `ToolUseBlock` 取回——**接口注释原话："工具入参从 Agent 状态取，前端只传同意/拒绝，防止篡改"**。前端永远碰不到真实参数，改不了"请 5 天"成"请 50 天"。你讲成"从库里拿参数"，把**防篡改**这个设计亮点整个丢了。
    - **落库落的是消息**（正文以 `AWAITING_CONFIRM` 状态落 `t_agent_message`），不是"落下参数等会儿取"。
  - **该主动抛的三个点**（逐字稿 `MCP怎么做（新）.md` Q10 全有，你一个没抛）：
    1. **`AWAITING_CONFIRM` 是 `AgentMessageStatus` 里唯一的非终态**，续跑成功改回 `NORMAL`；`streamChat` 顶部查 `hasPendingConfirm`——**上一步还等你确认时不接受新问题**（防止用户晾着确认卡又去问别的，把框架状态搅乱）。
    2. **确认卡状态机**：块级 `pending → approved / denied / expired`（`expirePendingConfirm` 兜底，防止会话永久卡死），全卡一次决策、不逐条勾选。

  - **逐条对上**：全局（跨实例共享）分布式信号量 = `RPermitExpirableSemaphore`（并发 **10**）；排队是 **ZSet 公平队列、score = 全局自增 seq**；"打标记" = **entry 存活标记**（`name:entry:{requestId}`，值 `"1"`，**带 TTL**，TTL = 剩余等待 + 5s 缓冲）；"提前结束" = **SSE `onCompletion`/`onTimeout`/`onError` 绑 `ticket.cancel()`**；僵尸清理 = **`queue_claim_atomic.lua`**（取队头窗口、entry 不存在的成员 `ZREM` 清掉、存活者按序计 rank、落在可用许可窗口内则 `ZREM` 出队 + `DEL` entry）；释放后 **Pub/Sub 广播**（topic `rag:global:chat:queue:notify`，每实例启动订阅）+ **200ms 轮询兜底**。
  - **三处要改的措辞**：
    1. **"用 Redis 的原子（类）做 CAS 抢占执行权" → 不准确**。防广播风暴的 CAS 是 **JVM 本地 `AtomicBoolean firing`**（`compareAndSet(false, true)` 抢执行权、跑完释放），**只在单实例内合并通知，不具备跨实例互斥**；跨实例真正的原子互斥靠的是 **Lua 原子出队 + `tryAcquire`**。说成"Redis 原子类"会被追问"哪个 key"而答不上。
    2. **"剩下的请求进来只做一个信号量加的操作" → 代码里找不到这个机制**。实际是 **`pendingNotifications` 计数器合并**：抢执行权期间把后续通知计数，跑完再决定要不要补一轮，避免一遍遍扫队列。
    3. **"后台定时调度任务判断这台机器的单机信号量是否释放" → 两个错**：① 是**每张 Ticket 各自的 200ms `scheduleAtFixedRate` 轮询**，不是一个全局定时任务；② **信号量是全局的，不存在"这台机器的信号量"**——这一句自我矛盾（前面刚说"单机挡不住所以用全局"，后面又冒出"单机信号量"）。
  - 数值口径（**以 yaml 为准，背这三个数**）：`max-concurrent=10` / `max-wait-seconds=15` / `lease-seconds=30` / `poll-interval-ms=200`（`application.yaml`）。代码默认值 50 / 20s / 600s 被 yaml 覆盖，**别报成现值**。
  - 锚点：`FairDistributedRateLimiter`（`:117` 信号量、`:146` 入队、`:384-392` entry 标记、`:422-425` seq、`:501-540` firing/pendingNotifications、`:427-429` 发布）；`lua/queue_claim_atomic.lua`；`ChatQueueLimiter:80-84`（SSE 断开取消）、`:145-156`（拒绝走 SSE `META→REJECT→FINISH→DONE`）；`application.yaml:108-114`。
- **自评**：🟢 **全场最好的一段**，能做根因、能讲竞态，与代码高度吻合。

### Q16 ｜ 题型：项目深挖 ｜ 广播具体怎么做

- **我当时怎么答**：发生在**大模型释放信号量**时；释放后信号量 +1，通过**订阅的 topic 投递**给每台实例广播；广播时用 **Redis 的原子（类）**抢占、用 **Boolean 类型**通过 **CAS** 拿执行权；拿到就把这批请求**跑一遍**看谁能拿到信号量。
- **标准答案 / 该答成什么样**：
  - **通路对**：`permit_changed` 发布到 `rag:global:chat:queue:notify` → 各实例 listener `pollNotifier.fire()` → 本地 poller 批量重扫。topic 名可以直接报，很显真做过。
  - **改 Q15 的两处措辞**（Redis 原子类 → 本地 `AtomicBoolean`；"跑一遍"要说清是**扫本实例的 pollers**，不是"这批实例的这批请求"）。
  - 可补一句**为什么要合并**：一次释放常常在几十毫秒内跟着好几次释放，**逐次广播会让每个实例被反复唤醒去扫同一个队列**（惊群）；用 CAS 把一轮通知合并成**一次扫描**，其余只记数。你说的"不想让这么多次广播同时去执行"就是这个意思，**但没说"惊群"这个词**——补上术语，观感立刻不同。
- **自评**：🟡 通路对、关键实现归属错（内存 vs Redis）。

### Q17 ｜ 题型：项目深挖 ｜ 那个标识是放在信号量上是吧（CAS 追问）

- **我当时怎么答**：怕用户释放请求时**同时释放好几次**（几十毫秒内连着释放），信号量加的次数很多、同时广播很多次，广播太多会**干扰执行**；所以用 **CAS 抢占**：广播进来时抢占、拿到**执行权**，跑一遍队列让**每个请求都算一下能不能拿到信号量**；其余请求进来只做一个信号量**加操作**；CAS 做完**释放执行权**，等下次广播再抢。
- **标准答案 / 该答成什么样**：
  - **你的推理链是对的、而且很漂亮**（释放抖动 → 广播风暴 → CAS 合并），**唯一的问题是把它说成了 Redis 级**。改成：
    > "广播进到实例后，先用一个**本地 `AtomicBoolean` 做 CAS 抢『这一轮的通知处理权』**——抢到的实例把**本机所有的排队 ticket** 扫一遍（而不是为每次通知各扫一遍）；抢不到的直接返回，只累加一个**待处理计数**；一轮扫完释放标志，等下一批通知再抢。**跨实例之间不需要互斥**——真正保证『一个 permit 不会发两次』的是 **Lua 里那次原子出队 + `tryAcquire`**。"
  - 这一改，三个问题（CAS 归属、"只做加操作"、"执行权"）一次性解决，而且比原答更清楚。
- **自评**：🔴 机制推理好，但**把内存级 CAS 讲成 Redis 级**，且"其余只做加操作"是临时编的（代码里是计数合并）。

### Q18 ｜ 题型：项目深挖 ｜ 排队 + 清僵尸（类比）

- **我当时怎么答**：想做的是**不让多次广播同时打进来**；瓶颈在队列，排队的用户**逐一计算**；类比**医院拿号**——医生叫到我时我已经走了，不想每次都去叫这个人，叫一次执行**同时清理僵尸**。
- **标准答案 / 该答成什么样**：
  - **类比好、可保留**，但应当先给术语再打比方：「这是**惊群（thundering herd）**问题——一次释放广播唤醒所有实例去抢同一批 permit，所以我们**合并通知 + 只让一个执行者扫队列**。比方说医院叫号……」**先术语、后类比**，专业度完全不同。
  - "逐一计算"其实不准确：真实是取**队头窗口**（`ZRANGE 0..maxRank+slack-1`，slack=16）局部扫描，不是全队列逐一。
- **自评**：🟢 类比生动、职责准确；缺术语、窗口大小没讲。

### Q19 ｜ 题型：八股（RocketMQ 事务消息 / 半消息 / 回查）

- **面试官问**：第二个项目（在校练习的**优惠券**项目）用的事务消息——"这就是**半消息**那块吗？还是**消息事务回查**？介绍一下**半消息跟回查的内部机制**。"
- **我当时怎么答**：半消息分**两个阶段**（两阶段提交）：① 生产者发消息给 Broker，Broker **持久化**、**此时不能投递、消费者看不到**；② 生产者收到后**执行本地事务**（库存扣减、创建订单），执行完**发消息给 Broker 二次确认**；**本地成功就 commit；本地事务失败就 Rollback，然后去做一个事务的回查**。
- **标准答案 / 该答成什么样**：
  - **两阶段框架对**（半消息 → 本地事务 → 二次确认 commit/rollback），但**"回查"讲反了，这是本场八股最硬的错**：
    > **回查（Transaction Check）不是"失败后"的动作，而是"Broker 迟迟没收到二次确认"时的兜底询问**。生产者执行完本地事务后如果**宕机 / 网络断 / 没发出二次确认**，这条半消息就会永远挂在 half topic 里；所以 Broker 会**主动回调生产者**（`TransactionListener.checkLocalTransaction`），让生产者**去查本地库**（"这个订单/这条库存扣减到底成没成功"）再回答 `COMMIT` / `ROLLBACK` / `UNKNOWN`。答 `UNKNOWN` 就继续回查，**超过最大回查次数默认回滚丢弃**。所以回查解决的是**"生产者与 Broker 状态不一致"**，跟本地事务成功失败没关系。
  - **该补的四个点**：① 半消息存在 **`RMQ_SYS_TRANS_HALF_TOPIC`**（消费者天然看不到）；② commit 是**把消息从 half topic 恢复到真实 topic**（不是"再发一次"）；③ 回查有**频率与上限**（默认从发送后约 6s 起、之后每 60s 一次，最多 15 次——⚠️ 具体默认值未核码，面试只说"定频 + 上限、超限回滚"即可，别报死数）；④ 生产者的 `checkLocalTransaction` **必须幂等且只查不改**。
  - **该主动抛的一句**（面试官最爱追的下一问）：「事务消息只保证**本地事务与消息发送**的原子，**不保证消费不重复**——消费端还要幂等（我们是 `uuid` 作 MQ keys + 状态机防重）。」
  - ⚠️ **这是本场第二次暴露 MQ 缺口**（小熊 Q5 已记一次）：`简历面试逐字稿/项目深挖/MQ怎么做.md` **至今未生成**。你在校项目用的就是 RocketMQ，这题不该卡。
- **自评**：🟡 两阶段对、回查讲反、消费端幂等没抛。
