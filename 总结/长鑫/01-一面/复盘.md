### Q4 ｜ 题型：项目深挖 ｜ RAGAS 那一类指标

- **我当时怎么答**：RAGAS 指标——有/无类指标：**忠实度、答案相关性、上下文准确度、上下文召回率**；这些跟意图不太相关。
- **标准答案（与 ragenteval 一致）**：RAGAS 是 **5 个标准指标**：`faithfulness`（忠实度）/ `answer_relevancy`（答案相关性）/ `answer_correctness`（答案正确性）/ `context_precision`（上下文精确率）/ `context_recall`（上下文召回率）。
  - **"上下文准确度"不是一个指标，是两项**：`context_precision` + `context_recall`——你口播把两项并成一项说，同时又漏了 `answer_correctness`，**净结果：五个只报出三个半**。
  - ⚠️ **这是第二次犯**：小鹏 Q7 同款（漏第 5 类 + "上下文准确性"命名不准）。**把五个全名背成肌肉记忆**。
  - 延迟类可补 TTFT P50/P95/P99（`latency.py`），比笼统"延迟"专业。
  锚点：`ragenteval/eval/rag/metrics/ragas_judge.py`；`retrieval.py`；`intent.py`；`behavior.py`；`latency.py`。
- **自评**：🟡 结构对，五指标只报出三个半（跨场复发）。

### Q5 ｜ 题型：项目深挖 ｜ 意图评测怎么跑、怎么算成功

- **我当时怎么答**：评测先跑 **20 条**；意图识别返回**三个意图**带置信度；取**置信度最高的第一个意图**与评测集标注比对，第一个准就算识别成功；看**三个层级**（大类/中类/小类）的准确率，最关心叶子节点那层。
- **标准答案 / 该答成什么样**：
  - **对的部分（与代码一致，放心讲）**：指标就是 **Top-1**（`intent_top1`），判分式 `intent_pred == intent_l2` 只认第一名；预测值取**每个子问题的第 1 个叶子**（上游已按分降序）；默认 **`--limit 20`**、全量集 **150 条**、冒烟 5 条。
  - **要改的两处**：
    1. **没有"三层分别算准确率"**：评估集只有 `intent_l1` / `intent_l2` **两级标签**，没有第三层；所谓分层只是按 `intent_l1`/`intent_l2` 标签对**同一个 Top-1 指标**做分组切片均值（`slice_mean`），不是每层各有一套准确率。该说成：「**只评叶子那一层的 Top-1 准确率**，再按一级/二级标签做分组切片看短板」。
    2. 补一句**最亮的评测口径**（逐字稿里有、你漏了）：**触发澄清的样本不进分母**——这类样本没有唯一期望意图，算进去是冤枉它们。这一句能立刻显出你懂评测边界。
  - 锚点：`ragenteval/eval/rag/metrics/intent.py:compute`（`intent_top1`）；`eval/rag/pipeline/runner.py:246`（`intent_pred` 取 `intent_leaf_ids[0]`）；`rag/eval/EvalController.extractTopLeafIds`；`eval/common/cli.py:188`（`--limit` 默认 20）。
- **自评**：🟡 Top-1 / 20 条对；"三层准确率"与代码不符，漏了"澄清样本不进分母"。

### Q7 ｜ 题型：项目深挖 ｜ 相近意图怎么处理（澄清机制）

- **我当时怎么答**：返回三个意图后，把**前两个意图的置信度**做判断是否相近，**公式是"第二个意图置信度 ÷ 第一个意图置信度"**看百分比；相近就把这两个意图**重新走一遍快速通道的大模型、再识别一次意图**，然后返回给用户让他澄清；这是我们**自研**的框架。
- **标准答案 / 该答成什么样**：
  - **真实机制（代码为准）**：澄清在 `IntentGuidanceService.detectAmbiguity`，触发条件是**四条全中**：
    1. `guidance.enabled = true`；
    2. **子问题数恰好 == 1**（多子问题直接 return，不做歧义检测——多子问题本来就被 cap 到"每问题保底 1 个"，候选不足两个，判了白判，且会变成 N 次来回的灾难）；
    3. 过滤 `<0.35` 后**仍有 ≥2 个 KB 候选**；
    4. **路径重名分叉**：以最高分候选为主路径，与其它候选路径比较，**分叉之后存在重名节点**（如"产品咨询 > 重疾险"与"条款解读 > 重疾险"），**且该名字真的出现在用户问题里**。
  - 命中重名后，才调一次 **FAST 档 LLM**（`AmbiguityLLMChecker`）做**布尔确认**：返回 `{ambiguous: true/false}`——**这是"是不是歧义"的确认，不是"重新识别一次意图"**。true 才发澄清卡（最多 6 个选项、展示带层级 fullPath、可多选、"都/全部"）；false 或 **LLM 失败/超时一律放行**（纯 RAG 只读流程，不能因模型抖动阻断用户）。
  - **你的说法错在哪（三处）**：
    1. **"前两意图置信度比值"这个判定，代码里没有**。你可能是照着 `GuidanceProperties.ambiguityScoreRatio = 0.8D` 讲的——但那个字段的 javadoc 明写「歧义判定按候选意图**路径重名**触发，**该值当前不参与判定**，保留以兼容既有 yaml」，全库无调用点。**你讲的是已废弃的残留配置**。
    2. **"重新识别一次意图"是错的**：FAST 档调用只返回布尔歧义判断，用户拿到的是**选项列表**让它选，不是模型重算后的新意图排序。
    3. 少了真正的触发条件（**路径重名 + 名字出现在问题里**），而这恰恰是**你上一题刚举过的重疾险例子**。
  - 锚点：`IntentGuidanceService.java:83`（size==1）、`:88`（≥2 候选）、`:109`（0.35 过滤）、`:92-95`/`:130-156`（`collectPathConflicts`/`detectConflictName` 路径重名）、`:97`（LLM 二次确认）；`AmbiguityLLMChecker.java:58-101`（`Tier.FAST`、输出布尔）；`GuidanceProperties.java:35-44`（`ambiguityScoreRatio`/`ambiguityMargin` **已废弃、不参与判定**）。
- **自评**：🔴 **本场最需要重写的题**。**第三次**在同一个点翻车：小熊"0.7 规则"（编的）→ 小鹏"低分当澄清"（混淆兜底与澄清）→ 长鑫"置信度比值"（**把废弃配置当现行机制**）。三次错法不同、病根同一个：**没有按"触发条件 → 判定 → 动作 → 兜底"四段把澄清背成一条不可换词的链**。

### Q9 ｜ 题型：项目深挖 ｜ MCP 写操作的权限 / 确认怎么控制

- **我当时怎么答**：内部有 MCP 服务分三层架构；意图识别挂执行单元（知识库/库检索/MCP 工具）；MCP 的**写场景**会做**拦截**、**检查权限**（是否有写权限、是否写操作）；是写操作就**让用户自己确认**，用**状态标志位把调用逻辑挂起**，**先落库**；之后**从库里拿到参数信息**，**再进行一次大模型推理**。
- **标准答案 / 该答成什么样**：
  - **骨架对**（拦截 → 权限 → 确认 → 挂起 → 落库 → 续跑），但有一条**最亮的设计讲反了**：
    - **参数不是"从库里拿的"，是从 `t_agent_state`（Agent 状态）里取当初模型提出的那个原件**。用户点确认时**只传 `approved=true/false`**，工具与入参一律从 `agent.getAgentState(userId, conversationId).getContext()` 里那条卡在 `ASKING` 的 `ToolUseBlock` 取回——**接口注释原话："工具入参从 Agent 状态取，前端只传同意/拒绝，防止篡改"**。前端永远碰不到真实参数，改不了"请 5 天"成"请 50 天"。你讲成"从库里拿参数"，把**防篡改**这个设计亮点整个丢了。
    - **落库落的是消息**（正文以 `AWAITING_CONFIRM` 状态落 `t_agent_message`），不是"落下参数等会儿取"。
  - **该主动抛的三个点**（逐字稿 `MCP怎么做（新）.md` Q10 全有，你一个没抛）：
    1. **`AWAITING_CONFIRM` 是 `AgentMessageStatus` 里唯一的非终态**，续跑成功改回 `NORMAL`；`streamChat` 顶部查 `hasPendingConfirm`——**上一步还等你确认时不接受新问题**（防止用户晾着确认卡又去问别的，把框架状态搅乱）。
    2. **确认卡状态机**：块级 `pending → approved / denied / expired`（`expirePendingConfirm` 兜底，防止会话永久卡死），全卡一次决策、不逐条勾选。
    3. **拒绝文案的隐藏坑**：AgentScope 被拒时返回英文 `"Permission denied by user"`，模型照抄会很生硬 → `AgentConfirmDenialMiddleware` 在进模型前改写成中文语义说明（"用户在确认卡片上点了取消，这次操作没有执行……"）。**只改写"用户取消"，规则拒绝不动**。
  - **"三层架构"要说得更准**：三层在 **MCP 客户端侧**——工具加载（`McpToolRegistry`）/ 参数提取（`LLMMcpParameterExtractor`，三态 `SUCCESS`/`NEED_CLARIFICATION`/`FAILED`）/ 执行与结果处理（`McpClientToolExecutor`）；**服务端是独立模块**（`mcp-server`，工具规格与读/写自报在 `McpServerConfig`/`McpToolAnnotations`，**强制自报读写、缺失即启动报错**）——说成"我们一个 MCP 服务分三层"会让人以为是服务端分层。
  - 锚点：`McpToolBridge.checkPermissions`（`requireConfirm || readOnlyHint == false` → ask）；`AgentStreamEventBridge`（`RequireUserConfirmEvent` → confirm 块 → `settleAwaitingConfirm`）；`AgentChatServiceImpl.startConfirmRun`（`:154-194` 取原件、`:217-269` 携 `ConfirmResult` 续跑）；`AgentMessageStatus`；`McpToolAnnotations`（`READ_ONLY`/`WRITE`）。
- **自评**：🟡 骨架对；**参数来源讲反、防篡改亮点全丢**、状态机与拒绝改写没抛。

### Q15 ｜ 题型：项目深挖 ｜ 分布式限流端到端

- **我当时怎么答**：瓶颈在大模型（要等结果）；用**分布式信号量**（单机挡不住、约 4 台实例但模型只能支持 **10 个并发**，所以从外部先控）；请求进来先拿信号量、值设为 **10**；第 11 个进**队列排队**并**打标记**；评估请求是否**提前结束**（用户关网页）；模型返回释放信号量后，用 **Redis 做原子信号量抢占**、算它能不能拿到；再做**僵尸清理**；然后**出队提交大模型**。
- **标准答案（**本场与代码吻合度最高的一段，主体可放心讲**）**：
  - **逐条对上**：全局（跨实例共享）分布式信号量 = `RPermitExpirableSemaphore`（并发 **10**）；排队是 **ZSet 公平队列、score = 全局自增 seq**；"打标记" = **entry 存活标记**（`name:entry:{requestId}`，值 `"1"`，**带 TTL**，TTL = 剩余等待 + 5s 缓冲）；"提前结束" = **SSE `onCompletion`/`onTimeout`/`onError` 绑 `ticket.cancel()`**；僵尸清理 = **`queue_claim_atomic.lua`**（取队头窗口、entry 不存在的成员 `ZREM` 清掉、存活者按序计 rank、落在可用许可窗口内则 `ZREM` 出队 + `DEL` entry）；释放后 **Pub/Sub 广播**（topic `rag:global:chat:queue:notify`，每实例启动订阅）+ **200ms 轮询兜底**。
  - **三处要改的措辞**：
    1. **"用 Redis 的原子类做 CAS 抢占执行权" → 不准确**。防广播风暴的 CAS 是 **JVM 本地 `AtomicBoolean firing`**（`compareAndSet(false, true)` 抢执行权、跑完释放），**只在单实例内合并通知，不具备跨实例互斥**；跨实例真正的原子互斥靠的是 **Lua 原子出队 + `tryAcquire`**。说成"Redis 原子类"会被追问"哪个 key"而答不上。
    2. **"剩下的请求进来只做一个信号量加的操作" → 代码里找不到这个机制**。实际是 **`pendingNotifications` 计数器合并**：抢执行权期间把后续通知计数，跑完再决定要不要补一轮，避免一遍遍扫队列。
    3. **"后台定时任务判断这台机器的单机信号量是否释放" → 两个错**：① 是**每张 Ticket 各自的 200ms `scheduleAtFixedRate` 轮询**，不是一个全局定时任务；② **信号量是全局的，不存在"这台机器的信号量"**——这一句自我矛盾（前面刚说了"单机挡不住所以用全局"，后面又冒出"单机信号量"）。
  - 数值口径（**以 yaml 为准，背这三个数**）：`max-concurrent=10` / `max-wait-seconds=15` / `lease-seconds=30` / `poll-interval-ms=200`（`application.yaml`）。代码默认值 50 / 20s / 600s 被 yaml 覆盖，**别报成现值**。
  - 锚点：`FairDistributedRateLimiter`（`:117` 信号量、`:146` 入队、`:384-392` entry 标记、`:422-425` seq、`:501-540` firing/pendingNotifications、`:427-429` 发布）；`lua/queue_claim_atomic.lua`；`ChatQueueLimiter:80-84`（SSE 断开取消）、`:145-156`（拒绝走 SSE `META→REJECT→FINISH→DONE`）；`application.yaml:108-114`。

### Q17 ｜ 题型：项目深挖 ｜ 那个标识是放在信号量上是吧（CAS 追问）

- **我当时怎么答**：怕用户释放请求时**同时释放好几次**（几十毫秒内连着释放），信号量加的次数很多、同时广播很多次，广播太多会**干扰执行**；所以用 **CAS 抢占**：广播进来时抢占、拿到**执行权**，跑一遍队列让**每个请求都算一下能不能拿到信号量**；其余请求进来只做一个信号量**加操作**；CAS 做完**释放执行权**，等下次广播再抢。
- **标准答案 / 该答成什么样**：
  - **你的推理链是对的、而且很漂亮**（释放抖动 → 广播风暴 → CAS 合并），**唯一的问题是把它说成了 Redis 级**。改成：

- **自评**：🔴 机制推理好，但**把内存级 CAS 讲成 Redis 级**，且"其余只做加操作"是临时编的（代码里是计数合并）。

### Q19 ｜ 题型：八股（RocketMQ 事务消息 / 半消息 / 回查）

- **我当时怎么答**：半消息分**两个阶段**（两阶段提交）：① 生产者发消息给 Broker，Broker **持久化**、**此时不能投递、消费者看不到**；② 生产者收到后**执行本地事务**（库存扣减、创建订单），执行完**发消息给 Broker 二次确认**；**本地成功就 commit；本地事务失败就 Rollback，然后去做一个事务的回查**。
- **标准答案 / 该答成什么样**：
  - **两阶段框架对**（半消息 → 本地事务 → 二次确认 commit/rollback），但**"回查"讲反了，这是本场八股最硬的错**：
    > **回查（Transaction Check）不是"失败后"的动作，而是"Broker 迟迟没收到二次确认"时的兜底询问**。生产者执行完本地事务后如果**宕机 / 网络断 / 没发出二次确认**，这条半消息就会永远挂在 half topic 里；所以 Broker 会**主动回调生产者**（`TransactionListener.checkLocalTransaction`），让生产者**去查本地库**（比如"这个订单/这条库存扣减到底成没成功"）再回答 `COMMIT` / `ROLLBACK` / `UNKNOWN`。答 `UNKNOWN` 就继续回查，**超过最大回查次数默认回滚丢弃**。所以回查解决的是**"生产者与 Broker 状态不一致"**，跟本地事务成功失败没关系。
  - **该补的四个点**：① 半消息存在 **`RMQ_SYS_TRANS_HALF_TOPIC`**（消费者天然看不到）；② commit 是**把消息从 half topic 恢复到真实 topic**（不是"再发一次"）；③ 回查有**频率与上限**（默认从发送后约 6s 起、之后每 60s 一次，最多 15 次——⚠️ 具体默认值未核码，面试只说"定频 + 上限、超限回滚"即可，别报死数）；④ 生产者的 `checkLocalTransaction` **必须幂等且只查不改**。
  - **该主动抛的一句**（面试官最爱追的下一问）：「事务消息只保证**本地事务与消息发送**的原子，**不保证消费不重复**——消费端还要幂等（我们是 `uuid` 作 MQ keys + 状态机防重）。」这一句能直接把话题引到你熟的地方。
  - ⚠️ **这是本场第二次暴露 MQ 缺口**（小熊 Q5 已记一次）：`简历面试逐字稿/项目深挖/MQ怎么做.md` **至今未生成**。你在校项目用的就是 RocketMQ，这题不该卡。
- **自评**：🟡 两阶段对、回查讲反、消费端幂等没抛。

  - **面试官答**：技术上——**多了解后端框架的底层设计**；表达上——比如**项目里有些功能是什么、模型做的是什么、功能的定位、以及它们之间的关系**，要**介绍得更清楚**；（对）一些技术设计实践（讲得）更直接、更快。
- **表达注意**：
  - **这个反问问得好**（是全场唯一拿到**具体改进信号**的动作），而且面试官的答案**就是本场复盘的结论**：他全程想问的是**"你的系统是什么、各部分什么关系"**——而你的回答模式是**把某个模块的细节铺开讲**（限流讲得极细，架构关系一句没有）。**"有细节、没地图"**是本场唯一的、也是重复出现的表达病。
  - 面试官说的"后端框架底层设计"≈ **Spring / 框架级理解**（他前面就追问过"你们用 Spring AI 吗""有没有编排"），建议补：**Agent 框架（AgentScope）的 ReAct 循环与中间件机制**、**Spring AI 的 Tool/Advisor 抽象**、以及**你自己那四件中间件各自挂在哪一步**——把"我用了个框架"变成"我知道它每步在干嘛"。
  - 具体动作：下次开场先给 **30 秒系统地图**（一张嘴就说清"一条流水线五段 + 三个档位 + 四类执行单元"），再往任何一个模块钻。逐字稿里的 **45s 开场总览**就是为这个准备的，本场一次都没用。
- **自评**：🟡 反问好、反馈准。
