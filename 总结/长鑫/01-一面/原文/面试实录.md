## 面试官问 / 我答

### Q1 开场：自我介绍
**面试官问：**（开场问候 + 「方便先做一下自我介绍吗」）

**我：** 你好，我叫 xxx，毕业于新疆大学软件工程专业。目前在中国平安人寿保险股份有限公司任职，岗位是开发工程师。目前我负责的项目是跟 **AI** 相关的，做的是一个 **RAG 系统**——内部的一个**智能知识问答平台**。我**深度参与**了**意图识别**模块、**问题改写与已知问题的拆分**（=问题改写与拆分）、**多路检索的召回**、**分布式限流**，还有**评测**的搭建。项目目前保持着**日均 5 万**的用量，服务了**上千个用户**（录音含糊）。在校读研和本科期间，也获得过一些奖项、有过论文的发表。自我介绍完毕。

### Q2 项目背景：为什么要自己部署模型？
**面试官问：**（详细介绍一下背景）

**我：** 我们内部如果是想使用外部的一些大模型、还有一些问答相关的模型，其实是会**受到一个监管的压力**，所以我们就选择了**将模型部署到我们的内部**，然后做一个这样的平台，去给我们内部的一些用户进行服务。这就是我们的一个背景。

### Q3 端到端：平台的链路流程是怎么走的？
**面试官问：**（问句未录清，据答推断为「整个链路流程」）

**我：** 我们的一个**端到端**的流程，其实是说：用户提交一个问题进来的时候，我们会先走几个**固定的流程**——这个流程是我们**内部写的**。首先我们会将用户提问的这个问题做一个**重写与拆分成子问题**；如果有（多个）问题的话，然后我们会提交给**线程池**，让线程池去用大模型将这个问题进行一个**意图识别**，因为我们会有一个**意图识别树**。识别意图之后，我们这个意图会有一些**执行的单元**——执行单元的意思就是说，我要么可以去**知识库里面检索**，可以去做一个 **MCP 走一个 MCP 工具**的调用，或者说如果是用户问一些**天气类**的问题、或者说「你好」「你是什么模型」之类的问题，我们就走这个**系统应答**，就不用再走这些检索了。**目前就这三类**。然后我们就去做——将这个识别到的意图，去做 MCP 的工具（调用）或者说**多路的检索**；然后我们就会将这个检索到的结果和工具结果返回给大模型，然后让他根据这个结果进行一个回答。我们目前整个流程就是这样子。

### Q4 评测体系：RAGAS 那一类指标
**面试官问：**（问句未录清，据答推断为评测指标）

**我：** 我们目前来说，我们去统计的时候，我们是做了一个**评测**。我们这个评测其实有**一类指标**，也就是 **RAGAS 这个指标**，就是**有 / 无类**的指标程度——包括**忠实度**、**问题的（答案）相关性**、**上下文的准确度**、**上下文的召回率**，是这一类的指标。其实这些**跟我们这个意图不太相关**。我现在要讲的下一个指标，其实就**跟意图相关**的：我们会自己写一个**旁路**的调用——我们正常的一个路径的调用，我们会把这些**中间的结果都封装一遍**拿出来，然后我们给这个**评测集**去跑。然后我们具体关注的指标就是**每一个层级**（的准确率），因为我们的意图有**三个层级**——比如说我们有一个**大类**、有一个**中类**、有一个**小类**，那么我们**最小这一类**就是我们需要关注的这个层级——**叶子节点**。所以我们会看这三类的**意图的准确率**。

### Q5 追问：意图评测具体怎么跑 / 怎么算成功
**面试官问：**（问句未录清，据答推断为意图评测流程）

**我：** 我们是这样子识别的：我们评测的时候，我们会**先跑 20 条**去进行一个测评。因为我们**意图识别**的时候，我们交给大模型（去识别）这个意图的时候，我们会有**三个意图返回**，所以它会有一些**置信度**。所以我们就将**第一个、置信度最高的这个意图**作为我们评测的一个要点：如果我们这个**第一个意图是准确的**，跟我们的**评测集标注**的这个意图是准确的，我们就算为**识别成功**；如果不是第一个的话，我们就不算成功。

### Q6 追问：剩下约 10% 没识别成功的是哪些？做过分析吗？
**面试官问：** 具体是哪些呢？会导致比如**剩下的 10%** 大概哪些没有识别成功？你们有做过这样的分析？

**我：** 目前是有几类是统计的（准确率）会比较低一点。第一个就是我们**保险领域**（的疑难）——比如说有个**重疾险条款**，这种重疾险条款，其实我们会分为这个**产品条款**；但是有时候它会识别到这种**重疾险的介绍**，就**产品咨询**这一类。这两类是比较相关的，目前我们统计到这一类会有比较难的一个检索的问题。

### Q7 追问：那相似意图你们怎么处理的？
**面试官问：**（问句未录清，据答推断为「那你们怎么处理这种相近意图」）

**我：** 所以我们就是——我们在意图识别的时候也会做一个判断，就是说我们返回**三个意图**，那么我们会将**前两个意图的置信度**做一个判断：**它们是否相近**。这个**是否相近的一个公式**，其实就是**第二类的这个意图（置信度）除以第一类这个意图（置信度）**，大概是百分比是多少，我们就判断这个作为**是否相近**。如果识别到——如果它这个**百分比相近**的话，那么我们就会**将这两个意图重新再走一遍快速通道的一个大模型**，然后再识别一次意图，然后返回给用户，**让他进行一个澄清**。这个是我们自己**自研**的一个框架。

### Q8 升级方向：正在接入 Agent（从固定工作流 → 有思考的 Agent）
**面试官问：**（问句未录清，据答推断为「你们现在在做什么升级」）

**我：** 目前的话，我们是正在接入这个 **Agent**（阿里推出的那个 Agent，[平台名未录清]）。目前是因为这个平台，其实我们（现在）是一个**固定的工作流程**，是吗？那我们现在有一个场景，就是它可能需要一些**编码**，我们想让它有一些**自己的思考**，就不走这个固定的工作流程这个形式。所以因为我们的这个 **RAG**，它只是**检索内容、返回生成内容**，它并没有自己的一些思考；所以我们就想接入这个 Agent，然后让它自己有这个能力。目前也是正在做，目前就是升级**两个模块**：一个是 **MCP 工具的一个升级**——我们会增加一个**写**的写的场景，然后会去**管住这个 MCP（写）场景的这个写操作**，因为这个（涉及）权限；第二个就是我们这个**会话记忆**。

### Q9 追问：这个权限 / 写操作是怎么控制的？
**面试官问：** 你的意思是说**控制他**？

**我：** 其实我们就是内部有一个服务，就是我们有一个 **MCP 的一个服务**，然后我们分成了**三层架构**。第一个就是我们先会让这个服务**独自去跑**；然后如果我们现在接的话，就是让它会去做**从意图识别，然后再去做这个 MCP 的一个调用**。那么我刚刚提到，就是我们这个**意图识别会挂一些（执行单元）**，我们会有（一个标识）去识别它是走**知识库调用**、还是走**库检索**、还是说走 **MCP 的一个工具的调用**，目前是这样子。然后如果是 **MCP** 的话，有一个场景：如果是**写**的场景的话，我们会（做一个拦截）去做一个**拦截**，然后我们去**检查一个权限**——他是否是**写的一个权限**、是不是**写的一个操作**。如果是写的操作，我们会**让用户自己去确认**，然后把这一个**调用的一个逻辑**（挂起来），我们会有一个**状态的标志位**把它**挂起**，然后**先落库**；之后我们会通过**拿到库里面的一些参数的信息**，然后再进行一次、**再进行一次大模型的一个推理**。目前是这么做的。

### Q10 追问：那你们这是不是智能体框架？用的 Spring AI？
**面试官问：**（问句未录清，据答推断为「这是不是智能体 / 用的什么框架」）

### Q13 Agent 的两种模式（ReAct / Supervisor）
**面试官问：**（问句未录清，据答推断为「Agent 有哪些模式」）

**我：** 其实它有一些模式：比如说它可以用 **ReAct 模式**，ReAct 模式的话其实就是**推理**，然后**思考**，要**调用工具**，然后再**循环**。然后还有一种模式就是 **Supervisor 监督者模式**：监督者模式的话，其实跟别的有一点不一样——（ReAct / 一般模式）的话，其实是将这一个问题、将用户的问题**提交之后**，它（自己）做一个**意图识别**，然后就**提交给他的一些（下属 Agent）**，然后他就**不管了**，他就直接拿返回的结果，然后去进行一个回答。那 Supervisor 的话，他就是**每一步都会收到**这个（下属 Agent 的答复），然后根据这个答复**再进行评估这个路径**，然后再去**返回给他的（下属）需要做什么**。目前我了解到这两种模式。

### Q15 分布式限流：端到端怎么做的？
**面试官问：**（问句未录清，据答推断为「你们这个限流是怎么做的」）

**我：** 其实是这样子：我们做这个**限流**的时候，因为我们调模型的话，我们需要**等这个结果**对吧？然后等这个结果的话，其实**所有的并发请求的压力的一个瓶颈，其实就在大模型这一个计算当中**。所以我们希望**不要让这么多请求进到我们大模型的这个服务里面**，他会提高这个**推理的延迟**。所以的话我从**端到端**这边讲一下这个流程是怎样子的：

其实就是我们会使用一个**分布式的一个信号量**。因为我们评估过，如果我们使用**单机的一个（信号量）机制**，其实我们没有办法做到——就是并发请求进来的时候，我们**没有办法挡住**（压向）我们这个服务器的大模型（服务）。比如说我们有**多台**服务器（约 4 台），但是我们（模型）只能支持 **10 个并发**，所以我们相当于就是说**从外部就先进行一个控制**。也就是说，我们**每一个请求进来的时候，我们都先去拿这个信号量**，我们这个信号量（的值）其实是**设置为 10**。然后的话，比如说有 **10 个用户去拿了这个信号量**，拿完信号量之后，我们**剩下第 11 个用户**，我们就会去我们的一个**队列**里面去进行一个**排队**；排队的话，我们会给（使用）这个用户的这个请求**寄一个标记**。

因为我们我们会评估他这个请求**是否会提前结束**——比如说用户**关闭了网页**，但是我这个请求**还是在进行**当中，那像这种情况的话，我们就会去评估。然后我们就会等到**每个模型都返回结果之后，他释放了这个信号量**，我们就会使用这个 **Redis 做一个原子的一个信号量的一个抢占**——抢占这个信号量，那么去计算它的这个（资格）：首先会去计算这个用户他这个请求**是否到达了、是否能拿到这个信号量**；然后我们再去做一个**僵尸的一些（请求）的一个清理**，我们会用这个操作去**清理这些已经不存活的用户**，然后再**进行出队，提交给大模型**。我们这个流程其实是这样子的。

然后我们内部其实还有一个操作、我们内部还实现一个细节：就是说我们在对接（排队）的时候，我们 **Redis 释放信号量**的时候，我们会使用（Redis）**一个广播机制**去对这几台实例进行**广播**，让他们**同时去抢占这个信号量**；然后还会有**后台一个定时调度的任务**去（判断）——这个实例还会有一个**后台的一个定时调度的任务**去判断他这个机器的**单机的一个信号量是否有释放**。这两个操作，一起合起来去做。那么就是一个整个流程。

### Q16 追问：那这个广播具体是怎么做的？
**面试官问：** 广播是怎么做的吗？

**我：** 广播其实是在——其实是发生在**这个用户**、就是发生在**这个大模型释放这个信号量的时候**。就是大模型回答完之后，我们后台会对这个信号量进行一个**释放**；释放之后，其实这个信号量就会加（1）；之后我们就会去给这个、我们就会通过我们**订阅的这一个 top（topic）**，然后**去投递**——投递给（每台实例），然后进行广播。

我们在这期间会做一些：比如说我们广播的时候，我们会用一个 **Redis 的一个原子（类）**去进行（计数 / 抢占），然后的话去**抢占**当前的一个——我们会用一个 **Boolean 类型去抢占**当前的一个（执行权），通过 **CAS 比较与交换**去拿到当前的一个**执行权**。然后的话，我们会对这一批这个实例的这一批请求**同时跑一遍**，然后**看谁能够拿到这个信号量**。知道（我）这样子描述能不能理解。

### Q17 追问：这个标识是放在那个信号量上是吧？
**面试官问：** 这个标识是放在那个信号（量）是吧？是的什么意思？

**我：** 我们其实——我们评估过，因为我们怕就是说，我们评估**这个用户释放这个请求的时候，可能会有同时释放好几次**这个信号量。就是比如说我们从（队列里）释放两个，然后突然间几十毫秒又释放一个、释放两个，然后几十毫秒后又再释放信号量——其实就是相当于**信号量加的次数（很多）**，但是我们同时要广播，我们同时要**广播很多次**。所以的话，我们觉得这个**广播太多**了，有可能会**干扰到我们的执行**。所以的话我们就会使用这个 **CAS 去抢占**这个（执行权）——当一个广播进来这个服务的时候，我们就会去抢占、使用（Redis）去抢占，然后（拿到）到这个**执行权**，然后我们去**跑一遍这个队列**的一些——我们让队列里面的**每个请求都计算一下它能不能拿到信号量**；然后剩下的、剩下的请求进来呢，我们就只是做一个**信号量的一个加的操作**。我们等这一个**等这个 CAS 的一个操作做完之后**，我们还会将这个**执行权释放回去**，然后再**等下一次广播进来**说再次去抢占。其实是这样子的竞争。
