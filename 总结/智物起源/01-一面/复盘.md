### Q6 ｜ 题型：项目深挖 ｜ MCP 服务升级：为什么加"写"？权限怎么控？

- **我当时怎么答**：因为希望 Agent 有自主思考，所以把 MCP 服务升级——原本只有查询（读），现在**增加写的功能**；写是危险操作，所以**重点是管写**。架构分三层：MCP 是**独立服务**，走端口调用，带工具 ID 和描述；**强制读写分离**——服务启动时强制让工具**上报**读/写类型，**不报就报错让服务起不来**；读操作继承接口改写权限判断、放行；**写操作走 AOP（洋葱模型）**，把调用流程状态**挂起来落库**，设为"等待用户确认"，用户确认后"**再重新从库里面拿出来，将这个结果拿出来**"，再进行 MCP 工具调用。
- **标准答案 / 该答成什么样**（沿用既往已核码结论）：
  - 🔴 **最严重的问题：把"防篡改"讲反了（第二次了）**。你说"用户确认以后…**再重新从库里面拿出来**，将这个结果拿出来，再调用"。**实际设计恰恰相反**——**工具名与入参从 Agent 状态 `t_agent_state` 里当初模型提出的那条原始 `ToolUseBlock` 取回，前端只回传 `approved=true/false`**。接口注释原话："**工具入参从 Agent 状态取，前端只传同意/拒绝，防止篡改**"——**前端永远碰不到真实参数**。
    - **改口模板（必背，第一句就要说）**：「写操作走确认卡：**工具与入参从 Agent 状态的原始 `ToolUseBlock` 取，前端只回传同意/拒绝**——这是**防篡改**设计，参数不经过前端。确认后携 `ConfirmResult` 续跑。」
    - ⚠️ `高频错题.md` 登记过（2026-09-11 长鑫 Q9），**本次是第二次**。锚点：`AgentChatServiceImpl.startConfirmRun:154-194`（取原件）、`:217-269`（续跑）；`McpToolBridge.checkPermissions`。
  - 🔴 **"写操作走 AOP（洋葱模型）"——这个说法不准（本轮核码新查出）**：全仓**没有任何 MCP 相关切面**（只有幂等 2 个 + `RagTraceAspect` 链路追踪，共 3 个 `@Aspect`），**没有切点表达式**。真实机制是**两层框架能力**：
    - ① **`McpToolBridge extends ToolBase` 覆写 `checkPermissions()`**（`agent/.../tool/McpToolBridge.java:83-88`）——只读返回 `allow("该工具未配置执行前确认")`、需确认返回 `ask("该操作会产生实际业务影响，执行前需要你确认")`；判定式 **`needsConfirm = requireConfirm || readOnlyHint == false`**（`:93-95`）。**这才是"读放行、写拦截"的真身**——**拦截方是框架自身，不是我们自己写的 AOP**。

### Q7 ｜ 题型：项目深挖 ｜ 分布式限流怎么做？

- **我当时怎么答**：1000+ 用户同时请求会把模型 **GPU 资源打爆**，所以要在 **Redis 做一层限流**；考虑过"只在最外层限流不够，流量还是会打到 GPU"，所以用 **Redis 信号量**分配，**每台实例分配到（这个）信号量**；请求进来先**入队**，按**请求类型的一个字段作为分数**排队，**先进先出**；出队前做**信号量窗口判断**；考虑**僵尸进程**——会分配**存活时间**、可能过期，顺便**清理僵尸**再出队；出队后走**状态机**，请求**原子抢占**信号量，从**等待抢占**过渡到**授予抢占**，才调大模型；调用结束若信号量耗尽就等待，某实例释放时**广播**让每个实例重新抢占。
