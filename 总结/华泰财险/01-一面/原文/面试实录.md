### Q4 为什么用 Java/Spring 技术栈，不用 Python？
**面试官问：**（问句未录清，据答推断为技术选型）

**我：** 做 RAG 平台其实 Python 和 Java 都能做。Python 更容易接触模型端、适配模型工具，可以直接调模型、避免一次接口调用。但选 Java：一是内部 Java 的人多；二是 Java 在整体流程搭建（限流、服务构件）的生态比 Python 好。为了服务更多用户、提高请求并发，所以我们用 Java 技术栈来搭建。

### Q5 分布式限流是怎么做的？
**面试官问：**（问句未录清，据答推断为分布式限流实现）

**我：** 生产上目前有两台实例（两个容器）。并发这块：一是端侧模型能承受多少并发，二是容器能承受多少并发，两者合起来。分布式限流：对容器 CPU 有限制，确定一个分布式总量——每台实例每秒只能承受 20 个请求，两台加起来 40 个请求，就设 40 个分布式信号量作为总并发。前端再做分布式限流：请求量过大就排队（用队列），排到再去请求模型。目前两台实例加起来每秒只能扛 500 次请求。

（⚠️ 注意：先说"两台 40 并发信号量"，后说"两台每秒 500 请求"，两处数字维度不同，原样保留。）

### Q6 追问：信号量/队列机制细节
**面试官问：**（是否要讲一整套技术执行？——据答推断为追问限流机制）

**我：** 先讲模型请求。我们有个信号量机制：请求进来先去 Redis 拿；前端请求进来先到一个消息队列，做排队处理。排队时计算请求总量（模型侧总量）。每个请求拿到后才能去请求模型，通过负载均衡均匀打到两台实例。当模型侧 40 个总量用完，就开始排队处理。进来的请求有些用户会关页面、或出现异常，我们会用 Redis 及时抢占——先判断能否入队服务模型端，再清理这些僵尸请求。
