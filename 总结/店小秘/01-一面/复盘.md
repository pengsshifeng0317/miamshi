### Q5 ｜ 题型：项目深挖（追问）｜ 滑动窗口的代码怎么实现

- **我当时怎么答**：定一个**开始指针**、一个**结束指针**，按固定步长滑动、固定轮次增加；「比如定了一个 A 等于 8，那中间那个窗就是从**开始的话其实就是 7+8**」；每进来一个问题指针就加，然后取值。

    |---|---|---|

    | `summaryCutoffId` | 摘要切点 id = `latestUserTurns.get((size-1)/2)`，即窗口**旧一半** | 同文件 `:276` `resolveSummaryCutoffId` |

  - **滑动方式**：每次都重新 `listLatestUserOnlyMessages(conversationId, userId, 8)`（**DESC，取最新 8 条 user 消息**），再换算成 id 做 `id > afterId AND id < cutoffId` 的区间查询。锚点：`rag/service/.../ConversationGroupServiceImpl.java:47-79`（:59 `listMessagesBetweenIds`）。

### Q6 ｜ 题型：八股（据答推断）｜ 双指针 / 快慢指针

- **我当时怎么答**：「可以用**双指针快慢指针**去判断这个（原意不明）」；快指针一次走两步、慢指针一次走一步；**相遇就是有环、不相遇就是没有**；用「一个人在走路、我在跑步肯定追得上他」「环形操场上跑步」作比喻。
- **标准答案 / 该答成什么样**：
  - **🔴 先切分场景（本题最大问题）**：你的**滑动窗口根本不是环**，不存在"判环"，用快慢指针判环属于**答非所问**。正确开场：「滑动窗口用的是**首尾两个索引**定位 id 区间，**不是快慢指针**；快慢指针是**链表判环**的算法，我们项目里没用到。如果您问判环，是这样——」
  - **Floyd 判圈（标准答法）**：快慢指针同起点，快走 2 慢走 1；**有环必相遇**（数学依据：进入环后相对速度恒为 1，环内距离每步减 1，必然追上）；**无环则快指针先到 null**。
  - **🔴 漏了环入口**（这是判环题的**真正考点**，只答"有没有环"等于答了一半）：「相遇后，把**一个指针移回头结点**，两指针**同速**各走一步，**再次相遇的点就是环入口**。」
  - 复杂度：时间 O(n)、空间 O(1)——这也是它优于哈希表判环的地方，**主动补这句**。
- **自评**：🔴 判环部分对但**套错场景**，且**漏环入口**这个核心考点。

### Q7 ｜ 题型：八股 ｜ FutureTask / 异步任务的底层

- **我当时怎么答**：「我**就是了解的不是很多，但是我可以尝试一下**」；配合线程池使用；**继承了一个应该是继承的 RunnableFuture 接口**；每步进来一个任务就提交给线程池执行；有 `get` 方法，任务没做完时**去阻塞或者挂起**；异步执行时**取这两个任务里最慢的那个进行合并**、控制状态；有进行中 / 执行中 / 执行完成的状态；状态**配合 CAS**，锁比较轻量、提升性能。
- **标准答案 / 该答成什么样**：
  - **✅ `implements RunnableFuture<V>`** 这点答对了（`RunnableFuture extends Runnable, Future<V>`）。
  - **⚠️ 状态机要答全**：`FutureTask` 内部是 `private volatile int state`，**7 个状态**：`NEW(0) → COMPLETING(1) → NORMAL(2)`，异常分支 `EXCEPTIONAL(3)`，取消分支 `CANCELLED(4) → INTERRUPTING(5) → INTERRUPTED(6)`。你只说了"进行中/执行中/完成"三个，**漏了取消链路**。
  - **⚠️ CAS 用得准不准**：`state` 用 `UNSAFE.compareAndSwapInt` 改（**没有用锁**，这点你方向对）；`runner` 字段同样用 CAS 抢，**保证 callable 只被执行一次**；结果存在 `outcome` 字段。
  - **⚠️ `get()` 不是"挂起"**：若 `state <= COMPLETING` 就走 `awaitDone()`——**自旋 + `LockSupport.park()` 阻塞当前线程**，被完成/取消时 `unpark` 唤醒。"挂起"这个说法要改成「**park 阻塞，等 unpark 唤醒**」。
  - **🔴 「取两个任务里最慢的合并」是编的**：那是 **`CompletableFuture.allOf`** 的语义（等项目里的并行加载用的就是这个），**不是 `FutureTask`**。`FutureTask` 是**单个任务**的封装，没有"合并多个任务"的能力。这两个概念场上混成一个了。
  - **挂靠到真实项目**：项目里真正的异步编排用的是 **`CompletableFuture`**（会话记忆的 `load()` 并行拉取摘要与历史，`DefaultConversationMemoryService.java:49`）＋ 专有线程池；`FutureTask` 是 `ThreadPoolExecutor.submit()` 的**返回类型**。`⚠️ 未核码`：本次未在 ragent 里逐一确认是否有代码直接 `new FutureTask`，被追问项目用例时别说死。
- **自评**：🟡 骨架（RunnableFuture + 线程池 + CAS）对，但**状态机漏一半、`get()` 机制说法不准、把 `CompletableFuture.allOf` 的语义安到了 `FutureTask` 头上**（编的）。

    - **检索类固定 CPU×4 且 core == max**（`ragContextExecutor`、`ragRetrievalExecutor`）——不用扩容，靠核心线程数直接顶满；
    - **轻量 IO 并行类 CPU → CPU×2**（`mcpBatchExecutor`、`intentClassifyExecutor`）——**这才是你该报的那一档**，因为它俩正好是意图识别和 MCP 并行，是最可能被追问的两个池；
    - **摘要/流式/加载类 max(2, CPU/2) → max(4, CPU)**，配 200 有界队列；
    - **`memorySummaryExecutor` core 锁死 1**（摘要串行化意图明显）；
    - **`chatEntryExecutor` core == max == `rag.rate-limit.global.max-concurrent`（=10）**。
    - 即：**全仓没有任何一个池是「core = CPU×2」**；CPU×2 只出现在两个池的 **max**。
  - **🔴 拒绝策略不能一概而论**：只有 **7 个池**是 CallerRunsPolicy（`mcpBatch`、`ragContext`、`ragRetrieval`、`innerRetrieval`、`intentClassify`、`memorySummary`、`memoryLoad`）；**另外 3 个是 AbortPolicy，会抛 `RejectedExecutionException`**——而其中就包括 `chatEntryExecutor`（全局并发入口）。场上说成"全都让调用方执行"，被追问立刻露馅。
  - **🔴 SynchronousQueue 的提交流程不能照教科书讲**：教科书那套「core 满 → **入队** → 队列满 → 建非核心线程 → 拒绝」在 SynchronousQueue 下**不成立**。它**容量为 0**，`offer()` 只在"恰好有空闲线程正阻塞在 `take()`"时才成功。所以真实流程是：
    1. core 未满 → 建核心线程；
    2. core 已满 → **入队尝试几乎必然立刻失败** → **提前触发扩容**，直接新建非核心线程一直到 max；
    3. 到 max 之后再提交 → **直接走拒绝策略**。
    - **三句话结论**：① SynchronousQueue 池的**队列长度恒为 0**，永远不会出现"任务在队列里排队"的中间态；② **maxPoolSize 才是真正的并发上限，corePoolSize 只影响线程回收**（配合 60 秒 keepAlive；`chatEntryExecutor` 还额外开了 `allowCoreThreadTimeOut(true)`，否则 core==max 时那 10 个线程会常驻）；③ 池在负载下会**很快把线程数顶到 max**，不存在"平滑扩容"。
  - **🔴「背压」挂错了地方**：项目里真正的**排队在 Redisson 分布式信号量层**——`ChatQueueLimiter.enqueue()` 先走 `FairDistributedRateLimiter` 排队（`max-wait-seconds: 15` / `lease-seconds: 30` / `poll-interval-ms: 200`），**拿到许可后**才 `chatEntryExecutor.execute()`；此时若线程池因 AbortPolicy 拒绝，就 catch `RejectedExecutionException` 转成「系统繁忙，请稍后再试」并落一条 REJECTED 消息。锚点：`rag/service/ratelimit/ChatQueueLimiter.java:61-72`（直通分支）、:74-86（限流分支）、:99-104（拒绝文案）。
    - **正确口径**：「**排队在 Redisson 分布式信号量层，线程池只是许可后的执行入口；SynchronousQueue 保证线程池这层不存任务，拒绝即降级。**」——场上把"排队"和"背压"都说成了线程池的行为，实际线程池这层**根本不排队**。
- **自评**：🔴 本场最严重。参数自相矛盾 + 拒绝策略一概而论 + SynchronousQueue 流程讲成教科书 + 背压挂错层，**一处都没对上代码**。

### Q11 ｜ 题型：八股 ｜ B+ 树与分库分表

- **我当时怎么答**：B+ 树是**多路平衡查找树**；**B 树每个节点会存完整数据** → 树高变高；**B+ 树非叶子节点只存键和指针、不存真实数据** → 磁盘空间小、**效率更高**；分库分表：**表数据量过大** → B 树/B+ 树**树高上涨** → 节点条目不断增多 → 查得慢 → 所以**降低高度** → 提高索引查询效率；「三层变四层就多查一次」。
- **标准答案 / 该答成什么样**：
  - **✅ 大方向对**：B+ 树非叶子只存索引键 + 指针、数据全在叶子。
  - **⚠️ 漏了 B+ 树最核心的选型理由——叶子链表**：「**B+ 树的叶子节点之间用双向链表串联**，所以**范围查询和顺序扫描**可以顺着链表走，不用回根重新查；B 树做不到（数据散在各层节点）。这是 B+ 树成为数据库索引默认结构的**首要原因**」——你只讲了"树矮/省空间"，把最强的理由漏了。
  - **⚠️ 补磁盘 IO 这层**：「InnoDB 按**页**读写（默认 16KB），一次磁盘 IO 读一页；**非叶子节点只存键+指针 → 一页能塞几百个键 → 树高每降一层就省一次随机 IO**。三层 B+ 树通常可支撑千万~亿级行。」
  - **🔴 分库分表的因果讲反（本场第二个硬伤）**：你说成「数据量大 → 树高上涨 → 所以分表降高度」。**B+ 树高度增长极慢**（3~4 层就够亿级），**分库分表的主因根本不是树高**——是**单机磁盘容量、连接数、写入吞吐**的瓶颈。这个因果面试官一追就穿。
    - **正确口径**：「分库分表是**单库单表的容量与写入瓶颈**驱动的——数据量、QPS、连接数逼近单机上限，所以**水平拆分**把数据分散到多库多表。降树高只是顺带的次要收益。**代价要一起说**：跨库 JOIN 没了、要分布式事务 / 全局唯一 ID / 跨分片分页。」
- **自评**：🔴 分库分表因果讲反（硬伤）；B+ 树漏了**叶子链表**这个最核心的选型理由。

### Q12 ｜ 题型：八股 / SQL ｜ 所有科目分数都大于 80 的学生

- **我当时怎么答**：这个就是 **student 表**，**select** 这个名称，然后**对名称进行分组**，「然后 **AVG** 这个科目的分数，然后**对这个分数取最小值，然后大于 80**」。
- **标准答案 / 该答成什么样**：
  - **⚠️ 口径混乱（先说清题意）**：题目是「**每科都 > 80**」。你的表述里 **AVG 和 MIN 同时出现**，说成了"先 AVG 再取 MIN"——**这两个是两个不同的答案**，别混：
    - `AVG(score) > 80` ❌ **错**（平均分 > 80 不等于每科 > 80）；
    - `MIN(score) > 80` ✅ **对**（最小值都 > 80 ⟺ 全部 > 80）。
  - **🔴 没点出 `HAVING`（SQL 题的必考点）**：`GROUP BY` 之后的聚合过滤**必须走 `HAVING`**，不能写 `WHERE`。你只说"对这个分数最小值大于 80"，**没有一处说出 `HAVING`**，这是面试官必然要听的词。
  - **🔴 漏了「参与所有科目」这个条件（本题真正考点）**：题目说的是"**参与所有科目**的分数都 > 80"。如果只写 `MIN(score) > 80`，**缺考的科目根本不会出现在成绩表里**，一个只考了 1 科（且 > 80）的学生也会被选出来——**语义错了**。正确做法是加上科目完整性校验：
  ```sql
  SELECT student_id
  FROM score
  GROUP BY student_id
  HAVING MIN(score) > 80
     AND COUNT(DISTINCT subject) = (SELECT COUNT(DISTINCT subject) FROM score);
  ```
  有 `student` 表就 JOIN 取 `name`。
- **自评**：🟡 思路方向对（分组 + 取最小 + 大于 80），但 **AVG/MIN 口径混了、`HAVING` 没点出、科目完整性没考虑**——后两条正是面试官准备追问的点。
