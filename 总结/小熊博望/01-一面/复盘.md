### Q3 ｜ 题型：八股 ｜ 缓存穿透 / 击穿 / 雪崩

- **我当时怎么答**：三个定义大体对（穿透=查不存在数据直打 DB；击穿=热点 key 过期瞬间并发打垮 DB；雪崩=大量缓存同时过期 DB 压力剧增）。解法：穿透=缓存空值+布隆过滤器（对）；击穿=**热点永不过期 +「随机漂移时间打乱过期时间」+ 服务限流/多级缓存**；雪崩**没给解法**。
- **标准答案 / 该答成什么样**（通用八股，无项目代码可查）：
  - 先一句话分清本质：**穿透=数据本身不存在**（缓存和库都没有）；**击穿=单个热点 key 过期瞬间**（一个 key，超高并发）；**雪崩=大批 key 同时失效或 Redis 整体不可用**（很多 key）。
  - **穿透**：① 缓存空值（带短 TTL，防恶意穿透打满缓存）；② 布隆过滤器前置；③ 入口参数/幂等校验。
  - **击穿**（单 key，**互斥锁 + 逻辑过期**是两个主流）：① **互斥锁**：只放一个请求查库重建，其余等待/快速返回旧值；② **逻辑过期**：物理永不过期，value 带逻辑过期时间，过期后异步重建（读旧值不阻塞）；③ 热点永不过期（对，但要说「物理不过期+异步更新」）。你说的「随机漂移时间」**不属于击穿**——它是雪崩的解法。
  - **雪崩**：① **过期时间加随机值/打散**，避免整片同时过期（你把这条安到击穿了，它属于这）；② 多级缓存（本地+Redis）；③ 熔断/限流/降级保护 DB；④ Redis 高可用 + 持久化快速恢复。
  - 挂靠项目一句（别硬挂）：「我们项目 Redis 用在**全局并发信号量 + 摘要/幂等分布式锁**上，热点路由数据（意图树）走 Redis 缓存；缓存雪崩的『限流降级保护下游』思想和分布式限流保护 LLM 通道是同一套取舍」。
- **自评：🔴 答错**：把「随机漂移打散过期时间」（雪崩解法）安到击穿头上；击穿漏了互斥锁/逻辑过期；雪崩漏了整套解法。定义会、解法乱，是没背熟的表现。

- **我当时怎么答**：瓶颈在模型环节 → 容器每秒约 30 请求、4 台实例 → Redis 分布式限流而非单机 → 信号量统一分发 + 公平队列先到先得 + 存活时间到期直接返回 + 清理僵尸等待进程 + 并发满运行结束后广播给 4 台实例重新抢占信号量。
- **标准答案 / 该答成什么样**（已核码，锚点：`rag/service/ratelimit/FairDistributedRateLimiter`、`ChatQueueLimiter`、`resources/lua/queue_claim_atomic.lua`、bootstrap `application.yaml` `rag.rate-limit` 段）：
  - 先讲场景与语义：核心链路是 **SSE 流式长连接**，一次对话几十秒，所以做**集群级全局并发上限**，不是按秒 QPS。**Redisson `RPermitExpirableSemaphore`**，当前配置 `max-concurrent=10`、`max-wait-seconds=15`、`lease-seconds=30`、`poll-interval-ms=200`（⚠️ 你答的「每秒 30 请求、4 台实例」不是这个语义；仓库无每实例 QPS/副本数配置，别再说）。
  - 四句框架（你答到了中间两句，前后各漏一句）：
    1. **信号量定并发上限**：permit 带 **lease 自动过期**，实例 JVM 崩了额度自动归还，不会「崩一次少一个槽」。
    2. **公平队列定先来后到**：拿不到 permit 进 Redis **ZSET**，score=**雪花自增序号**（非时间戳，避免同毫秒撞车），member=requestId；先写带 TTL 的 entry 存活标记。

### Q5 ｜ 题型：八股×项目 ｜ MQ 消息重复 / 消息丢失怎么防范（当场卡壳）

- **我当时怎么答**：说了「消息丢失：服务抖动没到 broker 做重试」之后，卡住，**主动请求重新整理**（「然后再重新整理一下可以吗」），实际没接上来。
- **标准答案 / 该答成什么样**——**你项目里就用了 RocketMQ，这题本不该卡**（已核码，锚点：`framework` 幂等组件（`@IdempotentConsume`/`@IdempotentSubmit`/`MessageWrapper.uuid`）、文档分块监听器 `KnowledgeDocumentChunkConsumer`、bootstrap `application.yaml` `rocketmq` 段）。**按「生产 → Broker → 消费」消息生命阶段讲，丢失和重复在各段分别交代**：
  - **开场先给骨架**：「我们用的 RocketMQ。我的回答按消息从生产到消费三个阶段走：**丢失**三段逐段堵，**重复**核心在消费端幂等兜底。」（先给骨架就不容易像上次那样卡壳断掉。）
  - **① 生产端 —— 要解决「本地操作和发消息的原子性」**：
    - **丢失**：最怕「库写成功、消息没发出去」或反之（进程在两者之间崩）。用 **RocketMQ 事务消息**：先 `sendInTransaction` 发**半消息** → 执行本地业务 → 提交则 `commit`、回滚则 `rollback`；若半消息迟迟没有结果，Broker 会**回查**（事务回查监听器按本地事务真实状态决定 commit/rollback）。这样「本地 + 发消息」要么都成、要么都不成，**生产端不丢**。
    - **重复**：每条消息带**唯一标识**（项目里是 `MessageWrapper.uuid` 打进 MQ `keys`），Broker 与消费端都用它做判重锚点。
  - **② Broker 端 —— 一笔带过即可**：**主从同步 + 消息落盘持久化**，Broker 故障不丢；同时讲清一个关键前提——MQ 的投递语义通常是 **at-least-once**：**可能重复投递**。所以重复不能指望 Broker 消掉，必须由**消费端幂等**兜底。
  - **③ 消费端 —— 丢失和重复在这里汇合，重点讲**：
    - **丢失（往往丢在 ack 时机）**：要**手动确认、处理成功后再提交 offset**，别用 auto-ack——否则「收到消息就 ack、业务还没处理完进程崩了」这条就真丢了。反过来，「业务处理完、offset 还没来得及提交就崩」→ 消息会被**重新投递** → 这恰恰是**重复消息的来源之一**（点出丢失和重复在这里是同一枚硬币的两面）。
    - **重复（面试官问的主语）**：消费端做**幂等**，三道保险由里到外：
      1. **业务状态机 guard**（你项目真实在用的第一道）：文档分块消费里 chunk 有处理状态（处理中/已处理），重复投递进来发现「已在处理 / 已处理」就不再跑一遍——**重复消息不产生重复业务**。
      2. **消息唯一键查重**：以 `MessageWrapper.uuid` 为幂等依据，消费前先查/先占唯一记录，命中则直接跳过。
      3. 框架层还备了 `@IdempotentConsume`（Redis `SET NX` + `CONSUMING→CONSUMED` 状态机，重复的 CONSUMING 抛异常交给 MQ 延迟重试、CONSUMED 直接跳过）可做统一拦截。
      - ⚠️ 诚实边界：这道注解目前**并未真正打在任一监听器上**，实际去重是**状态机 + uuid 在兜**——简历/面试别吹「所有消费者都走幂等注解」。
    - **失败处理**：临时失败（下游抖动）交给 **MQ 延迟重试**，别自己吞掉；多次仍失败 → 记录 + 告警，人工兜底。
  - **收一句证明「真用过」**：这套在三处落地——**文档上传分块/异步入库**（事务消息 + 消费状态机 guard）、**知识库删除后的物理资源清理**、**问答消息点赞/踩异步落库**。
- **自评：🔴 答错/卡壳**：最可惜的一道——自己项目就有 RocketMQ 事务消息+幂等框架，却讲成了通用八股还断了。下次就按上面「生产/Broker/消费 + 丢失/重复」的格子逐格讲。

### Q6 ｜ 题型：项目深挖 ｜ 文档上传 → 向量化的整体流程

- **我当时怎么答**：接口处理 embedding → 千问 embedding 模型 → 提交文档建知识库 → 拉线程跑分块 → 存 pgvector → 对分块做评测看检索效率 → Top-5 命中/召回率 → 跑过 128/256/512 区间评测，最终选 **128** 作为分块参数 → 固定长度分块，overlap 固定长度。
- **标准答案 / 该答成什么样**（已核码，锚点：`knowledge/mq/KnowledgeDocumentChunkConsumer`、`KnowledgeDocumentService#executeChunk`、`ingestion/node/{Fetcher,Parser,Enhancer,Chunker,Enricher,Indexer}Node`、`core/chunk/ChunkingService`、`core/chunk/model/ChunkBudget`、`core/chunk/text/TextSplitter`、`infra-ai/embedding/RoutingEmbeddingService`、bootstrap `application.yaml`、`ChunkingFixtureTest`、ragenteval）——**这题按四段答：开场主线 → 数据清洗/解析 → 分块策略+流程 → 评测结论。前两段是主答，后两段是深挖**：

  1. **开场主线（45 秒端到端，先背这版）**：「上传接口只做两件事：**存文件 + 发一条 RocketMQ 事务消息**，马上返回；真正耗时的解析、分块、向量化全在消费端异步执行。消费端收到事件先恢复登录上下文（记操作人），再调 `KnowledgeDocumentService.executeChunk` 跑一条 **6 节点 ingestion pipeline：Fetcher 取字节 → Parser 解析成结构化 Block → Enhancer 文档级增强 → Chunker 分块+向量化 → Enricher 块级增强 → Indexer 落库**。」（异步+事务消息消掉耗时、6 节点可插拔给扩展性——粗体就是整条线。）

  2. **「数据清洗」怎么解析文档（尤其 PDF）**——先纠正认知：**系统里没有一个节点叫「清洗」，清洗职责内嵌在 Parser 一站，分三层**：① 防脏文件进库：`MimeTypeDetector` 读**字节**探测 MIME 不信任扩展名，启动 selfCheck 在 23 个扩展名自检；② 按 (MIME × 档位) 经 `ParserRegistry` 路由真解析器：**PDF/Word/PPT 复杂版面走 MinerU**（保标题层级/表格/图），Excel 走 POI，Markdown 走 commonmark AST，兜底 Tika 纯文本——口径「**没有万能解析器，Tika 兜底会把结构抹平，所以保结构优先、纯文本兜底，认不出就报错不静默兜底**」；③ 统一产物 `List<Block>`（Heading/Paragraph/Table/List/Code/Image）——这是解析层和分块层的**契约**。PDF 单独一句：复杂版面靠 MinerU 版面分析还原结构、不是当纯文本抽；抽不出才走 Tika，兜底=丢结构=分块质量降级。

  3. **分块策略 + 分块流程**（从主线的 Chunker 展开）：先钉认知——**分块不是「按策略选」，是按文档结构长出来的**：v1 策略枚举已废弃，`ChunkingService` 只剩「整文档单块 / block-aware」两分支，依据是预算不是策略。流程三步照代码讲：**① Block 类型 → chunker 查表分发**（Heading 先维护大纲路径，各 chunker 用 `toleranceChars`=maxChars×容忍倍数、封顶 8192 判切不切，切点落结构边界）→ **② ChunkPacker 按「相邻两标题之间」为节打包**（不做块级重叠）→ **③ ChunkAssembler 装配**，content（展示原文）与 embeddingText（向量文本）分离。参数钉死：块长默认 **1024**、overlap=块长/8=**128**、表格 rowsPerChunk=**50**；TextSplitter 只在超长 Block 降级时出场，切点**边界回溯**（换行→中文句末→英文句末→targetEnd），**不是定长**。**分块是规则算法不调模型**；调模型的是 embedding（qwen-emb-8b = 百炼 `text-embedding-v4`，1536 维，`application.yaml` `rag.embedding.default-model`）。

  4. **结合评测讲分块、给出结论**（⚠️ 最关键，先读「评测边界」再背，**不编数据**）——仓库评测分两层，能讲清「分块结论」的都是**真实材料**：
     - **切分正确性**：`ChunkingFixtureTest` 用固定 fixture（同一份 markdown 的 md/docx/pdf 形态 + txt + csv）走真解析器真 chunker，**导出 `target/chunking-report.md` 人工核对**，覆盖 10 类规则（章节路径、表格行分组、图片资产、代码三倍容忍、长列表分组、句末切点、URL 断行复原、CJK 软换行、缩进代码块、强制推进）——切分行为回归，报告上肉眼看得出。
     - **检索质量（分块影响召回的真实归因）**：ragenteval 评 Doc Hit@5 / RAGAS `context_recall` 等；`context_recall` 失败时第一怀疑对象就是 **chunk 切分 / 路由**——「doc 命中但 recall 低 ⇒ 召回到了但 chunk 切错」。
     - **参数选型依据（为什么 1024/128）**：直接引 `ChunkBudget` 源码注释——1024 而非常见 512：防语义稀释靠 ChunkPacker 章节边界而非压小块；topK 默认 5，块太小会让 topK 名额被同章节碎片占满。overlap=size/8 是为 TextSplitter 回溯句末标点留足距离。
     - **诚实收口**：分块**没有**单独做「结构感知 vs 固定字符」的 A/B 消融；端到端 Hit@5=100% 是 **20 样本冒烟非 150 全量**。口径=「切分正确性由 fixture 回归报告锁死 + 分块是召回指标的前置条件」，不吹「分块提升 X%」。
     - **被追问「你自己验证过分块参数吗？512 和 2048 哪个好？」→ 给设计、不给编数**（关键加分句，别只回一句「没做过」就哑）：真实没跑全量消融，但可以讲「**可以这么做**」——分块规格**每个文档可配**（`IngestionSpec` 随上传携带、`ChunkBudget` 落库）、向量库**按知识库分 collection**，所以「同源文档按不同参数各灌一份」是**架构原生支持**、互不污染；验证=同一批 Query 只换分块参数做**配对对比**，看 RAGAS `context_recall`（信息切碎/没进来会掉）+ `context_precision`（块太大裹噪声会掉）+ 自建**「答案跨块数」**（标准答案横跨 ≥2 块=语义被切碎，最直观的切分信号）+ 成本轴（块数/单查询字数）；判据=recall 不降、precision 不降、跨块数不涨 → 锁 **1024** 是「512 太碎使 topK 名额被碎片占满 / 2048 单块噪声大」的折中，**overlap=÷8(128)** 是挡切点语义断裂的保险，0/128/256 三档可证。完整可背稿见逐字稿《文档解析与分块怎么做.md》扩展开场 **🎙 追问子稿**。⚠️ 全程不吐一个编造的「已跑」消融数字。
     - 🚫 四个词别出口：128/256/512 网格、**说成「已跑过」的分块 A/B 数字**、自训练模型、自部署千问——仓库没有，追到第二层就穿帮。**区分：讲「设计/可以这么做」≠ 讲「已跑结果」，前者面试可讲、后者编不得。**
