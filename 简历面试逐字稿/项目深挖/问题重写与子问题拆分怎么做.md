## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的问题重写和子问题拆分是怎么做的？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（两道都改文本的区别 / 什么时候拆 / 子问题怎么接意图 / 多轮省略怎么处理 / 挂了怎么办）正好接 Q2 / Q3 / Q4 / Q5 / Q6 / Q7。

**我：** 我们做问题重写，是因为"用户的问法"和"拿去检索的查询"根本是两回事——口语噪音、术语不对齐、多轮省略叠复合问句，这三类不处理，embedding 和 BM25 全被污染，Recall 自然上不去。所以我们在检索之前加了 `QueryRewriteService` 这一层，统一返回 `RewriteResult(rewrittenQuestion, subQuestions)`：改写后的主问 + 拆出来的子问题列表。

核心是四件事：

**第一，术语归一化，用确定性规则。** 规则存在 `t_query_term_mapping` 表、Redis 缓存加载，按 `priority` 加 `sourceTerm` 长度排，长词先匹配，防"平安"截胡"平安保司"；命中就安全替换，零成本把口语写法对齐库内写法，顺带洗掉"请帮我""详细介绍一下"这类纯噪音。

**第二，LLM 改写加拆分，是主力。** `MultiQuestionRewriteService` 走 FAST 档、temperature 0.1 / topP 0.3，输出严格 JSON `{"rewrite", "should_split", "sub_questions"}`，语义级处理规则看不懂的结构——把"一句话里的多个问题"拆成"各自独立可检索的查询"，还带多轮历史做指代消解和省略续问。

**第三，规则拆分兜底，链路永不空转。** LLM 失败或解析失败，就按 `[?？。;；\n]+` 物理切分、每段补个问号；再不行就降级成归一化问题直接检索。所以最差情况是"规则归一化 → 检索"，开关关掉也一样，永远有确定性的一条路。

**第四，子问题并行意图识别，总量控制。** 每个子问题用 `CompletableFuture` 提交到 `intentClassifyExecutor` 并行分类，所有子问题的意图加起来不超过 `capTotalIntents=3`，每子问题先保底 1 个最高分，剩余按分从高到低补——既保证每个子问题都不被丢掉，又不让意图数量失控拖慢检索。之后 KB-only 过滤、多路检索，证据合并回主答案。

一句话总结：**让"用户的问法"对齐"知识库的写法"，把"一句话里的多个问题"拆成"各自独立可检索的查询"。**

> 📦 涉及的表（面试官问"表怎么设计的"时展开，平时不用全背）：
>
> | 表 | 用途 | 关键字段 |
> |----|------|---------|
> | `t_query_term_mapping` | 关键词归一化映射表，重写层规则来源 | `source_term`→`target_term`、`match_type`(1精确/2前缀/3正则/4整词)、`priority`(数值小优先，长词在前)、`enabled`；Redis 缓存 key=`ragent:query-term:mappings`，TTL 7 天 |
> | `t_conversation` / `t_message` | 会话历史，多轮改写上下文 | `t_message.role`(user/assistant)+`content`，改写只取最近 4 条，过滤 System 摘要 |
> | `t_rag_trace_run` / `t_rag_trace_node` | 链路追踪，重写各节点可观测 | `trace_id` 串 run+node，`node_type`/`status`/`duration_ms`，线上能区分"哪一层在兜" |
> | `t_knowledge_chunk` / `t_knowledge_vector` | 检索落库，子问题最终命中的证据 | `chunk.content` 分块正文；`vector.collection_name` 分集合 + `embedding(1536)`(pgvector) |

讲到这里停一下，面试官大概率会顺着追问：术语归一化和 LLM 改写都改文本、区别在哪？拆与不拆怎么判？子问题怎么并行接意图？多轮省略怎么处理？整层挂了怎么办？——正好接上 Q2 / Q3 / Q4 / Q5 / Q6 / Q7。

## Q1（开场总览）介绍一下你的问题重写和子问题拆分是怎么做的？为什么需要这一层？

**我：** 先说为什么做——用户问的问题和"拿来检索的查询"是两回事。三个典型场景直接命中检索：

1. **口语噪音**："请帮我详细介绍一下 12306 系统的架构"——"请帮我""详细介绍一下"对 embedding 是纯噪音，污染向量。
2. **术语不对齐**：用户说"平安保司""你们平台"，知识库里写的是"平安人寿""寿险智能问答平台"，字面不匹配、语义也不一定能映射上。
3. **多轮省略 + 复合问句**："那保险系统呢？""12306 的订单流程是什么？支付环节怎么处理？"——前者脱离历史根本没法检索，后者一个 query 拆成两个才能各自命中。

所以做了 `QueryRewriteService` 这一层，返回一个 `RewriteResult(rewrittenQuestion, subQuestions)`：**改写后的主问题 + 拆分出的子问题列表**。内部是三层流水线：

**术语归一化（规则）→ LLM 改写 + 拆分（主力）→ 规则拆分（兜底）**。

一句话总结：**让"用户的问法"对齐"知识库的写法"，把"一句话里的多个问题"拆成"各自独立可检索的查询"。**

> 重写层整条链路先看这张图：

```text
用户原始问题（口语 / 术语不对齐 / 多轮省略 / 复合问句）
   │
   ▼
① 术语归一化  QueryTermMapping（确定性规则 · 零成本）
   │  长词先匹配 · 防"平安"截胡"平安保司"
   │  "平安保司" → "平安人寿"
   ▼
② LLM 改写 + 拆分  MultiQuestionRewriteService（主力 · FAST档）
   │  输出 {"rewrite", "should_split", "sub_questions"}
   │  temperature 0.1 / topP 0.3 / thinking=false
   ├──────────────────────────────┐
   ▼                              │ 失败/解析失败
③ 规则拆分（物理分隔符兜底）       │
   │  按 [?？。;；\n]+ 切开         │
   │  每段补问号                   │
   ▼                              ▼
RewriteResult(rewrittenQuestion, subQuestions)  ← 降级为归一化问题
   │
   ▼ 每个子问题
④ 并行意图分类  IntentResolver（intentClassifyExecutor）
   │  总量控制 capTotalIntents ≤ 3
   │  （每子问题保底 1 个最高分，剩余按分从高到低补）
   ▼
KB-only 过滤 → 作用域判定 → 多路检索
```

## Q2（追问）术语归一化（QueryTermMapping）具体怎么做？

**我：** 术语归一化是**确定性规则**，处理"已知的词面映射"；LLM 改写是**语义级**的，处理"看不懂的结构"。两道都要，因为规则确定可靠、零成本，能兜住高频固定映射。

实现细节（`QueryTermMappingService`）：

- **规则来源**：数据库 `QueryTermMapping` 表，Redis 缓存（key=`ragent:query-term:mappings`，TTL 7 天），管理端增删改会清缓存。这里有个细节——**一条规则都没配也要认缓存**，否则每次提问都会白读一次数据库。

> Q2 术语归一化一图看懂：

```text
规则来源
   DB QueryTermMapping 表 → Redis 缓存
   （key=ragent:query-term:mappings, TTL 7 天）
   管理端增删改 → 清缓存
   细节：一条规则都没配也认缓存（否则每次提问白读 DB）
   ▼
排序规则
   priority 降序 + sourceTerm 长度降序
   └─ 长词先匹配，防"平安"截胡"平安保司"
      （先换短的 → 长的永远命中不了）
   ▼
安全替换（QueryTermMappingUtil.applyMapping）
   手写遍历替换 + 关键防重：
   └─ 当前位置本来就是 targetTerm 开头 → 不重复替换
      （文本已是"平安人寿"，规则"平安→平安人寿"
        不能把它变成"平安人寿人寿"）
```
- **排序规则**：按 `priority` 降序 + `sourceTerm` 长度降序。为什么长度降序？**长词先匹配**，防止"平安"这种短词把"平安保司"截胡——不然替换完短的、长的就永远命中不了。
- **安全替换**（`QueryTermMappingUtil.applyMapping`）：手写遍历做替换，有个关键防重逻辑——**如果当前位置本来就是 targetTerm 的开头，就不重复替换**。比如文本里已经是"平安人寿"，不能因为规则"平安→平安人寿"把它变成"平安人寿人寿"。

**面试官追问**：那 LLM 改写这块呢？什么参数、输出什么？

## Q3（追问）LLM 改写 + 拆分的具体实现

**我：** 实现是 `MultiQuestionRewriteService`，核心是 `callLLMRewriteAndSplit`：

- **静态 prompt 模板**（`prompt/user-question-rewrite.st`）：写好角色、任务、改写规则、拆分规则、多轮上下文规则和 6 个示例。模板是静态的，不动态塞意图/知识库列表，因为它职责就是"改查询"，不掺杂业务上下文。
- **调用参数**：temperature 0.1、topP 0.3、thinking=false，走 **FAST 档模型**（`Tier.FAST`）——改写是高频低难度环节，没必要用贵档位。

> Q3 LLM 改写+拆分一图看懂：

```text
MultiQuestionRewriteService.callLLMRewriteAndSplit
   │
   ▼
① 静态 prompt 模板（user-question-rewrite.st）
     角色 / 任务 / 改写规则 / 拆分规则 / 多轮上下文规则 / 6 个示例
     └─ 不动态塞意图/知识库列表（职责=改查询，不掺业务上下文）
   ▼
② 调用参数
     temperature 0.1 / topP 0.3 / thinking=false
     → FAST 档（高频低难度，不花贵档位）
   ▼
③ 输出：严格 JSON
     {"rewrite": "...", "should_split": true,
      "sub_questions": ["...", "..."]}
   ▼
④ 容错解析
     stripMarkdownCodeFence 剥围栏 → JsonParser 解析
     rewrite 为空 → 返回 null 走兜底
   ▼
⑤ 兜底
     LLM 失败/解析失败 → 降级归一化问题 + 打 warn
     └─ 不跨档升级：FAST 失败不自动换贵档重试
        （档位内多候选已提供传输容错，升级=拿成本换极低概率收益）
```
- **输出**：严格 JSON `{"rewrite": "...", "should_split": true, "sub_questions": ["...", "..."]}`。
- **容错解析**：先 `stripMarkdownCodeFence` 剥掉可能包裹的 markdown 围栏，再 JsonParser 解析；`rewrite` 为空 → 返回 null 走兜底。
- **兜底设计**：LLM 调用失败或解析失败，**降级为归一化问题**（`RewriteResult(normalizedQuestion, List.of(normalizedQuestion))`），日志打 warn。注意一个取舍——**不跨档升级**：FAST 档调用失败不自动换更贵档位重试，因为档位内多候选已经提供了传输容错，升级是拿成本换极低概率的收益，不值。

**面试官追问**：拆分规则怎么写进 prompt 的？为什么"X 和 Y 有什么区别"这种不拆？

## Q4（追问）拆分规则的设计——什么时候拆、什么时候不拆？

**我：** 拆分判断交给 LLM 按语义判断，而不是硬编码分隔符。prompt 里写了两组规则：

**何时拆**：
- 多个明确问句："系统 A 怎么用？系统 B 呢？"
- 显式列举："1) ... 2) ..."
- 明确要求分别询问："A 和 B 分别是什么？"
- 分号或换行明确分隔多个独立问题

**何时不拆**：
- **抽象对比**："X 和 Y 有什么区别？"→ 不拆
- 笼统询问："从哪些方面考虑？"
- **省略续问**："保险系统呢？"→ 不拆
- 不确定时 → 不拆

关键是"抽象对比为什么不拆"——如果拆成"X 是什么""Y 是什么"两个独立检索，**对比语义就丢了**：答案需要同时看两份证据才能对比，拆开反而让每个子问题都回答不了"区别"。所以"多问句"和"对比问句"要区分对待。

> Q4 拆/不拆决策一图看懂：

```text
何时拆（多个真问题）
   ├─ 多个明确问句：  "系统 A 怎么用？系统 B 呢？"
   ├─ 显式列举：      "1) ... 2) ..."
   ├─ 要求分别询问：  "A 和 B 分别是什么？"
   └─ 分号/换行分隔独立问题

何时不拆
   ├─ 抽象对比：  "X 和 Y 有什么区别？"  ★重点
   ├─ 笼统询问：  "从哪些方面考虑？"
   ├─ 省略续问：  "保险系统呢？"
   └─ 不确定 → 不拆
   ▼
为什么"抽象对比"不拆：
   拆成"X 是什么""Y 是什么" → 对比语义丢失
   答案需同时看两份证据才能对比
   拆开 → 每个子问题都回答不了"区别"
   = "多问句"和"对比问句"要区分对待
   ▼
一致性约束：不拆分时 sub_questions 只含 1 条且 = rewrite
   → 下游不用关心"到底拆没拆"，接口语义统一
```

**一致性约束**：不拆分时，`sub_questions` 只含 1 条、且与 `rewrite` 完全一致——这样下游不用关心"到底拆没拆"，接口语义统一。

**面试官追问**：拆完的子问题，下游意图识别怎么处理？不会每个子问题都拉一堆意图吗？

## Q5（追问）子问题与下游意图识别、检索的衔接

**我：** 这是重写层和意图层的关键接口，在 `IntentResolver.resolve(RewriteResult)`：

- **每个子问题并行做意图分类**：`CompletableFuture.supplyAsync` 提交到独立线程池 `intentClassifyExecutor`，每个子问题产出自己的 `SubQuestionIntent(subQuestion, nodeScores)`，单子问题失败降级空意图，不影响别人。
- **总量控制 `capTotalIntents`**：所有子问题的意图**加起来不超过 `MAX_INTENT_COUNT=3`**。超了怎么办？**每个子问题先保底 1 个最高分意图**（保证每个问题都不被完全丢掉），剩余配额再按分数从高到低补。这个策略保证"重写拆分了子问题，但不让意图数量失控"——因为每个意图都要并发拉一个 collection，意图多会拖慢检索，这是 6 秒首字响应约束下的硬约束。

> Q5 子问题→意图衔接一图看懂：

```text
IntentResolver.resolve(RewriteResult)
   │
   ▼
① 每个子问题并行意图分类
     CompletableFuture.supplyAsync → intentClassifyExecutor
     每子问题产出 SubQuestionIntent(subQuestion, nodeScores)
     单子问题失败 → 降级空意图，不影响别人
   ▼
② 总量控制 capTotalIntents ≤ MAX_INTENT_COUNT=3
     ├─ 每子问题保底 1 个最高分意图（不丢任何问题）
     └─ 剩余配额按分数从高到低补
     └─ 理由：每个意图并发拉一个 collection
        意图多 → 拖慢检索 → 6s 首字约束下的硬约束
   ▼
③ KB-only 过滤（KnowledgeSearchFacade.filterKbOnly）
     ├─ MCP 意图 → 走原生工具
     ├─ SYSTEM → 由主 Agent 人设承担
     └─ 知识检索链路只处理 KB
   ▼
④ 零意图子问题不拦截
     └─ 作用域判定只在 RetrievalScopeResolver 一处
        零意图 → 回落全局检索
        （拦在这里 = 把工具调用否决两次，
          主 Agent 已判过一次"该查知识库"）
```
- **KB-only 过滤**：`KnowledgeSearchFacade` 里 `filterKbOnly` 只保留 KB 意图——MCP 意图走原生工具、SYSTEM 由主 Agent 人设承担，知识检索链路只处理 KB。
- **零意图子问题不拦截**：剩零意图的子问题照样往下走，作用域判定只在 `RetrievalScopeResolver` 一处——零意图在那里回落全局检索。注释里写得很清楚：拦在这里等于把工具调用否决两次（主 Agent 已判过一次"该查知识库"）。

**面试官追问**：你说 LLM 改写还会带会话历史？多轮对话里"保险系统呢"这种省略句怎么处理？

## Q6（追问）多轮对话的指代消解和省略续问

**我：** `rewriteWithSplit(question, history)` 会带历史，专门处理多轮。三个关键点：

**1. 历史怎么取**：只保留最近 4 条消息（≈2 轮对话），并且**只留 USER 和 ASSISTANT，过滤掉 System 摘要**——摘要体积大、对改写无用，留着纯浪费 token。

**2. 指代消解**：当前问题出现"它""这个""该系统""上面的"时，结合历史用户问题还原实体。prompt 里给了示例：
> 历史：12306 系统的架构是什么？ 当前：它的数据库用什么？
> 改写：12306 系统的数据库用什么

**3. 省略续问**："X 呢""那 X 呢""X 怎么样"这种，保留当前问题的新主体 + 继承上一轮被省略的问题意图。

这里有**三条红线**，是我觉得 prompt 工程里最见功力的地方：

> Q6 多轮处理一图看懂：

```text
rewriteWithSplit(question, history)
   │
   ▼
① 历史怎么取
     只保留最近 4 条消息（≈2 轮对话）
     只留 USER 和 ASSISTANT，过滤 System 摘要
     （摘要体积大、对改写无用，留着纯浪费 token）
   ▼
② 指代消解
     当前问题出现"它/这个/该系统/上面的"
     → 结合历史用户问题还原实体
     示例：历史「12306 系统的架构是什么？」
           当前「它的数据库用什么？」
           → 改写「12306 系统的数据库用什么」
   ▼
③ 省略续问
     "X 呢 / 那 X 呢 / X 怎么样"
     → 保留新主体 + 继承上一轮被省略的问题意图
   ▼
三条红线（防污染）
   1. 不继承 Assistant 回答的内容
      （防止把上一轮答案当检索词）
   2. 不得添加原问题不存在的条件/维度/事实（防 LLM 脑补）
   3. 非查询轮次原样返回
      （"回答得不错，谢谢" → 直接原样返回，不检索）
```
- **不继承 Assistant 回答的内容**：prompt 明确禁止"把历史回答中的答案、结论写进 rewrite"——否则会把上一轮的答案当检索词，纯污染。
- **不得添加原问题不存在的条件/维度/事实**：防止 LLM 脑补。
- **非查询轮次原样返回**："回答得不错，谢谢"这种评价轮，**直接原样返回，不检索**，也不从历史补出一个问题。

**面试官追问**：重写这层万一整体挂掉呢？有没有完全不用 LLM 的退路？

## Q7（追问）兜底链路——开关关闭 / LLM 不可用怎么办？

**我：** 分两个层面：

**功能开关**（`rag.query-rewrite.enabled`，默认 true）：关掉后**完全不走 LLM**，退化为"术语归一化 + 规则拆分"。规则拆分就是纯物理切分：按 `[?？。；;\n]+` 分隔符把问题切开，每段补个问号。注意它是"分隔符兜底"，不是语义拆分——语义拆分只能靠 LLM。

**运行时失败**（LLM 挂了/超时/解析失败）：降级为归一化问题，`subQuestions=[归一化结果]`，等价于"没拆分、用归一化后的文本直接检索"。所以最差情况就是：**归一化（规则，确定性）→ 检索**，链路永远不空转。

我把这条兜底链总结为**四级防线**：规则归一化（确定性）→ LLM 改写拆分（语义）→ 容错解析（剥围栏、空值判 null）→ 失败降级（归一化问题）。每一级失败都落日志，线上能区分"是哪一层在兜"。

> Q7 兜底链路一图看懂：

```text
功能开关 rag.query-rewrite.enabled（默认 true）
   ├─ 关掉 → 完全不走 LLM
   │      → 退化为「术语归一化 + 规则拆分」
   │        规则拆分 = 纯物理切分：[?？。;；\n]+ 切开，每段补问号
   │        （分隔符兜底，不是语义拆分；语义拆分只能靠 LLM）
   └─ 打开 → 正常走 LLM 改写+拆分
   ▼
运行时失败（LLM 挂/超时/解析失败）
   → 降级归一化问题，subQuestions=[归一化结果]
   → 等价于"没拆分、用归一化后的文本直接检索"
   ▼
四级防线（每级失败落日志，线上可区分哪层在兜）
   ① 规则归一化（确定性）
   ② LLM 改写拆分（语义）
   ③ 容错解析（剥围栏、空值判 null）
   ④ 失败降级（归一化问题）
   ▼
最差情况：归一化（规则，确定性）→ 检索
   = 链路永远不空转
```

**面试官追问**：最后一个——Recall@1 提升 20.8% 这个数，怎么测的？贡献到底来自哪一步？

## Q8（追问）指标口径

**我：** 口径讲透：

- **对照组**：同一批问题、同一套检索链路，只切换"是否走重写"——不重写直接检索 vs 重写后检索。
- **Recall@1 提升 20.8%**：检索 top-1 命中正确证据的比例，重写后相对不重写的提升。

**提升来源拆解**，我会分点讲而不是笼统报数：

> Q8 指标口径一图看懂：

```text
对照组：同一批问题、同一套检索链路
   只切换"是否走重写"：不重写直接检索 vs 重写后检索
   ▼
Recall@1 提升 20.8%
   = 检索 top-1 命中正确证据的比例，重写后相对不重写的提升
   ▼
提升来源四分解
   ① 删礼貌用语/回答指令 → query 变干净，embedding & BM25 更聚焦
   ② 术语归一化 → 口语对齐术语，"平安保司"→"平安人寿"
   ③ 子问题拆分 → 复合问句各自命中自己的库，不再互相稀释
   ④ 多轮指代消解 → "它的数据库用什么"还原"12306 系统的数据库用什么"
   ▼
诚实口径
   离线 RAGAS 评测集 + 部分线上抽样统计
   Recall@1 = "正确证据是否进了 top-1"，≠ 回答正确率
   多轮/复合问句提升最明显
   单轮简单问句提升有限甚至中性
   → 所以 prompt 强调"最小必要改写"（防改写引入噪声）
```
1. **删礼貌用语/回答指令** → query 变干净，embedding 和 BM25 都更聚焦。
2. **术语归一化** → 用户口语对齐知识库术语，"平安保司"→"平安人寿"，字面/向量都命中。
3. **子问题拆分** → 复合问句每个子问题各自命中自己的库，"订单流程 + 支付环节"不再互相稀释。
4. **多轮指代消解** → "它的数据库用什么"还原成"12306 系统的数据库用什么"，多轮场景 recall 直接拉起来。

**诚实说明**：这是离线 RAGAS 评测集 + 部分线上抽样统计的口径，Recall@1 看的是"正确证据是否进了 top-1"，**不等于回答正确率**；重写对多轮/复合问句提升最明显，单轮简单问句提升有限甚至中性（改写可能引入噪声，所以 prompt 强调"最小必要改写"）。

## 📋 面试建议（对真实面试的 3 条建议）

1. **把"最小必要改写"立成设计哲学**。prompt 里那句"尽量保留用户原文，只做完成检索所必需的修改"不是随便写的——它防的是"过度改写引入噪声"。面试时主动说这句 + Q8 里"单轮简单问句提升有限甚至中性"，能立住"不为了指标美化而堆改动"的工程态度，这是 1 年经验候选人稀缺的。
2. **"三条红线"是你的最高光点**。大多数人聊重写只会说"把问题改得更适合检索"，很少有人能讲出"不继承 Assistant 回答""不得添加原问题不存在的条件""非查询轮次原样返回"这三条 prompt 防污染规则——这说明你真正抠过 prompt 工程，而不是套模板。
3. **两个 ⚠️ 钩子提前备好**：「为什么只保留 2 轮历史」和「意图总量 3 的硬约束」。前者建议从 token 成本和上下文污染两个角度答；后者要能接住"意图多 → 并发拉多个 collection → 拖慢首字响应"这条链路（和 6 秒指标挂钩），这样能从重写模块自然地串起整个 RAG 链路。
