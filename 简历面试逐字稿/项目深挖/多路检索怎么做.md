## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的多路检索引擎是怎么做的？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（RRF 为什么不用原始分 / 闸门为什么整批判 / 补充路为什么固定名额 / 超时降级）正好接 Q5 / Q8 / Q3 / Q4。

**我：** 我们做多路检索引擎，是为了补传统 RAG 单路向量检索的三个短板——向量吃语义但不擅长精确匹配（产品编号、条款号这种）、一句话只有一种检索命中错了就全错、库里没答案时照样满额返回把噪声带进提示词。

核心是四件事：

**第一，意图定范围。** 检索不是"一刀切全库搜"，先由 `RetrievalScopeResolver` 定"去哪些库"：KB 意图最高分 **≥0.6** 高置信 → 收窄到命中库**定向**检索；**<0.6** 低置信 → 放开到全部有效库**全局**检索，防止"意图判错了、正确证据在别的库"被直接错过。

**第二，多路召回，四通道并行。** VECTOR（PG pgvector）、KEYWORD（ES BM25）、GRAPH（LightRAG 图谱）、WEB_SEARCH（联网），统一实现 `SearchChannel` 接口。`CompletableFuture` 提交到独立线程池 `ragRetrievalExecutor` 并行执行，每通道 `orTimeout(15s)` 超时降级为空结果——**单通道卡死只损失自己，其余照常融合**，这是"首字 6 秒"的保证之一。

**第三，后置处理器链，两阶段精排。** 全部到齐后按 order 串行：去重 → RRF 融合（**按名次、不用原始分**，天然跨模态可比）→ Rerank 精排 → 证据闸门（整批最高分 <0.2 整批丢弃）→ 回表补元数据。**粗排（RRF）+ 精排（Rerank）**两阶段，把"过度检索率"压到 13% 以内。

**第四，落库与存储。** 向量走 `t_knowledge_vector`（pgvector + HNSW 索引，按 collection 分集合）；关键词走 ES 共享索引（BM25）；图谱走 LightRAG 外部图；联网走外部 API。检索命中后回表 `t_knowledge_chunk` / `t_knowledge_document` 补标题元数据；一次问答全链路落 `t_rag_trace_run` / `t_rag_trace_node` 可观测。

> 📦 涉及的表（面试官问"数据存哪、怎么回表"时展开，平时不用全背）：
>
> | 表/存储 | 用途 | 关键字段 |
> |----|------|---------|
> | `t_knowledge_vector` | 向量通道数据源（pgvector） | `embedding vector(1536)`、HNSW 索引、按 `collection_name` 分集合 |
> | `t_knowledge_chunk` | 分块正文，命中后回表补元数据 | `id`(=chunkId)、`content`、`doc_id`、`kb_id` |
> | `t_knowledge_document` | 文档，回表补标题/归属 | `doc_name`、`kb_id` |
> | `t_knowledge_base` | 知识库，"有效库"判定依据 | `name`、`collection_name`(UNIQUE)、`embedding_model` |
> | `t_rag_trace_run` / `t_rag_trace_node` | 链路追踪，一次问答全链路可观测 | `trace_id` 串 run+node、`status`/`duration_ms`/`node_type` |

> | LightRAG（外部图） | GRAPH 通道 | `rag.graph.type=lightrag` 才注册 |

讲到这里停一下，面试官大概率会顺着追问：RRF 为什么不用各通道原始分？Rerank 之后为什么还要闸门？定向了为什么还要补充路？超时怎么办？——正好接上 Q5 / Q8 / Q3 / Q4。

## Q1（开场总览）介绍一下你的多路检索引擎是怎么做的？为什么传统单路向量检索不够？

**我：** 先说为什么做——传统 RAG 大多只有一条向量检索：把问题 embedding 后去库里找最像的 N 条。它有三个致命短板：

1. **语义盲区**：向量吃语义，但碰到**精确匹配**就露馅——产品编号、条款号、"重疾险保 28 种疾病里的第 3 种"这种，embedding 不擅长。
2. **一句话只有一种检索**：向量检索是一条"死胡同"，命中错了就全错，没有第二个证据源兜底。
3. **库里没答案时照样满额返回**：它只会返回"最像的 N 条"，不会告诉你"其实没有相关内容"，噪声直接进提示词，LLM 被误导或硬编。

所以我们做了**多路检索引擎**，核心是四个通道（`SearchChannelType`）：**VECTOR（向量）、KEYWORD（BM25 关键词）、GRAPH（图谱）、WEB_SEARCH（联网）**。所有通道实现同一个 `SearchChannel` 接口（getName / isEnabled / search / getType / emptyResult），**并行执行、统一进 RRF 融合 + Rerank 精排**，最后过一道**证据相关性闸门**才进提示词。

一句话总结架构：**意图定范围（去哪些库）、多路做召回（用哪些模态）、RRF 排名融合、Rerank 精排、闸门把关**。

> 整条链路先看这张图（面试时可以边画边讲）：

```text
用户提问「重疾险 条款3.2 怎么赔？」
   │
   ▼
① 意图定范围  RetrievalScopeResolver
   ├─ 高置信（≥0.6）→ 定向：只查命中库
   └─ 低置信（<0.6）→ 全局：跨全部有效库
   │
   ▼
② 多路召回  四个通道并行（CompletableFuture，各取 recallBudget=20）
   ├─ VECTOR 向量    ─┐
   ├─ KEYWORD BM25   ─┤  同一 SearchChannel 接口
   ├─ GRAPH 图谱     ─┤  通道超时 orTimeout 15s → emptyResult 降级
   └─ WEB_SEARCH 联网 ─┘  单通道挂只损失自己
   │
   ▼
③ 后置处理器链（按 order 串行执行）
   ├─ 1  Deduplication   多路命中去重（RetrievedChunkKey 保首次）
   ├─ 5  Fusion（RRF）   按名次融合 + 截断候选池（candidateLimit=40）
   ├─ 10 Rerank          精排模型重排 → 最终 topK=10
   ├─ 15 EvidenceGate    证据闸门：最高精排分 < 0.2 → 整批丢弃
   └─ 20 MetadataEnrich  回表补元数据
   │
   ▼
④ 合格证据 → 进提示词 → LLM 生成回答（避免噪声硬编）
```

**面试官追问**：你说"意图定范围"——意图识别在上一问里是路由知识库，这里怎么和检索衔接的？什么叫"去哪些库"？

## Q2（追问）意图是怎么决定检索范围的？作用域是怎么收窄/放开的？

**我：** 这块在 `RetrievalScopeResolver`，产出一个 `RetrievalScope`（record：directed、topScore、intents、targetCollections、supplementCollections）。逻辑一句话：

**KB 意图的最高分低于阈值 `confidenceThreshold=0.6`，就退化为全局检索（跨全部有效库）；否则收窄到"命中库"定向检索。**

> Q2 作用域一图看懂：

```text
RetrievalScopeResolver → 产出 RetrievalScope
   {directed, topScore, intents, targetCollections, supplementCollections}

意图列表
   │
   ├─ 上游已按 INTENT_MIN_SCORE=0.35 过滤一道
   └─ 这里再设 minIntentScore=0.4（低于它不参与"收窄"判定）
   ▼
KB 意图最高分 ?
   ├─ ≥ 0.6  高置信 → 定向
   │   targetCollections = 命中意图挂的 collection ∩ 全库有效库
   │   （收窄到"命中库"作主路）
   └─ < 0.6  低置信 → 全局
       范围放开到所有有效库
       （防止"意图判错、正确证据在别的库"被直接错过）
   ▼
作用域是请求级策略，与通道平级：
   向量/关键词/图谱三通道读同一个 scope
   → "去哪些库" 和 "用什么模态" 解耦，关任一通道不影响判定
```

拆开看：

- 上游意图分类先按 `INTENT_MIN_SCORE=0.35` 过滤过一道，这里 scope 再设一道 `minIntentScore=0.4`——低于它的意图不参与"是否收窄"的判定。
- **高置信（≥0.6）→ 定向**：`targetCollections` = 各命中意图挂的 collection，与全库**求交**后的有效库，作为主路。
- **低置信（<0.6）→ 全局**：范围放开到所有有效库，防止"意图判错了，正确证据在别的库"这种情况被直接错过。

这里有个很关键的设计细节：作用域是**请求级策略、与通道平级**——三条通道（向量/关键词/图谱）读的是**同一个 scope**，所以"去哪些库"和"用什么模态检索"是解耦的，关掉任一通道都不影响作用域判定。这也是我们配置设计的思路（`Scope` 类独立于 `Channels`）。

**面试官追问**：既然高置信才定向，那定向的时候为什么不只查命中库，还要"补充路"？

## Q3（追问）补充路（supplement）的设计——定向了为什么还要补没命中的库？

**我：** 这是本模块我自己最看重的一个取舍，代码注释里把理由写得很透：**意图判错时，正确证据只在未命中库里。**

问题在于：**判错与否事前无从可靠判定，事后也测不出来。**

> Q3 补充路一图看懂：

```text
为什么需要补充路：
   意图判错时 → 正确证据只在未命中库里

难点：判错与否 事前无法判定 / 事后测不出来
   （意图分没校准过；错库内容余弦相似度未必低）
   → 不做"判定要不要补"，无条件保底
   ▼
补充名额 = 主路配额 × supplementRatio(0.25)
   ├─ 是"保底"不是"自由竞争"
   │    正确证据在未命中库，拼 RRF 名次必然抢不过命中库证据
   │    → 给固定名额，而不是让它凭分数进来
   └─ 失败只损失自己
        补充路单独 CompletableFuture + exceptionally 兜底
        绝不用 join() 抛异常把已取回的命中库证据一起丢掉
        （兜底路把主路带走 = 鲁棒性方向反了）

```

为什么？因为意图分没校准过，0.6 以上不能证明意图就对；而错库里的内容余弦相似度也未必低。所以我不做"判定要不要补"，而是**无条件给补充路一个固定候选名额**（`supplementRatio=0.25`，从主路配额里划 25% 出来）。

两个落地细节：

1. **补充名额是"保底"，不是自由竞争**。为什么？因为正确证据在未命中库里，它和命中库证据拼 RRF 名次**必然抢不过**——所以要给它固定名额，而不是让它凭分数进来。
2. **补充路失败只损失自己**：补充路单独 `CompletableFuture` + `exceptionally` 兜底，挂了只丢补充证据；绝不能因为 `join()` 抛异常，把已经取回的命中库证据一起丢掉——兜底路把主路带走，鲁棒性方向就反了。

**面试官追问**：多个通道是同时跑的？超时了怎么办？

## Q4（追问）多通道并行和超时降级是怎么做的？

**我：** `MultiChannelRetrievalEngine` 干的活：遍历所有 enabled 的通道，用 `CompletableFuture.supplyAsync` 提交到**独立线程池 `ragRetrievalExecutor`** 并行执行，然后统一 `join()`。

**通道级超时降级**是重点：每个通道设置 `orTimeout(timeoutMs=15s)`，超时后 `exceptionally` 返回 `emptyResult`（空结果 + 记录耗时）。这样**单个通道卡死或超时，只损失它自己，其余通道照常融合**——不会因为最慢的通道拖垮整条链路。这就是我们"平均首字响应 6 秒内"的保证之一：最差情况下等最慢的通道 15 秒，正常情况几个通道并行、取最长而不是累加。

> Q4 并行与超时一图看懂：

```text
MultiChannelRetrievalEngine
   │
   ▼
遍历 enabled 通道 → CompletableFuture.supplyAsync
   │  提交到独立线程池 ragRetrievalExecutor
   ▼
四通道并行执行（取最长，不累加）
   ├─ 每通道设 orTimeout(15s)
   └─ 超时 → exceptionally 返回 emptyResult（空结果 + 记耗时）
   ▼
统一 join() 收齐
   ▼
后置处理器链（按 getOrder 排序执行）
   │   1   Deduplication      多路命中去重（RetrievedChunkKey 保留首次）
   │   5   Fusion(RRF)        跨模态排名融合 + 候选池截断
   │   10  Rerank             精排重排 → topK
   │   15  EvidenceGate       证据闸门，整批不合格整批丢弃
   │   20  MetadataEnrichment 回表补元数据
   ▼
单通道卡死只损失自己 → 最差等最慢 15s，正常并行取最长
   = 首字 6s 的保证之一
```

所有通道结果收齐后，进入**后置处理器链**——每个处理器实现 `SearchResultPostProcessor`，按 `getOrder()` 排序执行：

| order | 处理器 | 职责 |
|:--:|---|---|
| 1 | Deduplication | 多路命中去重，按 `RetrievedChunkKey` 保留首次 |
| 5 | Fusion（RRF） | 跨模态排名融合 + 按候选池上限截断 |
| 10 | Rerank | 精排模型重排，输出最终 topK |
| 15 | EvidenceGate | 证据相关性闸门，整批不合格则整批丢弃 |
| 20 | MetadataEnrichment | 回表补元数据 |

## Q5（追问）RRF 融合的细节和取舍

**我：** `FusionPostProcessor`。先说为什么不能用分数——**向量分（余弦相似度）和关键词分（BM25）量纲不同、分布不同，直接加权没意义**。RRF 只依据**名次**，天然跨模态可比。

> Q5 RRF 融合一图看懂：

```text
为什么不用各通道原始分数：
   向量分(余弦相似度) vs 关键词分(BM25) 量纲不同、分布不同
   → 直接加权没意义
   RRF 只依据名次 → 天然跨模态可比
   ▼
公式：score(chunk) = Σ 通道权重 / (k + rank)
   ├─ k=20（不是经典 60）
   │    经典60面向上千候选；我们每通道只有 20~40 条
   │    k=60 把名次差异过度抹平，k=20 让头部更有区分度
   └─ 通道权重
        vector=1.0  keyword=1.0  graph=0.5  webSearch=0.5
        （图谱新接入、单全局图、证据只经结果侧过滤 → 默认降权，
          等归因日志验证 Rerank 存活率后再上调）
   ▼
隐藏收益：同一 Chunk 多通道命中 → 分数累加（rrfScores.merge sum）
   → 多路命中的证据天然靠前 → 利好"上下文精准度"
   ▼
按 rerankCandidateLimit=40 截断候选池 → 只送前 40 进 Rerank
   ├─ 控 Rerank 成本/延迟（精排比召回贵得多）
   └─ 多路命中候选凭 RRF 分优先入选
   = 粗排(RRF) + 精排(Rerank) 两阶段分工
```

公式：`score(chunk) = Σ 通道权重 / (k + rank)`。两个参数都有讲究：

1. **k=20，不是经典的 60**。经典 60 面向上千候选的检索场景，但我们每个通道候选只有约 20~40 条，k=60 会把名次差异过度抹平（头部和尾部几乎拉不开分），k=20 让头部更有区分度。
2. **通道权重**：vector=1.0、keyword=1.0、graph=0.5、webSearch=0.5。为什么降权？RRF 丢掉分数量纲后各通道**默认等权**，一个新接入/噪声多的通道会和最可信通道在**每个名次**上平起平坐。图谱是新接入、跑在单一全局图上、证据只经结果侧过滤，所以默认降权，等归因日志验证它的 Rerank 存活率后再上调。

RRF 还有个隐藏收益：**同一 Chunk 被多个通道命中，分数会累加**（`rrfScores.merge(key, delta, sum)`），所以"多路命中"的证据天然靠前——这直接利好"上下文精准度"这个指标。

融合排序后**按 `rerankCandidateLimit=40` 截断候选池**，只把前 40 个送进 Rerank。两个目的：**控制 Rerank 的成本和延迟**（精排比召回贵得多），**让多路命中的候选凭 RRF 分数优先入选**——这就是"粗排（RRF）+ 精排（Rerank）"两阶段分工的落地。

**面试官追问**：你反复说"预算"——召回、候选、最终三个数字是怎么设计的？

## Q6（追问）三阶段检索预算（RetrievalBudget）

**我：** 检索漏斗有三个**各自独立**的预算段，用一个 record 传下去：

| 段 | 默认值 | 语义 |
|---|---|---|
| `recallBudget` | 20 | 每个通道的召回扇出，最宽的一层 |
| `candidateLimit` | 40 | Rerank 候选池上限（fusion.rerank-candidate-limit） |
| `contextTopK` | 10 | 最终进 LLM 的条数（defaultTopK） |

三个数字**单调收窄**：20 → 40 → 10。这里有个"40 比 20 大"的细节值得说——召回只有 20 条/通道，但融合后候选池上限是 40，说明 40 是多通道**累计**后的池子（单通道 20 条上限，但 2 个通道就去重合并出接近 40 条候选）。

> Q6 三阶段预算一图看懂：

```text
检索漏斗三段独立预算（一个 record 传下去）
   ├─ recallBudget   = 20   每通道召回扇出（最宽）
   ├─ candidateLimit = 40   Rerank 候选池上限
   └─ contextTopK    = 10   最终进 LLM 条数

   20 → 40 → 10 单调收窄
   "40 比 20 大"：40 是多通道累计后的池子
   （单通道 20 条上限，2 通道去重合并可接近 40 条候选）
   ▼
启动时强校验（afterPropertiesSet）
   ├─ recallBudget ≥ contextTopK   召回 ≥ 最终条数
   ├─ candidateLimit ≥ contextTopK  候选 ≥ 最终条数
   │    违反 = Rerank 无从产出足量结果
   │    配置矛盾启动即失败，胜过线上悄悄少召回
   └─ confidenceThreshold ∈ (minIntentScore, 1]
        （否则"低置信退化全局 / 高置信收窄"两分支变死代码）
```

**启动时强校验不变式**（`afterPropertiesSet`）：`recallBudget ≥ contextTopK` 且 `candidateLimit ≥ contextTopK`。为什么这么刚？因为违反意味着"召回还没最终条数多"或"送进 Rerank 的候选还没最终条数多"——Rerank 无从产出足量结果。**配置矛盾启动即失败，胜过线上悄悄少召回。** 类似的强校验还有：`confidenceThreshold` 必须落在 `(minIntentScore, 1]`，否则"低置信退化为全局"或"高置信收窄"这两条作用域分支会变成死代码——这类启动校验把"配置错误"从线上事故提前到部署失败，是我们工程化很在意的一环。

**面试官追问**：向量通道是核心通道，它内部怎么分配主路和补充路的名额？你说的"意图级 topK"是什么？

## Q7（追问）向量通道内部的预算分配

**我：** 向量通道（`VectorSearchChannel`）分两种作用域走不同逻辑：

**定向时**：`ScopeQuota.split` 把通道额度按 `supplementRatio=0.25` 切成主路 75% + 补充路 25%。主路查命中库、补充路查未命中库，**两路并行、共用一次 embedding**（查询向量只算一遍，省一次模型调用），所以补充路**不增加通道延迟**。这里对"平均首字响应 6 秒"也很关键——我们很多优化都是"不增加额外延迟的前提下补全召回"。

> Q7 向量通道预算分配一图看懂：

```text
VectorSearchChannel（分两种作用域）

定向时：ScopeQuota.split
   ├─ 主路 75%  （查命中库）
   └─ 补充 25%  （查未命中库，supplementRatio=0.25）
   └─ 两路并行、共用一次 embedding → 补充路不增加通道延迟

定向深度：resolveDirectedBudget 取各意图 node.topK 的 最大值
   ├─ 覆盖默认 recallBudget
   ├─ 取大不取均值：叶子可配自己 topK（绝对深度）
   │    多意图命中取大只放宽召回，多出候选交给精排收敛
   └─ 再按 candidateLimit 钳制（超出进不了 Rerank = 空转）
   （按意图切分配额 = 重造 fan-out，明确不做）

全局时：跨全部有效库，深度只受 recallBudget 管

兜底：后端不支持跨库单查 → CollectionParallelRetriever 逐库并行 fan-out
   ├─ 每库失败只损失自己
   └─ 先排序再截断
      （PG hnsw.iterative_scan=relaxed_order 允许轻微乱序，
       不先排后截就拿不到全局真正的前 N 条）
```

**定向深度的决定**：`resolveDirectedBudget` 取**各意图 `node.topK` 的最大值**，覆盖默认的 recallBudget。为什么取最大不取均值？因为意图树的叶子节点可以配置自己的 topK（绝对深度，可大可小），多意图命中时取大只放宽召回、多出的候选交给精排收敛——**任何按意图切分配额的方案都是在重造 fan-out**，我们明确不这么做。再按 `candidateLimit` 钳制：超出的部分进不了 Rerank，查了也是空转。

**全局时**：跨全部有效库，深度只受 `recallBudget` 管。

还有个兜底实现值得说：如果后端**不支持跨库单查**（比如 Milvus 和 PG 分开部署），走 `CollectionParallelRetriever` **逐库并行 fan-out**——每库各取预算、再统一按 score 降序排序截断。有两个细节：每库失败只损失自己；**先排序再截断**，因为 PG 开了 `hnsw.iterative_scan=relaxed_order`，pgvector 允许轻微乱序且规划器不补 Sort 节点，不先排后截就会拿不到全局真正的前 N 条。

## Q8（追问）证据相关性闸门（EvidenceGate）

**我：** 这是把"过度检索率"压下来的关键一环。先讲问题：**检索只保证返回最像的 N 条，库里没答案时照样满额返回**，下游只看证据文本非空——所以噪声必然进提示词。Rerank 只负责排序，不负责"这批料到底够不够格"。

`EvidenceGatePostProcessor` 补这道关，判据**唯一来自精排分**：`minRerankScore=0.2`，**整批证据的最高精排分低于 0.2，整批丢弃**（判为"没检索到相关内容"），否则放行。

> Q8 证据闸门一图看懂：

```text
问题：检索只保证返回最像的 N 条，库里没答案也满额返回
   → 噪声必然进提示词；Rerank 只排序，不判"这批够不够格"
   ▼
EvidenceGatePostProcessor（判据唯一来自精排分）
   ├─ 整批最高精排分 < 0.2 → 整批丢弃（判"没检索到相关内容"）
   └─ 否则 → 放行
   ▼
三个设计点
   1. 按整批最高分判，不逐条判
      → 误丢比误放贵：漏一条弱证据 LLM 顶多不参考，
         整批好证据误删 = KB 侧空、答案没法答
   2. 无分可读一律放行
      → Rerank 降级 noop 只截断不打分，照拦 = 精排最不稳时关掉 KB
         且与"库里没料"表现一致、线上无从分辨
         → 空转放行 + 打 warn
   3. 与 Rerank 开关强绑定
      → 启动校验：minRerankScore>0 但 rerank.enabled=false 直接抛异常
   ▼
指标关系：过度检索率 = 检索结果里多余/不相关比例
   闸门把"最像但不相关"整批挡在提示词外 = 降 13% 以内的直接手段
   （与意图澄清反问同一思想链：宁可少给，不可错给）
```

三个设计点：

1. **按整批最高分判，而不是逐条判**——因为**误丢比误放贵**：漏给一条弱证据 LLM 顶多不参考它，但把整批好证据误删，KB 侧就空了、答案直接没法答。
2. **无分可读一律放行**：Rerank 降级成 noop 时只截断不打分，照拦等于在精排最不稳的时候关掉整条 KB 侧，且表现与"库里没料"一致、线上无从分辨——所以它选择"空转放行 + 打 warn"。
3. **和 Rerank 开关强绑定**：启动时校验 `minRerankScore > 0` 但 `rerank.enabled=false` 直接抛异常——闸门靠精排出分，精排关了闸门恒放行，配置矛盾就得启动失败。

指标关系：**"过度检索率"就是衡量"检索结果里有多少是多余/不相关"**——多路召回容易扩大噪声（这是多路检索的固有代价），这道闸门把"最像但不相关"的整批证据挡在提示词外，是"降 13% 以内"的直接手段。它和我们意图的澄清反问（低置信不检索）是一个思想链条：**宁可少给，不可错给。**

**面试官继续追问**：检索指标的 ground truth 是怎么标的？Hit@K、Recall@K、MRR 这些精确怎么算？30.5% 到底怎么来的？

## Q10（追问）评测数据怎么建：检索 ground truth、指标公式与 30.5% 口径

**我：** 检索指标值不值钱，全看评估集里"正确证据"标的准不准。讲三件事：

**第一，评估集里每条"该查库"的样本都人工标了 ground truth**：

| 字段 | 作用 |
|---|---|
| `requires_rag` | 是否必须走检索——检索指标的分母锚点 |
| `expected_doc_ids` | 正确证据的文档 ID（must 口径，硬标准） |
| `expected_doc_ids_nice` | 宽容别名（inclusive 口径，同文档的其它编码） |

为什么标**文档级**不标 chunk 级：评测要的是"证据进没进 top-K"，标到文档粒度人工标注成本可控；至于它是从 VECTOR 通道还是 KEYWORD 通道召回的不标——**任何通道命中同一文档都算 hit**，通道差异不该影响 ground truth。

**第二，检索指标族**（`retrieval.py`，`Hit@1` 就是文档里报 30.5% 的那个"Top-1 召回命中率"）：

```text
Hit@K        top-K 里命中任一正确证据 = 1，否则 0（K=1/3/5/10）
Recall@K     |top-K ∩ 正确证据| / |正确证据|（must 口径）
Recall@K inc 正确证据并上 nice 别名再算（inclusive 口径）
MRR@10       第一个命中名次的倒数（1/rank）
样本过滤      只统计 requires_rag=true 且 expected_doc_ids 非空
             → SYSTEM 兜底类样本不污染检索指标
```

为什么 must + inclusive 两套口径：**must 严格、inclusive 宽容**。多路场景下同一文档可能被不同通道用不同编码返回，must 会误判成"漏召回"，inclusive 用 `expected_doc_ids_nice` 并集兜底——把"真漏"和"别名没对上"分开，这正是 `EvalSample` 里单独存 `expected_doc_ids_nice` 的原因。

**第三，30.5% 的口径**：同一批评测集 → 传统 RAG（单路向量+不重排）跑一次 run、多路（意图定向+四通道+RRF+Rerank+闸门）跑一次 run → `diff` 两份 `_scores.json` → 比的是 **Hit@1**（top-1 命中正确证据的比例）相对提升 30.5%。诚实讲：**30.5% 看的是"正确证据进没进第一名"，不是回答正确率**；而且多路召回后候选池反而变大了（各通道 `recallBudget=20` 累计、`candidateLimit=40`），检出来容易、**排进 top-1 难**——涨这 30.5% 恰恰说明 RRF 融合 + Rerank 精排把正确证据顶到了最前面，不是"多召回"带来的假象。

> 💡 面试官追问（真实被问）：expected_doc_ids 是人工标的，多路有四条通道，会不会漏标某通道的证据、把评测做假了？
>
> **我：** 三道防线：① **标的是文档级不是通道级**——四通道谁命中同一文档都算 hit，不存在"漏标某通道"；② **inclusive 口径兜底**——must 口径分数低可能是真漏召回，也可能是别名没对上，用 `expected_doc_ids_nice` 并集再看一眼，把两种情况分开，不冤枉也不放水；③ **样本过滤写死**——`requires_rag=true` 且 `expected_doc_ids` 非空的才算，标注不全的样本自己露馅、不进分母。

> 💡 面试官追问：多路召回后噪声也多了，评测怎么体现"检得多但乱"？30.5% 是不是挑数字？
>
> **我：** "检得多但乱"是召回指标看不出来的，要 **召回指标 + 噪声指标两套一起看**：召回指标（Hit@K/Recall@K/MRR）看"该检的检没检到"，噪声靠 `过度检索率 <13%` 和 `上下文精准度 +24.5%` 盯——它们量的正是"进上下文的证据里有多少无关/冗余"，证据闸门（最高精排分 <0.2 整批丢弃）就是为这个加的。而 30.5% 不是挑的：`diff` 用同一评测集、两次 run 的整体均值之差，两边过滤条件一致，差得出来才是真变化；我不报"召回全对"，主动讲"第一名命中率 + 噪声控制"两个口径，比一个漂亮平均分可信。

> Q10 评测数据一图看懂：

```text
评估集（每条该查库样本人工标）
   requires_rag + expected_doc_ids + expected_doc_ids_nice（文档级）
   ▼
检索指标族 retrieval.py
   Hit@K(1/3/5/10) | Recall@K must | Recall@K inclusive | MRR@10
   分母过滤：requires_rag=true 且 expected_doc_ids 非空
   ▼
30.5% = 同一评测集 传统RAG vs 多路 两次run 的 Hit@1 相对提升
   （diff 两份 _scores.json，过滤条件一致）
   ▼
诚实口径
   Hit@1 = 正确证据进没进第一名，≠ 回答正确率
   多路候选变多 → top-1 更难 → 涨 30.5% 靠 RRF+Rerank 精排
   噪声另用 过度检索率<13% / 上下文精准度+24.5% 盯
   = 召回指标（检没检到）+ 噪声指标（乱不乱）两套一起看
```

## 📋 面试建议（对真实面试的 3 条建议）

1. **把"为什么"讲成设计取舍，而不是功能罗列**。多路检索最容易答成流水账（"有向量、有关键词、有图谱、有 RRF"）。高分答法是每步都有"为什么/代价/兜底"：RRF 为什么不用原始分（量纲不同）、补充路为什么不判定直接补（判错不可测）、预算为什么要启动校验（配置矛盾晚失败不如早失败）——这比报参数值高级得多。
2. **"过度检索率"是你的专属杀手锏**。大多数候选人聊 RAG 只讲"召回多、效果涨"，很少有人主动讲"噪声控制"。证据闸门（整批判、误丢比误放贵、无分放行）加上"过度检索率降到 13%"是区分度最高的点，一定要主动展开。
3. **两个 ⚠️ 钩子提前备好**：「线程池拒绝策略」和「通道权重如何校准」。前者代码里是独立线程池但没在逐字稿里展开，建议想好核心数/队列/拒绝策略/监控；后者答案在 Rerank 的归因日志里（图谱证据存活率 graphOut/graphIn），建议把"如何用日志校准权重"这句话练顺。
