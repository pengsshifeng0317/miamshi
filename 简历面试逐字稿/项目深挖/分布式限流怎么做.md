## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的分布式限流是怎么做的？为什么不用单机限流？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（公平队列 / Lua 原子 / lease 兜底 / Pub/Sub 唤醒）正好接 Q2 / Q3 / Q4 / Q5。

**我：** 先说场景——我们的核心链路是 SSE 流式聊天，一次对话是长连接，可能占用几十秒（检索 + LLM 生成流式返回）。如果并发对话数失控：LLM 下游被拉垮、成本按 token 失控、首字延迟劣化。所以必须有一个**全局并发上限**。

**为什么单机不够**：系统是**多实例部署**的，每个实例自己的 `java.util.concurrent.Semaphore` 只能约束本机——N 个实例就 N 倍并发，等于没限。所以我把限流状态放到了 Redis，做成一个分布式的 `FairDistributedRateLimiter`。

核心是四件事：

**第一，信号量定并发上限。** 用 Redisson 的 `RPermitExpirableSemaphore` 存全局并发额度，拿 permit 才能进业务；permit 还带 lease 兜底，实例 JVM 崩了额度也能自动归还，不会卡死整个通道。

**第二，公平队列定先来后到。** 拿不到 permit 的请求进一个 Redis ZSET，score 用雪花自增序号（先到先服务），member 是 requestId；每条 entry 写一个带 TTL 的存活标记，等待预算内 JVM 崩溃也不占位。

**第三，Lua 脚本定原子抢占。** 检查存活、清僵尸、出队三步合一放在 `queue_claim_atomic.lua` 一个脚本里，靠 Redis 单线程保证原子，从根上避免并发误判——这是 Q3 的重点。

**第四，Pub/Sub 定即时唤醒。** 有 permit 释放就通过 Redis 主题广播，跨实例立刻唤醒等待者；本地再做合并去重，避免通知风暴，而不是傻等轮询。

> 📦 涉及的表（面试官问"状态存哪 / 表怎么设计"时展开，平时不用全背）——**限流状态全部在 Redis，不涉及数据库表**：
>
> | 存储 | 用途 | 关键点 |
> |----|------|---------|
> | `rag:global:chat:semaphore` | 全局并发信号量 | Redisson `RPermitExpirableSemaphore`，permit 带 lease 兜底自动归还（Q4 展开） |
> | `rag:global:chat:queue` | 公平队列（ZSET） | score = 雪花自增序号（先到先服务），member = requestId |
> | `rag:global:chat:queue:seq` | 自增序号生成器 | `RAtomicLong`，保证跨实例序号单调（Q2 展开） |
> | `rag:global:chat:queue:notify` | 跨实例唤醒通道 | Redisson `RTopic` Pub/Sub，释放 permit 即广播（Q5 展开） |
> | `rag:global:chat:entry:{requestId}` | 请求存活标记 | `RBucket` + TTL（等待预算 + 5s 缓冲），Lua 内缺失即视为僵尸 ZREM（Q3 展开） |
> | `rag:document:upload:semaphore` | 上传限流信号量 | 纯信号量无队列，超时直接 429（Q9 展开） |
>
> 补充一句不虚的：限流本身不落库；但**被拒绝的会话**仍会写 `t_conversation` / `t_message`（消息状态 `REJECTED`），保证前端能收到 DONE、会话记录完整——这是 Q1 reject 体验的落库部分，别在"表"上记混。

讲到这里停一下，面试官大概率会顺着追问：公平队列为什么用序号不用时间戳？claim 为什么必须放 Lua 里？lease 怎么兜底？Pub/Sub 怎么做到即时唤醒又不风暴？——正好接上 Q2 / Q3 / Q4 / Q5，最后限流参数 10 并发 / 15s 等待怎么定就接 Q9b。

## Q1（开场总览）介绍一下你的分布式限流是怎么做的？为什么不能用单机限流？

**我：** 先说场景——我们的核心链路是 **SSE 流式聊天**，一次对话是长连接，可能占用几十秒（检索 + LLM 生成流式返回）。如果并发对话数失控：LLM 下游被拉垮、成本按 token 失控、首字延迟劣化。所以必须有一个**全局并发上限**。

**为什么单机不够**：系统是**多实例部署**的，每个实例自己的 `java.util.concurrent.Semaphore` 只能约束本机——N 个实例就 N 倍并发，等于没限。

所以做了 `FairDistributedRateLimiter`，一句话概括：**信号量定并发上限、公平队列定先来后到、Lua 脚本定原子抢占、Pub/Sub 定即时唤醒**。

> 一次聊天请求的完整生命周期先看这张图：

```text
聊天请求（SSE 长连接）
   │
   ▼
ChatQueueLimiter.enqueue
   │
   ▼
① 写存活标记  entry:{requestId}（TTL = 等待预算 + 5s）
   ▼
② 入公平队列  ZSET :queue（score = 雪花自增序号，先到先服务）
   ▼
③ 排队等待   scheduler 轮询 200ms + Pub/Sub 即时唤醒（跨实例）
   ▼
④ Lua 原子 claim  queue_claim_atomic.lua（检查+清僵尸+出队三步合一）
   │  取队头窗口 → EXISTS 判存活 → 僵尸当场 ZREM
   │  ├─ 没排到队头窗口 → 返回 {0} 继续等
   │  └─ 排到 → ZREM 出队 + DEL 标记 → 返回 {1, score}
   ▼
⑤ tryAcquire 可过期信号量  :semaphore（lease=600s 兜底）
   │  ├─ 拿到 permit → onAcquired（TtlRunnable 跨线程传上下文）
   │  │        → 真正开始推理 → SSE 流式返回
   │  └─ 拿不到 / 排队超时 15s
   │        → 拒绝：走 SSE 事件流（META→REJECT→FINISH→DONE）
   │          并记入会话记忆（可回溯）
   ▼
业务 try/finally 释放 permit → Pub/Sub 广播"有位置了" → 唤醒下一位
```用到的 Redis 结构：


```

| Redis 结构                                  | Key 后缀             | 职责                                |
| ------------------------------------------- | -------------------- | ----------------------------------- |
| `RPermitExpirableSemaphore`（可过期信号量） | `:semaphore`         | 全局并发许可，permit 可自动过期     |
| `RScoredSortedSet`（ZSET）                  | `:queue`             | 公平等待队列，score=入队序号        |
| `RAtomicLong`                               | `:queue:seq`         | 单调递增的入队序号生成器            |
| `RTopic`（Pub/Sub）                         | `:queue:notify`      | permit 释放时广播，跨实例唤醒排队者 |
| `RBucket`                                   | `:entry:{requestId}` | 请求存活标记（防僵尸条目）          |

入口在 `ChatQueueLimiter`：聊天请求 `enqueue` 进限流器，**拿到 permit 才真正开始推理**，排队超时或连接断开则走拒绝路径。整个链路和 SSE 事件流、会话记忆、链路追踪都接好了。

## Q2（追问）公平队列的实现——为什么用序号做 score 而不是时间戳？

**我：** 核心是用一个**单调递增的序号**保证"先到先服务"：

> Q2 公平队列一图看懂：

```text
入队 → RAtomicLong.incrementAndGet() 拿自增序号
   → 作 ZSET score，member = 雪花 requestId
   → ZSET 天然按 score 升序：先入队 score 小、排前面
   ▼
为什么不用时间戳当 score？
   ① 并发撞车：毫秒时间戳，同一毫秒多请求 score 相同
      ZSET 相同 score 按 member 字典序排序 → 顺序不可控
   ② 序号单调 + 唯一：自增序号每请求唯一且全序
      → 天然是公平性的标尺
   ▼
公平性细节：重入队保留原 score
   已排到队头但信号量没空位（刚被别的请求抢走）
   → tryAcquireIfReady 按它原来的 score 重新入队
   └─ 不重新排号，维持原有排队位次
      （否则"反复到队头又反复被踢"的请求一次比一次靠后）
```

- 入队时 `RAtomicLong.incrementAndGet()` 拿到自增序号，作为 ZSET 的 score 入队（member = 雪花 requestId）。ZSET 天然按 score 升序排列，**先入队的 score 小、排前面**。

**为什么不用时间戳当 score**？两个原因：
1. **并发下时间戳会撞**：毫秒级时间戳，同一毫秒内多个请求 score 相同，ZSET 相同 score 会按 member 字典序排序，顺序不可控——"谁先到"就失真了。
2. **序号单调 + 唯一**：自增序号保证每请求唯一且全序，天然就是公平性的标尺。

还有一个公平性细节：**重入队保留原 score**。如果请求已经排到队头、但那一刻信号量没空位（比如刚好被别的请求抢走），`tryAcquireIfReady` 会**按它原来的 score 重新入队**——不重新排号，维持它原有的排队位次。否则"反复到队头又反复被踢"的请求会一次比一次靠后，就谈不上公平了。

**面试官追问**：那"排队到队头才允许 claim"这个判断 + 清理僵尸条目，是怎么保证原子性的？

## Q3（追问）Lua 原子脚本——claim 和僵尸清理为什么必须放一个脚本里？

**我：** 出队 claim 在 `lua/queue_claim_atomic.lua` 里，它干了三件事，**必须在同一个 Lua 脚本里原子执行**：

> Q3 Lua 原子一图看懂：

```text
queue_claim_atomic.lua —— 三步合一，同一 Lua 原子执行
   ① 取队头窗口：ZRANGE queue 0 maxRank+slack-1
      maxRank = 当前可用 permit 数
      slack=16 = 额外余量（僵尸密集时尽量推进存活条目进窗口）
   ② 遍历区分存活/僵尸：EXISTS entry:{requestId}
      Java 入队时写带 TTL 的存活标记
      标记缺失 = 僵尸（JVM 崩溃/已取消）→ 当场 ZREM
   ③ 定位自己：统计存活 liveCount
      liveRank<0（不在队）或 liveRank>=maxRank（没到队头窗口）
        → 返回 {0} 不 claim
      排到 → ZSCORE 记原 score → ZREM 出队 + DEL 标记 → {1, score}
   ▼
为什么必须 Lua 原子？
   检查(到队头?) + 清理(僵尸) + 出队 分开做会竞态
   两条并发同时读到"队头有位置"都出队，permit 只 1 个 → 超卖
   Redis 单线程执行脚本 → 天然串行
   ▼
僵尸为什么存在：入队后 JVM 崩溃，ZREM 永远等不到
   → Java 侧入队前先写 entry 存活标记（TTL=等待预算+5s）
   → 崩溃后标记自然过期，下次 claim 当僵尸清掉
   = 防死请求永久占队头窗口、饿死活请求
   （裸信号量不用管队列里的尸体 → "公平队列"更复杂的原因）
```

1. **取队头窗口**：`ZRANGE queue 0 maxRank+slack-1`，取头部"允许进入的并发窗口"条（maxRank = 当前可用 permit 数；**slack=16** 是额外余量，用于僵尸密集时尽量推进存活条目进入窗口）。
2. **遍历区分存活/僵尸**：对每条 member `EXISTS entry:{requestId}`——Java 侧入队时写了一个带 TTL 的存活标记；**标记缺失 = 僵尸**（JVM 崩溃或已取消），当场 `ZREM` 清理。
3. **定位自己**：遍历时统计存活条数 liveCount，若自己的 requestId 是第 liveRank 个存活条目：`liveRank < 0`（不在队列）或 `liveRank >= maxRank`（还没排到队头窗口）→ 返回 `{0}` 不 claim；否则 `ZSCORE` 记下原 score → `ZREM` 出队 + `DEL` 标记 → 返回 `{1, score}`。

**为什么必须 Lua 原子**：这是"**检查（是否到队头）+ 清理（僵尸）+ 出队**"三步。分开做会竞态——比如两条并发请求同时读到"队头窗口有位置"，都出队，但 permit 只有 1 个，就超卖了。Lua 把判断和动作锁在同一个 Redis 命令里，Redis 单线程执行脚本，天然串行。

**僵尸条目为什么会存在**：请求入队后 JVM 可能崩溃，`ZREM` 永远等不到。所以 Java 侧**入队前先写 entry 存活标记**（TTL = 等待预算 + 5 秒缓冲），崩溃后标记自然过期，下次任何 claim 的 Lua 都会把它当僵尸清掉——**防止死掉的请求永久占据队头窗口、把活着的请求饿死**。这也是为什么"公平队列"比"裸信号量"复杂：信号量不用管队列里的尸体，队列必须。

**面试官追问**：信号量 permit 本身呢？业务挂了不释放，槽位不就永久少了？

## Q4（追问）信号量 permit 的生命周期——lease 兜底怎么设计的？

**我：** 用的是 `RPermitExpirableSemaphore`——**可过期信号量**，这是关键。

> Q4 permit 生命周期一图看懂：

```text
RPermitExpirableSemaphore —— 可过期信号量
   ├─ 获取：tryAcquire(0, leaseSeconds, SECONDS)
   │    拿不到返回 null → 继续排队
   └─ 释放：grant 交给业务 Runnable 的 try/finally
        业务结束（含异常）自动释放
        release 失败打 warn（"可能已过期"）→ 幂等 + 容错
   ▼
lease 兜底：
   业务线程崩溃/挂起/finally 没执行 → permit 到期自动回信号量
   = 不会"崩溃一次永久少一个槽"
   （普通 Semaphore 没有这能力 → 选 RPermitExpirableSemaphore 的原因）
   ▼
两个配置对照
   聊天 lease=600s（10 分钟）
      SSE 单次最长几十秒，正常 finally 早就释放
      lease 纯粹是兜底、给足冗余
      lease 太短的风险：业务没跑完 permit 就过期
        → 新请求拿到"同一个槽"，实际并发超上限
   MinerU 文档解析 lease=900s
      长任务（可能几分钟），lease 必须更长
   = lease 是兜底，不是计时器，宁可长不能短
```permit 有个 **lease（租约）**，到期自动归还。

- **获取**：`tryAcquire(0, leaseSeconds, SECONDS)`，拿不到返回 null 就继续排队。
- **lease 兜底**：如果业务线程崩溃、挂起、或 finally 没执行到，permit 会在 lease 到期后**自动回到信号量**——不会出现"崩溃一次永久少一个槽"的泄漏。普通 `Semaphore` 没有这个能力，这就是选 `RPermitExpirableSemaphore` 的原因。

两个配置要讲清楚：
- **聊天限流 lease=600 秒（10 分钟）**：为什么这么长？SSE 一次对话最长也就几十秒，正常 try/finally 早就释放了，lease 纯粹是**兜底**，给足冗余——lease 太短反而有风险：业务还没跑完 permit 就过期了，新请求拿到"同一个槽"，实际并发就**超过了**上限。
- **MinerU 文档解析 lease=900 秒**：解析是长任务（可能几分钟），lease 必须更长。这里体现"lease 要匹配业务时长"——**lease 是兜底，不是计时器**，宁可长不能短。

释放细节：`grant` 把 permit 交给业务 Runnable 的 **try/finally**，业务结束（含异常）自动释放；`release` 失败打 warn（"可能已过期"）——这是**幂等 + 容错**，过期了就不该再释放，打了 warn 留痕。

**面试官追问**：信号量释放后怎么让别的实例立刻知道？是纯轮询还是事件驱动？

## Q5（追问）Pub/Sub 通知机制——怎么做到"即时唤醒 + 不通知风暴"？

**我：** 双通道：**RTopic（Pub/Sub）事件驱动 + 定时轮询兜底**。

> Q5 Pub/Sub 通知一图看懂：

```text
双通道：RTopic 事件驱动 + 200ms 轮询兜底
   ▼
发布：permit 释放 / 失败回滚 → RTopic.publish("permit_changed")
   所有实例订阅同一 topic → 触发本进程 PollNotifier.fire()
   = 跨实例广播"有位置了"
   ▼
唤醒：PollNotifier 拿本进程所有排队 poller，逐个 tryAcquireIfReady
   ▼
防通知风暴（实现里最讲究的地方）
   ├─ firing CAS 位：已在扫描中 → 返回，只累加 pendingNotifications
   └─ do-while 循环：扫完一轮，期间又有通知（计数>0）→ 再扫一轮
      = 连续到达的多次通知只触发一次扫描，直到无新通知
   ▼
permit 耗尽本轮不扫描：fire() 先看 availablePermits()<=0 直接 break
   → 队里根本没人能拿到 permit，扫了也是空转
   （等下一次真正的 release 会重新发通知驱动）
   ▼
兜底轮询：scheduleAtFixedRate(poller, 200ms, 200ms)
   Pub/Sub 挂掉只是退回轮询延迟，不会死锁
   通知是加速器，轮询是保底线
```

- **发布**：每次 permit 释放（或失败回滚）都 `RTopic.publish("permit_changed")`。所有实例订阅同一个 topic，收到消息触发本进程的 `PollNotifier.fire()`——**跨实例广播"有位置了"**。
- **唤醒**：`PollNotifier` 拿着本进程所有排队请求的 poller，逐个跑一遍 `tryAcquireIfReady`。

**防通知风暴**（这是实现里最讲究的地方）：消息可能瞬间涌来（比如 10 个 permit 同时释放），如果每条消息都触发一次全量扫描，就是风暴。`PollNotifier` 用两个字段合并：
- `firing` CAS 位：已经在扫描中就返回，后续通知只累加 `pendingNotifications` 计数。
- `do-while` 循环：扫描完一轮后，若期间又有通知进来（计数 > 0），**再扫一轮**——**连续到达的多次通知只触发一次扫描**，直到没有新通知为止。

还有个细节：**permit 耗尽时本轮不扫描**。`fire()` 先看 `availablePermits() <= 0` 就直接 break——队列里根本没人能拿到 permit，扫了也是空转；等下一次真正的 release 会重新发通知驱动。这就是"事件驱动为主、不做无谓扫描"。

**兜底轮询**：`scheduleAtFixedRate(poller, 200ms, 200ms)` 的定时器还在——**Pub/Sub 挂掉只是退回轮询延迟，不会死锁**。通知是加速器，轮询是保底线。

## Q6（追问）Ticket 状态机——取消/超时/授予的竞态怎么防？

**我：** 每个排队请求是一个 `Ticket`，带一个状态机：`PENDING → GRANTED / TIMED_OUT / CANCELLED`。**单一 CAS 协调点**：状态一旦从 PENDING 转走就不再变更，所以**业务回调最多触发一次**、资源清理幂等。几个关键竞态：

> Q6 Ticket 状态机一图看懂：

```text
Ticket 状态机：PENDING → GRANTED / TIMED_OUT / CANCELLED
   单一 CAS 协调点：从 PENDING 转走就不再变更
   → 业务回调最多触发一次、资源清理幂等
   ▼
5 个关键竞态
   1. grant 顺序：先设 permitRef，再 CAS
      cancel/timeout 抢先转走状态 → grant 的 CAS 失败
      → 对方能看到 permitRef 并正确释放（防 permit 泄漏）
      （若先 CAS 后设值，中间窗口 cancel 看不见 permit → 丢了）
   2. GRANTED 状态下 cancel 不释放 permit（防双释放）
      permit 已 grant → 由业务 try/finally 接管
      cancel 跨界释放 → 另一请求正好拿到同 permit、原业务还在跑
        = 把同一槽位让给两个人
   3. 入队与 claim race：先写 entry 标记再入队
      （否则并发 Lua 把"刚入队没标记"当僵尸清掉）
      claim 出队后、tryAcquirePermit 之间被取消
      → 必须释放 permit + 发通知（否则 permit 被吞，等者只能靠轮询）
   4. 重入队回查：按原 score 重入队 → add 后回查 state
      已终态(取消/超时) → 自行清条目 + 标记
      （防已取消请求重入队后永久占队头窗口）
   5. 提交失败降级：onAcquiredExecutor.execute 被线程池拒绝
      → warn + 显式释放 permit + 走 onTimeout 拒绝路径
      （cleanup 在 GRANTED 不释放 permit，但业务根本没运行
        → 必须这里显式释放，否则这个槽永久丢了）
```

**1. grant 顺序：先设 permitRef，再 CAS。** 如果并发 cancel/timeout 抢先把状态从 PENDING 转走，grant 的 CAS 会失败，此时对方能看到 permitRef 并正确释放——**防止 permit 泄漏**。反过来如果先 CAS 后设值，中间窗口 cancel 看不见 permit，permit 就丢了。

**2. GRANTED 状态下 cancel 不释放 permit。** 看起来反直觉，其实是防双释放：permit 一旦 grant 成功，就由业务 Runnable 的 **try/finally 接管**了。如果 cancel 在这里跨界释放，另一个并发请求可能正好拿到这个 permit，而原业务还在跑——**等于把同一槽位让给两个人**。所以 cancel 只在非 GRANTED 状态才动手。

**3. 入队与 claim 的 race。** 入队时先写 entry 存活标记、再入队——否则并发 claim 的 Lua 可能把"刚入队还没写标记"的条目当僵尸清掉。claim 出队后、`tryAcquirePermit` 之间被取消，必须**释放 permit + 发通知**——否则 permit 被吞，其他等待者只能等下次轮询才发现。

**4. 重入队回查。** 队头但无 permit → 按原 score 重入队 → **add 之后回查 state**：若此刻已被终态（取消/超时），自行把条目和标记清掉——防"已取消的请求重入队后永久占着队头窗口"。

**5. 提交失败降级。** `onAcquiredExecutor.execute` 被线程池拒绝 → 记录 warn + **显式释放 permit** + 走 `onTimeout` 拒绝路径。这里注释写得很清楚：cleanup 在 GRANTED 状态**不会**释放 permit（那是业务的事），但业务根本没运行，所以必须在这里显式释放——否则这个槽就永久丢了。

## Q7（追问）排队期间用户上下文怎么跨线程传递？为什么用 TtlRunnable？

**我：** 会丢，而且这是个真实 bug 的预防点。看线程流转：请求在 Web 容器线程入队 → `scheduler` 线程跑 poller → 拿到 permit 后 `onAcquired` 在 `chatEntryExecutor` 执行 → 排队超时 `onTimeout` 也在 executor 执行。**至少切换了 2 次线程**，而 `UserContext` 是 ThreadLocal 存的——跨线程就没了。

> Q7 跨线程上下文一图看懂：

```text
线程流转（至少切 2 次线程）
   Web 容器线程 入队
   → scheduler 线程 跑 poller
   → 拿到 permit → onAcquired 在 chatEntryExecutor 执行
   → 排队超时 → onTimeout 也在 executor 执行
   ▼
问题：UserContext 是 ThreadLocal 存的 → 跨线程就没了
   普通 Runnable 跨线程执行时 ThreadLocal 空白
   UserContext.getUserId() 返回 null
   → reject 时连会话记录都写不了（userId 为空会被跳过）
   ▼
解法：阿里 TransmittableThreadLocal（TTL）
   onAcquired / onTimeout 都用 TtlRunnable.get(...) 包装
   TTL 在提交线程捕获上下文、在执行线程回放
   → 排队期间拿到的 userId 原样带到真正推理的线程
   ▼
有单测兜底：ChatQueueLimiterTest
   shouldKeepUserContextWhenQueuedRequestIsAcquiredByScheduler
   → 排队被 scheduler 线程获取后，onAcquired 仍能拿到 userId
   还覆盖超时路径的上下文保留
```

解法是 **阿里 `TransmittableThreadLocal`（TTL）**：`onAcquired` 和 `onTimeout` 都用 `TtlRunnable.get(...)` 包装。TTL 会在**提交线程捕获**上下文、在**执行线程回放**——排队期间拿到的用户信息（userId 等）原样带到真正执行推理的线程。

为什么不用普通 Runnable：普通 Runnable 跨线程执行时 ThreadLocal 是空白的，`UserContext.getUserId()` 返回 null，**reject 时连会话记录都写不了（userId 为空会被跳过）**。

我写了单测专门验证这点（`ChatQueueLimiterTest`）：`shouldKeepUserContextWhenQueuedRequestIsAcquiredByScheduler`——**排队请求被 scheduler 线程获取后，onAcquired 回调里仍能拿到 userId**。测试里还覆盖了超时路径的上下文保留。这说明"跨线程上下文"不是嘴上说说，是有测试兜底的。

## Q8（追问）限流拒绝的体验设计——为什么走 SSE 事件流而不是 429？

**我：** 两个原因：

> Q8 拒绝体验一图看懂：

```text
为什么拒绝走 SSE 事件流而非 429？
   ① 前端已建立 SSE 连接，在等流式响应
      直接 429 → 前端要单独处理"连接被拒"分支，解析流程断掉
      且会话上下文丢：这轮问的话既没记录也没反馈 → "凭空断了"
   ② 保持协议统一
      正常：META → MESSAGE → FINISH → DONE
      拒绝：META(conversationId/taskId) → REJECT(系统繁忙)
            → FINISH(messageId/REJECTED) → DONE
      前端不需要知道"被限流"，只需按既有事件流消费
   ▼
拒绝不是干丢：handleReject 记进会话记忆
   user 问题 + assistant"系统繁忙"(REJECTED) 都 append
   新会话还会生成会话标题
   → 用户能在历史看到"我之前问过但被限流了"= 可回溯
   ▼
边界处理
   ├─ 记录失败不阻塞 emitter：只打 warn，继续发 DONE
   │    （否则前端永远收不到完成信号，会一直挂着）
   ├─ conversationId 为空：跳过 existence 查询（省一次 DB 往返）
   └─ cancelBinder：emitter.onCompletion/onTimeout/onError 绑 ticket.cancel()
        前端关页面 / 连接断 → 立刻取消排队，不再白等队列
```

1. **前端已经建立了 SSE 连接**，在等流式响应。如果这里直接返回 HTTP 429，前端要单独处理"连接被拒"分支，解析流程断掉；而且**会话上下文会丢**——用户这轮问的话既没有记录、也没有任何反馈，体验是"凭空断了"。
2. **保持协议统一**：正常对话走 `META → MESSAGE → FINISH → DONE`，拒绝也走一套 SSE 事件流：`META`（带 conversationId/taskId）→ `REJECT`（"系统繁忙，请稍后再试"）→ `FINISH`（带 messageId/REJECTED 状态）→ `DONE`。**前端不需要知道"被限流"这种异常，只需按既有事件流消费**。

而且拒绝**不是干丢**，`handleReject` 会把这次被拒的问答记进会话记忆：user 问题 + assistant"系统繁忙"消息（标记 `REJECTED` 状态）都 `append` 进对话；如果是新会话，还会**生成会话标题**。这样用户回头能在历史里看到"我之前问过、但被限流了"——**限流不丢会话，可回溯**。

边界处理（细节）：
- **记录失败不能阻塞 emitter**：`recordRejectedConversation` 抛异常只打 warn，继续发 `DONE`——否则前端永远收不到完成信号，会一直挂着。
- **conversationId 为空**：刚生成的雪花 ID 不可能命中已有会话，直接跳过 existence 查询，省一次 DB 往返。
- **cancelBinder**：把 `emitter.onCompletion/onTimeout/onError` 都绑到 `ticket.cancel()`——**前端关页面/连接断，立刻取消排队**，不再白等队列。

## Q9（追问）上传限流（UploadRateLimitFilter）——和聊天限流的区别、Filter 为什么前置

**我：** 有，`UploadRateLimitFilter`，用独立的 `rag:document:upload` 信号量（默认并发 10）。先回答"为什么 Filter 要放在 multipart 解析之前"——这是最容易被忽略的点：

**Spring 的 multipart 解析会把上传内容落成临时文件。** 如果等进入 Controller 再限流，高并发上传时临时文件已经写进磁盘了——**限流没拦住资源消耗**（磁盘 IO/临时目录占满）。所以这个 Filter 用 `@Order(HIGHEST_PRECEDENCE)` + `OncePerRequestFilter`，**在 multipart 解析之前**就 tryAcquire 信号量，失败直接返回 429 JSON。核心思想：**限流要在产生副作用之前拦截**。

> Q9 上传限流一图看懂：

```text
为什么 Filter 放在 multipart 解析之前？
   Spring multipart 解析会把上传内容落成临时文件
   等进 Controller 再限流 → 临时文件已写进磁盘
   限流没拦住资源消耗（磁盘 IO / 临时目录占满）
   ▼
UploadRateLimitFilter
   @Order(HIGHEST_PRECEDENCE) + OncePerRequestFilter
   在 multipart 解析前 tryAcquire 独立信号量
     rag:document:upload（默认并发 10）
   失败直接返回 429 JSON
   = 核心思想：限流要在产生副作用之前拦截
   ▼
聊天限流 vs 上传限流
   等待策略   排队(公平队列等15s)      vs  快速失败(tryAcquire等5s→429)
   数据结构  信号量+队列+Pub/Sub全链路 vs  裸信号量 tryAcquire
   连接形态  SSE长连接等得起          vs  HTTP短请求要明确答复
   为什么上传不排队：上传是短请求，排队无意义
     用户等的是"上传完成"不是"流式生成"
     干等不如直接告诉他"人太多了，稍后再试"
   ▼
补充第三个信号量：MinerU 解析 rag:mineru:parse（并发5，lease900s）
   长任务+异步轮询 → lease 给长(900s)匹配任务时长
   SemaphoreInitializer @PostConstruct setPermits 一次性初始化（幂等）
```

和聊天限流的三个区别（这题适合对比着答）：

| 维度 | 聊天限流 | 上传限流 |
|---|---|---|
| **等待策略** | **排队**（公平队列，等 maxWait 15s） | **快速失败**（tryAcquire 等 5s 拿不到直接 429） |
| **数据结构** | 信号量 + 公平队列 + Pub/Sub 全链路 | 裸信号量 `tryAcquire` |
| **连接形态** | SSE 长连接，等得起、且用户已建立连接 | HTTP 短请求，前端要的是"行不行"的明确答复 |

为什么上传不排队？因为上传是**短请求**，排队等待没有意义——用户等的不是"流式生成"而是"上传完成"，让他干等队列不如直接告诉他"人太多了，稍后再试"。

**补充第三个信号量**：MinerU 文档解析用 `rag:mineru:parse`（并发 5，lease 900s）——解析是**长任务 + 异步轮询**，lease 必须给长（900s）匹配任务时长。配置上是 `SemaphoreInitializer` 在 `@PostConstruct` 用 `setPermits` 一次性初始化（幂等，只在首次生效）。

**我：** 老实说，参数主要是**按资源约束反推 + 线上压测校准**，不是拍脑袋：

## Q10（追问）评测数据的边界：限流为什么不在端到端评测集里、稳定性指标怎么压测收集

**我：** 这要分清两件事——**评测验证"质量"，压测验证"容量"，测的根本不是一个东西**：

**第一，评估集的结构天然测不到限流。** ragenteval 跑的是**单用户顺序问答**——一条 query 一次一问、跑完再跑下一条，全程没有并发。而限流的价值**只在并发场景才存在**：没有第二个人，就不会有排队、不会有拒绝、不会有僵尸条目治理。用单用户顺序的评测集去测限流，等于用"一个人过马路"去验证红绿灯——不是限流不重要，是**评测场景根本不触发它**。

**第二，限流有自己的独立验证体系——压测 + 稳定性观测。** Q9b 讲过，这模块的指标是稳定性指标（拒绝率、队列长度、首字延迟 P95、超时率、LLM 错误率），不是业务效果指标。收集方式就是**上线前模拟并发压测**：灌并发对话，观测超时率 / 首字延迟 / LLM 错误率三条曲线，找"排队开始劣化"的点，把 max-concurrent 钉在劣化点之下。这套观测和 ragenteval 的指标板是**两套并行的体系**：评测板回答"单用户答得好不好"，压测板回答"多用户扛得住扛不住"。

**第三，两套体系的数据源也不同。** 评测数据来自真实链路的录制回放（`EvalRecord` 三段数据源），压测数据来自**构造的并发流量 + 被拒会话的落库**——被拒的问答会写进 `t_message`（REJECTED 状态），所以拒绝率不仅是一个压测期间的瞬时观测，还能**事后从库里回溯"哪些会话被拒、拒在哪个阶段"**，配合链路追踪把排队时长、等待时长对上去。**质量用评测闭环，容量用压测闭环，两个闭环合起来才覆盖限流。**

> 💡 面试官追问（真实被问）：评测没覆盖限流，是不是评测体系不完整？
>
> **我：** 我不这么看——**让评测集去测并发反而是错的**。评测集要的是"可复现的质量信号"，单用户顺序跑才能保证同一条样本在不同版本间可比；一旦引入并发，延迟、拒绝都变成随机事件，指标板就抖了。**测并发该用压测（隔离、可放大、可观测曲线），不该用评测集**——分工清楚，不是覆盖不全。

> 💡 面试官追问：稳定性指标的收集，除了压测还有什么手段？
>
> **我：** 两个补充：① **线上被动观测**——生产环境持续采"队列长度、拒绝率、首字延迟 P95"，看自然流量下的水位，和压测互相印证；② **链路追踪对齐**——被拒会话写进 `t_message`（REJECTED），trace_id 能把"被拒的这次请求"在追踪图上拉出来，看它是在排队超时还是 permit 耗尽阶段被拒。**压测给"极限在哪"，线上观测给"常态水位"，落库给"每一起拒绝都可回溯"**——这才是稳定性指标的完整闭环。

> Q10 限流评测边界一图看懂：

```text
为什么限流不在端到端评测集里
   评估集 = 单用户顺序问答（一条一条跑，无并发）
   限流价值只在并发场景存在（排队/拒绝/僵尸治理）
   → 评测场景不触发限流，不是不重要
   ▼
评测 vs 压测：两套并行体系
   评测板（ragenteval）→ 质量：单用户答得好不好
   压测板（稳定性观测）→ 容量：多用户扛得住扛不住
   质量用评测闭环，容量用压测闭环
   ▼
稳定性指标怎么收集
   ① 压测：灌并发对话，观测超时率/首字延迟/LLM错误率三条曲线
      找"排队劣化点"，max-concurrent 钉在劣化点之下
   ② 线上被动观测：队列长度/拒绝率/首字延迟 P95 常态水位
   ③ 落库回溯：被拒会话写 t_message REJECTED + trace 拉出被拒请求
   = 压测给"极限在哪"，线上给"常态水位"，落库给"每起拒绝可回溯"
```

## 📋 面试建议（对真实面试的 3 条建议）

1. **把"公平"和"僵尸治理"讲成你区别于他人的深度**。绝大多数候选人聊限流只会说"Redis 信号量"或"令牌桶/漏桶"。你能讲出"ZSET 公平队列 + 雪花序号 + 重入队保位次 + Lua 原子清理僵尸条目"这套组合，已经超过 90% 的答案；再点出"僵尸为什么存在（JVM 崩溃）""为什么裸信号量会泄漏（普通 Semaphore 崩溃即少槽）"，就是真实实现里才有的认知。
2. **"限流体验"是隐藏的加分项**。聊限流多聊"拒绝后怎么办"：SSE 事件流保持协议统一、被拒问答写进会话记忆、连接断开即取消排队、记录失败不阻塞 DONE——这些让面试官看到你不只关心"挡住请求"，还关心"被挡住的人"的体验和可回溯性。**限流是保护手段，不是丢请求的手段。**
3. **参数题要敢说"这是工程取舍，不是标准答案"**。Q9b 被问到"为什么是 10 并发"，别慌——没有标准答案，关键是讲出锚点逻辑（下游承载 + 成本 + 首字延迟容忍 + 压测校准）。主动说"默认配置保守、线上按压测收敛"，比假装有个精确推导更可信。另外准备好两个 ⚠️ 钩子：`scheduleAtFixedRate` 轮询间隔为什么 200ms（轮询对延迟和 Redis 压力的折中）、Redis 命令往返次数对高并发的影响（每个请求入队 2~3 次 Redis 往返，队列深度可控前提下可接受）。
