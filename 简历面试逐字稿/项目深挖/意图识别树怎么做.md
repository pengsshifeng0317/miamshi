## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的意图识别树是怎么做的？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（一次调用 / 0.35 / 落空兜底 / 澄清反问）正好接 Q2 / Q4 / Q5 / Q6。

**我：** 我们做意图识别树，是为了解决一个问题——寿险的问题五花八门，产品咨询、条款解读、查保单、甚至寒暄，如果直接丢给大模型，它不知道该去哪个知识库、该不该调工具。所以我们把"意图路由"前置到检索之前。

核心是四件事：

**树形结构，只有叶子参与打分** ->  **叶子挂执行单元，一次 LLM 调用完成打分** -> **两个兜底** -> **落库与热加载**

**第一，树形结构，只有叶子参与打分。** 三层树：业务系统 → 产品咨询/条款解读 → 重疾险/年金险。非叶子只是组织节点，只有叶子进分类 prompt，既避免层级间分数互相干扰，也控制 prompt 规模。

**第二，叶子挂执行单元，一次 LLM 调用完成打分。** 每个叶子是 KB（挂 PgVector collection，走知识库检索）、MCP（挂 mcpToolId，走工具调用）、或 SYSTEM（处理寒暄）之一。分类器把所有叶子的 id、路径、描述、例子拼成一个 prompt，让 LLM 一次调用输出候选列表，然后过滤 ≥0.35、取前 3 个。所以这棵树既是检索路由，也是工具路由的统一入口。

**第三，两个兜底。** 一是意图全落空（分数都太低）时走全局向量检索兜底，不让问题白问；二是分数接近、路径重名（比如产品咨询和条款解读下面都挂了"重疾险"）时，用 FAST 档 LLM 二次确认，仍判不准就反向澄清、列选项让用户选，不硬猜。

**第四，落库与热加载。** 树不是写死在代码里的——存在 `t_intent_node` 表，**一行一个节点**，靠 `parent_code` + `level` 两个字段串成树；叶子挂什么执行单元，就是它的 `kind` / `collection_names` / `mcp_tool_id` 字段。Redis 缓存、改树清缓存，管理端改完线上立即生效，不用发版。

> 📦 涉及的表（面试官问"表怎么设计的"时展开，平时不用全背）：
>
> | 表 | 用途 | 关键字段 |
> |----|------|---------|
> | `t_intent_node` | 意图树节点，一行一个节点 | `parent_code`+`level` 拼树；`kind`(0 KB / 1 SYSTEM / 2 MCP)、`collection_names`(JSONB)、`mcp_tool_id` 挂执行单元 |
> | `t_query_term_mapping` | 关键词归一化（问题重写后的词表归一，减少检索干扰） | `source_term`→`target_term`、`match_type`、`priority` |
> | `t_rag_trace_run` / `t_rag_trace_node` | 链路追踪，一次问答全链路可观测 | `trace_id` 串 run+node，`status`/`duration_ms`/`node_type` |
> | `t_knowledge_chunk` / `t_knowledge_vector` | 检索落库：分块正文 + 向量 | `chunk` 存分块；`vector` 存 `embedding(1536)`，按 `collection_name` 分集合 |

讲到这里停一下，面试官大概率会顺着追问：打分具体怎么做的？0.35 怎么来的？全落空怎么兜？澄清怎么实现？——正好接上 Q2 / Q4 / Q5 / Q6。

## Q1（开场总览）请介绍一下你的意图识别树是怎么设计的？为什么用"树"，和普通多分类有什么不同？

**我：** 先说是为什么做——寿险的问题五花八门，产品咨询、条款解读、查保单、甚至寒暄，如果让大模型直接回答，它不知道该去哪个知识库、该不该调工具。所以先把"意图路由"做在检索前面。

我们设计成三层树：`DOMAIN（业务系统/产品线）→ CATEGORY（产品咨询/条款解读）→ TOPIC（重疾险/年金险…）`。

> 整条链路先看这张图（面试时可以边画边讲）：

```text
用户提问「重疾险 条款3.2 怎么说？」
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  意图识别树 · 一次LLM调用打分（只看叶子，≥0.35 才命中）          │
│                                                          │
│  DOMAIN 业务系统 / 产品线                                    │
│   ├─ CATEGORY 产品咨询                                      │
│   │     ├─ TOPIC 重疾险   ◀ 叶子 · 打分                    │
│   │     ├─ TOPIC 年金险   ◀ 叶子 · 打分                    │
│   │     └─ TOPIC 意外险   ◀ 叶子 · 打分                    │
│   ├─ CATEGORY 条款解读    ◀ …叶子 · 打分                   │
│   ├─ CATEGORY 查保单      ◀ 叶子 · 打分（MCP · 挂 mcpToolId）│
│   └─ CATEGORY 寒暄        ◀ 叶子 · 打分（SYSTEM）           │
└──────────────────────────────────────────────────────────┘
   │
   ▼ 命中叶子 → 按 IntentKind 分发执行单元
   │
   ├─ KB（知识库）   → PgVector collection 检索
   ├─ MCP（工具）    → 查保单 / 核保，走 MCP 调用
   └─ SYSTEM（寒暄） → 直接回答，不进检索
      │
      ▼
  合并证据 → LLM 生成回答 → 返回用户
```

对应三个关键设计（① 只有叶子参与打分 = 图中"只看叶子"；② 叶子挂执行单元 kb/mcp/system = 图中分发那三段；③ 热加载 = 管理面，图未画）：

1. **只有叶子节点参与打分**。非叶子只是组织节点，避免层级间分数互相干扰，也控制 prompt 规模。
2. **叶子节点挂载"执行单元"**：有三个枚举，kb、mcp、system。KB 类型挂 PgVector 的 collection进行知识库检索，MCP 类型挂 mcpToolId，SYSTEM 处理寒暄——所以这棵树既是**检索路由**，又是**工具路由**的统一入口。
3. **热加载**：树存在库里，Redis 缓存，每次调用都从缓存读、缓存空再查库回填。管理端改树（加节点、挂工具）线上立即生效，不用发版。

**面试官追问**：你说是"LLM 打分"，具体怎么打？

## Q2（追问）具体打分流程是怎样的？

**我：** 用的串行分类器 `DefaultIntentClassifier`，**一次 LLM 调用**完成：把**所有叶子节点**的 id、path、description、examples、type 拼成一个 `intent_list` 塞进分类 prompt，让 LLM 只在这些 id 里选，输出 `[{id, score, reason}]` 这个 JSON 数组。

稳定性上做了三件事：

1. **参数压制**：temperature 0.1、topP 0.3、关闭 thinking，让输出尽量确定，也省钱。
2. **容错解析**：LLM 返回经常带 markdown 围栏 → 先 strip；有时外面多包一层 `{"results":[...]}` → 兼容；返回未知 id → 跳过并告警；JSON 解析失败或调用失败 → **返回空意图**，绝不让意图环节把整条链路拖垮。
3. **后处理**：按分数降序 → 过滤掉 <0.35 的 → 截断前 3 个。

> 加分细节：分类 prompt（`intent-classifier.st`）里还内置了**三类问题的匹配规则**——交互导向（问候/评价助手，只在 SYSTEM 节点里选）、实体导向（必须命中具体系统/产品名，**实体不一致即使领域相似也不匹配**）、主题导向（按 path/description 主题词匹配）。比如"重疾险 条款3.2 怎么说"因为实体强匹配（重疾险 + 条款3.2）只会选条款解读下的分类，不会误路由到产品咨询——直接解决了同类产品最常见的"跨分类误路由"问题。

> Q2 打分流程一图看懂：

```text
一次 LLM 调用（DefaultIntentClassifier）
   │
   ▼
① 拼分类 prompt：所有叶子节点的 id/path/description/examples/type
   │  → intent_list（只在这些 id 里选）（槽位）
   ▼
② LLM 输出 JSON 数组 [{id, score, reason}]
   │  temperature 0.1 / topP 0.3 / 关 thinking（确定性 + 省钱）
   ▼
③ 容错解析
   ├─ strip markdown 围栏
   ├─ 兼容外层 {"results":[...]}
   ├─ 未知 id → 跳过 + 告警
   └─ 解析/调用失败 → 返回空意图（不拖垮整条链路）
   ▼
④ 后处理
   ├─ 按分数降序
   ├─ 过滤 < 0.35
   └─ 截断前 3 个
   ▼
命中意图列表（KB / MCP / SYSTEM）
```

## Q3（追问）扩展性和并发

**我：** 两个层面：

- **单问扩展**：`IntentClassifier` 接口我预留了两种实现——串行（当前，意图数少够用）和**按 Domain 拆组**、**多路 LLM 并行**。目前树叶子量可控，串行是性价比选择，这是有意的取舍。
- **多子问题并行**：问题会先被改写/拆分成多个子问题，`IntentResolver` 用 `CompletableFuture.supplyAsync` 提交到**独立线程池**（`intentClassifyExecutor`：核心 = CPU 核数、最大 = 2×核数，`SynchronousQueue` + `CallerRunsPolicy`，任务打满时调用线程自己执行形成背压、不丢任务；TTL 包装保证子线程里链路追踪的 traceId 不丢），每个子问题并行分类、互不阻塞；单个失败降级空意图，不影响别人。
- 最后有一个**总量控制**：所有子问题加起来不超过 3 个意图。超了的话每个子问题至少保 1 个最高分，剩余配额按分数从高到低补——保证"每个问题都不被完全丢掉"。

> Q3 扩展性一图看懂：

```text
IntentClassifier 接口（两种实现）
   ├─ 串行实现（当前）：一次调用，意图少够用
   └─ 按 Domain 拆组、多路 LLM 并行（预留，等叶子多）

多子问题并行（IntentResolver）
   ├─ 子问题1 ─┐
   ├─ 子问题2 ─┤  CompletableFuture.supplyAsync
   ├─ 子问题3 ─┤  intentClassifyExecutor 独立线程池
   └─ ...      ┘  单个失败降级空意图，不阻塞别人
   ▼
总量控制：所有子问题意图 ≤ 3
   ├─ 每个子问题保底 1 个最高分（不被完全丢掉）
   └─ 剩余配额按分数从高到低补
```

> 💡 面试官追问（真实被问）：这个独立线程池具体怎么配的？用了什么策略、怎么考虑的？

> **我：** `intentClassifyExecutor` 完整配置：**核心 = CPU 核数、最大 = 2×核数、60s 保活、`SynchronousQueue`（无缓冲）、`CallerRunsPolicy`**，外层包 TTL（`TtlExecutors`）保子线程的 traceId。四个考量的思路：
>
> 1. **核心=核数、最大=2×核数**：意图分类主体是**一次 LLM 调用**，**属于 IO 密集**（主要等模型网络返回，不是跑本地 CPU），所以能超配到 2 倍；但再大没意义——分类的并发上限被 `capTotalIntents` 锁死在 ≤3 个子问题，2 倍留足余量即可。
> 2. **队列选 `SynchronousQueue`（无缓冲）**：这类任务并发量小、每次都是 LLM 调用（贵且慢），缓冲排队只会让延迟被悄悄拉长；宁可立即执行或立即触发拒绝策略，不积压。
> 3. **拒绝策略选 `CallerRunsPolicy`**：打满时**不丢任务、不抛异常**，由提交线程自己执行，形成**背压**——调用方变慢（**但是能调用完，不会丢掉用户的子问题**）、上游自然限流。意图场景尤其适合：单个子问题失败可以降级，但**不能因为池子满了把用户的问题丢掉**。对比 AbortPolicy 抛异常（杀请求）、DiscardPolicy 静默丢，CallerRuns 是"可用性优先"的正确选择。
> 4. **TTL 包装**：traceId 存在 TransmittableThreadLocal，直接 `CompletableFuture` 提交会丢上下文、子线程链路对不上（`t_rag_trace_node` 断链）。包 `TtlExecutors` 后子线程继承父线程 traceId，全链路可观测。
>
> > 顺带体现"一池一策"（面试官很吃这套）：检索通道池 `ragRetrievalExecutor` 核心=最大=4×核数（通道并行全开直跑）；记忆摘要 `memorySummaryExecutor` 核心=1 + `LinkedBlockingQueue(200)`（摘要是**后台任务**，可排队慢慢做、不能丢但忍延迟）；模型流 `modelStreamExecutor` / SSE 入口 `chatEntryExecutor` 用 `AbortPolicy`（面向用户的流式出口，满了宁可快速失败让用户重试，也不能无限背压憋死请求）。**一句话：在线请求路径用"无缓冲 + CallerRuns"保证不丢，后台路径用"有界队列"容忍排队，流式出口用 Abort 快速失败。**

**面试官追问**：0.35 阈值和 3 个上限怎么定出来的？

## Q4（追问）阈值和上限的来历

**我：** 0.35 是意图过滤线，低于它视为"聊偏了"，不进入检索——避免把不相干的 collection 拉进来污染上下文。3 个上限是**性能约束**：一次问答最多并发拉 3 个 collection，防止意图太多拖慢检索，这对我们首字响应压进 6 秒贡献很大。

调参逻辑：基于 RAGAS 的离线评测集扫阈值 + 线上 A/B，看上下文精准度、过度检索率这些指标取平衡点——阈值越低越漏、越高越错。这两类参数现在都配置化了。诚实说，目前是**全局统一阈值**，后续想改成按意图类型差异化，这块还做得比较简单。

> Q4 阈值和上限一图看懂：

```text
0.35 = 意图过滤线
   ├─ 低于它 → 视为"聊偏了"，不进检索
   └─ 目的：不拉不相干 collection 污染上下文

3 = 意图上限（性能约束）
   └─ 一次问答最多并发拉 3 个 collection
      → 防止意图太多拖慢检索（贡献首字 6s）

调参逻辑
   离线 RAGAS 扫阈值 + 线上 A/B
   └─ 看 上下文精准度 / 过度检索率 取平衡点
      ├─ 阈值越低 → 越漏
      └─ 阈值越高 → 越错
   现状：全局统一阈值（诚实：想改按意图类型差异化）
```

## Q5（追问）意图全落空怎么办

**我：** 返回空意图列表。检索侧有兜底——走**全局向量召回**（`multi_channel` 占位键），不因为意图没命中就空答。另外还有 SYSTEM 类意图专门接"你是谁、平台能干什么"这类寒暄，不让高频话术白白消耗检索成本。

我总结这个模块的设计原则是：**意图识别是"路由加速器"，不是"生死关卡"**——它负责把检索和工具路由得更准更快，但识别失败必须优雅降级，不能把用户卡死。

## Q6（追问）澄清反问的实现和交互

**我：** 这块在 `IntentGuidanceService`。先决条件：**只有一个子问题**（多子问题场景不做澄清，歧义判定会误伤）+ 过滤后有 **≥2 个 KB 候选**。然后规则层做一件事——**路径重名检测**：

> 💡 面试官追问（真实被问）：为什么多子问题就不做澄清了？"歧义判定会误伤"具体指什么？

> **我：** 这是 `findAmbiguityGroup` 第一行就写死的先决条件——`subIntents.size() != 1` 直接 return，连歧义检测都不做。三个原因：
>
> 1. **输入上根本不构成歧义**：多子问题时，每个子问题被总量控制（`capTotalIntents` ≤3）压到"保底 1 个最高分"——子问题一多，每个子问题分到的意图基本只剩 1 个。而澄清的前提是"同一问题下 **≥2 个候选**"才能做路径重名比较（`ranked.size() < 2` 也直接 return），候选都不足 2 个，判了也是白判，还白花一次 FAST 档 LLM 调用。
> 2. **交互上是 N 次来回的灾难**：澄清是"一问一答、答完再走检索"的串行交互。单个子问题澄清一次没问题；但多子问题时如果每个子问题各自触发澄清，就是 **N 次来回 + N 次重新检索**——用户一次问多个问题本来是想省事，反而被追问次数最多，体验崩坏。所以多子问题一律不拦，直接进检索。
> 3. **兜底够用**：多子问题直接走联合检索 + RRF 融合 + 重排，本身能兜住大部分歧义。这和 Q7 的"可用性优先"是同一个取舍思想：**澄清是给"单条主问题"的高价值二次确认，不是给"批量问题"的逐个盘问。**把最高分候选当作主路径，逐个看其它候选路径跟它在"分叉之后"有没有重名节点（比如产品咨询下面挂"重疾险"，条款解读下面也挂"重疾险"），并且**用户问题里必须真的提到了这个名字**才算冲突——用户问的本来就不是这个岔路口，就不拦。

规则层一旦发现重名，就调一次 **FAST 档 LLM**（`AmbiguityLLMChecker`）二次确认，让它返回 `{ambiguous, reason}`。LLM 判定 true 才触发澄清，false 则放行；**判定失败或超时同样放行**——纯 RAG 是只读流程，不能因为模型抖动反复阻断用户（这块和 Q7 的取舍呼应）。

> 为什么打分层和澄清层配合得这么顺？因为分类 prompt（`intent-classifier.st`）里本身就内置了这个设计：模板明确告诉模型，**"同名主题多系统"的歧义场景要返回 0.4~0.7 的多项候选**用于引导式问答——打分层特意把歧义候选送上来，澄清层再判断要不要拦下来问用户，两个模块是配套设计的闭环，不是两个独立功能。

> Q6 澄清反问真实流程：

```text
先决条件：单个子问题 + 过滤后 ≥2 个 KB 候选
   │
   ▼
规则层 · 路径重名检测（零 LLM 调用，O(1)）
   │  主候选路径 vs 其它候选路径
   │  ├─ 分叉之后有重名节点（如 产品咨询/条款解读 都挂"重疾险"）
   │  └─ 且用户问题里真的提到了这个名字
   │  └─ 无重名 → 不澄清，直接走检索
   ▼
命中重名 → FAST 档 LLM 二次确认（AmbiguityLLMChecker）
   │  返回 {ambiguous, reason}
   ├─ ambiguous=true   → 触发澄清
   ├─ ambiguous=false  → 放行
   └─ LLM 失败/超时    → 放行（不因模型抖动阻断用户）
   ▼
触发澄清：最多展示 maxOptions=6 个选项（fullPath 带层级）
   "请问你具体想了解哪个？请回复数字选择（可多选 1,2），或回复 都/全部"
   ▼
用户选完 → 解析回意图 → 再走检索（二次确认，降低拿错库概率）
```

用户看到的交互长这样（guidance-prompt 渲染，`resolveOptionDisplay` 展示带层级的 fullPath）：
> 关于**重疾险**，在知识库中检索到了以下内容：
> 1) 业务系统 > 产品咨询 > 重疾险
> 2) 业务系统 > 条款解读 > 重疾险
> **请问你具体想了解哪个？请回复数字选择（可多选，如 1,2），或回复"都/全部"**

最多展示 6 个选项（`guidance.max-options` 可配置），展示的是 fullPath 带层级，用户看得懂。用户选完（或回"都"）后解析回意图，再走检索。这是给 RAG 一次"二次确认"的机会，显著降低拿错知识库回答的概率。

**面试官追问**：为什么两层判断，规则层 + LLM 二次确认，不直接全丢给 LLM？

## Q7（追问）规则层先行的取舍

**我：** 三个原因：**成本、可解释性、可用性**。

- **成本**：规则层（路径重名检测）是纯规则，**零额外 LLM 调用**、O(1) 判断，绝大多数场景直接命中；只有命中重名才花一次 FAST 档调用，把 LLM 开销压到最低。
- **可解释性**：重名规则产品/运维直接看得懂（"两条路径都挂重疾险，用户又提到了重疾险"），改起来快；全 LLM 就成黑盒，上线后难排查。
- **可用性（和直觉相反，面试官最爱追问的点）**：LLM 二次确认失败或超时，我们**降级为"跳过澄清、放行联合检索"**，而不是反过来再问一次。因为纯 RAG 是只读流程——歧义确认失败大多是模型瞬时抖动，这时再抛澄清选项，会把一次本可正常回答的请求变成失败请求，对用户体感伤害更大；而联合检索 + 重排本身能兜住大部分歧义。这是"可用性优先"，不是"准确率优先"。

> Q7 取舍一图看懂（为什么规则层 + LLM 双层，不直接全丢给 LLM）：

```text
   ├─ 成本：规则层纯逻辑、零 LLM 调用、O(1)
   │      只有命中重名才花一次 FAST 档
   ├─ 可解释性：重名规则看得懂（"两条路径都挂重疾险"）
   │      全 LLM → 黑盒，上线后难排查
   └─ 可用性：LLM 二次确认失败/超时 → 放行联合检索
         （纯 RAG 只读流程，宁可多召回，不能把用户卡死）
```

**面试官追问**：MCP 工具调用也是意图？和知识库意图怎么共存？

## Q8（追问）MCP 与 KB 共存

**我：** 对，`IntentKind` 三种：KB（RAG）、SYSTEM（寒暄）、MCP（工具）。叶子节点挂 mcpToolId 就是 MCP 意图，比如"查保单""核保规则"。打 prompt 时给这些节点标注 `type=MCP`、`toolId=xxx`，让 LLM 识别"这是要调工具的问题"；命中后路由到 MCP 调用，走参数提取 prompt 从问题里抽参数，支持多工具并行。

而且**同一个问题可以同时命中 KB 和 MCP**——比如"查我的保单 + 重疾险保哪些病"，`IntentGroup` 把 mcpIntents 和 kbIntents 分开，工具调用和向量检索并行，结果合并后再生成答案。

> Q8 MCP 与 KB 共存一图看懂：

```text
IntentKind 三种：
   ├─ KB（RAG）    → 叶子挂 collection，走知识库检索
   ├─ SYSTEM（寒暄）→ 直接回答，不进检索
   └─ MCP（工具）  → 叶子挂 mcpToolId，走 MCP 调用

同一问题可同时命中 KB + MCP：
   "查我的保单 + 重疾险保哪些病"
   │
   ▼ IntentGroup 分两组
   ├─ kbIntents   → 向量检索（多路检索）
   └─ mcpIntents  → 参数提取 → 工具并行调用
   │
   ▼
KB 结果 + MCP 结果 并行合并 → 生成答案
​```所以意图树是天然的 router，这也是我们集成 MCP 的根本原因。

**面试官追问**：Top-1 准确率 90%+ 这个数怎么测的？口径是什么？

## Q9（追问）指标口径

**我：** 两个口径，我提前说明白：

- **离线**：RAGAS 评测集里有一批"意图标注样本"（问题 → 期望命中的叶子节点），跑 intent-resolve 看 **Top-1 是否命中**，聚合出准确率，覆盖各意图类型、包含歧义样本。
- **在线**：每次请求的 intent-resolve 都落 trace，线上抽检 + 人工校正，校正结果回流评测集，形成闭环。
- **口径澄清**：这个 90% 是"分类节点命中率"（正确叶子排第一），**不是**回答正确率；检索质量另用 Recall@1、上下文精准度等指标看。我主动把口径讲清楚，避免面试官混淆。
