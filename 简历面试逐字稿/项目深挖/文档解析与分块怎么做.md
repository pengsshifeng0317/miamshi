## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的文档解析和分块是怎么做的？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（为什么不是 Tika 打天下 / 策略为什么废弃 / 块大小为什么 1024 / 向量文本为什么和展示不一样）正好接 Q2 / Q6 / Q8 / Q9。

**我：** 我们做文档解析和分块，核心要解决一个矛盾：**RAG 的召回质量取决于"块"切得对不对，而"块"切得对不对，又取决于解析时有没有保住文档结构**。所以这条链路我分三件事讲。

**第一，多格式解析——不是"一个 Tika 打天下"。** Tika 输出是平文本，章节、表格、图片结构全丢了。我按格式选最擅长保结构的解析器：复杂版面（PDF / Word / PPT）走 MinerU，表格走 POI / CSV，Markdown 走 commonmark 的 AST，HTML / JSON / XML / RTF 这类纯文本才让 Tika 兜底。统一产出**结构化 Block 列表**。

**第二，分块——结构感知，不是固定字符切。** 解析已经给了章节、表格、列表这些结构，分块就按 Block 类型分发到专属 chunker，切口只落在结构边界（段落句末、表格行、列表项），最后按"相邻两个标题之间"打包成块。简历里"固定窗口 + 滑动重叠"其实是**兜底切超长段落时的底层切分器**，不是主策略。

**第三，元数据增强——展示与向量分离。** 每块存两份：`content` 是文档原貌给人看，`embeddingText` 是"章节路径 + 正文"给向量用——表格向量化成"列名: 值"、图片只留描述去掉 URL。再叠加 AI 增强（关键词 / 摘要）进 metadata。

一句话：**解析保结构 → 分块按结构切 → 元数据按用途分离**，让答案始终落在完整语义单元里，不被切碎。

> 📦 涉及的核心组件与存储（面试官问"数据存哪、怎么回表"时展开，平时不用全背）：

| 组件 / 存储 | 职责 | 关键点 |
|----|------|---------|
| `ParserRegistry` | (MIME × 档位) → 解析器，启动建表 + 自检 | 四档查找、键冲突启动失败 |
| `MimeTypeDetector` | 字节语义探测 MIME | 不信任扩展名 |
| `ChunkingService` | 分块入口 | 整文档 / block-aware 两分支，依据是预算不是策略 |
| `TextSplitter` | 边界感知文本切分（固定窗口+滑动重叠） | 换行→中文句末→英文句末回溯 |
| `ChunkPacker` | 按"相邻标题之间"为节打包 | 切口只在节边界，不做块级重叠 |
| `ChunkAssembler` | 草稿 → 成品块，content / embeddingText 分离 | 章节路径只拼进向量文本 |
| `ChunkMetadata` | 块元数据唯一序列化点 `toMap()` | outline_path / source_file / sheet_name / assets / extras |
| `t_knowledge_chunk` | 分块正文落库 | `content`(展示)、`embedding_text`(向量)、`doc_id`、`chunk_index`、outline 列 |
| `t_knowledge_document` | 文档表，回表补标题 | `doc_name`、`kb_id` |
| 向量库 metadata（JSONB） | 结构化元数据落向量库 | outline_path / sheet_name / assets / 富集 extras |
| RustFS | 图片等资产存储 | 按 `assets/{documentId}/...` 归档 |

讲到这里停一下，面试官大概率会顺着追问：为什么不是 Tika 打天下？MIME 怎么路由？策略枚举为什么废弃了？块大小为什么是 1024？向量文本为什么和展示不一样？——正好接上 Q2 / Q3 / Q6 / Q8 / Q9。

## Q1（开场总览）介绍一下你的文档解析和分块整体是怎么做的？

**我：** 先说这条链路要解决的根问题——**RAG 的召回上限，是被"切块质量"卡住的**。同样一份文档，切成"完整的一句话"和切成"半句话 + 半张表"，召回去的块能不能回答问题是天壤之别。而切块质量又完全取决于上游解析有没有保住结构。所以我们把"解析 → 分块 → 元数据"当一条流水线来设计，而不是三个孤立的工具。

整条链路（`IngestionNodeType`）是六个节点串起来的：**fetcher（取字节）→ parser（解析成 Block）→ enhancer（文档级 AI 增强）→ chunker（分块+向量化）→ enricher（块级 AI 增强）→ indexer（落库）**。我负责的是 parser、chunker 这两个核心，加元数据增强。

架构上三个关键决策：

1. **解析层做成"多解析器 + 注册表路由"，而不是一个通用解析器**。每个解析器只认领自己擅长的格式，`ParserRegistry` 按 `(MIME × 解析档位)` 路由。这样新增格式只补一个实现，不碰已有逻辑。
2. **分块层做成"Block 类型 → chunker 查表分发"的结构感知分块**。解析输出的是结构化 Block（标题、段落、表格、列表、代码、图片），每个 Block 类型有专属 chunker，切点天然落在结构边界上。
3. **元数据做"展示与向量分离"**。每块存 `content`（文档原貌）和 `embeddingText`（章节路径 + 正文）两份，向量文本才是检索真正吃的东西。

> 整条链路先看这张图（面试时可以边画边讲）：

```text
文档上传（保险条款 PDF / 产品费率表 Excel / 理赔指南 Markdown / 坐席笔记 txt）
   │
   ▼
① ParserNode  解析成结构化 Block 列表
   ├─ MimeTypeDetector 字节探测 MIME（不信任扩展名）
   ├─ ParserRegistry (MIME × 档位) 路由到解析器
   └─ 产出 Heading / Paragraph / Table / List / Code / Image Block
   ▼
② ChunkerNode 分块 + 向量化
   ├─ Block 类型 → chunker 查表分发
   ├─ 标题先更新 outline 章节路径（HeadingHandler）
   ├─ 各 chunker 切分（切点落结构边界）
   ├─ ChunkPacker 按"相邻标题之间"为节打包
   └─ ChunkAssembler 装配：content(展示) + embeddingText(章节路径+正文)
   ▼
③ Enhancer(文档级) / Enricher(块级)  AI 增强 → metadata.extras
   ▼
④ IndexerNode  向量化落库 + attachPipelineMetadata
   ▼
检索时命中 chunkId → ChunkMetadataResolver 回表补 doc_id / doc_name / chunk_index
```

**面试官追问**：你特意强调"不是 Tika 打天下"——Apache Tika 本身也能解析 PDF、Word、Excel，为什么还要自己拆这么多解析器？

## Q2（追问）为什么不用一个 Tika 打天下？解析器怎么分工？

**我：** 因为 Tika 的输出是**平文本**，它把 PDF / Word 解析完，标题、表格、图片这些结构**全压成一行行文字**，我拿不到"这是一张表""这是一个三级标题"这种信息。而后面分块恰恰要靠这些结构——没有结构，分块就退化回"按字符硬切"，召回质量直接崩。

所以 Tika 在我们的架构里**只做纯文本类格式的兜底**（`TikaDocumentParser` 认领 `text/*`、HTML、JSON、XML、RTF），复杂版面和结构型格式全部交给更专门的解析器：

| 格式 | 解析器 | 为什么是它 |
|---|---|---|
| PDF / Word / PPT | `MinerUDocumentParser`（MinerU SaaS） | 复杂版面（分栏、表格、公式），本地解析还原度不够 |
| Excel | `ExcelDocumentParser`（Apache POI） | 能拿到 sheet、单元格、公式，保留表格结构 |
| CSV | `CsvDocumentParser` | 自动探测字符集 + RFC4180，逐字段解析 |
| Markdown / txt | `MarkdownDocumentParser`（commonmark-java） | 走 AST，标题/表格/列表/代码/图片结构全保留 |
| HTML / JSON / XML / RTF | `TikaDocumentParser` | 本来就是纯文本，Tika 足够 |

这个分工有个代码里的注释写得很直白：**"复杂版面（PDF/Word/PPT）走 MinerU，表格走 POI/CSV，markdown 走 commonmark"**。每个解析器实现同一个 `DocumentParser` 接口（`getParserType` / `parseStructured` / `supportedMimeTypes`），返回统一的 `ParsedDocument`（`List<Block> + metadata`）——**解析器的输出就是 Block 列表，这是解析层和分块层的契约**。

> Q2 解析器分工一图看懂：

```text
为什么不是 Tika 打天下：
   Tika 输出 = 平文本，标题/表格/图片结构全压成一行行文字
   → 分块退化回"按字符硬切"，召回质量崩
   ▼
按格式选最擅长"保结构"的解析器：
   PDF/Word/PPT  → MinerUDocumentParser（复杂版面还原）
   Excel         → ExcelDocumentParser（POI，表格结构）
   CSV           → CsvDocumentParser（字符集探测+逐字段）
   Markdown/txt  → MarkdownDocumentParser（commonmark AST）
   html/json/xml/rtf → TikaDocumentParser（纯文本兜底）
   ▼
统一 DocumentParser 接口 → 统一产出 ParsedDocument(List<Block> + metadata)
   → "解析器输出 Block 列表" = 解析层与分块层的契约
```

## Q3（追问）MIME 探测和解析器路由怎么做的？为什么有"启动自检"？

**我：** 三件事：**字节探测、注册表路由、启动自检**。

**第一，字节探测，不信任扩展名。** `MimeTypeDetector.detect(bytes, fileName)` 用 Tika 按**字节内容 + 文件名**探测 MIME。为什么必须看字节？因为扩展名是用户给的可伪造标签，`.txt` 里可能塞的是别的；而字节是文档的真实语义，探测出来的 MIME 才是"这个文件到底是什么"的唯一权威源。

**第二，注册表路由，`(MIME × 档位) → 解析器`。** `ParserRegistry` 在启动时读所有解析器声明的 `supportedMimeTypes()` 建两张表：精确表（全量 MIME）和通配表（`text/*` 这种大类）。查找顺序四档：

```text
精确 + 请求档位 → 通配 + 请求档位 → 精确 + FAST → 通配 + FAST → 抛错
```

两个设计点：**精确键永远优先于通配键**——所以 `text/csv`、`text/plain`、`text/x-web-markdown` 这些"精确被认领"的 MIME 绝不会落到 Tika 的 `text/*` 通配兜底里。**认不出来就显式报错，不静默兜底**——塞给某个通用解析器只会产出垃圾文本，污染知识库。

这里还有"档位"（`ParseProfile`）这个维度：`FAST`（快速档，本地解析器，零外部成本，也是全局兜底档）和 `FIDELITY`（保真档，付外部服务成本换版面还原度）。格式和档位是**两个正交维度**——格式由 MIME 唯一确定，档位是"愿意付多少成本换多少保真度"。

**第三，启动自检（selfCheck）。** 这是我最想讲的工程细节：启动时把 23 个对外声明的扩展名（pdf/doc/docx/ppt/pptx/xls/xlsx/csv/md/markdown/txt/text/html/htm/json/xml/rtf/png/jpg/jpeg/svg）逐个探测 MIME，**只要有一个探测出的 MIME 没有被精确认领，直接启动失败**。

> Q3 路由与自检一图看懂：

```text
① 字节探测   MimeTypeDetector.detect(bytes, fileName)
   → 字节语义是唯一权威源，不信任扩展名
   ▼
② 注册表路由  ParserRegistry：(MIME × 档位) → 解析器
   查找四档：精确+请求档位 → 通配+请求档位 → 精确+FAST → 通配+FAST → 抛错
   ├─ 精确键优先于通配键（text/csv 不落 Tika 的 text/*）
   └─ 认不出显式报错，不静默兜底产出垃圾文本
   ▼
③ 启动自检   selfCheck()：23 个扩展名逐个探测
   ├─ 任一探测出的 MIME 无人精确认领 → 启动失败
   └─ 为什么落在"扩展名"不落"MIME"：
        MIME 是探测器的产出，拿它校验它自己恒为真
        漏认领一个没听过的 MIME（Tika 把 .md 探成 text/x-web-markdown）
        只会静默落到通配兜底 → 自检就是要让这种漏认领炸在启动期
```

为什么自检要落在**扩展名**而不是 MIME 上？这是代码里一句很关键的话：**"MIME 是探测器的产出，拿它校验它自己恒为真"**。如果清单写 MIME，那校验的就是"我探测出 A，A 在清单里"，永远通过。真正会漏的是"用户传了个 `.md`，Tika 把它探成 `text/x-web-markdown` 这个没听说过的 MIME，结果静默落到 `text/*` 通配兜底"——自检落在扩展名上，才能在启动期把这种"漏认领"炸出来。

**面试官追问**：Markdown 为什么还要用 commonmark 走 AST？直接按空行或 `#` 切不行吗？

## Q4（追问）Markdown 为什么要走 commonmark AST？结构怎么保住的？

**我：** 因为 Markdown 的"结构"是语法层面的，靠正则或按空行切是猜不准的——`#` 可能是标题也可能是代码块里的一行，表格有对齐分隔线，列表项里还能嵌套代码块和图片。所以用 **commonmark-java 走 AST**，把每个语法节点映射成对应的 Block：

| commonmark 节点 | 产出的 Block | 为什么单独成块 |
|---|---|---|
| `Heading` | `HeadingBlock`（带 level） | 标题是后面章节路径的锚点 |
| `Paragraph` | `ParagraphBlock` | 顶层段落 |
| `FencedCodeBlock` / `IndentedCodeBlock` | `CodeBlock`（带 language） | 代码要按行切、要带围栏 |
| `BulletList` / `OrderedList` | `ListBlock`（带 ordered） | 列表要按项切，不切项中间 |
| GFM `TableBlock` | `TableBlock`（表头+行） | 表格要按行切、KV 化 |
| 内嵌 `<table>` HTML | `HtmlTableBlock` | 保留原始 HTML 表格 |
| 独占一行的图片 | `ImageBlock` | 图片要单独成块 |

三个最容易踩的坑，代码里都专门处理了：

1. **图片必须保留 URL**。注释原话：**"只剩 alt 文本的话，md 里的图在知识库中既不可引用也不可预览"**。所以 `extractInlineText` 里图片保留 `![alt](url)` 完整形式，独占一行的图单独产出 `ImageBlock`。
2. **内嵌 HTML 表格要单独成块**。`HtmlBlock` 是 commonmark 的叶子节点，不接管就静默丢内容；而且 `<table>` 落成段落会被后面按字符硬切，断面停在标签中间。所以 `<table>` 开头单独产 `HtmlTableBlock`。
3. **缩进文本会被识别成代码块**。这是 `txt` 文件也走 `MarkdownDocumentParser`（认领 `text/plain`）的原因——坐席笔记里四个空格缩进的"材料清单"被解析成 `IndentedCodeBlock`，至少拿到了代码块这个结构，比按空行切更贴近原文语义。

> Q4 Markdown AST 一图看懂：

```text
commonmark-java PARSER.parse(text) → AST
   │
   ▼  BlockExtractingVisitor 逐节点映射
Heading ──────────────► HeadingBlock(level)     → 章节路径锚点
Paragraph ────────────► ParagraphBlock          → 顶层段落
Fenced/Indented Code ─► CodeBlock(language)     → 按行切 + 带围栏
Bullet/Ordered List ──► ListBlock(ordered)      → 按项切，不切项中间
GFM Table ────────────► TableBlock(表头+行)     → 按行切 + KV 化
内嵌 <table> HTML ────► HtmlTableBlock          → 保留原始 HTML
独占一行的图片 ────────► ImageBlock             → 保留 URL，单独成块
   ▼
三个坑：
   1. 图片必须留 URL（只剩 alt 文本 → 不可引用不可预览）
   2. 内嵌 HTML 表格单独成块（不接管会丢，按字符切会停在标签中间）
   3. txt 缩进段落→代码块（所以 text/plain 也认领，至少拿到结构）
```

## Q5（追问）Excel 解析怎么做？合并单元格、公式这些坑怎么处理？

**我：** Excel 走 Apache POI（`ExcelDocumentParser`），但它和 Markdown 的坑完全不一样——Excel 的坑是**单元格的"非规范状态"**。核心是把每个 sheet 规范化成一张二维表，产出**一个 `HeadingBlock`（sheet 名）+ 一个 `TableBlock`（表头 + 行）**。

单元格规范化交给 `ExcelTableNormalizer`，四个坑：

1. **合并单元格**：合并后的单元格只有左上角有值，其余是空。不展开，那几列就丢了。要**填充展开**，让每行每列都有值。
2. **多行表头**：`headerRows` 可配（默认 1），多行表头要**展平拼接**成一维表头，否则 KV 化时列名对不上。
3. **超链接**：单元格里的超链接要**内联成 `[text](url)`**，和 Markdown 图片保留 URL 一个道理——只剩显示文本，链接信息就丢了。
4. **公式**：用 `FormulaEvaluator` 求值，**求值失败回退缓存值，再回退公式字符串**——不能因为一个公式算不出来就把整格丢掉。

还有两个容易被忽略但很重要的细节：

- **跳过隐藏 sheet**（`isSheetHidden` / `isSheetVeryHidden`），隐藏的辅助表（比如费率表的中间计算表）不该进知识库。
- **sheet 名走 `HeadingBlock`（H1）而不是自建一套上下文字段**。这个设计很妙：H1 的"顶级重置"语义正好是 sheet 之间的关系——`HeadingHandler` 维护章节路径时，sheet 名自然落到**向量文本前缀、outline 列、ES 的 outline 字段**，不用给 Excel 单独开一条元数据通道。

## Q6（追问）"固定窗口 + 滑动重叠 + 结构感知"三种策略到底怎么落地的？

**我：** 这里我要先讲一个诚实的演进：**早期确实有"策略枚举"（`ChunkerSettings.strategy`），但内核化之后我们把它废弃了。** 原因是代码注释里写得很透的一句话——**"所有解析器都产出结构化 Block，分块一律走 block-aware 分支，策略参数在真实链路上不产生任何差异，被直接丢弃"**。

也就是说，简历里"多种分块策略"不是"用户三选一"，而是**一条结构感知链路上的三个层次**：

```text
简历里的三种"策略"，实际是一条链路的三个层次：

① 结构感知（主策略，全程生效）
   Block 类型 → chunker 查表分发（BlockAwareChunkerDispatcher）
   每个 Block 有专属切法：段落按句切、表格按行切、列表按项切、代码按行切
   + ChunkPacker 按"相邻标题之间"为节打包

② 固定窗口 + 滑动重叠（兜底，只在超长 Block 降级时生效）
   TextSplitter：段落/代码撑破容忍上限才按 maxChars 滑动窗口切
   切点不是下标，是"边界回溯"出来的自然边界（换行/句末标点）

③ 用户唯一可控的自由度 = 预算（ChunkBudget），不是策略
   maxChars / overlapChars / rowsPerChunk / toleranceFactor
   切法由文档结构唯一决定，用户只控制体量与冗余度
```

为什么废弃策略枚举？这是我觉得能体现工程判断力的一点：**当"选哪种策略"这个开关在代码里不产生任何差异时，保留它就是在骗用户——UI 上一个能点的按钮，点了没效果，比没有按钮更糟。** 所以把"策略 + 一堆自由键"收敛成一个 `ChunkBudget`（预算），用户只配三件事：块多大、overlap 多少、表格每块几行。切法交给文档结构自己决定。

这个演进带来的好处：**分块行为可预测、可回归测试**。切法不再依赖用户随机填的策略组合，`ChunkingFixtureTest` 能用固定 fixture（一份 markdown 的三种格式 + 一份 txt + 一份 csv）断言 10 类规则。

## Q7（追问）TextSplitter 固定窗口 + 滑动重叠的具体实现？

**我：** `TextSplitter` 只在一种场景出场：**某个 Block 撑破了容忍上限，必须降级硬切时**（比如一段几百字的超长段落、一个超大代码块）。它做的事是**滑动窗口 + 边界回溯**，核心是不在字符下标处硬切：

```text
TextSplitter.split(text, maxChars, overlapChars)
   ├─ 归一化 normalize()
   │   ├─ 去 \r
   │   ├─ 修复被换行拆开的 URL（https://example.com/lo 换行 gistics → 拼回一行）
   │   ├─ 合并中文词中间的软换行（商\n保通 → 商保通）
   │   └─ 两处绝不合并：跨空行 / 下一行像列表项开头(2. / 10))
   ├─ 滑动窗口切分：每片 maxChars，相邻片重叠 overlapChars
   └─ 切点边界回溯 adjustToBoundary（回溯距离 ≤ overlap）
        换行 → 中文句末标点(。！？) → 英文句末标点(. ! ? 且后接空白)
        → 都找不到才落 targetEnd
```

三个关键点：

1. **边界回溯顺序是"换行 → 中文句末 → 英文句末"**。英文点号必须后接空白或结尾才算边界——否则会把 URL 的域名点（`example.com`）切开。
2. **overlap 有双重身份**：它既是"相邻片重叠多少字符"（防答案被切断），又是**边界回溯的最大距离**。这个很关键——如果 overlap 取太小，回溯找不到句号，切口就落在句子中间。这也是为什么后面 `defaultOverlapFor(maxChars) = maxChars / 8` 按块大小等比给，而不是拍一个固定数。
3. **强制推进防停滞**：如果回溯过头（`end <= start`），直接落到 `targetEnd`，否则会片段重复甚至死循环。

还有个很细的归一化设计：**中文词被软换行拆开要合并**（`商\n保通` → `商保通`），但**两处绝不合并**——跨空行（空行是段落分隔，合并会把图片链接和后面的标题粘连）、下一行像列表项开头（`2.` / `10)`）。这些细节都是纯 `substring` 切分根本不会考虑的，但正是它们决定了切出来的块"语义完整不完整"。

> Q7 TextSplitter 一图看懂：

```text

   ▼
normalize 归一化：
   去 \r │ 修复被换行拆开的 URL │ 合并中文软换行(商\n保通→商保通)
   绝不合并：跨空行（段落分隔）/ 下一行像列表项开头(2. / 10))

   ▼

   换行 → 中文句末(。！？) → 英文句末(.!? 且后接空白/结尾) → targetEnd
   英文点号后接空白才算边界（防切 URL 域名点 example.com）
   ▼

   ① 相邻片重叠（防答案切断）
   ② 边界回溯最大距离（取太小 → 切口落句子中间）
   → defaultOverlapFor(maxChars) = maxChars/8 等比给，不拍固定数
   ▼

```

## Q8（追问）结构感知分块 + 章节打包怎么做的？块大小/overlap 为什么这么选？

**我：** 结构感知分两段：**先按 Block 类型切，再按章节边界打包**。

**第一段，Block 类型分发**（`BlockAwareChunkerDispatcher`）：遍历 Block 列表，`Block 类型 → chunker` 查表，每个 chunker 只切自己那类。切与不切的判据**全类型统一**：整块撑得住 `toleranceChars()`（= `maxChars × toleranceFactor`，封顶 8192）就不切，超出才降级切分，且切点落在结构边界——表格按行、列表按项、代码按行、段落按句末（委托 TextSplitter）。标题块先更新章节路径（`HeadingHandler`）再照常分发。

**第二段，章节打包**（`ChunkPacker`）：以"**相邻两个标题之间**"为一节，把节按体量装配成块。这里有一个反直觉的设计——**不做块级重叠**。为什么？因为切口只落在节边界上，而节边界处没有被切断的句子，重叠是为了防"答案被切断"，既然没切断就不需要。唯一的例外是整节超出容忍上限时的节内切分，那一层的重叠由 TextSplitter 在切段落时负责。

**块大小为什么默认 1024 而不是 512**——这是代码注释里一句我很认同的话：

> **"maxChars 取 1024 而非常见的 512：防语义稀释靠 ChunkPacker 的章节边界而非把块压小；而 RetrieveRequest.topK 默认 5，块太小会让名额被同一章节的碎片占满。"**

也就是说，很多人以为"块越小越精准"，其实块太小会让"同一个章节被切成五六个碎片、把 topK 名额全占满"，反而稀释了召回。我们的思路是**块可以偏大（1024），但边界必须对齐章节**，靠结构感知保证块内语义完整。

> Q8 结构感知分块一图看懂：

```text

   Block 类型 → chunker 查表，切与不切判据全类型统一：
   整块 ≤ toleranceChars(=maxChars×3，封顶8192) → 不切；超出 → 降级切
   切点落结构边界：表格按行 / 列表按项 / 代码按行 / 段落按句末(TextSplitter)
   ▼
第二段：章节打包（ChunkPacker）
   以"相邻两个标题之间"为一节，按体量装配成块
   不做块级重叠：切口只在节边界，节边界处没有被切断的句子
   唯一例外：整节超容忍上限 → 节内切分，重叠由 TextSplitter 负责
   ▼

   防语义稀释靠章节边界，不是压小块
   topK 默认 5，块太小 → 名额被同一章节碎片占满 → 召回稀释

   overlap 不只为冗余，还是 TextSplitter 回溯找句末标点的最大距离

```

表格和列表的切分尤其值得说：`TableChunker` 用 `rowsPerChunk`（默认 50）作**硬上限**，同时按"KV 行渲染后的字符体量"累加到预算——**兼顾宽表不超嵌入上限、窄表不过度碎片化**。`ListChunker` 按**字符体量**（不是项数）贪心分组，因为"项数"是体量的坏代理——十几条词条的清单合起来两百来字，按项数切开后打包器又原样并回来，只在正文里留一串多余空行。

## Q9（追问）content 和 embeddingText 为什么要分离？元数据增强怎么做？

**我：** 这是整条链路里我最看重的一个设计：**展示和检索的目的不同，喂给它们的内容就该不同。**

- `content`（展示原貌）：给人看和回填 LLM 上下文用，必须是**文档原样**，标题按原文位置在正文里。
- `embeddingText`（向量文本）：给嵌入模型用，要**去掉对向量是噪声的东西、补上对召回有用的上下文**。

四个典型差异，全在 `ChunkAssembler` 里装配：

1. **章节路径只拼进向量文本，不拼进展示文本**。同一节切成多块时，只有首块正文自带标题，续块全靠"章节路径前缀"补上下文——但展示文本里标题按原文位置已经在正文里，再拼一份合成前缀等于篡改原文。所以向量文本 = "正文还没覆盖的那截章节路径" + 正文。
2. **表格向量用 `列名: 值`，展示用 markdown 管道表**。因为 markdown 表格靠**位置**对齐列名和值，嵌入模型读不懂位置；KV 化让每格自带列名，向量才学得到"保证金: 20000"这种事实。
3. **图片向量只取描述，去掉 URL**。`ImageChunker` 注释原话：**"图片 URL 进向量是纯噪声，只在无描述时才回落到链接本身"**。展示文本则是"描述 + markdown 图片链接"。
4. **标题向量不带井号**。markdown 标记（`#`）对嵌入模型是零信息 token。

> Q9 content vs embeddingText 一图看懂：

```text
每块存两份，目的不同：
   content(展示原貌)     = 文档原样，回填 LLM / 前端预览
   embeddingText(向量文本) = 去噪声 + 补上下文，给嵌入模型
   ▼

   1. 章节路径只进向量文本：展示里标题已在原文位置，再拼=篡改原文

      （markdown 靠位置对齐，嵌入模型读不懂位置）

   4. 标题：向量不带井号（markdown 标记是零信息 token）

   ① 结构元数据（自动）：outlinePath 章节路径 + provenance 来源 + assets
      ChunkMetadata.toMap() 是全系统唯一序列化点，snake_case
   ② AI 增强（LLM）：EnhancerNode(文档级：上下文/关键词/问题生成/元数据)
                    EnricherNode(块级：关键词/摘要/元数据) → metadata.extras
   ③ 管道元数据（落库）：IndexerNode attachPipelineMetadata

```

**元数据增强分三层**，别混为一谈：

1. **结构元数据（解析/分块自动产生，零成本）**：`outlinePath`（章节路径，Excel 的 sheet 名也走这里）、`provenance`（来源文件 / sheet）、`assets`（图片引用）。`ChunkMetadata.toMap()` 是**全系统唯一的元数据序列化点**——关系库、向量库、关键词索引、图库都调它，新增字段只改这一处，键名统一 snake_case。
2. **AI 增强（LLM 产生，有成本）**：`EnhancerNode` 对整篇文档做（上下文增强、关键词、问题生成、元数据提取），`EnricherNode` 对每个块做（关键词、摘要、元数据）。产物统一进 `metadata.extras`。
3. **管道元数据（落库时注入）**：`IndexerNode` 的 `attachPipelineMetadata` 把 `task_id` / `pipeline_id` / `source_type` / `source_location` 注入每块。

这里还有个工程细节：**块不可变**。AI 增强的产物不是原地改一个自由 Map，而是收集到扩展位后**整块替换**（`withMetadata(withExtras(...))`）——这保证向量（在增强前已算完）和元数据不互相污染，也避免并发下改坏共享状态。

检索命中后，`ChunkMetadataResolver` 把 `chunkId` 批量回表 `t_knowledge_chunk` / `t_knowledge_document`，补 `doc_id` / `chunk_index` / `doc_name`，供上下文按文档聚合、标注来源。

## Q10（追问）效果怎么验证？分块对召回质量的贡献？

**我：** 分两个层面讲：**正确性用回归测试锁死，召回质量用端到端指标验证**。

**第一，正确性——回归测试（fixture 锁死 10 类规则）。** 分块是"切错一点、召回就崩"的逻辑，我们有一组固定 fixture（同一份 markdown 的三种形态 + 一份 txt + 一份 csv），`ChunkingFixtureTest` 断言 10 类规则：章节路径累积与硬边界、表格行分组与表头重复、图片资产随合并保留、代码块三倍容忍与按行降级、长列表按十项分组、长段落句末切点、URL 断行复原、CJK 软换行合并、缩进段落识别成代码块、无标点长文本的强制推进。**切分行为有任何回归，测试先炸。**

**第二，召回质量——端到端指标。** 分块本身我们没有做单独消融（把"结构感知"和"固定字符切"各跑一版的 A/B 没单独出报告），但要诚实讲清**分块和召回质量的关系**：

```text
分块如何影响召回质量：
   块边界对齐语义单元（章节/段落/表格/列表）→ 答案不被切断
   → 检索命中的块"完整可答"，Hit@K 才有意义
   ▼
反面：固定字符切（如每 500 字一刀）
   → 答案被切成两半，任一半都答不了
   → 即便向量相似度命中，faithfulness 也上不去
   ▼
我们的口径：
   端到端离线评测（20 样本冒烟）：Hit@5=100%、Faithfulness 98.2%、Context Precision 95.9%
   分块的结构保留是这些指标的前置条件，不是独立加分项
   诚实讲：没对"分块"单独做消融，但切分正确性用 fixture 回归锁死
```

所以我的口径是：**不编一个"分块策略提升了 X%"的假数字**，而是说清楚两件事——①切分正确性由回归测试兜底；②结构感知分块是"Hit@K / Faithfulness"这些召回质量指标能上去的**前置条件**。因为如果切分把答案切碎了，后面检索、重排做得再好也召回不到一个完整的答案。

如果面试官追"块大小有没有对比过"，我给业界共识的定性结论：**块太小（如 256/512）→ 语义碎片化、topK 名额被同章节碎片占满、上下文里噪声多；块太大（如 2000+）→ 语义被稀释、甚至超嵌入模型输入上限（我们硬约束 `MAX_CHARS_LIMIT=8192`）**。我们选 1024 + 结构感知打包，是"块偏大但边界对齐章节"的折中——块大小是**目标不是硬上限**，结构边界才是真正的切口。

## 📋 面试建议（对真实面试的 3 条建议）

1. **把"策略枚举废弃"讲成亮点，而不是露怯**。简历写"多种分块策略"，但代码里 `strategy` 已废弃、切法由文档结构唯一决定。这恰恰是区分度最高的一句话——大多数候选人会照着简历念"我实现了固定窗口、滑动重叠、结构感知三种策略"，而你能说"早期有三选一的枚举，后来发现它在真实链路上不产生差异，就废弃了、收敛成预算驱动"——**这体现的是"敢于删掉无意义配置"的工程判断力**，比报策略名高级得多。Q6 一定要练顺。
2. **主动讲"为什么/代价/兜底"，别报类名流水账**。文档解析最容易答成"我用了 Tika、POI、commonmark"。高分答法是每个选择都有理由：Tika 为什么只兜底（平文本丢结构）、图片为什么留 URL（不留不可引用）、表格为什么 KV 化（嵌入模型读不懂位置对齐）、overlap 为什么 128（同时是回溯距离）。这些"为什么"里藏着你对 RAG 召回质量的理解。
3. **两个 ⚠️ 口径提前想清楚**：①**域**——逐字稿示例用了保险域（条款 PDF / 费率表 Excel / 理赔指南），但回归测试 fixture 是电商"商家手册"，如果面试官追问"你测试用的什么文档"，如实说"用同一份 markdown 的三种形态（md/docx/pdf）+ txt + csv 做跨格式回归"，别把 fixture 内容说成保险条款。②**效果**——分块没有独立消融报告，端到端指标（Hit@5=100%、Faithfulness 98.2%）是 20 样本冒烟测试不是 150 全量，被追问数字时主动说清口径，别把"前置条件"吹成"独立提升 X%"。
