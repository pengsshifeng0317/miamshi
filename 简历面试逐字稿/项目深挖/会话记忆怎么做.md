## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你的会话记忆是怎么做的？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（并行加载 / 窗口存储 / 摘要触发与增量 / 合并式防遗忘 / 并发防重 / 失败兜底）正好接 Q2 / Q3 / Q4 / Q5 / Q6 / Q7。

**我：** 我们做会话记忆，是因为 LLM 本身无状态、每轮都是"从零开始"——多轮对话丢指代（"那保险系统呢"没法消解）、历史无限堆会撑爆窗口涨成本。所以加了这一层，一句话：**滑动窗口保留最近 8 轮原文 + 更早历史用 LLM 滚成 ≤200 字摘要 + PostgreSQL 持久化**，让模型永远带着"背景 + 近期"上下文作答。

核心是四件事：

**第一，滑动窗口保留原文。** 最近 8 轮（16 条 user/assistant 消息）原文直读 PostgreSQL 的 `t_message`，近期的指代消解靠它；更早的历史不再全量进 prompt，从根上控住 token 和注意力。

**第二，更早历史异步滚摘要。** 写回消息时只有 ASSISTANT 触发 `compressIfNeeded`，交给独立的 `memorySummaryExecutor` 异步跑、不阻塞响应；用 `last_message_id` 做增量游标不重复摘，旧摘要 ∪ 新消息合并式压缩（≤200 字），"重叠滑出才重摘"降频。

**第三，读路径并行加载。** `load()` 用 `memoryLoadExecutor` 把"最新摘要"和"窗口历史"并行查出来，摘要包成 SYSTEM 消息放最前（先背景后近期），历史做 `normalizeHistory` 防 assistant 开头、剥引用角标，再拼进 prompt。

**第四，并发防重 + 失败兜底。** 摘要任务拿 Redisson 分布式锁，同一会话同一用户只有一个摘要线程在跑；加载或摘要任一环节失败都降级——没摘要就只带历史、摘要失败保留旧摘要，绝不阻断正常问答。

> 📦 涉及的表（面试官问"表怎么设计的"时展开，平时不用全背）：
>
> | 表 | 用途 | 关键字段 |
> |----|------|---------|
> | `t_conversation` | 会话列表，一条会话一行 | `conversation_id`+`user_id` 唯一；`title` 存首个用户问题；`last_time` 最近活跃时间 |
> | `t_message` | 消息原文——窗口历史读取、append 写回都在这 | `role`(user/assistant)、`content` 正文；`thinking_content`/`thinking_duration`；`sources`/`retrieved_chunks`(JSONB)；`reply_to_message_id`、`message_status` |
> | `t_conversation_summary` | 会话摘要表，与消息表分离存储 | `content` 存 ≤200 字合并摘要；`last_message_id` 增量游标（摘要到哪条为止，防重复摘） |

## Q1（开场总览）介绍一下你的会话记忆管理机制？为什么需要记忆这一层？

**我：** 先说为什么做——LLM 本身是无状态的，每轮对话都是"从零开始"。两个问题直接暴露：

1. **多轮丢失**：用户问完"OA 系统数据安全怎么做"再问"那保险系统呢"，如果第二轮不带历史，"保险系统呢"就是废句——指代消解无从谈起。这个问题在改写层就要靠历史解决（我的问题重写模块 Q6 讲过）。
2. **上下文失控**：对话越长历史越长，全塞进 prompt 会撑爆窗口、token 成本线性涨、注意力被稀释、首字延迟变高。

所以做了**会话记忆层**，核心策略一句话：**滑动窗口（最近 8 轮保留原文）+ LLM 摘要压缩（更早历史滚成 ≤200 字摘要）+ PostgreSQL 持久化**。

> 两层记忆架构先看这张图：

```text
┌─ 会话记忆（管"跨轮"）─────────────────────────────────┐
│  写路径（append → 存储 + 摘要）：                       │
│  append(消息) → 滑动窗口（最近 8 轮=16 条，保留原文）       │
│       └─ 触发 compressIfNeeded（仅 ASSISTANT 触发）     │
│             ├─ 异步 memorySummaryExecutor（不阻塞响应）  │
│             ├─ 增量游标 lastMessageId（不重复摘）        │
│             ├─ "重叠滑出才重摘"（摘窗口前半段，降频）      │
│             └─ 合并式摘要（旧摘要∪新消息，≤200字）        │
│                    │ Redisson 分布式锁防重复摘要         │
│                    ▼                                  │
│              PostgreSQL 持久化                         │
│                                                      │
│  读路径（load → 拼接进 prompt）：                       │
│  load() → 并行加载摘要 + 历史（memoryLoadExecutor）      │
│        ├─ 摘要放最前，包成 SYSTEM 消息（先背景后近期）    │
│        └─ normalizeHistory（防 assistant 开头）        │
│              └─ 引用角标剥离（防污染当前轮编号）          │
│                    ▼                                  │
│        摘要 + 窗口历史 → 拼进 prompt                    │
└──────────────────────────────────────────────────────┘
   │
┌─ Agent 记忆（管"轮内多步"）────────────────────────────┐
│  ReAct 循环：思考 → 调工具 → 看结果                      │
│  上下文 > 20KB → AgentContextTrimmer                  │
│    ├─ 只替换 tool_result 为占位（不动 tool_use）        │
│    ├─ 白名单 evictableTools=[search_knowledge]         │
│    ├─ 循环保护：本轮 + 最近 2 个已完循环全保              │
│    └─ 最小回收量不足 20% 整次不动（保模型缓存）            │
└──────────────────────────────────────────────────────┘
```

再往上还有一层 **Agent 记忆**（ReAct 模式）：单轮内多步工具调用的上下文压缩（把过老的工具结果换成占位说明）。所以我是**两层记忆**：会话层管"跨轮"，Agent 层管"轮内多步"。后面会分别讲。

**面试官追问**：load 的时候摘要和历史怎么拼到一块的？为什么摘要放最前面？

## Q2（追问）load 的并行加载和拼接逻辑

**我：** `DefaultConversationMemoryService.load`：

- **并行加载**：摘要和历史各用一个 `CompletableFuture` 提交到独立线程池 `memoryLoadExecutor`，`allOf` 等两者都回来再拼——摘要和历史互不依赖，没必要串行等。

> Q2 load 一图看懂：

```text
DefaultConversationMemoryService.load()
   │
   ▼
并行加载（memoryLoadExecutor）
   ├─ CompletableFuture A → 摘要
   └─ CompletableFuture B → 历史
   └─ allOf 等两者都回来再拼（互不依赖，不串行）
   ▼
拼接 attachSummary
   ├─ 摘要放历史最前面
   └─ decorateIfNeeded 用 summary-wrapper 包成 SYSTEM 消息
      → 按对话时间序最先出现，先背景后近期
   ▼
双路 fallback
   ├─ 摘要失败 → 返回 null，只给历史
   └─ 历史失败 → 空列表
   = 任何一路挂都不拖垮整条对话记忆
```
- **拼接**：`attachSummary` 把摘要**放在历史最前面**，并且 `decorateIfNeeded` 用 `context-format.st` 的 `summary-wrapper` 段包成一条 **SYSTEM 消息**。为什么放最前？因为摘要承载的是"更早的全局信息"，按对话时间顺序应该最先出现，模型按顺序消费上下文，先看到背景再看到近期对话最自然。
- **双路 fallback**：摘要有失败就跳过（返回 null，只给历史），历史有失败就给空列表——**任何一路挂了都不能把整条对话记忆拖垮**。

**面试官追问**：滑动窗口的"8 轮"具体怎么算？存储层怎么保证拿到的历史是规整的？

## Q3（追问）滑动窗口的存储实现（JdbcConversationMemoryStore）

**我：** 存储层 `JdbcConversationMemoryStore`，直读 PostgreSQL 的对话消息表（JDBC 直读，所以 `refreshCache` 是空实现——不走缓存，保证读到的就是最新的）。

几个关键细节：

1. **轮数的换算**：`historyKeepTurns=8` 是"轮"，一轮 = user + assistant 两条，所以取 `maxMessages = 8 * 2 = 16` 条，DESC 排序。

> Q3 滑动窗口存储一图看懂：

```text
JdbcConversationMemoryStore（JDBC 直读 PG，不走缓存
   → refreshCache 空实现，保证读到最新）
   │
   ▼
① 轮数换算
     historyKeepTurns=8 轮 → maxMessages = 8×2 = 16 条，DESC 排序
     （一轮 = user + assistant 两条）
   ▼
② normalizeHistory（防 assistant 开头）
     跳过开头连续的 ASSISTANT 消息
     └─ 原因：摘要压缩后窗口首条可能是上一轮回答残留
        直接塞 prompt → 模型"先看回答再看问题"，上下文是碎的
        （这个坑不踩的人会直接踩进 prompt 里）
   ▼
③ 引用角标剥离
     ASSISTANT 消息做 CitationMarkup.strip
     └─ [1](#cite-1) 是给当前轮引用用的
        历史旧角标留着会污染当前轮的引用编号
   ▼
④ USER 消息触发会话更新
     append 时 USER 消息 → createOrUpdate lastTime
     → 会话列表按最后活跃排序
```
2. **normalizeHistory（防 assistant 开头）**：从 DB 取回来的历史，**跳过开头连续的 ASSISTANT 消息**。为什么会有 assistant 开头？因为摘要压缩后，窗口里的第一条可能是上一轮 assistant 的回答残留，直接塞进 prompt 会让模型"先看到回答再看到问题"，上下文是碎的。这个坑不踩的人会直接踩进 prompt 里。
3. **引用角标剥离**：加载历史时对 ASSISTANT 消息做 `CitationMarkup.strip`，把 `[1](#cite-1)` 这种回答内联角标剥掉——角标是给**当前轮**引用用的，历史里的旧角标留着会污染当前轮的引用编号。
4. **USER 消息触发会话更新**：append 时如果是 USER 消息，顺便 `createOrUpdate` 会话的 `lastTime`，让会话列表按最后活跃排序。

**面试官追问**：摘要什么时候触发？是不是每次加消息都要重摘要？那成本不得爆炸？

## Q4（追问）摘要的触发与增量控制

**我：** 这是整个模块设计最密的地方，`JdbcConversationMemorySummaryService`：

- **触发点**：`append` 之后调 `compressIfNeeded`。两个前置条件：①`summaryEnabled` 开关（默认关，是可选优化）；②**只有 ASSISTANT 消息触发**——用户消息只是被追加，不动摘要（用户消息频繁、无合成价值）。
- **异步执行**：`CompletableFuture.runAsync` 丢到独立线程池 `memorySummaryExecutor`，**不阻塞响应**——摘要再慢也不影响首字延迟。
- **阈值门槛**：`countUserMessages >= summaryStartTurns(9)` 才开始生成——8 轮窗口内的对话不值得摘要（原文都在窗口里，摘了也白摘）。
- **增量 + 游标**：摘要表每条带 `lastMessageId` 游标。下次生成从**上次摘要结束的位置之后**（`afterId`）开始取，不重复摘已摘过的内容。
- **"摘要覆盖约一半原文窗口"**（关键）：`resolveSummaryCutoffId` 取的是最新窗口**正中间那条消息的 id**——即本次摘要只摘"窗口前半段"，留后半段与下次重叠。为什么？注释写得很透：**只有这段重叠滑出窗口后才再次生成摘要**。否则每次 append 都重摘，LLM 调用次数随轮数线性涨——用"重叠滑出"把摘要频率降到 `窗口/2` 一次。

> Q4 摘要触发与增量一图看懂：

```text
append → compressIfNeeded
   │
   ▼
前置条件
   ① summaryEnabled（默认关，可选优化）
   ② 只有 ASSISTANT 消息触发
      （USER 消息只是被追加，不动摘要——频繁、无合成价值）
   ▼
异步执行 CompletableFuture.runAsync → memorySummaryExecutor
   └─ 不阻塞响应（摘要再慢也不影响首字延迟）
   ▼
阈值门槛：countUserMessages >= summaryStartTurns(9) 才生成
   └─ 8 轮窗口内的对话不值得摘（原文都在窗口里，摘了白摘）
   ▼
增量 + 游标：摘要表每条带 lastMessageId
   → 下次从 afterId 开始取，不重复摘已摘内容
   ▼
★ 摘要覆盖约一半原文窗口
   resolveSummaryCutoffId = 最新窗口正中间那条消息的 id
   → 本次只摘"窗口前半段"，留后半段与下次重叠
   → 只有这段重叠滑出窗口后才再次生成
   = 摘要频率降到 窗口/2 一次
   （否则每次 append 都重摘，LLM 调用随轮数线性涨）
```

## Q5（追问）合并式摘要——防止"摘要遗忘"

**我：** 这是摘要模块最有讲究的地方：**不做"只摘新消息"，而是"旧摘要 + 新消息合并去重"**。

> Q5 合并式摘要一图看懂：

```text
summarizeMessages —— 不"只摘新消息"，做"旧摘要 + 新消息合并去重"
   │
   ▼
三部分塞给 LLM
   ① system：摘要 prompt（约束 summary_max_chars=200）
   ② 旧摘要：以 assistant 消息传入 + 关键约束
      "历史摘要仅用于合并去重，不得作为事实新增来源；
       若与本轮对话冲突，以本轮对话为准"
   ③ 新对话：本次 afterId ~ cutoffId 之间要摘的消息
   ▼
user 要求：合并以上对话与历史摘要，去重后输出更新摘要
   严格 ≤200 字符；仅一行
   ▼
三个设计意图
   ① 合并去重：新摘要 = 旧摘要 ∪ 新信息，不丢旧事实
   ② "不得作为事实新增来源"：防"摘要自证"
      （摘要里编的"用户是北京客户"被当事实传给下一代
       = 逐代放大的"谣言滚雪球"）
   ③ "冲突以本轮为准"：旧说 A 本轮说 B → 以 B 为准
      （新信息优先，避免旧的错误/过时信息压过新事实）
   ▼
参数：temperature 0.3 / topP 0.9（比分类高，允许归纳多样性）/ FAST 档
   摘要带 lastMessageId 存回 ConversationSummary 表
```

`summarizeMessages` 把三部分塞给 LLM：
1. **system**：摘要 prompt（约束 `summary_max_chars=200`）。
2. **旧摘要**：以 **assistant 消息**形式传入，附带一句关键约束：**"历史摘要（仅用于合并去重，不得作为事实新增来源；若与本轮对话冲突，以本轮对话为准）"**。
3. **新对话**：本次 `afterId ~ cutoffId` 之间要摘的消息。

最后 user 消息要求："合并以上对话与历史摘要，**去重后输出更新摘要**。要求：严格 ≤200 字符；仅一行。"

三个设计意图：
- **合并去重**：新摘要 = 旧摘要 ∪ 新信息，不丢旧事实。
- **"不得作为事实新增来源"**：旧摘要只能当"合并的背景"，不能因为旧摘要里写了"用户是北京客户"就继续保留——那是防止**摘要自证**（摘要里编的东西被当事实传给下一代摘要，逐代放大的"谣言滚雪球"）。
- **"冲突以本轮为准"**：旧摘要说 A、本轮对话说 B，以本轮 B 为准——**新信息优先**，避免旧的错误/过时信息压过新事实。

参数上：temperature 0.3、topP 0.9（比分类任务高一点，允许一定归纳多样性）、FAST 档省钱。摘要结果带 `lastMessageId` 存回 `ConversationSummary` 表。

**面试官追问**：多端同时发消息，会不会并发重复摘要？

## Q6（追问）并发控制——Redisson 分布式锁

**我：** 会，而且是真实风险：`append` 是高频的，如果同一会话两端同时触发 `compressIfNeeded`，两边都会去摘同一段消息、写两条摘要。所以：

- 用 **Redisson 分布式锁**，key = `ragent:memory:summary:lock:{userId}:{conversationId}`。

> Q6 分布式锁一图看懂：

```text
风险：同一会话两端同时触发 compressIfNeeded
   → 两边都去摘同一段消息、写两条摘要（append 高频）
   ▼
解法：Redisson 分布式锁
   key = ragent:memory:summary:lock:{userId}:{conversationId}
   ▼
tryLock() 失败 → 直接 return 跳过（不做阻塞等待）
   └─ 摘要本来就是"尽力而为"的优化
      拿不到锁 = 另一节点正在做 → 没必要等，放弃本次
      等下次 append / 窗口滑出后再摘，结果一样
   ▼
任务整体 exceptionally 兜底打 error 日志，不抛给调用方
   ▼
这个锁值不值？
   值——摘要涉及"读消息区间 + 写摘要表" = 非原子读改写
   不锁就重复摘要
   锁的粒度必须细（按会话，key 带 conversationId）
   → 不会互相阻塞不同会话
```
- **`tryLock()` 失败直接 return 跳过**——不做阻塞等待。为什么？摘要本来就是"尽力而为"的优化，拿不到锁说明另一个节点正在做，我**没必要等它**，直接放弃这次触发，等下一轮 append 或窗口滑出后再摘，结果一样。
- 摘要任务整体 `exceptionally` 兜底打 error 日志，不抛给调用方。

这里我顺带讲一个判断：**分布式锁用在这里值不值**？值得——因为摘要涉及"读消息区间 + 写摘要表"，是个**非原子读改写**，不锁就会出现重复摘要；但锁的粒度必须细（按会话），key 里带了 conversationId，所以不会互相阻塞不同会话。

## Q8（追问）Agent 层记忆（ReAct 上下文压缩）

**我：** 这是另一套东西，管的是 **Agent（ReAct）模式**下"单轮内多次工具调用的上下文"。ReAct 一轮对话里，Agent 会多次思考→调工具→看结果，工具结果（尤其 `search_knowledge` 检索出来的长证据）**占上下文字节的一半**，多步后上下文暴涨。全塞进去 token 爆炸，全砍掉这轮的推理就废了。

`AgentContextTrimmer` 的解法是**只替换、不删除**：

> Q8 Agent 层压缩一图看懂：

```text
问题：ReAct 单轮内多次 思考→调工具→看结果
   工具结果（尤其 search_knowledge 长证据）占上下文字节一半
   多步后上下文暴涨 → 全塞 token 爆炸 / 全砍推理废
   ▼
AgentContextTrimmer：只替换、不删除
   ① 过老工具结果 → 等长占位文案
      "[历史工具结果已省略，原长 X 字符]"
      不动 tool_use → 永不产生孤儿结果块
      （tool_use 还在、结果没了 → 模型行为错乱）
   ② 触发按体量：总字符 > triggerChars(20000) 才动手
      （线上最长会话十余条，条数不敏感，体量才敏感）
   ③ 循环保护：本轮开启的循环 + 最近 keepRecentCycles(2) 全保
      （绝不裁掉模型本轮自己查的证据）
   ④ 最小回收量：< totalChars×clearAtLeastRatio(0.2) → 整次不动
      （清理总从最早循环下手、作废几乎整份前缀
        → 每轮改写前缀 = 模型侧 prompt 缓存失效 = 每轮重新计费）
   ⑤ 白名单而非黑名单：evictableTools=["search_knowledge"]
      （MCP 工具副作用无法静态判定，黑名单=默认可裁
       = 会把有副作用的工具结果裁掉）
   ⑥ 等长原位替换：先全重建再统一提交
      （重建抛异常时上下文一个字节没动
       → 无"库里是占位、模型看到原文"的不一致）
   ▼
实现：AgentContextCompactionMiddleware 挂在推理前 onReasoning
   每次推理前裁剪、失败走原列表（省上下文不值得赔这轮对话）
   按引用逐条替换上行消息（整体覆盖会抹掉框架人设消息）
   状态持久化 PostgreSQL（PgAgentStateStore）
```

- **把过老的工具结果换成等长占位文案**：`[历史工具结果已省略，原长 X 字符]`，不动 `tool_use`——所以**永远不会产生孤儿结果块**（tool_use 还在、结果没了会导致模型行为错乱）。
- **触发按体量**：总字符 > `triggerChars(20000)` 才动手，不是按消息条数——因为线上最长会话才十余条，条数不敏感，体量才敏感。
- **循环保护**：按"工具循环"切分（带 tool_use 的 assistant 消息开启、用户消息闭合），**本轮开出的循环 + 最近 `keepRecentCycles(2)` 个已完成循环全保**——绝不裁掉模型本轮自己查的证据。
- **最小回收量**：可回收量不足 `totalChars × clearAtLeastRatio(0.2)` 就**整次不动**。为什么？清理总是从最早的循环下手、作废的是几乎整份前缀，**每轮都改写前缀会把模型侧 prompt 缓存打废**（上下文前缀变了，缓存失效，每轮都重新计费）——宁可这轮不省，也不为几百字符把缓存作废。
- **白名单而非黑名单**：`evictableTools=["search_knowledge"]`——MCP 工具集由意图树运行期决定，副作用无法静态判定，**不能用黑名单**（黑名单=默认可裁，会把有副作用的工具结果裁掉），只能用白名单（默认不可裁，只裁明确安全的）。
- **等长原位替换**：先全部重建再统一提交——重建阶段抛异常时上下文一个字节没动，不会出现"库里是占位、模型看到的是原文"的不一致。

Agent 状态本身持久化到 PostgreSQL（`PgAgentStateStore`），配合这个中间件做到"Agent 长会话也能跑"。实现上是 `AgentContextCompactionMiddleware` 挂在推理前的 `onReasoning`，**每次推理前裁剪、失败走原列表**（省上下文不值得赔上这轮对话），并且按引用逐条替换上行消息（整体覆盖会把框架挂的人设消息抹掉）。

## Q11（业界）Claude 的记忆系统架构

## Q12（业界）MemGPT / Letta 的分层记忆（OS 类比）

**我：** MemGPT 用**操作系统分页**类比 LLM 记忆，思路非常巧：

- **main context = 内存（RAM）**：模型推理时真正看得到的上下文，类比"工作内存"。
- **external context = 外部存储（磁盘）**：向量库 / PG 等，类比"磁盘"，装不下但都存着。
- **LLM 本身是操作系统**：由 LLM 自己决定**什么时候把信息换出内存（归档）**、什么时候**从磁盘换入（检索）**——通过特殊工具调用触发（如 `memory_append`、`memory_search`、`memory_replace`）。
- **核心记忆（core memory）**：用户的身份、长期目标等"绝不能丢"的块，永远驻留内存。

和我的项目对比：滑动窗口 ≈ main context，摘要压缩 ≈ "换出"的动作，PostgreSQL ≈ external context。**差别在于"换出/换入"的决策者**：项目里是**固定规则**（轮数/字符数阈值），MemGPT 是 **LLM 动态决策**。固定规则可预期、成本可控；LLM 决策更聪明但更难测。对生产系统我倾向规则为主 + 少量 LLM 决策（我们的摘要合并去重就是"LLM 决策"与"规则触发"的结合）。

> Q12 MemGPT 分页一图看懂：

```text

   main context      = 内存(RAM)     模型推理真正看到的上下文
   external context  = 外部存储(磁盘) 向量库/PG，装不下但都存着
   LLM 本身          = 操作系统      自己决定何时换出/换入
```

## Q13（业界）向量检索式记忆（Mem0 / Zep）怎么做？

**我：** 这是"检索式记忆"的成熟实现，我以 Mem0 为例：

- **不是把原文存起来检索，而是抽取"事实"**：每轮对话后，LLM 从对话里抽取结构化事实（用户的偏好、身份、已确认的事实），如"用户偏好年金险""用户是平安员工"。
- **去重 + 冲突消解**：新抽取的事实与库里已有事实比对，重复的合并、冲突的按"新信息优先"（和我的摘要"冲突以本轮为准"思想一致）。
- **向量存储 + 检索**：事实 embedding 进向量库，新对话开始时检索最相关的 N 条注入 prompt。
- **收益**：跨会话长期记忆、不受窗口限制、能回答"我之前问过什么"这类问题。
- **代价**：抽取有成本（每轮一次 LLM）、检索可能召回错事实、事实级记忆丢失对话上下文（只记事实不记推理过程）。

**对我们项目的启示**：如果给项目升级，最自然的是"摘要语义化"——把当前"≤200 字压缩文本摘要"升级为"结构化记忆块"（按 Mem0 方式抽取用户偏好/身份），这样既保留摘要的低成本，又获得跨会话的能力。这是我想过的下一步。

> Q13 Mem0 一图看懂：

```text
Mem0：不是存原文检索，而是抽取"事实"
   ① 每轮后 LLM 抽取结构化事实
      用户偏好/身份/已确认事实
      如"用户偏好年金险""用户是平安员工"
   ② 去重 + 冲突消解
      新事实 vs 库内已有 → 重复合并、冲突按"新信息优先"
      （和我的摘要"冲突以本轮为准"思想一致）
   ③ 向量存储 + 检索
      事实 embedding 进向量库
      → 新对话开始召回最相关 N 条注入 prompt
   ▼
收益：跨会话长期记忆 / 不受窗口限制 / 能答"我之前问过什么"
代价：抽取每轮一次 LLM / 检索可能召回错事实
     事实级记忆丢失对话上下文（只记事实不记推理）
   ▼
对我们项目的启示：摘要语义化
   把"≤200字压缩文本摘要"升级为"结构化记忆块"
   → 保留摘要低成本 + 获得跨会话能力（我想过的下一步）
```

## Q14（业界）长上下文模型（1M token）出现后，还需要记忆压缩吗？

**我：** 我的观点是**要，而且更要想清楚"为什么压缩"**。长上下文解决的是"塞不下"，但暴露三个问题：

1. **成本**：token 按量计费，1M 窗口装得下不等于花得起——记忆管理本质是"用最少的 token 拿到最相关的信息"。
2. **注意力稀释**：业界有"lost in the middle"现象，超长上下文里中间部分信息召回显著下降——装得下、但模型"看不见"。
3. **延迟**：首字延迟随输入 token 涨。

所以业界不是"长上下文替代压缩"，而是**长上下文扩大兜底 + 压缩控制成本**：窗口可以大（兜底不漏），但仍要压缩（控制账单和精度）。Claude Code 的做法就是这个逻辑——单会话长上下文靠自动总结，而不是无限撑大。**上下文工程的本质不是"把窗口撑大"，而是"让该进来的进来、不该进来的不进"。**

## Q15（业界）如果让你给项目的记忆模块设计一次升级，优先做什么？

**我：** 我会排三个候选，按"性价比"排序：

1. **首选：结构化记忆块（Mem0 式抽取）**——在现有摘要链上，让摘要输出从"压缩文本"升级为"结构化字段"（用户身份/偏好/已确认事实/未解决问题）。成本最低（复用现有 append 后的异步链 + 现有 LLM 调用），收益最大（记忆从"可读"变"可用"，能支撑个性化）。
2. **次选：跨会话记忆检索**——把结构化记忆块 embedding 存向量库，新会话开始时召回注入。这是对"当前只有会话内记忆、跨会话不记得用户"的直接补强。
3. **再考虑：MemGPT 式动态换页**——LLM 决定何时换出/换入。这个最"酷"但最难测，我会等前两步跑出数据、确认记忆调用路径稳定后再上。

## 📋 面试建议（对真实面试的 3 条建议）

1. **主动把"没指标"转化成"有工程判断"**。这模块简历没写数字，面试官第一反应可能是"这模块是不是简单"。你的反击是 Q9 的"成本/正确性/可用性"三维 + "摘要默认关"的清醒定位——**用工程决策的质量代替指标的缺失**，这是高级候选人的答法。
2. **"两层记忆"是别人没有的认知**。大多数候选人只聊过"窗口"或"摘要"其中一个，你能同时讲会话层（跨轮）和 Agent 层（轮内多步），并点出"Agent 层为什么只能替换不能删除""为什么用白名单不用黑名单"，区分度极高——这些是真实实现里才有的坑。
3. **业界 5 问务必先声明边界**。Q10~Q15 是"视野题"，回答前先说"项目里做的是窗口+摘要，下面是我对业界方案的了解"，再输出。**主动划清"我做的"和"我了解的"**，比含糊其辞更可信，也防止面试官顺着业界名词深挖到项目里不存在的实现。
