## 1. 项目概述

寿险问题五花八门：产品咨询、条款解读、查保单、甚至寒暄。如果让大模型直接回答，它不知道"该去哪个知识库、该不该调工具"。所以平台的核心思路是：

**先路由、再检索、后生成**——意图定范围（去哪些库）、多路做召回（用哪些模态）、RRF 排名融合、Rerank 精排、证据闸门把关、LLM 生成，全程被分布式限流与评测体系护航。

```text
一句话架构：意图路由 → 问题重写 → 多路检索 → 证据把关 → 工具增强 → 流式生成
                                    ↕
                      会话记忆（滑动窗口 + 增量摘要）
                                    ↕
                    分布式限流 + RAGAS 评测（质量与稳定双保险）
```

### 1.1 需要解决的核心问题

| 问题 | 对应模块 |
|---|---|
| LLM 无状态，多轮对话丢历史、上下文失控 | 会话记忆 |
| 问题该去哪个库 / 该不该调工具 | 意图识别树 |
| 口语噪音、术语不对齐、多轮省略、复合问句 | 问题重写与子问题拆分 |
| 单路向量检索有语义盲区、无兜底 | 多路检索引擎 |
| 外部业务能力（天气/销售数据/工单）不该写死在链路里 | MCP 工具接入 |
| 多实例部署下并发失控、单机限流失效 | 分布式限流 |
| 链路多段参数改了不知好坏，上线靠运气 | RAGAS 评测体系 |

## 4. 核心模块技术架构

### 4.1 会话记忆（会话层）

**职责**：解决 LLM 无状态——多轮丢失 + 上下文失控。

**架构图**：

```text
┌─ 会话记忆层（rag/core/memory/ + agent/memory/）───────────────┐
│  工作记忆 = 滑动窗口（最近 8 轮保留原文，≈16 条消息）             │
│  情景记忆 = 更早历史压缩成 ≤200 字摘要                          │
│  持久化   = PostgreSQL（消息 + 摘要表）                        │
└────────────────────────────────────────────────────────────┘
  写入流程：
  用户消息 ──► 消息入库（游标 lastMessageId）──► 窗口滑出时
             ──► LLM 增量摘要（合并式，≤200字）──► 覆盖最久历史
  读取流程：
  组装 prompt 前 ──► 读最近 8 轮原文 + 旧摘要 ──► 注入上下文
```

**关键机制**：

- **滑动窗口 8 轮**：保留原文当工作记忆，够用且控上下文成本。
- **增量游标 `lastMessageId`**：只对新产生的消息做增量摘要，不做全量重算。
- **重叠滑出才重摘**：只有某条消息真正滑出窗口才触发新一轮摘要，避免每轮都压缩。
- **合并式摘要**：新摘要 = 旧摘要 + 本轮新内容压缩，冲突以本轮为准（防"摘要自证"）。
- **Redisson 分布式锁**：并发时 tryLock 失败即放弃，不阻塞主链路。
- **Agent 层 `AgentContextTrimmer`**：只替换 `tool_result`、白名单 `evictableTools`，不污染系统提示词。
- **线程池隔离**：`memoryLoadExecutor` / `memorySummaryExecutor` 读写分离，不占用检索/生成线程。

### 4.2 意图识别树（意图层）

**职责**：把"路由"做在检索前面——决定该去哪个知识库、该不该调工具。

**架构图**：

```text
                   用户问题
                      │
                      ▼
         ┌── 规则层（快路径）──┐
         │ 关键词/正则匹配命中？ │
         └──────┬───┬────────┘
           命中  │   │  未命中
                ▼   ▼
          ┌────────────────┐
          │ 三层树逐层下钻    │      DOMAIN（业务系统/产品线）
          │ DOMAIN→CATEGORY │  →   CATEGORY（产品咨询/条款解读/保单）
          │    →TOPIC       │  →   TOPIC（重疾险/年金险…）
          └────────────────┘
                │
                ▼
       ┌── LLM 兜底（可选）──┐
       │ 输出(域/类/主题)+置信度 │
       └──────┬───┬────────┘
         高置信│   │低置信
              ▼   ▼
        采用意图   澄清追问（澄清后可再进一次）
              │
              ▼
        路由到知识库 / MCP 工具
```

**关键机制**：

- **三层树**：`DOMAIN → CATEGORY → TOPIC`，比"普通多分类"多了层级——子类可继承父类规则、错误可在上层被兜住。
- **规则层先行**：关键词/正则快路径，命中率高、零延迟、可解释；没命中才走 LLM，控制成本与抖动。
- **置信度门槛**：LLM 低置信不硬答，进入澄清追问（决策树：是否必须、是否够信息），减少误导。
- **规则与 LLM 双层兜底**：规则兜 LLM 的漂移，LLM 兜规则的盲区。

### 4.3 问题重写与子问题拆分（改写层）

**职责**：用户问题和"拿来检索的查询"是两回事——口语噪音、术语不对齐、多轮省略、复合问句都直接命中检索。

**架构图**：

```text
用户问题（可能带 2 轮历史）
   │
   ▼
① 术语归一化（规则）
   口语噪音清洗 / 术语对齐（"平安保司"→"平安人寿"）
   │
   ▼
② LLM 改写 + 拆分（主力）
   改写后的主问题 rewrittenQuestion
   + 子问题列表 subQuestions（capTotalIntents ≤ 3）
   │   LLM 失败 / 超限
   ▼
③ 规则拆分（兜底）
   按顿号/逗号/连词拆，主问截断改写
   │
   ▼
返回 RewriteResult → 主问 + 每个子问题分别走检索
```

**关键机制**：

- **三层流水线**：规则归一化（快、稳）→ LLM 改写拆分（准、可处理复合）→ 规则拆分（兜底，保证一定有结果）。
- **四条红线**：改写后不改变原意、不新增知识、不丢失关键实体、子问题数有上限。
- **`capTotalIntents≤3`**：意图总量硬上限，防子问题爆炸撑爆检索预算。
- **多轮历史限 2 轮**：只取最近两轮做指代消解，够用且省 token。
- **四级防线**：LLM 输出结构校验 → 拆分兜底 → 空结果兜底 → 原问题兜底。

### 4.4 多路检索引擎（检索层）

**职责**：解决单路向量检索的语义盲区、无兜底、噪声直接进提示词。

**架构图**：

```text
                 改写后的查询
                      │
                      ▼
         ┌── 四个通道并行（SearchChannelType）────────┐
         │ VECTOR（向量）    KEYWORD（BM25）          │
         │ GRAPH（图谱）     WEB_SEARCH（联网）       │
         │ 统一接口 SearchChannel（getName/isEnabled/ │
         │ search/getType/emptyResult）              │
         └──────────────────┬───────────────────────┘
                            │ 全部到齐（等最慢，orTimeout 15s）
                            ▼
                    ① RRF 融合排名
                            ▼
                    ② Rerank 精排
                            ▼
                    ③ EvidenceGate 证据闸门
                       最高精排分 < 0.2 → 整批丢弃
                            ▼
                   高质量证据 → 进提示词 / LLM
```

**关键机制**：

- **四通道**：VECTOR 吃语义、KEYWORD 吃精确匹配（产品编号/条款号）、GRAPH 吃实体关系、WEB_SEARCH 吃最新信息。
- **并行 + 取最长**：并行执行取最长不累加，平均首字响应 6 秒内的保证之一；最差等最慢通道 15 秒。
- **RRF 融合**（k=20，vector/keyword=1.0，graph/web=0.5）：不依赖各通道分数可比，只比排名。
- **EvidenceGate**：精排分低于 0.2 整批丢弃——"库里没答案就明确说没有"，而不是硬编。
- **三阶段预算** 20→40→10，`supplementRatio=0.25` 补充路，控制召回与成本。

### 4.5 MCP 工具接入（工具层）

**职责**：把外部业务能力"协议化"，不写死在 RAG 链路里。

**架构图**：

```text
┌─ LLM / Agent ─┐   ┌─ Client（rag/core/mcp/）─┐   ┌─ Server（独立进程 :9099）─┐
│ 输出 tool_use  │──►│ 连接/发现/注册/执行工具     │──►│ 7 个工具                  │
│ 消化工具结果    │◄──│ McpToolBridge+工具注册表   │◄──│ 天气/销售/工单/请假/资产/  │
└───────────────┘   │ AgentToolCatalog 快照      │   │ 联网搜索                  │
                    └──────────────────────────┘   └────────────────────────────┘
```

**关键机制**：

- **三层架构**：Server 独立进程（可独立部署/扩容）、Client（连接、发现、注册、执行）、消费侧（检索链路 + Agent）。
- **Schema 驱动**：工具用 Schema 声明必填/枚举/默认值，LLM 据此提参。
- **提参三态**：`SUCCESS` / `NEED_CLARIFICATION`（isError=false，澄清后重来）/ `FAILED`（isError=true）。
- **多工具两层并行**：多个工具并行 + 每个工具内部两层并行，缩短工具调用等待。
- **快照 fingerprint**：`AgentToolCatalog` 快照指纹，工具列表变更时才重新发现，避免每请求全量扫描。
- **收敛权限**：模型不直接调服务，所有工具调用经过 Client 层统一鉴权/审计（对照 Claude Memory Tool 的 client-executed 思路）。

### 4.6 分布式限流（治理层）

**职责**：SSE 长连接并发失控会拉垮下游、token 成本失控、首字延迟劣化。多实例下单机 `Semaphore` 等于没限。

**架构图**：

```text
聊天请求（SSE）
   │
   ▼
拦截器 → FairDistributedRateLimiter
   │
   ├─ ① 信号量 acquire：Redis 可过期信号量（扣减并发额度）
   │     满 → 进公平队列
   ├─ ② 公平队列：ZSET，score=雪花序号（先来先服务）+ 到期时间
   ├─ ③ Lua 原子 claim（queue_claim_atomic.lua，slack=16）
   │     有额度 → 扣减 + 出队，原子操作防并发抢
   ├─ ④ 拿到 permit → 放行（Ticket 状态机：先设 permitRef 再 CAS）
   ├─ 执行业务（检索 + LLM 流式）
   └─ ⑤ 释放 permit → Pub/Sub 广播 → 唤醒排队者（firing CAS + do-while 防风暴）
         lease 兜底 600s（防止占位卡死）
```

**关键机制**：

- **可过期信号量 + ZSET 公平队列**：既有并发上限，又保证"先来先服务"而非随机抢。
- **Lua 原子性**：claim 在 Redis 侧一步完成，天然防多实例并发抢占。
- **Pub/Sub 即时唤醒**：释放时广播，排队者立刻竞争，不用轮询；`firing CAS + do-while` 防广播风暴。
- **Ticket 状态机 + TtlRunnable**：跨线程持有 permit，超时自动释放，防泄漏。
- **SSE 事件流拒绝**：对长连接流式场景友好，拒绝也走 SSE 事件返回。

### 4.7 RAGAS 评测体系（评测）

**职责**：链路是多段流水线，任何一段改参数都可能变好或变坏——没有尺子等于没有优化依据。

**架构图**：

```text
eval_set_v1.jsonl（人工标注评估集）
   │ load_samples()
   ▼
List[EvalSample]
   │ runner.run()：端到端调真实生产链路（不 mock）
   │   ① 登录 ② SSE /rag/v3/chat + JSON /rag/eval 旁路
   │   ③ 手写 SSE 解析器 ④ doc_id_map 反向映射
   ▼
EvalRecord
   │ score() 按序：intent → retrieval → behavior → latency → ragas
   ▼
reports/<run>/：report.md / per_sample.csv / failures.jsonl / slides.html
   │ diff 命令 → A/B 对比 + 退化检测（⚠ 标显著退化）
   ▼
驱动优化：失败样本 = 优化清单
```

**关键机制**：

- **自建四组指标**：意图 `intent_top1` / 检索 `Hit@K·Recall@K·MRR@10`（只统计 requires_rag=true）/ 行为红线（误拒率、兜底率、过召回率）/ 延迟（TTFT P50、总耗时）。
- **RAGAS 五指标**：faithfulness、answer_relevancy、answer_correctness、context_precision、context_recall；judge 用 JSON mode 防中文引号解析炸、metric 需 `copy.copy()` 防跨线程共享。
- **可信度工程化**：n_runs 取均值（发版开 3 次）、三级降级（batch+JSON→batch→逐条隔离）、超时 900→1200、reasoning 模型不发 temperature。
- **A/B Diff + 退化检测**：对比两次 run 的 `_scores.json`，`LOWER_IS_BETTER` 集合 + 独立阈值（faithfulness 0.05 / answer_relevancy 0.05 / hit@5 0.03 / TTFT 500ms），避免 0.003 抖动当退化。
- **manual override**："manual value first, fallback to ragas"——关键样本允许人工打分优先。
- **口径诚实**：+10.3% / +8.0% 是百分点差（0.82→0.923 = +10.3pp），非相对增幅。

## 5. 技术选型（技术栈）

| 分类 | 技术选型 | 选型理由 |
|---|---|---|
| 后端语言/框架 | Java 17 + Spring Boot | 团队主流栈、生态成熟、SSE/异步/线程池支持好 |
| 会话与消息存储 | PostgreSQL | 强一致、事务可靠，适合会话/消息/摘要结构化持久化 |
| 缓存/分布式原语 | Redis（String/ZSET/Lua/PubSub） | 信号量、公平队列、广播唤醒、记忆索引全用它，原子性靠 Lua |
| 分布式 ID | 雪花算法（Snowflake） | 高并发、趋势递增，直接当 ZSET 排序依据 |
| 向量检索 | 向量库 + `text-embedding-3-large` | VECTOR 通道，语义召回 |
| 关键词检索 | BM25（Elasticsearch/Lucene 系） | KEYWORD 通道，精确匹配（产品编号/条款号） |
| 知识图谱 | 图谱存储（实体/关系） | GRAPH 通道，实体关联召回 |
| LLM | GPT-5 系列（OpenAI 兼容，aihubmix 中转） | 生成主模型 + judge 评测模型（gpt-5.4-mini）|
| 流式协议 | SSE（Server-Sent Events） | 长连接流式返回，首字快、实现简单 |
| 工具协议 | MCP（Model Context Protocol） | 工具能力协议化，与链路解耦 |
| 评测 | Python `ragenteval`（RAGAS + 自建指标） | 端到端评测 + A/B Diff，LLM 自评需工程化降噪 |
| 并发控制 | 线程池（检索并行池 / `mcpBatchExecutor` / `memoryLoadExecutor` / `memorySummaryExecutor`） | 各链路隔离，避免相互占用 |
| 分布式锁 | Redisson（tryLock 失败即放弃） | 记忆摘要等写路径加锁，不阻塞主链路 |

> 选型原则：**能交给 Redis/PG 的就别自己维护状态**（多实例可水平扩展）；**能用成熟协议的就别自造**（MCP、SSE）；**评测链路当生产系统对待**（显式报错、不静默吞、降级可见）。

## 7. 关键设计原则与亮点

1. **先路由、再检索、后生成**——意图层把"该去哪"定死，检索才有意义；避免 LLM 瞎猜知识库。
2. **索引与内容分离、按需召回**——会话记忆的"索引 + 主题文件懒加载"、长期记忆的"≤N 条注入"，本质都是控制注入量、防上下文被撑爆（fading memory）。
3. **多路并行 + 证据把关**——四通道并行取最长不累加；EvidenceGate 低分整批丢弃，宁可"没有"也不硬编。
4. **工具能力协议化（MCP）**——不写死在链路里，独立进程可独立部署、扩容、审计；权限收敛到 Client 层。
5. **状态全部外置**——记忆在 PG、限流在 Redis、工具在 MCP Server，应用无状态可水平扩展。
6. **评测链路当生产系统**——自建指标补齐 RAGAS 盲区（行为红线、检索、延迟），n_runs 均值 + 降级 + 重试 + 显式报错，不静默吞。
7. **全链路降级兜底**——改写有规则兜底、意图有规则兜底、检索有空结果兜底、评测有三级降级，任何一层失败都不至于让主链路白屏。

| 指标 | 数值 | 口径 |

| Top-1 召回命中率 | 相对传统 RAG 提升 30.5% | 多路检索 |

### 8.1 评测数据全貌：指标公式、指标板与数字来源

> 本节回答"上表的数字从哪来、怎么算"——对应自建评测工程（ragenteval）的真实口径。

#### 8.1.1 指标公式与样本过滤

| 指标族 | 指标 | 公式 / 口径 | 样本过滤条件 |
|---|---|---|---|
| 意图 | intent top-1 准确率 | `value = 1 if intent_pred == intent_l2 else 0` | `intent_l2` 非空，空值不计分母 |
| 检索 | Hit@K（K=1/3/5/10） | `top-K ∩ reference_doc_ids 非空 → 1，否则 0` | `requires_rag = true` 且 `reference_doc_ids` 非空 |
| 检索 | Recall@K | `\|top-K ∩ ref\| / \|ref\|`（must 口径）；inclusive 变体分子/分母换 `ref ∪ reference_doc_ids_nice` | 同上 |
| 检索 | MRR@10 | 第一个命中结果的排名倒数 | 同上 |
| 行为 | 误拒率 | `requires_rag=true` 但检索结果为空 | `requires_rag=true` |
| 行为 | 兜底率 | response 包含"未检索到与问题相关的文档内容" | `requires_rag=true` |
| 行为 | 过召回率 | `requires_rag=false` 但实际检索到 | `requires_rag=false` |
| 延迟 | TTFT | P50 / 均值；`first_token_ms` 缺失回退 `latency_ms` | `final_status = success` |
| 质量 | RAGAS 五指标 | faithfulness / answer_relevancy / context_precision / context_recall / context_relevancy | response / contexts / reference 三项齐全 + success |

#### 8.1.2 指标板（25 项怎么摊）

```text
意图识别   intent_top1                                     ×1
检索       hit@1/3/5/10                                    ×4
           recall@K（must + inclusive）                     ×8
           mrr@10                                          ×1
行为       误拒率 / 兜底率 / 过召回率                         ×3
延迟       TTFT P50 / TTFT mean / total mean                ×3
RAGAS      faithfulness / answer_relevancy / context_*
           （precision / recall / relevancy）               ×5
合计                                                      ≈ 25 项
```

#### 8.1.3 第 8 节数字来源

| 第 8 节指标 | 数字 | 来源口径 |
|---|---|---|
| 平均首字响应 | 6 秒内 | 评测旁路录制 `latency_ms` / `first_token_ms`，多路并行取最长而非累加 |
| Top-1 召回命中率 | 相对提升 30.5% | **同一评估集**、传统 RAG vs 多路检索两次 run 的 Hit@1 相对提升 |
| 过度检索率 | 降至 13% 以内 | 行为指标过召回率（`requires_rag=false` 但检索到）经 EvidenceGate 闸门 |
| 上下文精准度 | 提升 24.5% | 多路检索开关前后的 context_precision |
| Recall@1 | 提升 20.8% | 问题重写开关前后的 recall@1 |
| faithfulness | +10.3% | 百分点差（0.82 → 0.923），RAGAS |
| 答案相关性 | +8.0% | 百分点差，RAGAS answer_relevancy |

**口径说明**：上表所有"提升 X%"均为**同一评估集、开/关某机制的两次 run 的差值**，不是跨数据集绝对值对比；样本过滤规则保证两次 run 的分母一致。评估集规模约 150 条样本，覆盖意图标注、检索标注与 RAGAS 可评样本三类。

## 9. 已知局限与演进方向

- **记忆**：当前为滑动窗口 + 摘要；演进方向是结构化记忆块（按角色/项目/技术偏好分槽），对标 Claude 的 `user/feedback/project/reference` 四类。
- **检索**：通道权重目前靠经验 + 归因日志校准；演进方向是用评测数据反推权重。
- **意图**：意图树为静态配置；演进方向是支持运行时热更新 + 数据驱动剪枝。
- **评测**：评估集样本规模有限、人工标注成本高；演进方向是半自动标注 + 线上回归采样（同 diff 机制）。
- **跨项目记忆**：无全局记忆（对标 Claude 局限）；演进方向是把记忆从 PG 单库扩展到多项目共享 + 垃圾回收。
