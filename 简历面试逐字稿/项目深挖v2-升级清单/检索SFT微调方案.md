## 🎤 开场总览（45 秒版，可直接背）

> 面试官问"你们做微调了吗 / 如果做 SFT 怎么做？"时，先把下面这段一气呵成讲完，再落到 Q1 展开。
> 末尾留的钩子（为什么 Qwen / 数据哪来 / 对比学习不是 SFT / 优先级）正好接 Q2 / Q3 / Q5 / Q10。

**我：** 先诚实说：我们线上**还没做微调**，检索链路现在靠的是预训练模型 + 规则阈值 + LLM 原生能力，多路检索 + RRF + Rerank + 证据闸门这些架构红利已经吃满。如果要给寿险 RAG 补 SFT，我的方案是五件事：

**第一，底座全选 Qwen 开源系。** 不用百炼 API（API 模型参数不开放、不能自训），用开源 Qwen 底座本地/云上微调，训完再部署回 vLLM 或百炼。选 Qwen 三个理由：**Apache 2.0 商业可商用**（金融合规，BGE-M3 的 CC-BY-NC 这类非商用协议直接排除）、**和主供应商百炼同源**（推理生态一致）、**全家桶齐全**（重写/意图/向量/精排一套覆盖）。

**第二，微调两个"语言理解"组件——问题重写器 + 意图路由。** 重写用 **Qwen3-8B-Instruct** 做 LoRA SFT，把"多轮口语 + 指代"重写成"单轮、书面化、可独立检索"的 query，并做多跳分解；意图路由用 **Qwen3-1.7B** 加分类头，输出意图标签 + 置信度，替代现在的 0.35/0.6 硬阈值。

**第三，检索侧用 Embedding + Rerank 微调。** Embedding 用 **Qwen3-Embedding-0.6B** 做**对比学习**（严格说不是 SFT，是对比学习 InfoNCE）；Rerank 用 **Qwen3-Reranker / bge-reranker** 做 cross-encoder **二分类 SFT**——这个才是标准 SFT。

**第四，数据三来源。** 真实日志（query + 命中条款 + 有无追问当正负信号）、条款结构化（书面语反向生成口语 query）、LLM 合成 + 蒸馏（百炼 Qwen-Max 批量造样本）。几千到上万条就够启动 LoRA，不用百万级。

**第五，按收益/成本比排序落地。** 先意图路由（小模型、便宜、见效快）→ 再问题重写（见效最快）→ 最后检索侧（成本最高）。而且遵循"**先架构后微调**"——架构没打满之前，微调的边际收益不划算。

讲到这里停一下，面试官大概率会顺着追问：为什么选 Qwen 不用 BGE？数据具体怎么造？对比学习和 SFT 什么区别？优先级为什么这么排？——正好接上 Q2 / Q3 / Q5 / Q10。

## Q1（开场总览）你们系统有没有做微调？如果做 SFT，整体方案和模型选型是什么？

**我：** 先讲现状，再讲方案——这是两条线，不能混。

**现状：没做微调。** 我们的检索质量提升来自架构：多路检索（VECTOR/KEYWORD/GRAPH/WEB）+ RRF 融合 + Rerank 精排 + 证据闸门，以及问题重写层的术语归一化 + LLM 改写 + 意图树的意图定向。模型都是预训练的，靠 prompt 工程和规则把能力调出来。

**方案：如果做，用 Qwen 开源底座做 LoRA SFT，微调四个组件。**

| 环节 | 微调对象 | 底座模型 | 方法 | 训练数据 |
|---|---|---|---|---|
| 问题重写 | 小 LLM 重写器 | **Qwen3-8B-Instruct** | LoRA SFT | 多轮对话 → 单轮重写 + 子查询 |
| 意图路由 | 小 LLM 分类头 | **Qwen3-1.7B** | LoRA + 分类头 SFT | 意图标签（日志 + 蒸馏） |
| 向量检索 | Embedding | **Qwen3-Embedding-0.6B** | 对比学习（InfoNCE） | 条款-query 对 + hard negative |
| 精排 | Reranker | **Qwen3-Reranker / bge-reranker** | cross-encoder 二分类 SFT | (query, doc, 相关/不相关) |

> Q1 整体方案一图看懂：

```text
现状（诚实）：没做微调
   ├─ 检索质量来自架构：多路 + RRF + Rerank + 证据闸门
   └─ 模型全预训练，靠 prompt 工程 + 规则调能力

方案（如果做）：Qwen 开源底座 + LoRA SFT，微调 4 个组件
   ├─ 问题重写   Qwen3-8B-Instruct    LoRA SFT
   ├─ 意图路由   Qwen3-1.7B           LoRA + 分类头
   ├─ 向量检索   Qwen3-Embedding-0.6B  对比学习（非SFT）
   └─ 精排       Qwen3-Reranker       cross-encoder 二分类（SFT）
   ▼
关键边界
   百炼 API 模型参数不开放 → 不能自训
   微调必须用开源 Qwen 底座，训完部署回 vLLM / 百炼
```

一个容易混淆的点要讲清：**百炼 API 的模型是调用接口，参数不对外开放，不能自己微调**；要微调得拿开源的 Qwen 权重自己训，训完再部署。所以"选 Qwen"不是"选百炼"，是"选百炼同源的开源底座"。

## Q2（追问）为什么底座选 Qwen？不用 BGE / GTE？

**我：** 三个理由，按重要性排：

**1. 商业合规（最硬的理由）。** 金融行业用模型，协议是第一道闸门。Qwen 系列是 **Apache 2.0**，可以商用、可以改、可以再分发；而很多 embedding 的 SOTA 是**非商用协议**——比如 NV-Embed 是 CC-BY-NC-4.0，BGE-M3 是 MIT 但部分衍生数据有约束。寿险是持牌业务，模型协议上不能有风险，这条直接筛掉一大批。

**2. 和主供应商同源，推理生态一致。** 我们线上主模型就是阿里云百炼，用 Qwen 微调后，权重能直接走百炼的部署或 vLLM 推理，tokenizer、模板、推理链路都不用改。选 BGE 就得再拉一套不相干的部署栈。

**3. 全家桶齐全，一个底座覆盖全链路。** 重写用 Qwen3-8B、意图用 Qwen3-1.7B、向量用 Qwen3-Embedding、精排用 Qwen3-Reranker——同一个 tokenizer、同一套训练框架（Swift/LLaMA-Factory）、同一套评测脚本，不用为每个组件单独踩一遍坑。

> Q2 为什么选 Qwen 一图看懂：

```text

   ① 商业合规（最硬）
      Qwen = Apache 2.0 可商用
      对比：NV-Embed = CC-BY-NC（非商用，排除）
            BGE-M3 = MIT 但衍生数据有约束
      → 寿险持牌业务，协议不能有风险

   ▼
"选 Qwen" ≠ "选百炼"
   = 选"百炼同源的开源底座"（可自训、可商用、生态一致）
```

## Q3（追问）问题重写怎么 SFT？和现状的 QueryRewriteService 什么关系？

**我：** 先对齐现状，再讲怎么微调。

**现状**：我们的重写层 `QueryRewriteService` 是"规则 + LLM 原生"——术语归一化（`t_query_term_mapping` 规则表，长词先匹配）→ LLM 改写 + 拆分（`MultiQuestionRewriteService`，FAST 档，输出 `{rewrite, should_split, sub_questions}`）→ 规则拆分兜底。这里面的 LLM 是**通用模型 + prompt**，没有领域微调。

**SFT 要替换/增强的就是中间这一层**：把"通用模型 + 一份静态 prompt"换成"领域微调的小模型"。目标不是重写整个链路，是让 LLM 改写这一步更懂保险：

- **口语 ↔ 条款书面语对齐**："得癌症赔不赔" → "恶性肿瘤-重度保险责任"，这是通用模型改写不出来的领域映射。
- **多跳分解**："给孩子买重疾，哪款能豁免保费" → 拆成 `[险种匹配：儿童重疾险, 条款匹配：保费豁免条款]` 两个子查询，各自命中各自的库。
- **保险术语归一化**：把"原位癌""轻症""重症"这些通用模型分不清的边界对齐到条款定义。

**底座 Qwen3-8B-Instruct，LoRA SFT**，训练数据是 `(多轮对话 + 省略/指代 → 单轮重写 + 子问题列表)` 对。数据三来源里，这块最吃**条款结构化反向生成**——拿条款片段让大模型反向生成口语 query，天然得到"口语→书面语"的正样本对。

> Q3 问题重写 SFT 一图看懂：

```text
现状 QueryRewriteService（规则 + LLM 原生，未微调）
   术语归一化(规则) → LLM改写+拆分(通用模型+prompt) → 规则拆分兜底

SFT 增强的是中间这一层
   通用模型 + 静态 prompt  →  领域微调小模型（Qwen3-8B LoRA）

SFT 目标（通用模型做不好的三件事）
   ① 口语↔书面语对齐  "得癌症赔不赔" → "恶性肿瘤-重度保险责任"
   ② 多跳分解        "给孩子买重疾哪款豁免保费"
                     → [儿童重疾险, 保费豁免条款] 两个子查询
   ③ 保险术语边界    "原位癌/轻症/重症" 对齐条款定义

数据：多轮对话+省略指代 → 单轮重写+子问题列表
   ├─ 最吃"条款反向生成口语 query"（天然口语→书面语正样本）
   └─ 训练对样例
      输入：第2轮"那这个病保不保？"（上文聊 XX重疾险/恶性肿瘤）
      输出："XX重疾险对恶性肿瘤的赔付责任与免责条款是什么"
            + 子查询 ["XX重疾险恶性肿瘤赔付标准","XX重疾险恶性肿瘤免责条款"]
```

一个关键细节：**SFT 不改重写层的三层结构**。术语归一化（规则）和规则拆分（兜底）这两层保留不动，因为它们是确定性的、零成本、永远能兜底；SFT 只是把中间"LLM 改写"这步从"通用模型"升级成"领域微调模型"，兜底链路不变，最差情况还是"归一化 → 检索"。

**面试官追问**：意图识别呢？你们不是有意图树吗，怎么还要微调？

## Q4（追问）意图路由怎么 SFT？和现在的意图树什么关系？

**我：** 现状意图树是"LLM 一次调用对所有叶子打分 + 阈值过滤"。`DefaultIntentClassifier` 把全部叶子的 id/path/description 拼成一个 prompt，让 LLM 输出 `[{id, score, reason}]`，然后过滤 <0.35、取前 3。下游 `RetrievalScopeResolver` 再按 **KB 意图最高分 ≥0.6 定向 / <0.6 全局** 收窄检索范围。

这里有两个可以微调升级的点：

**1. 打分模型从"通用 LLM"换成"微调小 LLM + 分类头"。** 底座 **Qwen3-1.7B**，加一个分类头做 LoRA SFT，直接输出意图标签 + 置信度。好处是**延迟和成本**——意图识别是每次提问必经的高频环节，通用大模型打分又慢又贵，1.7B 小模型能快一个量级。

**2. 用置信度阈值 + 大模型兜底，替代现在的硬阈值。** 现在 0.35/0.6 是全局统一阈值，比较粗。微调后小模型能输出**校准过的置信度**，低置信度自动回退到大模型（或走现有澄清反问），比"一刀切 0.6"更准。

**为什么保险意图适合小模型微调**：保险意图标签天然稳定——`投保咨询 / 理赔 / 条款查询 / 续保 / 退保 / 产品对比 / 保费测算`，不会天天变。意图树叶子就是这些标签，直接把叶子当分类头，用日志 + 大模型蒸馏出标签数据来训。

**关键：微调意图路由不推翻意图树。** 树的组织、热加载、叶子挂 KB/MCP/SYSTEM 执行单元这套路由机制都保留，SFT 只是把"打分"这一步从"通用模型一次调用"换成"微调小模型"，路由骨架不变。

> Q4 意图路由 SFT 一图看懂：

```text
现状（LLM 一次调用打分 + 硬阈值）
   DefaultIntentClassifier：全叶子拼 prompt → LLM 输出 [{id,score,reason}]
   过滤 <0.35 → 取前3 → RetrievalScopeResolver(≥0.6定向/<0.6全局)

SFT 升级两个点
   ① 打分模型：通用 LLM → 微调小 LLM + 分类头（Qwen3-1.7B LoRA）
      好处：延迟/成本降一个量级（意图是高频必经环节）
   ② 硬阈值：0.35/0.6 一刀切 → 校准置信度 + 大模型兜底
      低置信度 → 回退大模型 或 走现有澄清反问

为什么保险意图适合小模型微调
   意图标签天然稳定：投保/理赔/条款/续保/退保/对比/保费测算
   意图树叶子 = 分类头标签，日志 + 大模型蒸馏出标签数据

关键边界
   微调不推翻意图树：树组织/热加载/叶子挂 KB+MCP+SYSTEM 都保留
   SFT 只替换"打分"这一步，路由骨架不变
```

**面试官追问**：你前面说 Embedding 是对比学习不是 SFT，这怎么区分？Rerank 又是什么？

## Q5（追问）向量检索和精排的微调——对比学习 vs SFT 怎么区分？

**我：** 这是个很关键的区分，面试里讲错会被扣分。**SFT 是"有监督标签的监督学习"，而 Embedding 微调的主流是"对比学习"，两者不是一回事。**

**Embedding（对比学习，InfoNCE）**：不学"这条 query 该归哪类"，学的是"**让正样本对拉近、负样本对推远**"。损失是 InfoNCE（sentence-transformers 的 `MultipleNegativesRankingLoss`），负样本 = in-batch negatives（同 batch 其它 query 的正样本白嫖当负样本）+ hard negatives（挖掘出来的难负样本）。底座 **Qwen3-Embedding-0.6B**。

**Rerank（这才是标准 SFT）**：cross-encoder 输入 `(query, doc)` 对，输出相关/不相关的二分类，用 binary cross-entropy——这就是标准的监督学习 SFT。底座 **Qwen3-Reranker 或 bge-reranker**。

**保险领域的 hard negative 是胜负手**，就三类：

| hard negative 类型 | 例子 | 为什么难 |
|---|---|---|
| 险种混淆 | 问"重疾险"，返回"意外险"条款 | 都是保险，语义接近 |
| 同产品不同条款 | 问"等待期"，返回"保障范围" | 同一文档，片段相似 |
| 近义疾病 | 问"恶性肿瘤-重度"，返回"恶性肿瘤-轻度/原位癌" | 字面高度重叠，赔付标准天差地别 |

> Q5 对比学习 vs SFT 一图看懂：

```text
Embedding 微调 = 对比学习（InfoNCE，不是 SFT）
   学"正样本拉近、负样本推远"
   损失：MultipleNegativesRankingLoss（InfoNCE）
   负样本 = in-batch（免费）+ hard negative（值钱）
   底座：Qwen3-Embedding-0.6B

Rerank 微调 = 标准 SFT（cross-encoder 二分类）
   输入 (query, doc) 对 → 输出 相关/不相关
   损失：binary cross-entropy
   底座：Qwen3-Reranker / bge-reranker

保险 hard negative（胜负手，三类）
   ├─ 险种混淆       "重疾险" → 返回"意外险"条款
   ├─ 同产品不同条款 "等待期" → 返回"保障范围"
   └─ 近义疾病       "恶性肿瘤-重度" → 返回"轻度/原位癌"
                    （字面高度重叠，赔付标准天差地别）
   ▼
面试必须说清：SFT 和监督标签绑定；对比学习学的是相对远近
   两个词不能混用
```

一个易踩的坑要提前说：**Embedding 微调的负样本，业界已经有共识——"相似度/难度比来源更重要"**，similarity-mined 的 harder negatives 效果最好，纯 LLM 生成的负样本可能不如 BM25/cross-encoder 挖掘的，所以主流是**混合 + 过滤**。这条体现了你懂业界前沿，不只是背流程。

**面试官追问**：数据具体怎么造？样本量多大？会不会标注成本太高？

## Q6（追问）训练数据怎么来？量级多大？会不会很贵？

**我：** 三块数据源，全部来自我们自己的场景，不买外部数据：

**① 真实日志（正负信号免费）。** 问答平台的 query + 命中条款 + **有无追问/采纳**。用户问完没有再追问、没有点"没答好"，就是"检索答对了"的正信号；问完立刻追问或驳回，就是"检索没答好"的负信号。这块是**零标注成本**的行为数据。

**② 条款结构化（反向生成）。** 把条款文档切块后，让大模型**反向生成口语 query**——"恶性肿瘤保险责任"这个条款片段，反向生成"得癌症赔不赔""癌症怎么赔"这些口语问法。天然得到 `(口语query, 条款片段)` 正样本对，专门打口语↔书面语的 gap。

**③ LLM 合成 + 蒸馏（2026 主流手段）。** 用百炼 Qwen-Max 批量做三件事：生成重写对（多轮→单轮+子查询）、打意图标签、生成 hard negative（"相似但不相关"的条款）。大模型当"教师"，小模型当"学生"，**蒸馏**。

**量级**：LoRA 微调不需要百万级。**重写器几千到一万条对话对、意图几千条标注、Embedding 一万条 (query, 正条款, 4-5 个负条款) 三元组**，就够启动第一轮。这是 LoRA 的核心优势——参数量小，数据需求也小，不需要全参微调那种大规模语料。

**成本**：大头是 LLM 合成的 token 费，不是人工标注费。因为标签几乎全是日志行为信号 + LLM 合成，人工只做少量抽检校准，不是逐条标注。

> Q6 数据三来源一图看懂：

```text
① 真实日志（零标注成本）
   query + 命中条款 + 有无追问/采纳
   ├─ 无追问/未驳回 → 正信号（检索答对）
   └─ 追问/驳回     → 负信号（检索没答好）

② 条款结构化（反向生成）
   条款片段 → 大模型反向生成口语 query
   "恶性肿瘤保险责任" → "得癌症赔不赔""癌症怎么赔"
   = (口语query, 条款片段) 正样本对，打口语↔书面语 gap

③ LLM 合成 + 蒸馏（2026 主流）
   百炼 Qwen-Max 当教师，小模型当学生
   ├─ 生成重写对（多轮→单轮+子查询）
   ├─ 打意图标签
   └─ 生成 hard negative（相似但不相关条款）

量级（LoRA 数据需求小，不用百万级）
   重写器：几千~一万条对话对
   意图：几千条标注
   Embedding：一万条 (query, 正条款, 4-5 负条款) 三元组

成本大头 = LLM 合成 token 费，不是人工标注费
   （标签几乎全来自行为信号 + LLM 合成，人工只抽检）
```

**面试官追问**：训练具体怎么落地？框架、显存、超参？会不会要很多卡？

## Q7（追问）训练怎么落地？框架、显存、超参？

**我：** 都是轻量级，单卡能跑。

**框架**：**LLaMA-Factory**（一键 LoRA，社区最主流）或阿里 **Swift**（Qwen 官方微调框架，和底座同源）。选哪个看团队习惯，两者都能一条命令起 LoRA 微调。

**显存**：LoRA 只训少量低秩旁路参数，冻结主干。**8B 模型 LoRA 微调单卡约 20G 显存**，一张 A100/4090 就够；1.7B 更小，消费级卡都能跑。这是 LoRA 对比全参微调的核心优势——全参微调 8B 要 8 卡，LoRA 一卡。

**超参（业界共识默认值）**：

| 环节 | LoRA rank | lr | epoch | 其它 |
|---|---|---|---|---|
| 重写器（8B） | 8–16 | 1e-4 | 2–3 | — |
| 意图路由（1.7B） | 8 | 1e-4 | 2–3 | — |
| Embedding（0.6B） | 8 | 1e-5 | 1–2 | 4–5 hard negative/对、batch 128+、temp 0.02 |

> Q7 训练落地一图看懂：

```text
框架
   LLaMA-Factory（社区最主流，一键 LoRA）
   或 Swift（Qwen 官方，与底座同源）

显存（LoRA 冻结主干，只训低秩旁路）
   8B LoRA ≈ 20G → 单卡 A100/4090 够
   1.7B 更小 → 消费级卡能跑
   对比：全参 8B 要 8 卡，LoRA 一卡 = 核心成本优势

超参（业界默认值）
   重写器 8B   rank 8-16 / lr 1e-4 / epoch 2-3
   意图 1.7B   rank 8    / lr 1e-4 / epoch 2-3
   Embedding   rank 8    / lr 1e-5 / 4-5 hard neg/对 · batch 128+ · temp 0.02
```

一个工程细节：**lr 为什么 Embedding 用 1e-5 而重写用 1e-4？** 因为 Embedding 是对比学习，要在"保持预训练语义"和"往领域拉"之间找平衡，lr 太大容易把通用语义冲坏（灾难性遗忘更明显）；重写器是生成式 SFT，lr 可以稍大一点。这个差异面试官问了能接住，体现你真的训过，不是背参数。

**面试官追问**：微调完怎么评估？会不会把通用能力训没了？

## Q8（追问）怎么评估微调效果？怎么防灾难性遗忘？

**我：** 两个问题分开答。

**评估——复用我们现有的评测集，微调前后 diff。** 我们已经有 `requires_rag + expected_doc_ids` 标注的评测集和 `ragenteval` 评分脚本（Hit@K/Recall@K/MRR/NDCG），微调后**同一批样本、同一套指标，diff 微调前后的分数**：

| 环节 | 评估指标 |
|---|---|
| 重写器 | 改写后召回 Hit@K 提升；多跳子查询覆盖正确文档的比例 |
| 意图路由 | Top-1 意图准确率 + 低置信度兜底率（复用现有意图评测） |
| Embedding/Rerank | Hit@5 / Recall@5 / NDCG@10 微调前后 diff |

**关键：微调前后 diff 必须用同一评测集、同一过滤条件**，和我们报 30.5% 一样的严谨度——否则分不清是微调带来的、还是评测集换了。

**防灾难性遗忘——三招：**

1. **LoRA 本身就抗遗忘**：只改少量低秩参数，主干冻结，天然保留预训练的通用能力。
2. **通用语料 + 领域语料混合**（约 7:3）：训练集里掺通用问答/通用检索对，防止模型"只会保险、别的全忘"——这是最实用的一招。
3. **评测里加"通用能力回归项"**：评测集里留一批非保险的通用样本，微调后通用能力掉了，立刻暴露。

> Q8 评估 + 防遗忘一图看懂：

```text
评估 = 复用现有评测集，微调前后 diff
   requires_rag + expected_doc_ids + ragenteval（Hit@K/Recall@K/MRR/NDCG）
   ├─ 重写器     改写后 Hit@K / 多跳子查询覆盖
   ├─ 意图路由   Top-1 准确率 + 低置信度兜底率
   └─ Embedding  Hit@5 / Recall@5 / NDCG@10
   ▼
   必须同一评测集 + 同一过滤条件（否则分不清是微调还是换集）

防灾难性遗忘三招
   ① LoRA 天然抗遗忘（冻结主干，只训低秩参数）
   ② 通用语料 + 领域语料 7:3 混合（最实用）
   ③ 评测加"通用能力回归项"（非保险样本，掉了立刻暴露）
```

**面试官追问**：那这四个微调，你按什么顺序做？是不是全都要做？

## Q9（追问）优先级怎么排？为什么不全做？

**我：** 不全做，按**收益/成本比**排，而且有个前提——**先架构后微调**。

**先架构后微调**：我们现在的检索质量提升主要来自架构（多路 + RRF + Rerank + 证据闸门 + 意图定向 + 重写），这些是**确定性的、成本低、见效快**的。架构红利没吃满之前就上微调，是拿高成本、长周期去换一个"可能有用"的边际收益，不划算。业界共识也是这个顺序。

**吃满架构后，微调顺序**：

1. **先意图路由**：1.7B 小模型、延迟成本降一个量级、数据好造（意图标签稳定），收益最快体现。
2. **再问题重写**：重写是召回质量的上游，改写了检索全链路受益，但数据（多轮对话对）比意图贵一点。
3. **最后 Embedding/Rerank**：成本最高、周期最长，而且依赖前面两步先跑通数据管道（日志、条款、合成都熟了），放最后。

> Q9 优先级一图看懂：

```text
前提：先架构后微调
   现有提升主要来自架构（多路+RRF+Rerank+闸门+意图定向+重写）
   架构 = 确定性、成本低、见效快
   架构红利没吃满就微调 = 高成本换边际收益，不划算

吃满架构后的微调顺序（收益/成本比）
   ① 意图路由（1.7B，延迟降一个量级，数据好造）→ 最优先
   ② 问题重写（召回上游，全链路受益，数据稍贵）
   ③ Embedding/Rerank（成本最高、周期最长，放最后）
   ▼
理由：前两步先跑通数据管道（日志/条款/合成）
      第三步复用这套管道，边际成本最低
```

**面试官追问**：最后一个问题——你既然没做微调，这些方案你怎么敢说？

## Q10（追问）既然没实际做微调，凭什么相信这套方案可行？

**我：** 这是个很实在的问题，我分三层答：

**第一，我没做过，但我知道业界怎么做。** 这套方案不是我拍脑袋，是 2025–2026 业界已经收敛的主流配方——**通用强底座 + 对比学习/SFT + 日志/合成数据 + LoRA**。NVIDIA 的合成数据配方在领域文档上实测 +10.9% NDCG@10；query 重写方向的 RL/蒸馏（INF-Query-Aligner、DGPO）都是公开可复现的路线。我讲的是"业界验证过的方法论落到我们场景"，不是"我自己发明"。

**第二，方案里的每一步都能和我们真实系统对上。** 重写器对接的是我们真实存在的 `QueryRewriteService`，意图路由对接意图树，评估复用我们真实的 `requires_rag + expected_doc_ids` 评测集。数据来源（日志、条款）都是我们系统里现成的东西，不是凭空假设。

**第三，诚实是更优的策略。** 面试里把"没做"说成"做了"，一追问具体显存、loss 曲线、bad case 就穿帮。大方承认"这是设计，我理解业界主流怎么做、如果落地我会这么落"，反而体现工程判断力和诚实——这比硬装一个"我微调过"的人设可信得多。

> Q10 可行性一图看懂：

```text
凭什么相信方案可行（三层）
   ① 业界验证过的主流配方（不是我发明）
      底座 + 对比学习/SFT + 日志/合成数据 + LoRA
      NVIDIA 合成数据 +10.9% NDCG@10；重写 RL/蒸馏公开可复现
   ② 每一步都对接真实系统
      重写器 → QueryRewriteService；意图 → 意图树
      评估 → requires_rag + expected_doc_ids 评测集
      数据 → 日志 + 条款（系统里现成的）
   ③ 诚实是更优策略
      "没做"说成"做了"一追问就穿帮
      大方承认设计 + 懂业界 + 会落地 = 更可信的人设
```

## 📋 面试建议（对真实面试的 3 条建议）

1. **"没做微调"不是短板，是诚实人设的起点。** 大多数 1 年经验候选人会硬说"我微调过 embedding"，一问显存、loss 曲线、bad case 就崩。你反过来——主动说"我们没做微调，靠架构把指标打上去了"，再补一套"如果做我会怎么做"的方案，立刻拉开差距。**诚实 + 懂方案 > 吹牛 + 穿帮。**

2. **"先架构后微调"是你的专属叙事。** 这条能把你没做微调这件事**合理化**——不是"不会做"，是"还没轮到做、且不该先做"。配合你真实的多路检索 + 证据闸门 + 意图定向这些架构成果，逻辑自洽："架构红利吃满后，微调才划算"。这是区分度最高的一句话。

3. **两个 ⚠️ 钩子提前备好**：「对比学习 vs SFT 的区别」和「lr 为什么 Embedding 用 1e-5」。前者是面试官爱考的术语区分，答错了直接暴露不懂；后者是"你真的训过 vs 背参数"的试金石——能说出"对比学习更怕灾难性遗忘所以 lr 更小"，比报一堆超参数值高级得多。
