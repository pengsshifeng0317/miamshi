# SSE 流式端到端怎么做（Agent 档）

> **简历产出**：主导设计并落地 Agent 模式 SSE 流式协议——8 个事件的双端契约、端到端一致性、跨 4 节点取消
> **覆盖模块**：Agent 流式链路（入口编排 / 事件桥接 / 生命周期 / 跨节点取消 / 块与时间的事实源）
> **熟练度**：🔴

> **这篇讲什么**：一条 Agent 对话流，从浏览器发出请求，到浏览器把界面渲染出来，**中间每一帧是怎么产生的、按什么顺序发出去的**。
>
> **端到端边界**：浏览器 → 浏览器。落库与刷新回放只在结尾简短带过。
>
> **口径**：纯概念稿，**不出现类名、方法名、代码片段**。事件名是协议本身的词汇，保留。**例外**：二·五 是实现版，允许类名、方法名、代码。
>
> **不在本篇**：记忆抽取与游标。会话标题、落库细节、并发闸门、评测侧消费只做一句话说明。
>
> **署名边界**：服务端协议、事件桥、生命周期、跨节点取消是**我主导设计并实现**的；前端解析与投影层由前端同学实现，我负责定义契约——所以文里讲前端的地方，讲的是**我定的约束**，不是"我写的代码"。
>
> **怎么用**：先读**第二部分的线**建立整体认知，再背**第五部分的追问链**。别反过来——先背问答会得到一堆孤立的机制，说不出流程。

## 一、一页纸总览

### 1.1 这条流跨了三个边界

```
┌─────────┐   ① HTTP + SSE    ┌──────────┐   ② 响应式事件流   ┌──────────┐
│ 浏览器   │ ◄──────────────► │ 服务端    │ ◄───────────────► │ Agent 引擎│
└─────────┘                   └──────────┘                    └──────────┘
     ▲                              │
     │                              │ ③ 中间有一座桥：把引擎事件翻译成对前端的契约
     └──────────────────────────────┘
```

| 边界 | 两边是什么 | 谁负责转换 |
|---|---|---|
| ① 浏览器 ↔ 服务端 | 单向 SSE 帧；请求侧是普通 HTTP | 服务端写帧、前端手写解析 |
| ② 服务端 ↔ 引擎 | 引擎吐出的是**响应式事件流** | 服务端**命令式订阅**它 |
| ③ 引擎事件 → 前端契约 | 引擎只说"过程"，前端要"可渲染的过程" | **桥**：翻译、缓冲、截断、补建、投影时间 |

### 1.2 一条流的一生（鸟瞰）

```
浏览器                服务端                         引擎
  │                     │                             │
  │ ① GET 提问           │                             │
  ├────────────────────►│                             │
  │                     │ ② 建流对象（还不发帧）        │
  │                     │ ③ 抢并发闸门（失败→普通JSON） │
  │                     │ ④ 前置准备（标题/用户消息）    │
  │                     │ ⑤ 装配（时钟/事实源/句柄）     │
  │ ⑥ meta 帧           │                             │
  │◄────────────────────┤                             │
  │                     │ ⑦ 订阅引擎事件流 ───────────►│
  │ ⑧ message 增量       │◄──────────── 文本增量 ───────┤
  │◄────────────────────┤                             │
  │ ⑨ block 帧           │◄──────────── 工具事件 ───────┤
  │◄────────────────────┤                             │
  │ ⑩ confirm 帧         │◄──────────── 要求确认 ───────┤
  │◄────────────────────┤                             │
  │ ⑪ finish + done      │◄──────────── 流结束 ─────────┤
  │◄────────────────────┤                             │
  │ ⑫ 解析 → 投影 → 渲染  │                             │
```

### 1.3 一句话本质

> **这条流不是"模型吐 token 的转发"，而是"一次推理过程的投影"。**

三件事依次对应三个边界：
- 引擎负责**产生过程**（文本、工具、确认）
- 桥负责**把过程翻译成契约**（增删改）
- 浏览器负责**把契约投影成界面**（不推断、只照抄）

**整篇文档的所有设计，都是为了保证"投影是可信的"**——帧里的状态和时间，必须和落库、和刷新后回放看到的一模一样。

### 1.4 线上形态

**4 个实例，前面是负载均衡，Redis 做取消广播和闸门。** 这条事实决定了后面一个核心不对称：

> **连接是单机的，取消是跨节点的。**

一条 SSE 连接只活在某一台机器上，别的节点碰不到。所以"停止"这个动作天生就要跨节点——这是本设计里最难、也最值得讲的一块。

## 二·五、线程与对象：从外到内拆解

> **这一章是「实现版」**：保留真实类名、方法名与线程名，方便对照代码。文首口径对本章不适用。
>
> 第二章按"时间"讲了一遍，这一章按"结构"再讲一遍——**谁持有谁、代码在哪条线程上跑、桥到底站在哪**。

下面按**从外到内、从创建到销毁**的完整顺序拆一遍。先给全局骨架，再逐层展开。

---

### 2.5.1 全局骨架：一次请求只有 5 步

```
① 浏览器发请求
       ↓
② Tomcat 线程接住，创建 SseEmitter，返回
       ↓
③ Spring 把连接挂起（不关、不占线程）
       ↓
④ 业务组装对象：sender / runHandle / bridge，然后订阅 AgentScope 的事件流
       ↓
⑤ AgentScope 在别的线程上产出事件 → bridge 转成 SSE 帧 → 写回连接
```

第 ⑤ 步会重复几百次（每个 token 一次），直到流结束。

**理解整个结构的关键**：Tomcat 线程只负责 ② 和 ④ 的一部分。真正干活的是第 ⑤ 步里的**另一批线程**。

---

### 2.5.2 空间结构：对象从属关系

一个请求进来后，创建出来的对象是这样套起来的：

```
AgentChatController
 │  持有 SseEmitter（Spring 给它，代表这条 HTTP 连接）
 │
 └─ AgentChatServiceImpl
     │
     ├─ SseEmitter                    ← 连接的门把手
     │    └─ 被包装成
     ├─ SseEmitterSender             ← 加了一个 closed 开关
     │
     ├─ ReActAgent（单例，来自 Provider）
     │    └─ streamEvents(...) 产出
     ├─ Flux<AgentEvent>             ← 事件流（每次订阅新建）
     │
     ├─ AgentToolExecutionFacts      ← 事实源：批次号、时刻、工具结果
     │
     ├─ AgentRunHandle               ← 生命周期管家
     │    ├─ taskId
     │    ├─ sender ──────────────┐
     │    ├─ lifecycleLock        │
     │    └─ settled              │
     │                            │
     └─ AgentStreamEventBridge  ←─┘  ← 事件翻译官
          ├─ sender（从 runHandle 拿）
          ├─ runHandle
          ├─ stateLock
          ├─ blocks / openTextBlock / sealedTextBlocks
          └─ facts

全局单例：
StreamTaskManager
 ├─ tasks: Cache<taskId, StreamTaskInfo>
 └─ Redis：取消标记 + 属主 + 广播频道
```

三个对象的分工：

| 对象 | 一句话职责 | 有锁吗 |
|------|-----------|--------|
| `SseEmitterSender` | 把数据写进这条连接，连接关了就不写 | 无锁，`AtomicBoolean closed` |
| `AgentRunHandle` | 保证 complete/cancel/fail 三条出口只有一条收尾 | `lifecycleLock` |
| `AgentStreamEventBridge` | 把 AgentScope 事件翻译成 SSE 帧，同时维护消息状态 | `stateLock` |
| `StreamTaskManager` | 跨节点取消 | `AtomicBoolean` + Redis |

**桥不是线程，也不是连接，它就是一个普通对象**。谁调用它的 `onEvent`，它就借用谁的线程执行。

### 2.5.3 时间结构：一次请求的完整生命周期

#### 阶段 1：接住请求（Tomcat 线程）

```
http-nio-9090-exec-3
  │
  ├─ AgentChatController.chat()
  │    SseEmitter emitter = new SseEmitter(900_000);
  │    agentChatService.streamChat(question, conversationId, emitter);
  │    return emitter;
  │
  ├─ Spring 发现返回值是 SseEmitter
  │    → request.startAsync()
  │    → emitter.initialize(...)
  │
  └─ 方法返回，worker 归还线程池  ← 注意：此时一个字节都还没发
```

**这条连接现在的状态**：挂着，等有人往它里面写。

#### 阶段 2：组装对象（仍然是 Tomcat 线程）

`streamChat` 是同步调用，所以下面这些都在 `http-nio-9090-exec-3` 上执行：

```
launchStream(...)
  │
  ├─ new AgentToolExecutionFacts(taskId, clock)
  ├─ new SseEmitterSender(emitter)
  ├─ new AgentRunHandle(taskId, sender, taskManager, facts, ctx)
  ├─ bindReleaseHooks(runHandle, agent, scope)
  │    ├─ 收尾钩子1：需要补存盘就存
  │    ├─ 收尾钩子2：释放会话锁
  │    └─ 收尾钩子3：调度记忆抽取
  ├─ bindEmitterLifecycle(emitter, runHandle, taskId)
  │    └─ onTimeout/onError/onCompletion → 转异步 cancel
  ├─ sender.sendEvent(META, {conversationId, taskId})   ← 第一帧
  ├─ new AgentStreamEventBridge(...)
  ├─ taskManager.register(taskId, userId, bridge::finishCancelledStream)
  └─ runHandle.start(() -> {
         events.subscribe(bridge::onEvent, bridge::onError, bridge::onComplete);
         runHandle.bindStream(disposable, interruptAction);
         taskManager.bindHandle(taskId, runHandle::interruptUpstream);
     })
```

**到这里，对象全都建好了，事件流还没开始跑。**

#### 阶段 3：订阅（Tomcat 线程 → 切走）

`events.subscribe(...)` 这一行是整条链的转折点：

```
http-nio-9090-exec-3
  │
  │ events.subscribe(bridge::onEvent, bridge::onError, bridge::onComplete)
  │   ① 创建 subscriber
  │   ② 向上游发 request(Long.MAX_VALUE)
  │   ③ 遇到 .subscribeOn(boundedElastic)
  │         → 把"继续订阅"打包成任务
  │         → 提交给 BoundedElasticScheduler
  │
  └─ subscribe() 返回，Tomcat 线程继续往下走，最后归还
```

**从这一刻起，Tomcat 线程和这条流没有任何关系了。**

#### 阶段 4：AgentScope 干活（boundedElastic 线程）

```
boundedElastic-7
  │
  ├─ 订阅真正到达 OkHttpTransport
  ├─ while (readLine() != null)
  │    │
  │    ├─ 解析出一个 token
  │    ├─ sink.next(TextBlockDeltaEvent)
  │    │     └─► 同步调用下游 onNext
  │    │           └─► bridge.onEvent          ← 桥在这里被调用
  │    │                 ├─ synchronized(stateLock) { 改 blocks }
  │    │                 └─ sender.sendEvent(MESSAGE, delta)
  │    │                       └─► emitter.send → socket → 浏览器
  │    │
  │    └─ 下一个 token
  │
  └─ 流读完，sink.complete()
```

**同一时间，工具执行可能发生在另一条线程上：**

```
boundedElastic-12
  │
  ├─ 执行某个工具
  ├─ 通过 AgentEventEmitter.emit(...) 把工具事件回推
  │    └─► sink.next → bridge.onEvent
  │
  └─ 工具结束，线程归还
```

所以**桥会被多条线程调用**，这就是 `stateLock` 存在的原因。

#### 阶段 5：收尾

```
boundedElastic-7
  │
  └─ sink.complete()
       └─ bridge.onComplete()
            └─ runHandle.complete(body)
                 └─ settle(body)  ← 进入 lifecycleLock
                      ├─ settled = true
                      ├─ body.run()
                      │    ├─ settleAndPersistMessage()  落库，拿 messageId
                      │    │    ├─ synchronized(stateLock) 取快照
                      │    │    ├─ flushSealedTextBlocks()
                      │    │    └─ conversationService.addAssistantMessage(...)
                      │    ├─ sendEvent(FINISH, {messageId, title, status})
                      │    └─ sendEvent(DONE, "[DONE]")
                      ├─ taskManager.unregister(taskId)
                      └─ runReleaseHooks()
                           ├─ 补存盘
                           ├─ 释放会话锁
                           └─ 调度记忆抽取
                  ← 退出 lifecycleLock
            └─ sender.complete()
                 └─ AsyncContext.complete()
                      └─ Tomcat 触发 onCompletion
                           └─ recycleUpstream → 发现已 settled，不重复取消
```

**连接在这里才真正关闭。**

#### 阶段 6：异常路径（取消）

```
用户点停止
  │
  ▼
http-nio-9090-exec-8  （另一条 Tomcat 线程，另一个请求）
  │ POST /agent/v1/stop
  └─ taskManager.cancelByUser(taskId)
       ├─ 校验 Redis 里的属主
       ├─ 写 Redis 取消标记
       └─ 发布广播

任意节点的 Redisson 监听线程
  │
  └─ cancelLocal(taskId, requester)
       ├─ 复核属主
       ├─ CAS cancelled = true
       ├─ cancelAction.run()       → runHandle.interruptUpstream()
       │    ├─ agent.interrupt()
       │    ├─ 等 2 秒优雅结束
       │    └─ 超时则 disposable.dispose()
       └─ finalizer.run()          → bridge.finishCancelledStream()
            ├─ synchronized(stateLock) 取快照
            ├─ 落库（INTERRUPTED）
            └─ sendEvent(CANCEL) + sendEvent(DONE)
                 └─ runHandle.cancel(body) → settle → sender.complete()
```

**取消路径和正常路径走的是两套线程，但共用同一把 `stateLock`** —— 这就是"锁内改状态、锁外发帧"要解决的问题。

### 2.5.4 线程结构：谁在什么时候跑

| 线程 | 谁创建 | 什么时候跑 | 干什么 | 活多久 |
|------|--------|-----------|--------|--------|
| `http-nio-9090-exec-N` | Tomcat | 请求到达 | Controller、组装对象、subscribe | 毫秒级 |
| `boundedElastic-7` | Reactor | `subscribeOn` 后 | 模型阻塞读 + 每 token 回调 | 整个模型响应期 |
| `boundedElastic-12` | Reactor | 工具执行时 | 工具执行 + 工具事件回推 | 工具耗时 |
| `boundedElastic-21` | Reactor | 取消时 | `taskManager.cancel` | 取消耗时 |
| Redisson 监听线程 | Redisson | 广播到达 | `cancelLocal` | 瞬时 |
| Tomcat AsyncTimeout | Tomcat | 超时扫描 | `onTimeout` 回调 | 瞬时 |
| Tomcat Poller | Tomcat | 写失败 | `onError` 回调 | 瞬时 |

**注意最后三行**：容器生命周期回调线程很宝贵，所以项目在 `bindEmitterLifecycle` 里把它们转手给 `boundedElastic`：

```java
Schedulers.boundedElastic().schedule(() -> taskManager.cancel(taskId));
```

### 2.5.5 数据流的完整管道

```
AgentScope 内部事件
   AgentEvent
      │
      │  publishEvent → sink.next
      ▼
   FluxSink
      │
      │  onNext（同步，在发射线程上）
      ▼
   bridge.onEvent  ──────────────────────┐
      │                                  │
      │  ① 按事件类型分发                  │
      │  ② stateLock 内改状态              │
      │  ③ stateLock 外构造要发的帧         │
      ▼                                  │
   SseEmitterSender.sendEvent            │
      │  检查 closed                      │
      ▼                                  │
   SseEmitter.send                       │
      │                                  │
      ▼                                  │
   HttpServletResponse.getOutputStream   │
      │                                  │
      ▼                                  │
   Tomcat 输出缓冲 → socket → 浏览器       │
                                         │
   状态数据（blocks）─────────────────────┘
      │
      └─ 收尾时落库 → t_message / t_knowledge_chunk 等
```

### 2.5.6 用一句话串起来

> Tomcat 线程接住请求、把连接挂到 `AsyncContext` 上、组装好 `sender` / `runHandle` / `bridge` 三个对象，然后**把事件流订阅交给 Reactor**；Reactor 在 `boundedElastic` 线程上跑模型和工具，每产出一个事件就同步回调 `bridge.onEvent`；`bridge` 在锁内改状态、锁外把帧通过 `sender` 写回那条挂起的连接；流结束时 `runHandle` 负责只收尾一次，最后 `sender.complete()` 关闭连接。

### 2.5.7 如果还想再简化

把这套东西想成一个**快递中转站**：

| 角色 | 对应 |
|------|------|
| 客户下单 | 浏览器发 HTTP 请求 |
| 前台收单，给你一张取件码 | Tomcat 线程创建 `SseEmitter` 并返回 |
| 前台去忙别的了 | worker 归还线程池 |
| 仓库（AgentScope）慢慢生产 | `boundedElastic` 上跑模型和工具 |
| 每产出一个包裹就送到中转台 | `sink.next` → `bridge.onEvent` |
| 中转台贴单、记录、打包 | `bridge` 改状态、转协议 |
| 装车发走 | `sender.sendEvent` → socket |
| 全部发完，关单 | `complete()` + `AsyncContext.complete()` |
| 客户中途取消 | `/stop` → Redis 广播 → 各节点取消 |

中转台（`bridge`）只有一个，但**多个仓库工人会同时往这里送包裹**，所以贴单的时候要上锁——这就是 `stateLock`。而上锁的时候不能去装车（发帧），因为装车慢，会堵住其他工人——这就是"锁内改状态、锁外发帧"。

## 三、8 个事件速查

| 事件 | 什么时候发 | 载荷要点 | 落库 |
|---|---|---|---|
| **meta** | 订阅前，**第一帧** | 会话 id、任务 id | — |
| **message** | 文本增量 | `type` = 回答 / 思考 / 错误 + 增量文本 | 累积进块 |
| **block** | 块状态变化 | 见下 | 是（块序列） |
| **hint** | 系统级提示 | 提示码 + 文案 | **否** |
| **confirm** | 等待用户确认 | 消息 id、标题、待确认调用清单、耗时 | 是（状态=待确认） |
| **finish** | 本轮结算完成 / 异常中断 | 消息 id、标题、状态、总耗时 | 是 |
| **done** | 每条出口的**最后一帧** | 固定字面量 | — |
| **cancel** | 用户取消 | 消息 id、标题、状态、总耗时 | 是 |

**`block` 帧有两种形态，靠 `kind` 区分**

| 形态 | 载荷 | 何时 |
|---|---|---|
| **文本块封口** | 类型、开始时刻、结束时刻、时长 | 文本块断开的瞬间 |
| **工具块进度** | 类型、工具 id、**调用 id**、可读名、状态、结果、批次、批内序号、起止、耗时、耗时来源 | 工具状态每次变化 |

> 注意：**文本块只有"封口"这一个时刻会发 `block`**，过程中只发 `message` 增量。工具块则相反——**每次状态变化都发 `block`**。

## 四、帧顺序的六条硬约束

这六条是"实现对不对"的判据，面试可以当成 checklist 用。

| # | 约束 | 违反的后果 |
|---|---|---|
| 1 | **`meta` 必须是第一帧** | 前端无法归属后续帧，停止按钮拿不到任务 id |
| 2 | **封口帧必须早于终态帧** | 前端收到终态后不再收块，最后一段永远不封口 |
| 3 | **`finish` 与 `confirm` 互斥** | 前端先渲染"完成"再渲染"待确认"，状态打架 |
| 4 | **终态帧与 `done` 成对** | 前端无法区分"正常结束"和"连接被掐断" |
| 5 | **落库失败不发带 id 的终态** | 前端拿空 id 做后续操作，直接失败 |
| 6 | **没有起止的块不发封口帧** | 前端错误收口正在接收的块，界面错位 |

```
  ├─ ③ hasPendingConfirm ? → 抛                    ← 上一轮还在等裁决
  │
  ├─ ④ 前置准备：建会话 / 取标题 / 用户消息落库
  │
  ├─ ⑤ 装配：Clock → 事实源 → 发射器 → 生命周期句柄 → 绑定释放钩子链
  │
  ├─ ⑥ bindEmitterLifecycle                        ← 注册三个容器回调
  │

  │
  ├─ ⑧ taskManager.register(taskId, userId, 收尾回调)
  │      · 属主写进 Redis（TTL 30 分钟）
  │      · 回查取消标记 —— 若已被取消，当场收尾，然后 return
  │        ★ 引擎根本不启动，这就是"取消早于注册"的兜底
  │
  ├─ ⑨ 建 Flux（此时只是拿到一个"流"，还没订阅，引擎没跑）
  │
  └─ ⑩ runHandle.start {                          ← 锁内
           结算确认卡 → subscribe → 绑定中断动作
           失败 → 先 dispose 订阅 → 再抛
       }
  │
  └─ return emitter                                ← Servlet 异步化
Tomcat 请求线程归还 ──────────────────────────────────────────
```

**三个必须点出来的位置：**

| 位置 | 为什么重要 |
|---|---|
| **② 抢闸门在请求线程上同步 join** | 用异步 API 是为了拿到可控的失败；`join` 是为了在建流**之前**就失败。异步抢锁 + 同步等待，是"零帧阶段必须干净失败"的直接要求 |
| **⑦ 发 meta 在请求线程上** | 第一帧是最早能发的一帧。它一发出去，这个请求就从"可能返回 JSON"切换到"只能流内表达" |
| **⑩ 整段在生命周期锁里** | 结算卡片、订阅、绑定中断动作必须原子。否则取消先跑完收尾、这边再订阅，用户的写操作照样执行一遍 |

#### 图 3 · 线程模型（谁在什么线程上干活）

| # | 线程 | 由谁触发 | 干什么 | 阻塞风险 |
|---|---|---|---|---|
| 1 | **Tomcat 请求线程** | 用户请求 | 建流、抢闸门、前置准备、发 meta、订阅；构造完就归还 | 抢锁 `join`、首帧写 |
| 2 | **引擎 / Reactor 线程** | 引擎吐事件 | 桥翻译、锁内改块状态、出锁发帧 | **发帧阻塞会直接卡住这条流** |
| 3 | **容器回调线程** | 超时 / 错误 / 断连 | 只做一件事：把取消**提交**到弹性线程池 | 必须极短，不能做业务 |
| 4 | **弹性线程池** | 线程 3 提交 | 执行本地取消：打断引擎（等 2 秒）→ 收尾 | 最多阻塞 2 秒 |
| 5 | **Redis 订阅线程** | 其他节点的广播 | 复核发起方 → 打断引擎 → 收尾 | 最多阻塞 2 秒 |
| 6 | **Redis 看门狗** | 定时续期 | 给闸门锁续期，保证长流不被误释放 | — |

**线程 2 的说明（面试常被问）**：订阅之后回调落在哪个线程，**由引擎决定，编排层不假设**。所以桥不依赖线程亲和——它只用一把锁保护自己的状态，任何线程进来都一样。

#### 图 4 · 一次取消，线程怎么交接

```
【本地取消】用户关页面 / 超时 / 断连

  [3] 容器回调线程  onTimeout / onError / onCompletion
        │   只做一件事：schedule，立刻返回
        ▼
  [4] 弹性线程池   taskManager.cancel(taskId)      ← 不走 Redis，本机直达
        │   ├─ cancelAction：打断引擎，等上游终止 ≤ 2 秒
        │   └─ finalizer：封口块 → 落库 → cancel 帧 → done → 释放链
        ▼
      客户端收到 cancel + done


【跨节点取消】停止请求落在节点 B，流在节点 A

  [B] Tomcat 线程   cancelByUser
        │   查 Redis 属主 → 比对当前用户 → 不一致统一回"任务不存在"
        ▼
  [B] 写 Redis 标记(TTL 30min) → 广播 topic: taskId|发起方
        │
        ├──────────── 4 个节点都收到 ────────────┐
        ▼                                        ▼
  [A] Redis 订阅线程                       [C/D] Redis 订阅线程
        │  本地任务表没有 → return              本地没有 → return
        │  复核发起方 → 不匹配 → return（且不置任何标志）
        │  CAS 抢占"已取消"
        │  cancelAction → 打断（等 2 秒）
        │  finalizer → 收尾
        ▼
      客户端收到 cancel + done
```

**注意图里的两个"立刻返回"**：容器回调线程和 Redis 订阅线程都**不是**业务线程，能越早交出去越好。容器回调只提交、不执行；广播监听里非属主节点只查表、不复核。

#### 图 5 · 线程之间共享了什么，靠什么保护

| 共享物 | 谁写 | 谁读 | 保护手段 |
|---|---|---|---|
| 桥的块状态（开着的文本块、工具块表） | 引擎线程 | 引擎线程 | **一把状态锁**：锁内改状态，锁外发帧 |
| 生命周期句柄（已收尾？要补存盘？） | 三条出口 | 三条出口 | **可重入锁**（同步结束会重入） |
| 本地任务表（taskId → 属主/回调） | 注册、取消 | 取消、绑定 | 并发 Map + **原子布尔 CAS** |
| 发射器开关 | 任意 | 任意 | **原子 CAS**，关一次生效 |
| Redis 属主 / 取消标记 | 各节点 | 各节点 | Redis 原生 + TTL 兜底 |

**三条"不要跨线程做"的规则（这三条答出来，线程模型就算讲清楚了）：**

1. **容器回调线程不做业务**——它只负责提交，执行交给弹性线程池。
2. **持锁期间不做 IO**——锁只保护内存状态，发帧一律出锁。
3. **收尾只跑一次**——不管从哪个线程进来，抢到收尾权的那一个才准改标志、才准写库、才准发终态。

> 🪝 **这一节的钩子**：图 2 的第 ⑧ 步——"注册时发现已被取消，引擎根本不启动"。**取消怎么会跑在注册前面？** 这就是 Q10 / Q11 要讲的东西。

### Q1 · 开场总览（45 秒口播 + 一张时序图）

**面试官追问**：你这个 SSE 流式是怎么做的？

**我**：

一句话：**它不是把模型的 token 转发给前端，是把一次推理过程投影成一条可信的帧序列。**

拆开是六段——建流、抢闸门、前置、装配发首帧、登记订阅、推帧。先看时序，再讲顺序。

```
浏览器          网关           服务端实例                              Agent 引擎
  │              │                 │                                        │
  │ 提问          │                 │                                        │
  ├─────────────►├────────────────►│ ① 建流：连接交出去，15 分钟，一帧不发
  │              │                 │ ② 抢闸门：会话互斥 + 每人最多 5 条
  │              │                 │ ③ 前置：查挂起确认 → 建会话 → 消息落库
  │              │                 │ ④ 装配：时钟 / 工具事实源 / 发射器 / 句柄
  │ event: meta  │                 │    装配完立刻发首帧——整条流只发这一帧
  │◄─────────────┼─────────────────┤ ⑤ 登记任务，再进启动锁订阅事件流
  │              │                 │                        ──────────────►│
  │              │                 │◄────────── 文本增量 ───────────────────┤
  │ event:message│                 │ ⑥ 推帧：桥翻译成帧                      │
  │◄─────────────┼─────────────────┤◄────────── 工具状态 ───────────────────┤
  │ event: block │                 │ 块状态机在服务端封口                     │
  │◄─────────────┼─────────────────┤◄────────── 要求确认 ───────────────────┤
  │ event:confirm│                 │ 流关闭，会话挂起                        │
  │◄─────────────┼─────────────────┤◄────────── 流结束 ─────────────────────┤
  │ event:finish │                 │ 先落库拿消息 id                         │
  │ event: done  │                 │ 再发终态                                │
  │◄─────────────┼─────────────────┤                                        │
```

六段，每段为什么必须在这一格：

**① 建流——一帧都不发。**
先把连接交出去，超时定 15 分钟。此刻还没有任何帧，所以后面任何一步失败，都还能干净地返回一个普通 JSON 错误。

**② 抢闸门——必须紧跟着建流。**
同一会话互斥，同一用户最多 5 条。抢不到就直接抛——因为一帧没发，前端拿到的是普通错误，而不是一条"刚开始就断了"的流。

**③ 前置——三件有副作用的事。**
查上一轮是不是还挂着确认、建会话并取标题、用户消息落库。**必须先于订阅**：消息不落库，后面工具执行产生的回复就没有可以挂靠的那条用户消息。

**④ 装配 + 首帧。**
把一个时钟、一个工具事实源、一个发射器、一个生命周期句柄备齐，然后发出第一帧 meta，只带会话 id 和任务 id。

> 这一帧是分水岭：**发出去之前，失败可以回 JSON；发出去之后，失败只能走流内表达。**

**⑤ 登记 + 订阅——整段在启动锁里。**
先按任务 id 登记本地任务和属主，让取消系统认识这个任务；再进一把锁，把"结算上一条确认卡、订阅事件流、交出中断动作"三件事一起做完。

> **六段里只有这一段不能挪。** 挪了不是顺序难看，是**用户点了停止、这轮照样跑完并执行一遍写操作**。

**⑥ 推帧——桥只翻译，不编排。**
引擎事件进来，桥把它翻译成 8 种协议帧：文本增量、工具块、系统提示、确认、三种终态。翻译过程中要做四件事——过滤、缓冲、截断、投影时间。

**收束**：所以这条流的本质是**投影**，不是转发。帧的顺序、块的边界、工具的时间，全都在服务端定死，前端只负责画。

> 🪝 **钩子**：六段里只有第 ⑤ 段不能挪，而且它不是"顺序问题"，是"竞态问题"。**为什么订阅要放在一把锁里？**

### Q2 · 为什么订阅要放在一把启动锁里？

**面试官追问**：你说"订阅整段在启动锁里"——这把锁到底防的是什么？我把顺序换一下会怎样？

**我**：

**换不了，因为这不是顺序问题，是竞态问题。**

先看事实顺序：**先登记任务和属主**（取消系统得先认识这个任务），**再进锁**做三件事——结算上一条确认卡、订阅引擎事件流、把"怎么打断上游"交出去。

危险就藏在**登记和订阅之间**那段空隙里。这期间任务在取消系统里已经有记录了，取消完全落得进来：

```
登记完成 ──►【空隙】取消到达 ──► 收尾跑完：补存盘 / 清缓存 / 放闸门 / 注销
                                        │
                                        └──► 这边才订阅 ──► 引擎从头再跑一轮
```

结果就是：**用户明明点了停止，这一轮的工具照样执行了一遍。**

所以订阅必须和"这轮是不是已经结束了"的判断待在同一个互斥区里。进锁第一件事就是看一眼——**已结算或已取消，直接不订阅**，把最坏情况挡在锁外。

**为什么这把锁必须可重入？**

因为引擎的流可能同步结束：一订阅就回调完成。收尾就发生在**订阅这条调用栈上**，而收尾要的是同一把锁。不可重入，这里当场自锁。

**代价是什么？**

锁里做了订阅，持锁时间被拉长。但订阅只是登记回调，推理跑在别的线程，不会占住一个推理周期。真正的代价是**启动路径上多了一道互斥**——所有并发提问都要过它。所以这把锁的粒度必须小到只包这几步，绝不能把前置、装配这些 IO 也圈进去。

**兜底**：订阅之后才抛异常 → 当场把订阅掐掉再往上抛。否则一条没人管的流会空转到迭代上限。

> 🪝 **钩子**：订阅之后事件就进来了。接着就是那句——**引擎事件为什么不直接透给前端？**

---

### Q3 · 引擎事件为什么不直接透给前端？

**面试官追问**：引擎吐出来的事件，你直接转给前端不行吗？为什么中间要加一层？

**我**：

**不行，因为引擎事件是引擎的私有语义，不是给前端的契约。** 三个原因，从重到轻：

**第一，契约的稳定性不能押在第三方框架上。**
引擎升级可能改名、拆合事件、加内部事件。前端如果直接依赖，**升级一次全崩**。中间有一层桥，引擎怎么变，我只改桥。

**第二，粒度不匹配。**
工具结果是**逐段吐**的，一段文档可能吐几百次。直接透出去，前端帧数爆炸、渲染卡死。所以必须**在服务端缓冲，等工具结束时一次性给**，还要做 64K 截断。

**第三，有些事件不该透。**
引擎有的内部事件是给自己用的，不是用户要看的，直接过滤掉。

**所以桥的本质是翻译，而且翻译过程中一定要增删改**：

```
引擎事件 ──► 过滤 ──► 缓冲 ──► 截断 ──► 补建 ──► 投影时间 ──► 协议帧
```

| 动作 | 具体做什么 |
|---|---|
| **过滤** | 内部事件不对外 |
| **缓冲** | 工具结果先攒着，结束才发 |
| **截断** | 超过 64K 直接丢，不落库不展示 |
| **补建** | 三种场景下工具块没有开头事件，得手动建 |
| **投影** | 时间不从桥取，从事实源抄 |

**代价**：多一层就多一个可能出错的地方——桥自己要维护块状态、要加锁、要处理补建。**兜底**是把桥的所有状态收敛到一把锁里，且**锁内只改状态、锁外才发帧**。

> 🪝 **钩子**：说到锁，就有人问——**为什么发帧一定要放到锁外面？**

---

### Q4 · 为什么锁内改状态、锁外发帧？

**面试官追问**：你这里加锁我能理解，但为什么发帧要挪到锁外面？

**我**：

**先澄清一下：不是"很多线程抢这把锁"。** 同一条订阅里，事件是**串行投递**的（一个订阅者在任何时刻只有一个线程在回调），不同会话又是不同的桥、不同的锁。所以这里不存在 A、B、C、D 四个线程排队的情况。

**真正的理由是：这把锁有第二个使用者——取消收尾。**

```
引擎线程：synchronized { 改块状态 }   →  出锁  →  send
取消线程：synchronized { 封口 + 发终态 }       ← 同一把锁
```

用户点停止时，收尾要拿同一把锁去封口块、结算工具、发终态帧。所以一旦把发帧放进锁里：

```
引擎线程  持锁 → send 卡住（客户端慢 / TCP 缓冲满）→ 一直不放锁
取消线程  用户点停止 → 等锁 → 卡住 → 收尾发不出去
                          ↑
            用户看到的是"点了停止没反应"
```

**卡住的不是吞吐，是"停不下来"**——这比慢更严重。

所以规则是：**锁内只改内存状态，出锁之后再发帧。**

```
① 锁内：判断要不要封口、建块、算起止 —— 只动内存
② 出锁
③ 锁外：拿着锁内算好的快照，把帧发出去
```

**代价**：慢客户端仍然会卡住**这条流**的引擎线程（发帧本身是阻塞 IO，出锁躲不掉这一层）；多一次快照拷贝，代码也多一点。

**兜底**：发帧是**幂等 + 静默失败**的——连接关了就直接返回，发失败就静默关闭，**不抛异常**。因为响应已经开始写了，这时候抛会被全局异常处理器二次处理，把一次正常断连变成一条无意义的错误。

> 🪝 **钩子**：那块的边界到底由谁说了算——服务端封口，还是前端自己推断？

### Q5 · 文本块的边界怎么保证？

**面试官追问**：流式文本一块一块的，你怎么知道哪一段属于同一个块？

**我**：

**块在服务端封口，前端不推断。**

三个封口时机，缺一不可：

| 触发 | 场景 |
|---|---|
| **类型变了** | 思考转回答，或回答转思考 |
| **工具事件来了** | 工具是过程的一部分，文本必须先断 |
| **流收尾了** | 最后一个块由收尾统一封口 |

封口时盖结束时间戳、算时长，**出锁之后**才发封口帧。

**为什么不能让前端推断？**
因为刷新重放的时候，前端手里只有落库的块，没有生成过程。它如果当时是自己算的起止，重放时算出来的和第一次不一样，**界面就会跳**。

**这里有个最容易做错的边界：只广播"有起止"的块。**

有两种块没有起止：

- 非流式终答的兜底补发（引擎直接给一段完整文本）
- 异常时的中断提示

这两种是**一次性补发**，没有生成过程，所以**不给起止，也不发封口帧**。

> 为什么？契约上要求前端按"封口帧到达顺序"去认领"最早那个还没收口的同类块"。你给一个没有起止的块发封口帧，前端会把**正在接收的那个块**错误地收口，界面直接错位。

> 🪝 **钩子**：说到起止，工具那边的起止是谁记的？也是桥吗？

### Q6 · 工具的执行时间为什么不由桥记录？

**面试官追问**：工具的执行耗时，你在桥里算一下不就行了？

**我**：

**不行，因为同一个事实有两个算法，迟早会算出两个值。**

同一次工具调用，会出现在**两个地方**：
- 工具卡片上（展示"执行了 1.2 秒"）
- 对应的文本块封口帧里（也带耗时）

如果卡片用工具自己记的、文本块用桥打的时间，**两处显示的数字会不一样**。用户和面试官都会看到。

所以规则是：**桥只投影，不测量。**

| 数据 | 谁产生 | 谁读 |
|---|---|---|
| 批次号 | 工具执行侧（进入一批时开） | 桥、前端、落库 |
| 批内序号 | 工具执行侧（首个观测者分配） | 同上 |
| 单工具起止 | 工具执行侧（进入/退出工具体时打点） | 同上 |
| 本轮起点 | 事实源构造那一刻 | 轮次总耗时 |

**这里踩过一个很典型的坑：计时锚点挂错了。**

最早是在"模型开始吐工具参数"那一刻打时间。结果工具卡片**把模型生成参数的时间也算进去了**——用户看到"查订单耗时 3.2 秒"，实际执行只有 200 毫秒，剩下 3 秒是模型在写参数。

改法：**计时锚定在真正进入工具执行体那一刻**；模型吐参数的时间归到"准备阶段"，不算工具耗时。改完之后，卡片上的数字才和用户直觉对得上。

**顺手一个细节**：批次的终点取的是**这一批真正的结束**，不是"成员里最晚结束的那个"。因为权限判定和后处理也算在批里，取最晚成员会把这部分时间漏掉。

**还有一条约束**：如果这一批被中途截断（比如取消），**不能编造结束时间**——有结果的按它自己的结果结算，没结果的判 `interrupted` 并取中断时刻，而不是拿批次结束时刻糊上去。

**代价**：桥必须持有事实源的引用，并且知道什么时候去取。

**兜底**：事实源里的每个时刻都是**原子地写一次**，重试、重复订阅都不会改已经定格的时刻。

> 🪝 **钩子**：工具有七种状态，其中"等确认"这个状态有个坑——一批工具里只要有一个要确认，剩下的怎么办？

### Q7 · 一批工具里有一个要确认，剩下的怎么办？

**面试官追问**：并行调了三个工具，其中第二个需要用户确认，另外两个直接跑吗？

**我**：

**不跑。整批都改成"等待确认"。**

因为**它们是一个事务边界**——模型是一批提出来、一批执行、一批回结果的。拆开跑，会出现"一半执行了、一半等你点"的中间态，语义上解释不清。

所以收到确认请求时：

```
① 封口当前文本块
② 所有还没到终态的工具块 → 统一改成 awaiting
③ 记录待确认清单
```

**只改卡片点名的那个会怎样？**
其余两个留在 `pending`。等流收尾时，`pending` 会被判成 `interrupted`——界面上显示"已中断"。**用户会以为自己点错了或者系统出错了**，而实际上是在等他确认。

**还有一条：整批被拒的块不给起止。**
因为它**从来没执行过**，给时间就是撒谎。前端应该显示"未执行"，不是"耗时 0 毫秒"。

| 场景 | 给批次号？ | 给起止？ | 前端应该显示 |
|---|---|---|---|
| 正常执行 | 给 | 给 | 耗时 |
| 等确认 | 给 | 不给 | 等待授权 |
| 整批被拒 | **不给** | **不给** | 未执行 |
| 收尾没结果 | 给 | 给（取中断时刻） | 已中断 |

> 🪝 **钩子**：这些状态和帧都要发出去，那**第一帧应该发什么？为什么它必须是第一帧？**

### Q8 · 第一帧为什么一定是 meta？

**面试官追问**：你发的第一个包是什么？

**我**：

**是 `meta`，载荷只有会话 id 和任务 id。**

**为什么必须是它：**

1. **后续所有帧都不带会话 id**，前端必须先拿到它，才能把后面的帧归到正确的会话上。
2. **任务 id 是停止按钮的唯一凭证**——停止接口只认任务 id。用户可能在第一帧之后两秒就想中断，所以停止能力必须尽早可用。

**更重要的是，这一帧划了一条规则分界线：**

```
发帧之前 → 任何失败都可以返回普通 JSON 错误
发帧之后 → 只能走流内表达：错误增量 → 落库 → 终态帧 → done
```

> 为什么这条线重要？很多实现把这两种混在一起，结果前端偶尔拿到一个 JSON 响应体，却按事件流去解析，**直接报错，而且报的是一个和真实原因毫无关系的错**。

**兜底**：前端那边也做了一次防御——如果响应的 Content-Type 不是事件流，就按 JSON 读，取里面的错误文案抛出去。两端对齐，才不会有"看不懂的错误"。

> 🪝 **钩子**：既然是流内表达失败，那**用户主动点停止**算哪种？停止为什么不能直接把连接断了？

### Q9 · 取消为什么不能直接断流？

**面试官追问**：用户点停止，你把连接关掉不就行了？

**我**：

**不行，因为引擎有跨轮状态要存盘。**

直接断流，框架连保存状态都来不及，**本轮的工具执行结果会丢**。下一轮 Agent 会"忘记"自己刚才做过什么——**可能把同一个写操作再执行一遍**。

正确顺序：

```
① 标记"这一轮被中断了"（供追踪）
② 打断引擎
③ 等上游流终止，最多 2 秒
④ 没等到 → 标记"需要补存盘" → 强制断流
⑤ 收尾：落库 → 发 cancel → 发 done
```

**这三步的顺序不能换**，尤其①②要在断流之前——一旦断了，追踪的 span 就结束了，再写属性没用。

**代价**：用户点停止之后，最多要等 2 秒才看到"已停止"。

**兜底**：即使等到了优雅终止，**也不代表存盘一定成功**。所以取消和异常这两条路径**都强制标记"需要补存盘"**，在释放钩子里再补一次。而且这个标记**只置位、不清零**——失败路径已经标记过的，取消流程不能把它冲掉。

**这条链上踩过两个坑，都很能说明问题：**

**坑一：关标签页漏了取消。**
最早只绑了"超时"和"出错"两个回调。用户直接关页时，容器**两个都不触发**，只走"完成"回调。结果是：用户关页走人，后台推理循环继续跑，**一直跑到迭代上限（10 轮）才停**——白白烧 token，而且如果这轮里有写操作，它照样执行。

改法：三个回调统一到一个取消动作，再用一个原子标志去重，避免重复提交。

**坑二：取消提交失败就永久丢了。**
取消要切到别的线程去跑（不能阻塞容器回调线程）。这里用了"一次性"去重标志：先置位、再提交。但**如果提交本身被线程池拒绝**，标志已经置位了，后续任何回调都不会再重试——**用户点了停止，彻底没反应**。

改法：提交失败时**把标志恢复回去**，允许后续生命周期回调重试。这是一个"去重"和"可靠性"打架的地方，去重让位给可靠性。

**还有一个容易忽略的点：取消不能记成故障。**
用户主动停止时，线程被打断，抛出来的是中断异常或取消异常。如果直接按普通异常上报，**告警里全是"用户停止"，真故障被淹没**。所以我加了一层判定：在这个出口上先判断"这是不是一次取消"，是的话按取消处理，不当故障。

顺带一个细节：中断异常会**清掉线程的中断标记**，如果不补回来，上游的判据就失灵了。所以还原取消异常时要把标记补回去。

> 🪝 **钩子**：这是单机的取消。**多实例部署，停止请求可能打到别的机器上，怎么办？**

### Q10 · 多实例下，停止怎么打到正确的节点？

**面试官追问**：你们线上有几台机器？用户的连接在 A，停止请求被负载均衡打到了 B，B 怎么把 A 上的流停掉？

**我**：

**线上 4 个实例。核心是一个不对称：连接是单机的，取消是跨节点的。**

一条流的连接对象活在某台机器上，别人碰不到。所以取消走 **"Redis 标记 + Pub/Sub 广播"**：

```
B 收到停止请求
  ├─ ① 校验属主
  ├─ ② 先写 Redis 取消标记（30 分钟 TTL）
  └─ ③ 再往广播主题发消息：任务id | 发起方
        ↓ 4 个节点都收到
A 上的监听器
  ├─ ④ 查本地任务表，没有 → 不是我这台的，return
  ├─ ⑤ 复核发起方（这一步才是真正的安全闸门）
  ├─ ⑥ 原子抢占"已取消"，抢不到就 return
  ├─ ⑦ 先打断上游（等 2 秒）
  └─ ⑧ 再跑收尾（落库 + cancel + done）
```

**为什么用广播而不是点对点？**
因为发停止请求的节点**根本不知道**这条流在哪台机器上。广播让"谁持有谁处理"，不用维护路由表。4 个节点里只有一个命中，其余三个在④就返回了——成本是可接受的。

**为什么先写标记、再发广播？**
**标记是持久事实，广播是通知。** 通知可能丢、可能当时没人在听；标记不会。注册的时候会**回查一次标记**，把窗口期漏掉的取消补上。

**代价**：每次停止多两次 Redis 往返，且 4 个节点都要处理一遍广播。

**这里踩过一个分布式才会有的坑：注销之后，任务被广播"复活"了。**

现象：一个已经结束的任务，被一条迟到的取消广播重新建出记录，然后收尾逻辑**第二遍执行**——重复推送、重复落库。

根因：查本地任务表用的是"取不到就新建"的语义。取消路径上沿用这个语义，等于**给一个已经死掉的任务重新投胎**。

改法：取消路径和绑定路径都改成**只查不建**——本地没有，说明不是我这台的（或者已经结束），直接返回。

> 🪝 **钩子**：第⑤步"复核发起方"——任务 id 本身能不能当凭证？

### Q11 · 任务 id 为什么不能当访问凭证？

**面试官追问**：停止接口传一个任务 id，我拿别人的 id 去停，行不行？

**我**：

**不行，而且这里是两段式校验：发布端宽松、执行端严格。**

**先说为什么 id 不能当凭证**：
任务 id 是**雪花 ID——时间有序、可预测**。不是随机不可猜的令牌。所以：

- 停止前先查 Redis 里的属主，和当前登录用户比对
- **不区分"任务不存在"和"你不是属主"**，统一返回"任务不存在或已结束"

> 为什么统一文案？否则停止接口就变成了**探测别人任务是否存在的工具**——能停的报一个错，不能停的报另一个错，等于告诉攻击者"这个 id 是真的"。

**再说那个不对称：**

| 位置 | 能不能查到属主 | 策略 | 为什么 |
|---|---|---|---|
| **发布端** | 可能查不到（注册还没落地） | **查不到就放行** | 它**分不清**"任务已结束"和"注册还没完成" |
| **执行端** | 一定查得到（能进执行端说明注册已跑过） | **严格比对** | 这就是兜底 |

**用执行端的严格，兜住发布端的盲区。** 所以广播载荷里必须带发起方——不只是为了日志，是为了让执行端能复核。

**最反直觉的一条：执行端拒绝时，连"已取消"标志都不能置。**

因为注册那一刻会**回查 Redis 标记**。如果提前把本地标志置成已取消，回查就被**短路**了（它第一步就是看这个标志）——等于踩一脚就把整道鉴权门绕过去。

所以：**拒绝 = 完全不动任何状态。**

**这条也踩过**：最早只做了发布端校验，结果发现**别人埋的标记照样能生效**。改成"标记里存发起方 + 执行端复核"之后，还要补上"拒绝时不置标志"，否则校验形同虚设。

> 🪝 **钩子**：这套广播…**发布过程中一半节点是新版本、一半是旧版本**，怎么办？

### Q12 · 滚动升级期间，老版本的广播怎么处理？

**面试官追问**：灰度发布的时候，老节点发的消息你没有 "|发起方" 这个字段，你会不会直接当非法丢掉？

**我**：

**不会，有一条显式的兼容分支。**

载荷解析是这么判断的：

```
找 "|" 的位置
  ├─ 找到了 → 新格式：前半任务 id，后半发起方
  └─ 没找到 → 老格式：只有任务 id，发起方按"系统侧"处理
```

**为什么必须兼容？**
发布过程中 4 个实例一半新一半旧。老版本发出的广播里**只有任务 id**。如果新版本把它当格式非法丢掉，那么**升级期间老节点发出的所有停止请求都会静默失效**——用户点了停止没反应，**而且不报错**。这种问题最难查。

**为什么可以直接当"系统侧"信任？**
因为老版本在发布前**已经做过同样的属主校验**了。这里不是降级，是**信任链条的延续**：上一跳验证过了，这一跳不重复验证。

**兜底**：即便这条分支判断错了，执行端还有一次复核——最坏是被拒，不是误杀。

### Q13 · 并发怎么控？为什么不用计数器？

**面试官追问**：同一个会话并发两条流会出事，你怎么挡？

**我**：

**两道闸门，都在编排层，不在网关。**

| 维度 | 解决什么 |
|---|---|
| **同一会话互斥** | 同一份会话状态被两条流同时改 |
| **每用户 5 个名额** | 一个用户开太多流，把资源占满 |

**名额的抢法值得说：不是计数器，是 5 个独立的锁槽。**

从 0 遍历到 4，抢到哪个算哪个。

> 为什么不用计数器？**计数器释放的时候可能把别人的名额还回去**——重复释放、超时释放都会。5 个独立锁槽天然幂等：谁抢的谁释放，还错了会直接抛"锁不属于你"，**当场暴露**。

**为什么锁不带租约？**
因为一条流可能跑 15 分钟，还可能停下来等人确认。设了租约要么会被误释放，要么得设一个很离谱的值。所以**不设租约，由看门狗持续续期**——流活着，锁就活着。

**代价**：如果持锁进程**直接崩掉**，锁要等看门狗判定超时才会释放。这是这个方案唯一不优雅的地方。

**为什么闸门覆盖整条流，而不是只在同步窗口？**
因为 Agent 一轮可能几十秒、还可能停在待确认。只在同步窗口拦，用户在等待确认期间再发一问就能进来。

> 🪝 **钩子**：闸门是 Redis 锁，流是内存里的连接。**流挂了，锁谁放？**

### Q14 · 怎么保证锁和连接一定释放？

**面试官追问**：如果收尾逻辑自己抛异常了，锁还放得掉吗？

**我**：

**放得掉，因为释放逻辑在兜底块里，而且不依赖收尾逻辑成功。**

四道防线：

**① 收尾权互斥，收尾体只跑一次。**
三条出口抢同一把锁，抢到的那条执行收尾。无论收尾成没成，**都无条件注销任务 + 跑释放钩子**——即使收尾体自己抛异常，资源一定释放。

**② 释放钩子逐个兜异常。**
一个钩子失败不能拖累其余。否则"补存盘"失败就会导致"放闸门"不执行，那个用户的并发锁要守过期。

**③ 发射器幂等关闭。**
关闭用原子 CAS，重复关闭只生效一次；已关闭后所有发送直接返回，不报错。

**④ 任务表自带过期和上限。**
内存任务表是**写后 30 分钟过期 + 最多 1 万条**。即使某条流的收尾彻底没跑到，也不会永远占着内存。

**最亮的一条是启动期断言：**

> **SSE 超时必须小于任务保留时间，这个不等式在应用启动时就被校验，不满足直接起不来。**

不这么做的后果：会出现"流还活着、任务记录已经过期"的窗口——取消广播找不到任务，**用户点了停止没有任何效果，而且不报错**。这种 bug 在线上极难定位，所以干脆在启动期就掐死。

**这里踩过两个泄漏，都是"失败路径没走释放"：**

**泄漏一：闸门没放。**
启动失败时直接抛异常，闸门是在"启动成功"之后才交给释放钩子的——**失败路径上没人放**。用户被限流"5 条已满"，其实一条流都没在跑。

改法：启动失败统一走一个清理动作。而且清理动作**要各自兜异常**——"放闸门"失败不能连累"注销任务"。

**泄漏二：只 catch 了异常，没 catch `Error`。**
第一版只做了 `catch (Exception)`，如果启动时抛的是 `Error`（比如内存不足、类加载失败），清理逻辑被跳过，闸门泄漏。改成同时捕获 `Exception` 和 `Error`。

> 🪝 **钩子**：说完可靠性，说个我做的不够的地方——**慢客户端**。

### Q15 · 慢客户端会不会拖垮服务？

**面试官追问**：客户端网络很慢，你的 send 一直阻塞，会怎样？

**我**：

**先诚实说：没有做显式的背压。**

**已有的间接防护：**

| 机制 | 挡住什么 |
|---|---|
| 工具结果 64K 截断 | 单帧过大 |
| 工具结果缓冲后一次性发 | 逐帧爆炸 |
| 每用户 5 条并发上限 | 单用户占满资源 |

**缺的是什么：**
写响应是**阻塞 IO**，而且发生在**引擎线程**上。客户端一慢，这把引擎线程就卡住，这条流的后续事件全部排队。**爆炸半径主要是自己这条流**，但如果共享调度器，邻居也会被拖慢。

**改进方向（是方案，不是已实现）：**

1. 发帧挪到**独立发送线程**，引擎线程只往有界队列里塞
2. 队列满时**丢帧而不是阻塞**——这是可以的，因为**落库走的是块，不是帧**。丢帧只影响这一屏的动画，不影响数据正确性
3. 或者对慢客户端**主动断开**，让它走"连接中断"的失败路径

> 第 2 点的推理能证明一件事：**我清楚"帧"和"块"是两个东西。帧可以丢，块不可以丢。**

> 🪝 **钩子**：还有个场景比慢客户端更极端——**停下来等用户确认**。

### Q16 · 等确认的时候，这条流是什么状态？

**面试官追问**：工具要用户确认，这时候你的 SSE 连接还开着吗？

**我**：

**流关掉了，但会话的挂起态保留。**

**为什么关流**：挂起期间服务端没有东西要推，用户可能几分钟后才裁决，占着连接就是浪费。

**为什么状态要保留**：**"等确认"的真正载体是会话状态，不是连接。**

**协议上**：收尾时发现有待确认，**不发 `finish`，改发 `confirm`**。

```
引擎要求确认
   ↓
封口文本块 → 打开的工具块改 awaiting → 记录待确认清单
   ↓
引擎流正常结束 → 进入收尾
   ↓
有待确认？ ── 是 ──► 落库（状态=待确认）→ confirm 帧 → done
           └─ 否 ──► 落库（状态=正常）  → finish 帧 → done
```

**为什么 `finish` 和 `confirm` 互斥？**
`finish` 的语义是"这一轮结算完了"。确认场景下工具还没执行，**根本没结算完**。两个都发，前端会先渲染"完成"再渲染"待确认"，状态打架。

**落库失败怎么兜底**：拿不到消息 id 就没法裁决。这时发系统提示 + `finish` 收尾，**绝不能发 `confirm`**——一个没有 id 的确认卡，点了也没用。

> 🪝 **钩子**：用户点"同意"之后呢？**续跑的时候，工具参数从哪来？**

### Q17 · 确认续跑，为什么工具参数不从请求里取？

**面试官追问**：用户点同意，前端把工具参数一起传回来，不是更简单？

**我**：

**不行，这是安全边界：请求里只传"同意/拒绝"，参数必须从引擎状态里取。**

> 如果让前端把完整参数传回来，攻击者可以**在确认卡上篡改写操作的入参**。最后真正执行的，和用户看到的，就不是同一份数据了。

**续跑的完整流程：**

```
① POST 裁决（只带 会话id / 消息id / approved）
② 重新抢闸门（和首问一样）
③ 从引擎状态里取待确认的工具调用
④ 取不到 → 先结算卡片（标记失效）再报错
⑤ 构造一条"空正文"消息，只携带裁决结果
⑥ 重新走一遍建流：meta → 订阅 → 推帧
```

**第④步为什么重要**：如果状态里已经没有待确认工具了（比如进程重启、状态过期），**必须先结算卡片再报错**——否则这个会话会**永远卡在"待确认"**，用户既发不了新问题，也点不了确认。

**第⑤步为什么是"空正文"**：这条消息只承载裁决结果，不承载用户说的话。框架不会把它并进对话上下文，用户看到的历史里不会多出一句空白提问。

**两个顺序细节：**

| 顺序 | 违反会怎样 |
|---|---|
| **先结算卡片，再订阅** | 反过来时若流被取消，这次工具执行漏结算，卡片永远停在待确认 |
| **续跑时补建工具块** | 续跑不会再有"调用开始"事件（参数上轮就吐完了），不补建就没有工具卡片 |

> 🪝 **钩子**：收尾这块，**三条出口并发到达**的时候怎么办？

### Q18 · 三条收尾出口，怎么保证只有一个生效？

**面试官追问**：引擎回调、容器回调、用户点停止，三个可能同时触发收尾，你怎么保证只收一次？

**我**：

**靠一个生命周期句柄，用一把锁保证收尾体只跑一次。**

```
        ┌──────────┐
引擎正常 ─┤          │
引擎出错 ─┤ 抢收尾权 ├─► 抢到 → 执行收尾 → 释放资源
用户取消 ─┤          │
        └──────────┘
             └─ 没抢到 → 直接返回
```

**收尾体里做四件事，顺序固定：**

```
封口所有块 → 补发最后一批帧 → 落库拿 id → 发终态 + done
```

**这把锁必须可重入**，这是容易踩的坑：
如果引擎的流**同步结束**，收尾会在**订阅的那一栈里**就被回调——同一线程重复进锁。**不可重入就直接自锁死。**

**还有一个容易漏的：兜底块里必须注销任务 + 跑释放钩子。**
不能依赖收尾体成功——它自己抛异常，资源也必须放掉。

**落库失败怎么办？**
**不发带消息 id 的终态帧。** 没写进库就没有 id，发一个 id 为空的 `finish`，前端会拿着空 id 去加载历史，直接失败。宁可发一条错误增量，也不要发一个"看起来成功但其实没有 id"的终态。

**一个竞态细节：取消和正常完成同时到，谁赢重要吗？**
重要，因为**只有赢的那条能改"要不要补存盘"这个标志**。如果取消赢了，必须标记补存盘；如果正常完成赢了，**不能**标记——否则会重复存一次。所以这个标志必须**在收尾体里写**，没抢到收尾权的那一次不许碰它。

> 🪝 **钩子**：后端做到这儿基本闭环了，**前端那边有个决定，和常规做法是反的**。

### Q19 · 前端失败为什么不重试？

**面试官追问**：流断了，前端为什么不自动重连或者重试？

**我**：

> 先说明边界：前端实现是前端同学做的，**契约是我定的**。下面讲的是契约要求的策略和它背后的原因。

**因为 Agent 一轮里可能已经执行过写操作，而客户端无法自证"这一轮在服务端没跑起来"。**

这条链路是这样的：

```
前端连一帧都没收到
   ↓
可能 A：请求根本没到服务端
可能 B：服务端跑完了、写操作执行了，只是回程断了
   ↓
前端分不出 A 和 B
   ↓
重试 = 赌它是 A = 有概率让写操作执行第二遍
```

重试在这里的代价不是"浪费一次请求"，而是**写操作可能执行第二遍**。

**所以契约上是这么定的：**

| 策略 | 要求 | 原因 |
|---|---|---|
| **只发一次** | 不重试、不退避 | 上面的副作用问题 |
| **`done` 是硬信号** | 没收到且非主动取消 → 直接报错 | 否则永远停在"等待响应" |
| **解析层手写** | 按行切、空行分发 | 需要精确控制"一帧什么时候算完整" |
| **投影层不推断** | 状态/时间全部照抄 | 保证刷新前后一致 |

**代价**：网络抖动时用户体验差——会看到"连接已中断，本轮回答未完成"，得自己重问。

**兜底**：错误文案写得很明确，并且服务端的异常提示会写"**如果上面有提交类操作，请先到对应业务系统核对是否生效**"——把不确定性**明示给用户**，而不是假装成功。

> 🪝 **钩子**：讲了这么多设计，**哪一块你觉得做得最值钱？哪一块没做好？**

### Q20 · 这套设计最值钱的地方是什么？有什么没做好？

**面试官追问**：如果让你评价一下这套东西，你满意在哪，不满意在哪？

**我**：

**最值钱的一句话：把"一次推理过程"变成了一个可信的投影。**

可信靠三条：

1. **桥只投影不测量**——工具时间单一事实源，同一件事不会有两个数字
2. **块 = 帧 = 回放**——落库和流出同一组字段，刷新前后是同一条
3. **三条出口互斥收尾**——不管从哪条路结束，落库、发帧、释放资源的顺序只有一个

**关键的几个数，都带口径：**

| 数字 | 含义 | 口径 / 约束 |
|---|---|---|
| **15 分钟** | 单条流的超时 | 下限：覆盖"多次工具 + 等确认"的最长一轮；上限：**必须小于任务保留 30 分钟**，启动时断言 |
| **30 分钟** | 任务记录 / 取消标记保留 | 本地任务表写后过期，与 Redis TTL 对齐，两边不能不一致 |
| **5 条** | 每用户并发流 | 就是 5 个 Redis 锁槽的数量，锁槽数和配置项是同一个数 |
| **2 秒** | 打断后等框架落盘 | 超时就转强制断流 + 标记补存盘，两条路都不丢状态 |
| **64K** | 单工具结果上限 | 单帧可承受的上限，超出截断且不落库不展示 |
| **1 万条** | 本地任务表容量 | 内存兜底上限，配合 30 分钟过期防堆积 |

**没做好的，五条，都敢说：**

| 缺口 | 后果 | 该怎么补 |
|---|---|---|
| **没有显式背压** | 慢客户端会卡住引擎线程 | 独立发送线程 + 有界队列 + 丢帧 |
| **没有心跳保活** | 长时间无帧的等待期，中间代理可能掐连接 | 定期发注释帧 |
| **没有 TTFT / 帧间隔埋点** | 说不清"卡住了"还是"在思考" | 在首帧和每类帧上加时间戳 |
| **文本封口帧没有块 id** | 丢一帧就整体认领错位 | 契约上补一个块标识 |
| **取消等待是固定 2 秒** | 不同引擎的存盘耗时不一样 | 做成可配置 + 按引擎分档 |

**还有一条架构上的取舍，我会主动讲**：
这套协议**只装 Agent 真正会产生的状态**，不为了"通用"去预留用不上的字段。多留一个状态位，前端就要多写一条永远走不到的分支——**那是契约层面的不诚实**。

> 🪝 **钩子**：如果面试官继续追，就往"怎么补"上走——每一条缺口我都准备了改法。

### 五之附 · 线上修过的坑（快速复习表）

| # | 现象 | 根因 | 沉淀成的约束 |
|---|---|---|---|
| 1 | 关标签页后，后台还跑到迭代上限 | 只绑了超时/错误，漏了"完成"回调 | 三个容器回调统一到取消 |
| 2 | 偶发点停止没反应 | 去重标志先置位、提交失败后不再重试 | 提交失败要恢复标志 |
| 3 | 已结束的任务被迟到广播"复活"，收尾跑两遍 | 取消路径用了"取不到就新建" | 取消/绑定路径只查不建 |
| 4 | 越权取消能生效 | 只校验发布端，没校验执行端 | 标记带发起方 + 执行端复核 |
| 5 | 同名并行工具结果串块 | 只能按工具名配对 | 工具事件带调用 id，优先按 id |
| 6 | 工具卡片耗时明显偏大 | 计时锚在"模型吐参数"，不是执行 | 计时锚定执行体入口 |
| 7 | 告警里全是"用户停止" | 取消抛的异常被当故障上报 | 出口先判"是不是取消"，并补回中断标记 |
| 8 | 下一轮偶发加载不到上一轮状态 | 放闸门早于清缓存 | 释放钩子顺序固定 |
| 9 | 用户被限流，其实没有流在跑 | 启动失败没放闸门；只 catch 了 Exception | 失败路径统一清理，且兜住 Error |
| 10 | 流跑起来了但没人管，空转 | 订阅后启动失败没 dispose | 启动失败先 dispose 再抛 |

## 七、面试建议

**① 开场从"这条流要解决什么"讲起，不从"我用了 SSE"讲起。**
SSE 本身三分钟就能学会，区分度全在"你怎么保证它是可信的"。第一句话就给结论：**这不是 token 转发，是推理过程的投影**——面试官会立刻知道你想过层次。紧接着补一句"线上 4 个实例"，把"设计过"变成"上过线"。

**② 缺口和数字，都要成对给：缺口配改法，数字配口径。**
"没有背压"单独说是减分，配上"因为落库走块不走帧，所以可以丢帧"就是加分——**缺口 + 爆炸半径 + 改法**三件套一起给。数字同理：15 分钟、5 条、2 秒、64K，每一个都要能说出**它受谁约束**（15 分钟受 30 分钟保留期约束，5 条就是锁槽数，2 秒是落盘等待上限）。

**③ 多实例那段能画图就画图；修过的坑，讲现象不讲名词。**
"连接单机、取消广播"这个不对称，一张两节点的图胜过五分钟文字。讲修复时先说**用户看到什么**（"点了停止没反应""耗时显示 3.2 秒"），再说根因和改法——面试官听到现象会追问，听到名词只会点头。五之附那张表，面试前一晚过一遍就够了。
