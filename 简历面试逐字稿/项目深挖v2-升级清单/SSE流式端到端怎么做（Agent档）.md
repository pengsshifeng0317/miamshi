# SSE 流式端到端怎么做（Agent 档）

> **这篇讲什么**：一条 Agent 对话流，从浏览器发出请求，到浏览器把界面渲染出来，**中间每一帧是怎么产生的、按什么顺序发出去的**。
>
> **端到端边界**：浏览器 → 浏览器。起点是前端发起请求，终点是前端把帧投影成时间线并渲染完成。落库与刷新回放只在结尾简短带过。
>
> **口径**：纯概念稿，**不出现类名、方法名、代码片段**。事件名（`meta` / `message` / `block` / `hint` / `confirm` / `finish` / `done` / `cancel`）是协议本身的词汇，保留。
>
> **不在本篇**：记忆抽取与游标。会话标题、落库细节、并发闸门、评测侧消费只做一句话说明。
>
> **怎么用**：先读**第二部分的时间线**建立整体认知，再用**第五部分的 Q&A**练追问。别反过来——先背问答会得到一堆孤立的机制，说不出流程。

---

## 一、一页纸总览

### 1.1 这条流跨了三个边界

```
┌─────────┐   ① HTTP + SSE    ┌──────────┐   ② 响应式事件流   ┌──────────┐
│ 浏览器   │ ◄──────────────► │ 服务端    │ ◄───────────────► │ Agent 引擎│
└─────────┘                   └──────────┘                    └──────────┘
     ▲                              │
     │                              │ ③ 中间有一座桥：把引擎事件翻译成对前端的契约
     └──────────────────────────────┘
```

| 边界 | 两边是什么 | 谁负责转换 |
|---|---|---|
| ① 浏览器 ↔ 服务端 | 单向 SSE 帧；请求侧是普通 HTTP | 服务端写帧、前端手写解析 |
| ② 服务端 ↔ 引擎 | 引擎吐出的是**响应式事件流** | 服务端**命令式订阅**它 |
| ③ 引擎事件 → 前端契约 | 引擎只说"过程"，前端要"可渲染的过程" | **桥**：翻译、缓冲、截断、补建、投影时间 |

### 1.2 一条流的一生（鸟瞰）

```
浏览器                服务端                         引擎
  │                     │                             │
  │ ① GET 提问           │                             │
  ├────────────────────►│                             │
  │                     │ ② 建流对象（还不发帧）        │
  │                     │ ③ 抢并发闸门（失败→普通JSON） │
  │                     │ ④ 前置准备（标题/用户消息）    │
  │                     │ ⑤ 装配（时钟/事实源/句柄）     │
  │ ⑥ meta 帧           │                             │
  │◄────────────────────┤                             │
  │                     │ ⑦ 订阅引擎事件流 ───────────►│
  │ ⑧ message 增量       │◄──────────── 文本增量 ───────┤
  │◄────────────────────┤                             │
  │ ⑨ block 帧           │◄──────────── 工具事件 ───────┤
  │◄────────────────────┤                             │
  │ ⑩ confirm 帧         │◄──────────── 要求确认 ───────┤
  │◄────────────────────┤                             │
  │ ⑪ finish + done      │◄──────────── 流结束 ─────────┤
  │◄────────────────────┤                             │
  │ ⑫ 解析 → 投影 → 渲染  │                             │
```

### 1.3 一句话本质

> **这条流不是"模型吐 token 的转发"，而是"一次推理过程的投影"。**

三件事依次对应三个边界：
- 引擎负责**产生过程**（文本、工具、确认）
- 桥负责**把过程翻译成契约**（增删改）
- 浏览器负责**把契约投影成界面**（不推断、只照抄）

**整篇文档的所有设计，都是为了保证"投影是可信的"**——帧里的状态和时间，必须和落库、和刷新后回放看到的一模一样。

## 二、端到端时间线

下面按**真实发生顺序**走一遍。每段都回答三件事：**这一步做了什么 / 此时前端看到什么 / 为什么必须这样**。

---

### 第 0 段 · 浏览器发起请求

**做了什么**

- 首问：`GET` 请求，带问题文本和可选的会话 id
- 裁决：`POST` 请求，带会话 id、消息 id、**同意或拒绝**
- 停止：独立接口，只带任务 id

**前端看到什么**

- 什么都没有。请求刚发出去。

**为什么必须这样**

- **首问用 GET**：首次提问本身没有副作用，浏览器和网关把它当普通请求处理最省事。
- **裁决必须用 POST 且带请求体**：裁决是**有副作用的动作**（同意后真的会执行写操作）。如果塞进 URL 查询串，浏览器、代理、日志都可能重放它，等于把"执行一次"变成"可能执行多次"。这是安全边界，不是风格问题。

---

### 第 1 段 · 服务端建流（零帧阶段）

**做了什么**

- 立刻创建一个"流对象"，设置**15 分钟超时**
- 把它交给服务层，然后**同步返回**

**前端看到什么**

- 连接已建立，但**还没有任何事件**。此时页面仍处于"等待首帧"。

**为什么是 15 分钟**

老 RAG 档是 5 分钟。Agent 档为什么翻三倍：

1. 一轮里可能**多次工具调用**，每次都要等下游；
2. 中间可能**停下来等用户确认**——这个阶段流是**一直开着**的，不产生任何帧（见第 8 段）。

**这一段最关键的隐性事实：此时还没有发过任何帧。**

这决定了后面所有失败的处理方式——**建流失败可以返回普通 JSON，一旦发过第一帧就只能走流内表达**。这个分界线在第 4 段。

---

### 第 2 段 · 抢闸门与前置准备

**做了什么（顺序不能换）**

1. **抢并发闸门**：同一会话互斥 + 同一用户最多 5 条并发流
2. 检查是否有**上一轮还挂着的确认**——有就直接拒绝新问题
3. 建会话 / 取标题（简短带过）
4. 用户消息落库（简短带过）

**前端看到什么**

- 仍然什么都没有。

**为什么闸门必须在建流之前**

- 抢不到闸门时抛异常，**因为一帧都没发**，全局异常处理能干净地返回一个 JSON 错误。
- 这和老的幂等拦截有本质区别：老方案只覆盖"控制器返回之前"的**同步窗口**；新方案覆盖**整个流的生命周期**——一条流跑多久，闸门占多久。
- 为什么必须覆盖全程：Agent 一轮可能几十秒、还可能停下来等人确认。如果只在同步窗口拦截，用户在等待确认期间再发一问就能进来，**同一份会话状态会被两条流同时改**。

**为什么"有待确认就拒绝新问题"**

挂起的确认是**会话级状态**，不是消息级。新问题进来会覆盖当前轮次，导致用户永远无法裁决那个待确认的写操作。

---

### 第 3 段 · 装配（还在零帧阶段）

**做了什么**

在发第一帧之前，先把这一轮需要的几样东西备齐：

| 装配项 | 作用 |
|---|---|
| **一个时钟** | 全轮所有时间戳的唯一来源 |
| **工具执行事实源** | 批次号、批内序号、每个工具的**真实起止**，只在这里产生 |
| **帧发射器** | 对底层连接的幂等封装：关闭后不再发、重复关闭只生效一次 |
| **生命周期句柄** | 保证"正常/异常/取消"三条出口**只有一条**能收尾 |
| **释放钩子链** | 收尾后依次执行：补存盘 → 清引擎缓存 → 放闸门 → 调度记忆 |

**前端看到什么**

- 仍然什么都没有。

**为什么释放钩子的顺序不能换**

```
补存盘  →  清缓存  →  放闸门  →  调度记忆
```

- **补存盘必须在清缓存之前**：清缓存后引擎就取不到本轮状态，补存盘无从谈起。
- **放闸门必须在清缓存之后**：否则下一轮流可能先加载了状态，又被本轮收尾把缓存清掉。
- 放闸门是最后一道，但记忆调度要再往后——记忆要读到本轮完整落库结果。

---

### 第 4 段 · 第一帧：`meta`

**做了什么**

发出一条 `meta` 帧，载荷只有两样：**会话 id** 和 **任务 id**。

**前端看到什么**

- 拿到会话 id：可以绑定当前会话、更新 URL。
- 拿到任务 id：可以显示"停止"按钮——**停止接口只认任务 id**。

**为什么第一帧必须是它**

- 后续所有帧都不带会话 id，前端**必须**先有它才能把帧归属到正确的会话。
- 停止能力必须尽早可用——用户可能在第一帧之后就想中断。

**从这一刻起，规则变了**

流里已经出现过帧了。此后的**任何失败，都不能再返回 HTTP 错误码或 JSON**，只能：

1. 发一条错误增量，
2. 落库留痕，
3. 发终态帧 + 结束帧。

> 面试里这是一个很好的分界点：**"建流前失败 = JSON；建流后失败 = 流内表达"**。很多实现会把这两种混在一起，导致前端偶发拿到 JSON 却按事件流解析，直接报错。

---

### 第 5 段 · 订阅引擎事件流

**做了什么**

把引擎吐出的**响应式事件流**，用三个回调接过来：

```
每个事件   → 翻译成帧
出错了     → 走异常收尾
正常结束   → 走正常收尾
```

同时给上游挂一个**终止信号**：无论正常、出错还是被取消，只要上游流结束就置位。这个信号在第 10 段的取消流程里要用。

**前端看到什么**

- 还看不到新东西，但接下来随时可能有 `message` 帧。

**为什么订阅必须放在锁里**

这是 Agent 档**独有的竞态**，也是必须讲清楚的一点：

> 如果"取消"先跑完了收尾、释放了闸门，而"订阅"随后才执行，那么用户明明点了停止，**这一轮的推理循环照样从头跑、写操作照样执行一遍**。

所以「结算确认卡片 + 订阅 + 绑定取消动作」是**一个原子块**，整段放在生命周期锁里。

**为什么桥拿到的已经是"成形的事件"**

响应式的调度、背压、线程切换，引擎内部已经处理完了。桥做的事是**翻译**，不是编排。

**代价**：桥的回调是在**引擎的线程**上被调用的，不是请求线程。所以桥内部的状态必须自己保护——这直接导出第 6 段"锁内改状态、锁外发帧"。

---

### 第 6 段 · 文本怎么流出去

这是整条流里帧数最多的一段。

**做了什么**

引擎每吐一小段文本，服务端做**两件事**：

1. **发一帧增量**：`message`，带一个 `type` 区分是**回答**还是**思考**
2. **同时累积成"块"**：同一类型连续累积，类型一变就开新块

**前端看到什么**

- 回答区一个字一个字地长出来；思考区同理，按 `type` 分到不同区域。

**块什么时候封口**

三个触发点，缺一不可：

| 触发 | 场景 |
|---|---|
| **类型变了** | 思考转成回答，或回答转成思考 |
| **工具事件来了** | 工具是过程的一部分，文本必须先断 |
| **流收尾了** | 最后一个块由收尾统一封口 |

**封口时做什么**

- 盖上**结束时间戳**
- 算出**持续时长**
- 放进"待广播队列"
- **出锁之后**才真正发封口帧

**为什么锁内改状态、锁外发帧**

发帧是 **IO 操作**。如果在持锁期间发帧，而发送又阻塞（客户端慢、网络差），**所有引擎回调线程都会被这把锁卡住**，整条流就停了。

所以规则是：**锁只保护内存状态，IO 一律出锁做**。

**一个最容易做错的边界：只广播有起止的块**

有两种块**没有起止**：

- 非流式终答的兜底补发（引擎直接给了一段完整文本）
- 异常时的中断提示

这两种块是"一次性补发"，**没有生成过程**，所以不给起止、**也不发封口帧**。

> 为什么？因为前端是按"封口帧到达的先后"去认领"最早那个还没收口的同类块"的。如果你给一个没有起止的块也发封口帧，前端会把**正在接收的那个块**错误地收口，界面直接错位。

**这一段的三个"为什么"要能连起来答**

```
为什么块在服务端封口？
  → 因为客户端自己推断块的起止，刷新重放时时间对不上
为什么时间可信？
  → 因为整轮只有一个时钟，且工具时间只从事实源投影
为什么工具时间要单独投影？
  → 见第 7 段
```

---

### 第 7 段 · 工具怎么流出去

**做了什么**

工具是 Agent 档相对 RAG 档**新增的过程**，也是协议里 `block` 帧的主要用途。

**状态机（这是必须背下来的）**

```
pending ──► running ──► done / failed
   │           │
   │           └──► interrupted   （收尾时没等到结果）
   ├──► awaiting                  （等用户确认）
   └──► denied                    （整批被拒）
```

**逐状态说明**

| 状态 | 什么时候进入 | 前端表现 |
|---|---|---|
| `pending` | 模型**开始吐工具参数**（还没执行） | 显示"准备调用" |
| `running` | 工具**真正开始执行** | 转圈 / 计时开始 |
| `done` | 执行成功 | 显示结果摘要 |
| `failed` | 执行报错 | 红色 |
| `awaiting` | 需要用户确认 | 停在"等待授权" |
| `denied` | 整批被用户拒绝 | 显示"未执行" |
| `interrupted` | 收尾时这个工具没等到结果 | 显示"已中断" |

**三个必须知道的细节**

**① 工具结果增量不逐段发。**

工具返回可能是**一大段文档**，引擎会分很多次吐。如果每次都发一帧，前端帧数爆炸。做法是：**先在服务端缓冲，等工具结束时一次性给**，并且有 **64K 上限**，超出部分直接丢弃（截断后缀既不落库也不展示）。

**② 时间不自己测，从事实源投影。**

桥不负责记录工具的起止。真实的开始和结束由**工具执行侧**记录在事实源里，桥在工具结束时把这两个值**投影**到块上。

> 如果桥自己打时间，同一批工具在"工具卡片"和"文本块"两处会显示**不同的耗时**——因为两套口径。这是最容易被面试官抓的破绽。

**③ 有三个补建场景。**

普通路径下块在"调用开始"时就建好了，但这三种情况没有开头事件，块要补建：

| 场景 | 为什么没有开头 |
|---|---|
| **确认续跑** | 续跑的那一轮，工具参数早在上一轮就吐完了，不会再有"调用开始" |
| **只有结束没有开始** | 框架异常或事件丢失 |
| **整批被拒** | 框架不发工具事件，只在最后给一个"整批拒绝" |

注意：**整批被拒的块不给批次号、不给起止**——因为它**从来没执行过**，给时间就是撒谎。前端应该显示"未执行"，而不是"耗时 0 毫秒"。

**为什么"整批"都要改成等待确认**

当一批并行工具里有一个需要确认，**整批都不能跑**（它们是一个事务边界）。所以：

- 所有还没到终态的工具块，**统一改成 `awaiting`**
- 不能只改卡片点名的那个

> 反例：只改点名的那几个，其余的留在 `pending`。收尾时这些 `pending` 会被判成 `interrupted`，界面上看起来像"被中断了"，而不是"在等你确认"。**用户会以为出错了。**

### 第 8 段 · 确认怎么挂起

这是 Agent 档特有的第三种流命运。

**做了什么**

1. 引擎发来"要求用户确认"事件
2. 服务端：**封口当前文本块** → 把所有打开的工具块改成 `awaiting` → 记录待确认清单
3. 引擎这条流**正常结束**，进入收尾
4. 收尾时发现有待确认 → **不发 `finish`，改发 `confirm`**

**前端看到什么**

- 一张确认卡：标题 + 每个待执行工具的字段（字段名、可读标签、参数值）
- **流结束了，但页面停在"等你裁决"**——没有"回答完成"

**为什么 `finish` 和 `confirm` 互斥**

- `finish` 的语义是"这一轮结算完了"。
- 确认场景下**根本没结算完**——工具还没执行。
- 两个都发，前端会先渲染"完成"再渲染"待确认"，状态打架。

**为什么流要关掉**

- 挂起期间**不需要保持连接**：服务端没有东西要推了。
- 用户可能几分钟后才裁决。占着连接就是浪费。
- 但**会话的挂起态要保留**——这才是"等确认"的真正载体，不是连接。

**如果落库失败怎么办**

极端情况：待确认消息写不进库。这时**拿不到消息 id**，前端就无法裁决。

降级方案：发一条系统提示（"系统繁忙，这一步没执行，请新建会话"）+ 发 `finish` 收尾。**不能发 `confirm`**——一个没有 id 的确认卡，点了也没用。

---

### 第 9 段 · 收尾：三种出口，一个口径

一轮流只有三种结局，但**正常、异常、取消三条路径可能同时到达**（引擎回调、容器回调、用户操作）。所以收尾权必须互斥。

**先分清两层**：生命周期句柄只有**三条出口**（正常 / 异常 / 取消）；**"挂起"不是第四条出口**，它是"正常收尾"里的一个分支——引擎正常结束了，只是这一轮没结算完。

**对前端的四种终态**

| 出口 | 触发 | 落库状态 | 终态帧 |
|---|---|---|---|
| **正常** | 引擎流正常结束 | 正常 | `finish` |
| **挂起** | 同上，但存在待确认 | 待确认 | `confirm`（替代 `finish`） |
| **异常** | 引擎流出错 | 中断 | `finish` |
| **取消** | 用户停止 / 断连 / 超时 | 中断 | `cancel` |

**收尾的统一动作，顺序固定**

```
1. 封口所有还没封口的文本块
2. 把还没到终态的工具块收口（有结果按结果，没结果判 interrupted）
3. 补发最后一批封口帧和工具终态帧
4. 落库，拿消息 id
5. 发终态帧
6. 发 done
7. 执行释放钩子链
```

**四条顺序约束，每条都有反面教材**

**① 封口帧必须早于终态帧。**

前端收到 `cancel` 之后就**不再接收块帧**了。如果最后一个块的封口帧在终态之后到，前端会丢帧，最后一段文本永远不封口。

**② 终态帧与 `done` 成对。**

`done` 是前端的**硬性完成信号**。只看终态不看 `done`，前端无法区分"正常结束"和"连接被掐断"。

**③ 落库失败，不发带消息 id 的终态。**

没写进库就没有 id。发一个 id 为空的 `finish`，前端会拿着空 id 去做后续操作（比如加载历史），直接失败。

**④ 异常要留痕。**

异常时不仅发错误增量，还要**追加一个专门的中断提示块落库**。

> 为什么？因为历史回放只读块、不读消息正文。只把提示塞进正文，刷新后这句话就消失了——用户看到的是"回答莫名其妙断了"，而不是"这里中断了，请核对"。

**异常时的一个细节：中断提示单独成块**

中断提示是**系统在说话**，不是模型的回答。混进回答块里，就给了它和模型输出**同样的身份**。所以单独一个错误类型的块，前端可以渲染成不同样式。

---

### 第 10 段 · 取消怎么走

**触发源：三个容器回调归一**

```
流超时      ┐
流错误      ├──► 同一个动作：提交取消
流正常关闭  ┘
```

> 第三个最容易被漏：**用户直接关闭标签页**，容器不会触发超时或错误，**只有"完成"回调能兜住**。漏了它，引擎的推理循环会空跑到迭代上限。

**为什么取消要提交到别的线程**

取消动作里要**打断引擎 + 等它存盘**，最多等 2 秒。如果直接跑在容器的生命周期回调线程上，会阻塞容器的连接回收。

**打断的顺序（不能反）**

```
1. 标记"这一轮被中断了"（供追踪用）
2. 打断引擎
3. 等上游流终止，最多 2 秒
4. 如果没等到 → 标记"需要补存盘" → 强制断流
5. 执行收尾（落库 + cancel + done）
```

**为什么不能直接断流**

> **引擎有跨轮状态要持久化。** 直接断流，框架连存盘都来不及，本轮的**工具执行结果**会丢——下一轮 Agent 会"忘记"自己刚才做过什么，可能重复执行写操作。

2 秒换的是**框架优雅存盘的机会**。超时了才强制断流，并且**标记补存盘**，在释放钩子里再补一次。

**一个反直觉的点：取消时如果有待确认，走的是确认流程，不是中断**

用户点"停止"取消的是**这条流**，不是**那个待确认的写操作**。那个操作还挂在引擎状态里等裁决。所以收尾时如果发现有待确认，仍然发 `confirm`。

**另一个细节：标记补存盘只置位、不清零**

失败出口可能已经标记过"需要补存盘"。取消流程即使优雅等待成功，**也不能把它清掉**——优雅中断不代表存盘一定成功。

---

### 第 11 段 · 确认后怎么续跑

**做了什么**

1. 前端 `POST` 裁决，**只传"同意/拒绝"**
2. 服务端**重新抢闸门**（和首问一样）
3. 从**引擎的会话状态**里取当前待确认的工具调用
4. 如果取不到 → 先结算卡片（标记失效）再报错，**否则会话永远卡住**
5. 构造一条**空正文**消息，只携带裁决结果
6. 重新走一遍建流流程（发 `meta` → 订阅 → 推帧）

**前端看到什么**

- 一个新的 `meta` 帧（新任务 id）
- 确认卡变成"已同意/已拒绝"
- 工具块从 `awaiting` 变成 `running`，然后 `done` / `denied`
- 最后 `finish` + `done`

**为什么工具入参不从请求里取**

请求里只传"同意/拒绝"。**工具的真实参数必须从引擎状态里取。**

> 如果让前端把完整参数传回来，攻击者可以**在确认卡上篡改写操作的入参**。确认卡展示的和真正执行的，必须是同一份数据。

**为什么是先结算卡片、再订阅**

如果反过来（先订阅、后结算），而恰好这时流被取消，**这次工具执行就漏掉了结算**——卡片永远停在"待确认"。

**为什么续跑要补建工具块**

续跑那一轮，引擎**不会再发"调用开始"事件**（参数上一轮就吐完了）。所以工具块只能在"执行开始"时补建。这就是第 7 段三个补建场景的第一个。

---

### 第 12 段 · 浏览器怎么消费

**前端看到什么**

从"等待首帧"到"完整时间线渲染完成"。

**解析层：手写，不用现成库**

按行处理，规则很朴素：

```
按行切 → 空行 = 一帧结束 → 分发
event: xxx   → 帧名
data: xxx    → 帧内容（多行拼接）
: xxx        → 注释，忽略
```

**两个 Agent 档特有的硬约束**

**① `done` 是硬性完成信号。**

没收到 `done`、又不是用户主动取消的，**直接报错**："连接已中断，本轮回答未完成"。

> 否则这一轮会永远停在"等待响应"，用户以为还在生成。

**② 只发一次，不重试。**

RAG 档有指数退避重试；**Agent 档不能有**。

> 因为 Agent 一轮里可能**已经执行过写操作**。而客户端**没有办法自证"这一轮在服务端没跑起来"**——连一帧都没收到，也可能只是回程断了，服务端其实已经跑完并写入了。重发 = 整轮重跑 = 写操作再执行一遍。

**投影层：一个都不推断**

这一层是 Agent 档前端最值得讲的。它的原则是：

> **状态、批次、序号、执行耗时全部照抄服务端——这里一个都不推断，也不碰当前时间。**

三个具体体现：

| 机制 | 做法 | 不这么做会怎样 |
|---|---|---|
| **文本封口帧** | 按到达顺序，认领"最早那个同类且还没收口"的块；认不到就丢弃 | 无主的起止挂到别的块上，就是把一段文字的耗时说成另一段的 |
| **工具配对** | 优先按**工具调用 id** 配对；只有旧数据没 id 时才按名字回落 | 同名并行工具串块，结果张冠李戴 |
| **批次时间** | 批头取**事实源时间的包络**：最早开工到最晚收工 | 并行工具区间本就重叠，逐条相加会把重叠段算两遍 |

**为什么"纯投影"值这么多钱**

因为它保证了**刷新前后是同一份**：

> 落库的块和流出的帧，**写的是同一组字段**。前端回放时不重新计算，照抄服务端——所以刷新不会"跳一下"。

这是"块 = 帧 = 回放"三者的字段一致性，也是整条流可信度的落脚点。

---

### 第 13 段 · 落库与刷新回放（简短带过）

- 一轮结束时，把所有块**按顺序**写成一条助手消息，状态是"正常/中断/待确认"之一。
- 刷新后，前端读落库的块，走**和流式同一套投影逻辑**重建时间线。
- 能这么做的前提是：**块和帧的字段是同一套**（类型、起止、耗时来源、批次、序号）。
- 如果两套字段对不上，刷新后就会"跳一下"——这是这类设计最常见的翻车点。

## 三、8 个事件速查

| 事件 | 什么时候发 | 载荷要点 | 落库 |
|---|---|---|---|
| **meta** | 订阅前，**第一帧** | 会话 id、任务 id | — |
| **message** | 文本增量 | `type` = 回答 / 思考 / 错误 + 增量文本 | 累积进块 |
| **block** | 块状态变化 | 见下 | 是（块序列） |
| **hint** | 系统级提示 | 提示码 + 文案 | **否** |
| **confirm** | 等待用户确认 | 消息 id、标题、待确认调用清单、耗时 | 是（状态=待确认） |
| **finish** | 本轮结算完成 / 异常中断 | 消息 id、标题、状态、总耗时 | 是 |
| **done** | 每条出口的**最后一帧** | 固定字面量 | — |
| **cancel** | 用户取消 | 消息 id、标题、状态、总耗时 | 是 |

**`block` 帧有两种形态，靠 `kind` 区分**

| 形态 | 载荷 | 何时 |
|---|---|---|
| **文本块封口** | 类型、开始时刻、结束时刻、时长 | 文本块断开的瞬间 |
| **工具块进度** | 类型、工具 id、可读名、状态、结果、批次、批内序号、起止、耗时、耗时来源 | 工具状态每次变化 |

> 注意：**文本块只有"封口"这一个时刻会发 `block`**，过程中只发 `message` 增量。工具块则相反——**每次状态变化都发 `block`**。

---

## 四、帧顺序的六条硬约束

这六条是"实现对不对"的判据，面试可以当成 checklist 用。

| # | 约束 | 违反的后果 |
|---|---|---|
| 1 | **`meta` 必须是第一帧** | 前端无法归属后续帧，停止按钮拿不到任务 id |
| 2 | **封口帧必须早于终态帧** | 前端收到终态后不再收块，最后一段永远不封口 |
| 3 | **`finish` 与 `confirm` 互斥** | 前端先渲染"完成"再渲染"待确认"，状态打架 |
| 4 | **终态帧与 `done` 成对** | 前端无法区分"正常结束"和"连接被掐断" |
| 5 | **落库失败不发带 id 的终态** | 前端拿空 id 做后续操作，直接失败 |
| 6 | **没有起止的块不发封口帧** | 前端错误收口正在接收的块，界面错位 |

## 五、Q&A 逐字稿

> 下面是**纯口播**，可以直接背。每条先给结论，再给理由，最后给代价。

---

### Q1：一条 Agent 流从头到尾是怎么跑的？

**答**：

分三段。

**第一段，建流但不发帧。** 浏览器发 GET 请求，服务端先建流对象（15 分钟超时），然后抢并发闸门——同一会话互斥、同一用户最多 5 条。抢不到就直接抛异常返回 JSON，因为这时候一帧都没发。抢到之后做前置准备，装配时钟、工具事实源、生命周期句柄，然后发出第一帧 `meta`，里面是会话 id 和任务 id。

**第二段，订阅和翻译。** 服务端订阅引擎的响应式事件流，用三个回调接：每个事件翻译成帧、出错走异常收尾、正常结束走正常收尾。引擎一共会吐十一种事件，翻译成八种协议事件。文本增量发 `message`，同时累积成块；工具状态发 `block`；要确认了发 `confirm`。

**第三段，收尾。** 四条出口只有一条能收尾：正常发 `finish`，异常也发 `finish` 但状态是中断，取消发 `cancel`，挂起发 `confirm`。每条出口都以 `done` 封尾。

前端拿到帧之后手写解析，再走一层纯投影，把帧变成时间线。**这一层不推断任何东西，状态和时间全部照抄服务端。**

---

### Q2：为什么用 SSE，不用 WebSocket 或者长轮询？

**答**：

因为这条流**本质是单向的**。

服务端只需要往下推帧，客户端不需要在同一条连接上往上发东西。裁决、停止都是独立请求。

SSE 的收益：

- **协议简单**：就是 HTTP 响应，天然过网关、过鉴权、过日志，不用为它开新的通道。
- **断线语义清楚**：连接断了就是断了。
- **不需要额外握手**。

WebSocket 的问题是**双工能力用不上**，但要多维护一套连接管理、心跳、重连、鉴权。为一条单向流付这个成本不划算。

长轮询的问题更直接：**每次轮询都要重新建立一次请求**，首帧延迟做不到，而且一轮里可能有几百个增量，长轮询会被打爆。

**代价**：SSE 是单向的，所以裁决必须另开 POST。这反而是好事——见 Q9。

---

### Q3：你们用了响应式编程，为什么不上 WebFlux？

**答**：

因为**那个响应式流不是我的 SSE 出口，是引擎的内部事件流**。这两个东西经常被混为一谈。

引擎吐的是"推理过程中发生了什么"，WebFlux 的响应式 SSE 是"我要发给浏览器的帧"。方向都不一样。

正确的架构是：**引擎吐响应式事件流，我用命令式订阅把它接到 Servlet 的流对象上。** 三个回调正好对应三条出口。

不上 WebFlux 三个理由：

1. **双技术栈不划算。** 整个应用是 Servlet 栈，认证、异常处理、拦截器全在这条栈上。为一条接口引入 WebFlux，等于同一进程维护两套 Web 基础设施。
2. **不需要背压。** 单个用户一条流，不存在"上游快下游慢"需要协调的量级。
3. **取消语义要重做。** 取消这块已经和任务管理、生命周期句柄深度绑定，换框架等于推倒重来。

**代价**：命令式订阅意味着桥的回调跑在**引擎的线程**上，所以桥的状态必须自己保护。这就是"锁内改状态、锁外发帧"的由来。

---

### Q4：引擎的事件为什么不直接透给前端？

**答**：

因为**引擎事件是引擎的私有语义，不是给前端的契约**。三个原因：

**一，命名和语义会变。** 引擎升级可能改名、拆合事件。前端如果直接依赖，升级一次全崩。**契约的稳定不能押在第三方框架上。**

**二，粒度不匹配。** 工具结果是逐段吐的，一段文档可能吐几百次。直接透出，前端帧数爆炸。所以要在服务端**缓冲，等工具结束时一次性给**，还要做 64K 截断。

**三，有些事件不该透出。** 引擎有些内部事件是给自己用的，不是用户要看的，直接过滤。

**所以桥的本质是翻译，而且翻译过程中要增删改**：缓冲、截断、过滤、补建、投影时间。

---

### Q5：文本块的边界怎么保证正确？

**答**：

**块在服务端封口，不由前端推断。**

三个封口时机：类型变了（思考转回答）、工具事件来了、流收尾了。

封口时盖结束时间戳、算时长，然后**出锁之后**才发封口帧。

这里有两个容易做错的点：

**第一，为什么锁内改状态、锁外发帧。** 发帧是 IO。持锁发帧，一旦客户端慢、发送阻塞，**所有引擎回调线程都被这把锁卡住**，整条流直接停。

**第二，只广播有起止的块。** 非流式终答的兜底补发、异常中断提示，这两种是"一次性补发"，没有生成过程，所以**不给起止，也不发封口帧**。因为前端是按到达顺序认领"最早那个还没收口的同类块"的——你给一个没起止的块发封口帧，前端会把正在接收的那个块错误收口，界面直接错位。

---

### Q6：工具的状态怎么保证前端看到的是真的？

**答**：

靠三件事。

**第一，状态机只有一条合法路径。**
`pending`（模型开始吐参数）→ `running`（真正执行）→ `done`/`failed`。
另外三个分支：`awaiting`（等确认）、`denied`（整批被拒）、`interrupted`（收尾没结果）。

**第二，时间不自己测，从事实源投影。**
真实起止由工具执行侧记在事实源里，桥只在工具结束时把值投影上来。

> 如果桥自己打时间，同一个工具在卡片和文本块两处会显示不同的耗时——两套口径。

**第三，三个补建场景要兜住。**
普通路径块在"调用开始"时建好，但这三种没有开头事件：确认续跑（参数上一轮就吐完了）、只有结束没有开始（事件丢失）、整批被拒（框架不发工具事件）。
特别注意**整批被拒的块不给起止**——它从没执行过，给时间就是撒谎。

还有一个：**一批并行工具里有一个要确认，整批都要改成 `awaiting`**。只改点名的那些，其余的留在 `pending`，收尾时会被判成 `interrupted`，用户看到的是"被中断了"而不是"在等你确认"。

---

### Q7：为什么时间只能有一个事实源？

**答**：

因为**耗时会被用户和面试官同时看到**。

同一次工具调用，会出现在两个地方：工具卡片上、以及对应的文本块封口帧里。如果这两处的时间来自不同的地方——比如卡片用工具自己记的、文本块用桥打的时间——**两处显示的数字会不一样**。

所以规则是：**桥只投影，不测量。** 工具的批次号、批内序号、真实起止，全部从工具执行侧的事实源取。

文本块的起止是桥用整轮**同一个时钟**记的，因为文本块没有"工具执行侧"这个来源。

**代价**：桥必须持有事实源的引用，并且要知道什么时候该去取。但这比"两套时间各算各的"便宜得多。

---

### Q8：取消为什么不能直接断流？

**答**：

**因为引擎有跨轮状态要存盘。**

直接断流，框架连存盘都来不及，本轮的**工具执行结果**会丢。下一轮 Agent 会"忘记"自己刚才做过什么，可能**重复执行写操作**。

所以顺序是：先打断引擎 → **等上游流终止，最多 2 秒** → 没等到才强制断流，并标记"需要补存盘"，在释放钩子里再补一次。

2 秒换的是框架优雅存盘的机会。

**还有一个坑：取消的触发源有三个——超时、错误、正常关闭。** 第三个最容易被漏：用户直接关标签页，容器不会触发超时或错误，**只有"完成"回调能兜住**。漏了它，推理循环会空跑到迭代上限。

**最后一点**：取消时如果还有待确认的工具，走的**不是中断，是确认流程**。用户取消的是这条流，不是那个待确认的写操作。

---

### Q9：等用户确认的时候，这条流是什么状态？

**答**：

**流关掉了，但会话的挂起态保留。**

为什么关流：挂起期间服务端没有东西要推，用户可能几分钟后才裁决，占着连接就是浪费。

为什么状态要保留：**"等确认"的真正载体是会话状态，不是连接。**

协议上，收尾时发现有待确认，**不发 `finish`，改发 `confirm`**。两者互斥——`finish` 的语义是"结算完了"，但确认场景下工具还没执行，根本没结算完。

**裁决为什么走 POST 且只传同意/拒绝**：裁决是有副作用的动作，塞进 URL 会被重放。而且**工具的真实参数必须从引擎状态取**——如果让前端传回来，攻击者可以篡改确认卡上的入参，展示的和执行的就成了两份数据。

**落库失败的降级**：拿不到消息 id 就没法裁决。这时发系统提示 + `finish` 收尾，**不能发 `confirm`**——一个没有 id 的确认卡，点了也没用。

---

### Q10：三条收尾出口，怎么保证只有一个生效？

**答**：

靠一个**生命周期句柄**，用一把锁保证收尾体只跑一次。

正常、异常、取消三条路径可能同时到达：引擎回调、容器回调、用户点停止。谁先抢到锁谁收尾，后来的一律返回。

收尾体里做四件事，顺序固定：**封口所有块 → 补发最后一批帧 → 落库拿 id → 发终态和 `done`**，最后执行释放钩子链。

**锁必须可重入**——这是一个容易踩的坑：如果引擎的流**同步结束**，收尾会在订阅的那一栈里就被回调，等于同一线程重复进锁。不可重入就直接自锁死。

**释放钩子的顺序也有依赖**：补存盘 → 清引擎缓存 → 放闸门 → 调度记忆。补存盘必须在清缓存之前，放闸门必须在清缓存之后，否则下一轮可能加载了状态又被本轮清掉。

---

### Q11：前端是怎么消费的？

**答**：

两层，解析和投影。

**解析层是手写的**：按行切，空行代表一帧结束，`event:` 是帧名，`data:` 是内容。两个 Agent 档特有的约束：

- **`done` 是硬性完成信号。** 没收到又不是主动取消，直接报错。否则页面永远停在"等待响应"。
- **只发一次，不重试。** RAG 档有退避重试，Agent 档不能有——因为 Agent 可能已经执行过写操作，而客户端**无法自证"这一轮在服务端没跑起来"**，重发就等于让写操作再执行一遍。

**投影层是纯函数，一个都不推断。** 状态、批次、序号、耗时全部照抄服务端，连当前时间都不碰。

三个体现：文本封口帧按顺序认领最早未封口的同类块，认不到就丢弃；工具优先按调用 id 配对，旧数据才按名字回落；批头时间取事实源时间的**包络**，因为并行工具区间重叠，逐条相加会算两遍。

**这一层的价值是保证刷新前后是同一份**——落库的块和流出的帧写的是同一组字段，回放时不重算，所以刷新不会跳。

---

### Q12：这套设计最值钱的地方是什么？

**答**：

一句话：**把"一次推理过程"变成了一个可信的投影。**

可信靠三条：

1. **桥只投影不测量**——工具时间单一事实源，同一件事不会有两个数字。
2. **块 = 帧 = 回放**——落库和流出同一组字段，刷新前后看到的是同一条。
3. **三条出口互斥收尾**——不管从哪条路结束，落库、发帧、释放资源的顺序只有一个。

**顺带一个取舍**：Agent 档有意和老的 RAG 档**保留两套协议**，不合并。因为合并会让 RAG 契约背上一堆它永远不会收到的状态——那是契约层面的不诚实。

## 六、面试别踩的坑

| 坑 | 正确说法 |
|---|---|
| 说"我把引擎事件直接推给前端" | 中间有桥，做了翻译、缓冲、截断、过滤、补建 |
| 说"取消就是不再发帧" | Agent 档取消要先打断、等存盘（最多 2 秒），超时才强断 |
| 说"块是前端推断出来的" | 块在服务端封口，前端只按顺序认领 |
| 说"工具耗时是桥算的" | 桥只投影，真实起止来自工具执行侧 |
| 说"流超时是 5 分钟" | Agent 档 15 分钟；RAG 档才是 5 分钟 |
| 说"确认时流还开着" | 流关掉，挂起态保存在会话上 |
| 说"前端失败会重试" | Agent 档不重试，因为有写操作 |
| 只报数字不说口径 | 每个数字都要带"为什么是这个值" |

## 七、如果换你来重做，哪三件事会变

面试里被问"有什么可以改进"时，这三条比空泛的"多加监控"有说服力：

1. **块的标识可以显式化。** 现在文本封口帧不带块 id，靠前端"按顺序认领"。虽然能工作，但一旦丢一帧，认领就整体错位。带上 id 是更稳的做法。
2. **非流式终答和中断提示，应该走独立的块类型而不是复用文本块。** 现在靠"有没有起止"来区分，规则隐式。
3. **取消的 2 秒等待是拍出来的，不是量出来的。** 应该按引擎存盘的 P99 来定，或者做成可配置 + 观测。

---

> **最后一句**：这套东西的区分度不在"我知道 SSE 怎么用"，而在**"每一个一致性都是我主动设计出来的"**——时间只有一个来源、块和帧和回放同一套字段、三条出口只有一个收尾。面试时把这三点钉住，比背事件名有用得多。
