# 面试项目介绍 · 万能营销智能体

> **这份文档怎么用**：
> - 面试前 10 分钟 → 背「三、端到端主线」和「四、话术陪练」两张流程图
> - 面试官问「整体架构是什么」→ 翻「六、四层架构（备用答案）」
> - 被追问 → 翻「八、快速应答卡」
> - 出门前 → 翻「十一、自检清单」
>
> **技术细节完整版**：同目录 `Ragent升级清单.md`
>
> **⚠️ 用词纠正**：是 **ReAct**（Reasoning + Acting，推理-行动循环），不是前端那个 React。面试时主动说一句「ReAct 是推理-行动循环」，是加分项。
>
> **✅ 已定口径**：四大模块用「**话术陪练**」，不是「话术支持」。全篇统一，不要混用。

## 一、讲法决策：为什么用端到端，不用分层

| 讲法 | 什么时候用 | 问题 |
|------|-----------|------|
| **分层讲**（接入层→引擎→能力层→数据层） | 面试官明确问「你的架构分几层」 | 听起来像背文档，听完记不住，亮点散落 |
| **端到端讲**（跟着一次请求走） | **默认用这个** | 需要你对链路烂熟，不能卡壳 |

**端到端的三个好处**：
1. 每个技术点出现在它该出现的位置，不用硬塞；
2. 面试官能「看见」系统在动，而不是听你念目录；
3. **追问会沿着你铺好的线走——你掌控节奏**。

分层讲法降级为备用答案（第六节）。陪练是**第二条独立主线**（第四节）。

## 二、能力边界：哪个能深挖，哪个要补

| 模块 | 代码里实际对应 | 状态 |
|------|--------------|------|
| **智能问答** | RAG 检索管线（多路并行召回 + RRF 融合 + 精排）+ `KB_ANSWER` 槽位 | ✅ 随便问 |
| **知识搜索** | `search_knowledge` 工具（整条 RAG 管线工具化） | ✅ 这是最大升级点 |
| **营销** | MCP 工具集 + ReAct 自主编排 | ✅ 需把电商示例工具在叙事上换成寿险工具（产品库/保单/核保/理赔） |
| **话术陪练** | 需按第四、十节落地 7 项 | ⚠️ **不补就会被问穿** |

## 三、端到端主线 · 营销展业（主菜 · 4 分钟）

### 3.1 一句话定位（开场 20 秒）

> 我做的是一个面向寿险代理人的营销智能体平台。底层原本是一套 RAG 问答系统，我把它升级成了 Agentic 架构——**检索不再是一条写死的管线，而是变成 Agent 手里的一把工具**。智能问答、知识搜索、营销推荐、话术陪练四个模块都挂在同一个 Agent 运行时上。

然后**立刻切进场景**，不要停在架构名词上。

---

### 3.2 主路径流程图

```
【0】代理人一句话
      │  "帮我看看张伟名下已有保单，再推荐一款教育金"
      ▼
【1】接入层 ── SSE 建立流 ──────────────────────────────
      │  首包 + 工具进度实时下发（"正在查保单…"）
      ▼
【2】会话编排 ── Redis 用户级单流闸门 ──────────────────
      │  setIfAbsent 抢占 + TTL = SSE超时×2 + CAS 释放
      ▼
【3】构建 RuntimeContext ── 身份 / 会话状态 / 追踪上下文 ──
      │  ★ 身份放上下文对象，不放 ThreadLocal
      ▼
【4】七层中间件洋葱 ────────────────────────────────────
      │  追踪 → 记忆注入 → 压缩 → 拒绝改写 → 技能遮蔽 → 工具批
      │  ★ 顺序由「副作用谁吸收谁」决定
      ▼
【5】ReAct 第 1 轮 ── 模型看到的是【遮蔽后】的工具子集 ──
      │
      ├──▶【6】search_knowledge ── 整条 RAG 管线 ──▶ 条款/产品知识
      │         ★ RAG 从主流程降级为一个 Tool
      ▼
【7】ReAct 第 2 轮 ── 模型自己决定"还得查客户" ──────────
      │         ★ 步骤数取决于中间结果，流程写不死
      ▼
【8】MCP 工具 ── 保单查询 ─────────────────────────────
      │  ★ 身份走 _meta，不进模型可见参数；服务端只绑回环
      ▼
【9】ReAct 第 3 轮 ── 生成推荐方案 ──▶ 命中写操作 ──────
      │         ★ 未声明只读 = 要确认
      ▼
【10】确认卡片 ── 挂起 ──▶ 用户批准 ──▶ 恢复续跑 ──────
      │         ★ 参数在服务端，前端只回传布尔
      ▼
【11】流式输出 ── 事件桥接 → SSE 帧 ───────────────────
      │         ★ 工具块耗时是实测值，不是估算
      ▼
【12】收尾 ── 三出口 CAS 互斥 ──▶ 异步抽取长期记忆 ────
      ▼
【13】可观测 ── OTel → LangFuse ──▶ 按消息 ID 反查全链
```

### 3.3 中断分支

```
  [用户点停止]
       │  前端不中断 fetch，只发停止请求
       ▼
  interrupt() → 等框架存盘（≤2s）→ 超时才 dispose()
       │         ★ 不等就丢本轮状态
       ▼
  工具侧报 INTERRUPTED（不是 ERROR）
       │         ★ 报 ERROR 模型会在下一轮重试，而用户已经喊停
       ▼
  finish + done 收尾，落库口径与前端一致
```

### 3.4 逐节点：每个点讲什么

#### ①②③ 快速带过（共 40 秒）

**【0】入口**

> 「代理人正在跟客户谈，客户 35 岁、年收入 40 万、想给孩子存教育金。他问：『帮我看看张伟名下已有保单，再推荐一款教育金。』**这一句话同时触发了检索、业务查询、推荐三件事**——这就是写死的管线做不了的地方。」

**要点**：业务场景开场，不技术开场。

**【1】接入层**

> 「前端走 SSE。不是因为想流式，是 Agent 一次决策可能十几秒，而且**工具执行的进度也要实时透出**——代理人得看到『正在查保单』，否则以为卡死了。」

**追问预案**：断线怎么办？→ 消息落库，刷新可回放。

**【2】单流闸门**

> 「这层有个闸门：Redis 抢位，一个代理人同时只跑一条会话。**因为寿险很多操作是提交类的**，多端并发容易重复提交。」

**追问预案**：多节点？→ Redis 集中式，天然跨节点；释放用 CAS，只放自己占的位。

**【3】运行时上下文**

> 「把身份、会话状态、追踪上下文装进 RuntimeContext 往下传。**身份不能放 ThreadLocal**——后面切到弹性线程池会丢，这是旧代码踩过的坑。」

**要点**：敢于说「踩过坑」，可信度远高于「我设计得很优雅」。

---

#### ④ 七层中间件链（60 秒 · **第一个亮点峰值**）

**慢讲，这是全场最能证明「不是抄的」的地方。**

> 「Execution 引擎用的是 AgentScope 的 ReActAgent，但框架只给了 ReAct 循环，**运行时治理得自己写**。我做了一条七层中间件洋葱链：追踪、记忆注入、上下文压缩、确认拒绝改写、技能遮蔽、工具批治理。
>
> **这七层的顺序不是随手排的，是按『副作用谁吸收谁』推出来的。** 举两个例子：
>
> - **压缩必须排在拒绝改写之前**。因为被压进摘要的拒绝结果已经不在消息列表里了，改写分支自然跳过；反过来排，改写会对着一个已经不存在的消息空转。
> - **技能遮蔽必须排在压缩之后**。手册被压缩带走时，工具要跟着一并收回——工具与手册同生共死。排在压缩前面，就会出现手册没了、工具还挂着的状态。」

**追问预案**：
- 「加第 8 层放哪？」→ 看它读什么、改什么，插在「能吸收它副作用」的那层内侧。
- 「顺序排错了会怎样？」→ 拿上面两个例子反推，能说出具体后果。

---

#### ⑤⑥ 第一轮推理 + RAG 工具化（30 秒）

**【5】**

> 「第一轮推理，模型看到的工具清单是**遮蔽后**的——话术类的工具先藏起来，逼它先判断场景、再加载手册。」

**亮点**：工具不是全给的。

**【6】**

> 「它先查知识库。这个工具背后是**整条 RAG 管线**：多路并行召回、RRF 融合、精排。**RAG 从主流程降级成了一个工具**，这是整个升级的核心。」

**追问预案**：检索质量会不会降？→ 管线本身没变，只是调用方从「工程师写死的流程」变成「模型」。

---

#### ⑦⑧ 第二轮推理 + MCP 身份（40 秒 · **第二个亮点峰值**）

**【7】**（这段是「为什么需要 Agent」的直接答案）

> 「第二轮，模型看到检索结果，**自己判断『还得查这个客户的已有保单』**，于是调第二个工具。**这一步是流程写不出来的**——步骤数取决于中间结果，你不知道它要先查什么。」

**追问预案**：
- 「会不会乱调工具？」→ 工具目录由意图树约束，只挂该挂的；加上 `max-iters` 封顶，超了熔断收尾。
- 「为什么不用固定流程 + 分支？」→ 分支会爆炸，而且每加一个业务就要改一次流程。

**【8】**

> 「查保单走 MCP。这里有个我比较坚持的设计：**身份不走工具参数，走 `_meta`**——工具参数是模型能看见甚至能改的，身份走参数等于让模型自己填 userId。服务端那边也只绑回环地址，并且明确『不做认证决策』，只用来圈定数据范围。」

**亮点**：三层安全边界（身份不可见 / 服务端不认证 / 网络只回环）。

**追问预案**：模型能伪造身份吗？→ `_meta` 不在模型可见的参数里，模型没有填它的路径。

---

#### ⑨⑩ 写操作确认（40 秒 · **第三个亮点峰值**）

> 「第三轮生成推荐方案，但它要落地成待办，属于**写操作**——挂起，出确认卡片。
>
> 这里有两个细节。第一，**参数存在服务端会话状态里，前端只回传一个批准布尔**，防止篡改。第二，**服务端没声明『是否只读』时，我把它当成要确认**——默认值方向是『未声明即不可信』。
>
> 用户批准后是**续跑，不是重跑**。」

**追问预案**：
- 用户拒绝呢？→ 框架默认文案「Permission denied by user」会被模型误判成权限不足，我加了一层中间件改写成「用户主动取消，不是故障」。
- 怎么保证不重复提交？→ 单流闸门 + 续跑语义 + 前端删掉了自动重试。

---

#### ⑪⑫⑬ 收尾与可观测（30 秒）

**【11】**「事件桥接把框架事件转 SSE 帧。**工具块的耗时是工具执行体实测的**，不是前端估算。」

**【12】**「收尾三条出口 CAS 互斥，只跑一次。记忆抽取**异步**做，不阻塞响应。」

**【13】**

> 「全链 OTel 打到 LangFuse。**从一条消息 ID 能反查出完整 span 树**——线上代理人说『它答错了』，我能定位到那一轮调了哪个工具、检索回了什么、模型为什么那么说。」

---

#### 中断分支（挑任意节点插入一句）

> 「如果这时用户点停止，前端**不会中断 fetch**，而是先请求后端。后端 interrupt 后**等框架存盘最多 2 秒**再断流，不等就丢本轮状态。而且工具侧报的是『已中断』不是『失败』——**报失败模型会在下一轮重试，可用户已经喊停了**。」

### 3.5 时间分配

| 版本 | 分配 |
|------|------|
| **4 分钟版**（主用） | ①②③ 40s → **④ 60s** → ⑤⑥ 30s → **⑦⑧ 40s** → **⑨⑩ 40s** → ⑪⑫⑬ 30s |
| **2 分钟版** | 砍掉 ①②③⑪⑫，只讲 **④ → ⑥ → ⑦⑧ → ⑨⑩ → ⑬** |
| **30 秒版** | 只讲 **0 + 6 + 7**：「一句话触发三件事，检索降级成工具，后续步骤模型自己决定」 |

**节奏原则**：**④、⑦⑧、⑨⑩ 是三个亮点峰值**，其余快速带过。不要在 ①②③ 上恋战——那是基础设施，讲多了反而显得没重点。

## 四、话术陪练主线（第二条主线 · 90 秒）

### 4.1 流程图

```
【P0】代理人选场景（新人破冰 / 异议处理 / 促成 / 加保）
      ▼
【P1】Skill 加载 → 场景剧本进上下文
      │  ★ 同时遮蔽知识库与话术工具（防作弊）
      ▼
【P2】槽位切换 → 模型扮演"难缠客户"
      │  ★ 同一个 Agent，不新建实例
      ▼
【P3】多轮对练 → 客户持续抛异议
      │  ★ 每轮仍走同一个七层中间件链
      ▼
【P4】对练结束 → 触发评分工具
      │
      ├──▶【P5】四维度评分（每维度引用代理人原话作证据）
      │
      └──▶【P6】合规核对：拿关键表述检索条款库
                        ★ RAG 当裁判，模型不能自评
      ▼
【P7】评分报告落库 + 弱项写长期记忆
      ▼
【P8】下次推荐薄弱场景（记忆驱动）
```

### 4.2 口播（90 秒）

> 陪练不是一个独立系统，是**复用主 Agent 运行时的三种能力拼出来的**。
>
> **第一，剧本用 Skill。** 一个练习场景就是一份技能手册——客户画像、可能异议、练习目标。用渐进式披露，选了场景才加载，不占常驻上下文。
>
> **第二，角色用槽位。** 我加了一个客户人设槽位，让模型切换成「扮演一个有异议的客户」，而不是换一个 Agent。这里有个关键设计：**陪练模式下我把知识库和话术工具遮蔽掉**——不然代理人边练边查标准答案，陪练就没意义了。遮蔽机制本来就是为这个设计的，在这里正好有第二重用途。
>
> **第三，评分用工具。** 对练结束触发评分，四个维度：需求引导、异议处理、合规表述、促成动作。评分不是主观打分，**每个维度都要给证据**——引用代理人原话，还要引用条款。
>
> 最特别的是合规那一项。**模型会顺着上下文说「你刚才讲得挺好」，所以合规表述绝不能让它自评**。我的做法是把代理人说的关键表述拿去做条款检索，**用检索结果做事实核对**。这正好复用平台的 RAG 能力——纯做陪练的竞品没有这套检索基建，做不到。
>
> 最后评分进长期记忆，形成代理人的弱项画像，下次推荐针对性场景。**三层记忆在这里不是概念，是产品功能。**

### 4.3 评分维度 = 深挖的靶子

| 维度 | 考什么 | 怎么判 |
|------|--------|--------|
| **需求引导** | 有没有先问清家庭结构、收入、已有保障、预算 | 对照剧本 KYC 清单，逐项检查有无覆盖 |
| **异议处理** | 面对「太贵了」「我再想想」「我问问家里人」有没有正面回应 | 对照剧本异议库，看有没有漏答/回避 |
| **合规表述** | 有没有承诺收益、夸大保障、遗漏免责 | **RAG 检索条款库做事实核对** |
| **促成动作** | 有没有给出明确下一步 | 检查是否出现约定动作 |

### 4.4 三个能立住的差异化点

| 点 | 为什么别人做不出来 |
|----|------------------|
| **遮蔽 = 防作弊** | 需要 Skills 机制已经在跑。竞品要么工具全开（可作弊），要么另做一套权限 |
| **RAG 当合规裁判** | 需要条款库 + 检索管线。纯陪练产品没有这套基建 |
| **弱项进记忆、下次出题** | 需要三层记忆 + 跨会话抽取。这是平台既有能力 |

### 4.5 评分输出必须结构化 + 带证据

这是能不能扛住「你凭什么给这个分」的关键：

```json
{
  "dimension": "compliance",
  "score": 2,
  "evidence": "代理人原话：'这个产品保证年化 5%'",
  "violation": "承诺收益",
  "clause_ref": "条款库 #3.2 分红不确定声明"
}
```

**只有 `score` 没有 `evidence` 和 `clause_ref`，一问就穿。**

### 4.6 追问预案

**Q：陪练怎么模拟客户异议？**
> 异议库写在 Skill 剧本里，按客户人设分档——比如「价格敏感型」先抛「太贵了」，「犹豫型」抛「我再想想」。模型扮演客户时按人设逐步释放，不会一次全倒出来。

**Q：陪练结果准不准？**
> 分两块看。合规项是**事实核对**，检索到条款就有依据，不是模型主观判断；其余三项是**行为覆盖检查**，对照剧本清单看有没有做，比「说得好不好」可验证得多。

**Q：为什么不做独立的陪练系统？**
> 因为需要的能力平台已经有了——多轮会话、记忆、权限、追踪。独立做等于重建一遍，还会和主链路割裂。**复用运行时是这套设计的核心。**

## 五、三层记忆（可插在节点 ④ 或 P7 之后）

| 层 | 触发条件 | 做什么 | 寿险场景话术 |
|----|---------|--------|-------------|
| **短期** | 上下文到 50% | 老旧工具结果换成等长占位 | 「检索回来的大段条款不用一直挂着」 |
| **中期** | 上下文到 80% | 安全前缀压缩成摘要 | 「上午聊过的客户情况，下午还接得上」 |
| **长期** | 每轮结束异步抽取 | 跨会话事实落库，下次开场注入 | 「代理人和客户跨天沟通，家庭结构、已有保单、上次卡在哪，不用重复问」 |

**陪练场景的第二重价值**：长期记忆不只是记客户，也记**代理人自己的弱项**——「这个人在『收益承诺』上反复出错」，下次针对性出题。

**主动抛出的实测结论**（很值钱，因为它推翻了直觉）：

> 我原本以为「多数会话靠裁剪工具结果就能压住上下文」，**实测不成立**。关掉压缩跑满 15 轮，末轮 3 万字符里用户话和回答占 45%、模型思考占 26%，**裁剪能动的只有 22%**——射程正好顶在下限上，所以裁剪连续九轮空转，上下文一路涨到预算的 3.8 倍。这个结论直接决定了压缩不是可选优化，是必需的兜底。

> **能讲「我原本以为…实测推翻了」的候选人，比讲十个架构名词的强。**

## 六、四层架构（备用答案 · 只在被问「整体架构」时用）

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层      H5 / 企业微信 / App      SSE 流式 + 确认卡片        │
├─────────────────────────────────────────────────────────────┤
│ 会话编排层                                                  │
│   AgentRunGate(Redis 用户级单流) → AgentChatService → RunHandle │
│                                    (complete/cancel/fail CAS) │
├─────────────────────────────────────────────────────────────┤
│ Agent 执行引擎      ReActAgent（单例 + 指纹懒重建）             │
│   ┌─ 7 层中间件洋葱链 ─────────────────────────────────┐      │
│   │ 追踪 → 记忆注入 → 上下文压缩 → 拒绝改写 →           │      │
│   │ 技能遮蔽 → 工具批治理                                │      │
│   └────────────────────────────────────────────────────┘      │

│ 能力层（四大模块，全部以 Tool 挂载）                          │
│  智能问答(RAG) │ 知识搜索 │ 营销推荐 │ 话术陪练(Skills)       │
├─────────────────────────────────────────────────────────────┤
│ 工具层    MCP（产品库/保单/核保/理赔/客户画像）                │
```

**口播（30 秒）**：
> 「分四层。接入和会话层管流式和并发闸门；执行引擎是核心，用 ReActAgent 加七层中间件做运行时治理；能力层四个模块全部以 Tool 挂载，通过 MCP 接业务系统；数据层做混合检索和状态存储。另有全链追踪。」**然后就切回端到端故事**，别停在这。

## 七、三个核心设计决策

### ① 为什么把 RAG 降级成工具？（最高频追问）

**不要说「因为 Agent 更先进」。** 给取舍：

> 检索链路固定、延迟低、结果可预期，简单问答走管线更划算；但展业场景里「帮我看看这个客户适合推什么」需要先查客户、再查产品、再比对条款，**步骤数量取决于中间结果，写不死**。所以做了 `workflow / agent` 双档位，部署级切换：简单问答走 v1 管线，复杂展业走 ReAct。

**加分点**：
- 档位是**部署级决策**、不开放后台切换（切换要重启，且 Agent 档依赖外部服务存活）；
- 配置类**不挂在 `rag` 前缀下**——因为 Agent 档里 RAG 只是主 Agent 的一个 Tool，档位在语义上包含 RAG，而不是从属于 RAG。

### ② 长会话为什么不会爆上下文？

见第五节。要点是「**我量过，不是我觉得**」。

### ③ 为什么要有写操作确认？

见节点 ⑨⑩。核心是「强监管场景 + 未声明即不可信 + 参数在服务端」。

## 八、快速应答卡

### Q：为什么用 AgentScope 不用 LangChain4j / Spring AI？
> 它把 ReAct 循环、工具调用、会话状态存储都给了，而且是 Actor 模型、原生响应式，和我的 Reactor + SSE 链路对得上。但框架只给循环，**运行时治理得自己做**——中间件链、取消语义、上下文压缩都是我加的。

### Q：单例 Agent 并发安全吗？（**高频且危险**）
> 有一个已知缺陷：AgentScope 单例 Agent 被不同会话并发使用时，共享 Toolkit 里的工具组状态会串话（上游 issue #2439）。我做了三层应对：① **用户级单流闸门**，同一用户不并发；② 会话状态按 session 隔离存在 PostgreSQL；③ **写了缺陷复现测试**盯着，断言的是当前框架的错误行为，上游修了我再改成回归断言。
>
> **诚实说一句**：不同用户之间目前不互斥，这是已知风险面，靠的是状态按会话隔离。**主动说出来，比被问穿强。**

### Q：寿险答错了是合规事故，怎么防幻觉？
> 四层：① 强制走检索，不裸答；② 答案可溯源到条款；③ 关键表述做事实核对；④ 写操作一律人工确认。另外工具异常统一换成安全文案，不让内部地址、SQL、凭据进模型上下文。

### Q：工具调用失败了怎么办？
> 失败不抛异常，回一个模型可读的错误摘要让它换路；如果用户已点停止，**报「已中断」而不是「失败」**——报失败模型会在下一轮重试，而用户已经喊停了。

### Q：怎么评测效果？
> 两层。① **记忆回归台**：15 轮剧本，短期/中期/长期三层，判定五态（通过/失败/待实现/意外命中/未覆盖），每层硬断言。② **全链追踪**：一条 trace 看检索回了什么、调了哪个工具、耗时多少，线上问题按消息 ID 反查。

### Q：10 万调用怎么扛的？
> 见第九节。

## 九、数字防御（必看）

- **10 万 / 天 ≈ 1.16 QPS**。面试官心算很快，会接着问峰值、P99、单次成本。
- **更稳的说法是给分布**：「日均 10 万次调用，峰值集中在早会后和夕会前两个时段」——给分布比裸数字可信。
- 优先用你**确实测过**的：上下文压缩率、单轮工具调用次数、会话中断率、记忆命中率。
- **不要现编 P99**。答不上就说「延迟我主要看首包时间，P99 没单独统计过」——诚实比编造安全。

## 十一、面对「陪练没做完」怎么办

如果面试时其实还没落地，**不要硬编**。可以这样讲：

> 「陪练这块我目前实现到角色扮演和评分骨架，合规核对接了条款检索，弱项记忆还在做。**设计上我是把它当成主运行时的一组配置来做的**，不是独立系统——所以剩下的工作量主要在剧本和评分维度校准上。」

**这个说法的好处**：既承认了进度，又展示了架构判断（复用而非新建），还把「没做完」归因到了正确的地方（内容校准，不是架构重构）。
