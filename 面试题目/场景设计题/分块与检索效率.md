## 题面

> 「假设 1000 页的一个文档丢给我的分块系统，要怎么做才能提高检索效率？」

**陷阱**：上来就答「换更好的 embedding / 加大 topK / 上更强的 rerank」——这题考的是**分层拆解能力**，不是单点技术选型。

---

## 一、先拆题：「效率」是两层含义

| 含义 | 症状 | 优化方向 |
|---|---|---|
| **找得准**（质量） | 1000 页里信号被稀释，正确块排不进候选 | 切分粒度、多粒度索引、精排 |
| **找得快**（延迟 / 成本） | 候选集大 → rerank 贵、LLM 上下文爆 | 缩小搜索空间、索引类型、路由 |

**量级估算**（示意，非实测）：1000 页 × 每页 500–800 字 ≈ **50–80 万字**；按 1024 字符 / overlap 128 切 ≈ **500–900 个 chunk**。而最终只喂 **10 条**给 LLM。

→ **结论：瓶颈不在「检索得快不快」（HNSW + 20 条召回很快），而在「这 20 条里能不能捞到对的」和「能不能只在小范围里捞」。**

---

## 二、通用四层手段（不依赖项目，先立的骨架）

**① 入库层（决定上限）**
- 按**文档结构**切（标题层级 / 章节边界），不要定长硬切
- 块要**语义自洽**：太小丢上下文、太大稀释向量
- 挂全**元数据**：文档 id、标题、章节路径、页码、块序号 —— 有元数据才能「过滤」，否则只能「全库扫」
- ⭐ **父子块（parent-child）**：用小块建索引提升召回精度，命中后返回所属父块保证上下文完整 —— **大文档最有效的一招**

**② 索引层（决定速度）**
- ANN 选 **HNSW**（查询快、召回好）优于 IVFFlat
- **分区 / 隔离**：按 KB、按文档分区，把搜索空间从「全库」降到「子集」
- **多粒度**：文档级摘要 / 目录 → 先路由到文档，再文档内检索

**③ 检索层（决定质量）**
- **逐层缩小范围**：query → 意图 / KB → 文档 → chunk
- **元数据过滤**：按 KB / 文档 / 章节过滤，而不是全库 ANN
- **粗召回 + 精排**：宽召回（50–100）→ Rerank → topK（5–10）
- **混合检索**：向量 + 关键词（BM25）互补

**④ 评测层（决定能否证明）**
- Hit@K / Recall@K / MRR 量化；**分档对比**（大 vs 小文档）+ **消融**（有 / 无 rerank、不同块长）

## 五、针对 1000 页的具体做法（按性价比排序）

**① ⭐ 把已在算的 `outlinePath` 落库 + 加 `page`（几乎白送）**
分块时 `HeadingHandler` **已经在内存里算出了章节路径**，只是没写进向量库 metadata。连同页码一起落库，**立刻获得「限定在某章节内检索」的能力** —— 成本最低、收益最大。

**② ⭐ 把「节」变成父块（也是白送）**
`ChunkPacker.splitSections` 本来就把文档切成了一段段「节」，节内才切块 —— **这个「节」就是现成的 parent**。做法：小块（256–512）建向量索引召回，命中后返回整个「节」喂 LLM，**上下文完整 + 召回精准同时拿到**，无需重写分块算法。

**③ 入库分批 + 进度回调**
数百块一次性塞进单事务，内存与事务时长都难看。改成分批（如 200/批）+ 进度上报，把「一个巨事务」拆开。

**④ 两阶段检索（文档路由 → 块检索）**
先按文档标题 / 摘要把候选缩到几篇，再进块级检索。需补**文档级摘要**（入库时顺带生成，一个文档一次 LLM 调用即可）。

**⑤ 打开关键词通道**：`rag.keyword.type=es` 即可，专有名词 / 编号类查询它能兜住向量漏掉的。

**⑥ 用评测证明**：`Hit@{1,3,5,10}` + `MRR@10`（`retrieval.py:11`），全量集 **150 条**（`eval_set_v1_all.jsonl`；小集 `eval_set_v1.jsonl` 只有 20 条），主指标 **Doc Hit@5 ≥ 90%**（`evaluation-plan.md:173-174`）。做消融：改前 vs 加元数据过滤 vs 加父子块。

## 六、面试话术（可直接讲）

> 先拆「效率」——分**质量**和**延迟**。1000 页按 1024 字符切大概是五六百到近千个块，而最终只喂 10 条给模型，所以瓶颈不在检索速度，**在「候选能不能捞到对的」和「能不能只在小范围里捞」**。
>
> 我的做法分四层：**入库**按 Block 结构 + 标题层级分节、节内切块（预算 1024 / overlap 128、容忍 3 倍、边界回溯到句末）；**索引**用 HNSW；**检索**靠意图绑 KB 缩范围 + 20 召回 → RRF → 40 候选精排 → top 10；**评测**用 Hit@5 / MRR@10 做消融。
>
> 针对 1000 页我还会补三件事：一是把已有的**章节路径和页码落进向量 metadata**，支持按章节过滤而不是全库搜；二是用现有的「节」做**父子块** —— 小块召回、整节返回，兼顾精度和上下文；三是**分批入库**避免单事务过大。前两项目前还没做，是我下一步的优化项。

**红线**：父块与元数据过滤**当前都没有**，讲成「已实现」下轮必穿帮。按上面「已有原料 → 下一步这么做」的说法，反而更像真实做过的人。

## 七、追问预案

| 追问 | 怎么答 |
|---|---|
| 「块长 1024 怎么定的？」 | 预算驱动而非定长：1024 为基础，容忍 3×（3072）才切，overlap 取 1/8=128；边界回溯到句末，保证块语义完整 |
| 「为什么不用定长切？」 | 定长会切断句子 / 表格；我们按 Block 类型分发，表格按行数（50 行/块）单独处理 |
| 「父子块具体怎么实现？」 | 复用已有「节」结构做父块；小块建索引召回，命中后按 `docId + 节范围` 回表取父块 |
| 「1000 页入库会不会 OOM / 要多久？」 | 当前是单事务全量写，这正是要改的点 —— 分批 + 进度回调 |
| 「怎么证明有效？」 | 离线评测 `Hit@5` / `MRR@10` 消融；线上看首 token（TTFT）与召回不足的 badcase 回放 |
| 「为什么不直接把 topK 调大？」 | 候选大 → rerank 成本与延迟线性上升，且噪声进上下文反而降低 faithfulness；应先提精度再谈数量 |
